# Coordinator plan

Design of **coordinator delegation**: one coordinator splits a story into Builder-sized pieces with declared file ownership, places each piece (one Builder in order, shared-tree Builders, or worktree Builders), steers them while they run, integrates their work as the only writer, runs the full checks and the Critic once, and reports. Phases C0–C8 are built. The C8 story benchmark ([story-2026-10-01.md](../benchmarks/story-2026-10-01.md)) found that parallel placement and pieces in order both fail their turn-off criteria (section 10); parallel Builders stay on by default (the user's decision) while the bugs it found (B1–B3) are fixed and it is re-run.

Read with [HARNESS_PLAN.md](HARNESS_PLAN.md) (the lean harness around it) and [ROUTING_PLAN.md](ROUTING_PLAN.md) (code scan, Builder floor, complexity rule). Evidence: [routing-live-2026-09-27.md](../benchmarks/routing-live-2026-09-27.md), [harness-e2e-lean-2026-09-27.md](../benchmarks/harness-e2e-lean-2026-09-27.md).

## Status

- **Mode.** `COORDINATOR_MODE` (`off`, `shadow`, `in_order`, `parallel`), default `parallel` (`apps/server/src/config.ts`); set `in_order` or `shadow` to override it, for example while debugging. `COORDINATOR_PLACEMENT` (`shared` or `worktree`, unset by default) forces the list placement under `parallel` for benchmarks (`forcedPlace` in `place-list.ts`); the project's parallel setting, one slot and the task copy still win. The browser test server runs `parallel`. Spark off never engages the coordinator or records a shadow row. Thresholds are in `advisor/policy.ts` (`COORD_*`, policy `coord-2`).
- **Project settings.** `projects.parallel_pieces` defaults to true (`0077_builder_defaults.sql` flipped existing rows; the flag stays for the API and specs, with no UI; false gives "parallel pieces are off for this project"). `projects.piece_slots` (1–3, default 3) is "Builders at once" in Settings → Projects; 1 runs pieces in order. The same group has "Where Spark works" (`projects.work_place`: each chat in its own worktree, the default, or in my files). `stable_checkout` was dropped in `0077`: worktree-first chats already keep the user's folder untouched. `builder_env` has no UI.
- **Migrations.** `0063_coordinator.sql`, `0069_parallel_pieces.sql`, `0070_piece_notes.sql`, `0077_builder_defaults.sql`.

What is built, and where:

- **Placement at write time** (`coordinator/place-list.ts`): the ladder (section 2) runs on the validated pieces with the same project facts the shadow row uses; the list and each piece store the placement and its reason.
- **Slots** (`orchestration/slots.ts`): `PARALLEL_AGENT_LIMIT` (default 6) caps Builders per worker; each task gets `piece_slots`, or one slot while its provider has an open rate-limit or usage-limit issue.
- **The ready-set scheduler** (`coordinator/schedule.ts`, `run-pieces.ts`) runs every placement (in order is one slot): pieces whose dependencies landed start in dependency order, up to the slots; after a failure, Stop or a budget cut nothing new starts and the running pieces finish; two ownership strikes narrow the rest to one piece at a time. Each Builder gets its slot as `SPARK_BUILDER_SLOT`. A skipped piece counts as settled, and its dependents are skipped with it unless the user said otherwise.
- **Shared tree** (`coordinator/shared-landing.ts`, `projects/shared-tree.ts`): a group base is committed once per task; each piece's diff check ignores files other pieces own; at every landing the piece runs' snapshots are re-pointed (base plus the files of pieces whose last run came earlier), so Changes shows each Builder only its files. Files no piece owns go to the piece that landed last.
- **Worktrees** (`coordinator/group.ts`, `merge.ts`, `migrations.ts`): each piece gets a copy from the current main (`copyFor` from `solo-copy.ts`, dependency prep started at once; scoped checks wait for it). The copy lands as soon as its scoped checks pass: colliding migration numbers are renumbered in the copy, the copy is committed, merged into main (`tryMerge`, `applyTree`) and removed; the other running copies get main merged in at their next turn boundary (their base moves, so their Changes stay theirs), with the notice in their next fix turn. A conflict goes to the integrator (`${taskId}:integrator`) with both sides' diffs, twice at most (a reply starting "Unresolved:" or failing scoped checks counts as not settled); then the `merge_conflict` card at Review each step and Automatic, and a stop with the conflict in the report at Full auto → PR. A budget cut keeps the cut pieces' copies so Continue resumes them in place; Stop, failure and the end of the task remove them, and the worker's orphan sweep removes what a crash left.
- **Main is the chat's root.** In a chat worktree the copies live under `<chat worktree>/.spark/worktrees/` and land into the chat worktree, never the user's checkout.
- **Pieces follow the task's copy.** When the level or mode needs a task copy (only when the chat works in place: Full auto → PR, a mode that skips the gate, destructive work, a busy repo), every piece runs in that one copy, in order, and it merges back once at the end. Chats in their own worktree never need a task copy.
- **The piece-list card** (checkpoint kind `pieces`: Build it, Build in order instead, Revise with a note, Stop) is asked at Review each step for a shared or worktree list or 5+ pieces; the proposed list shows on the board meanwhile. Revise re-runs the coordinator turn with the note as a new list version. Automatic and Full auto approve by level and show the board read-only.
- **UI.** Shared-tree and worktree Builders fold into one "Working in parallel" group in the crew turn (`ParallelGroup`), each head labelled with its piece and placement; the piece board is `crew/PieceBoard.tsx` (every status has a symbol and a word, placement badge, provider and model, check, cost, and the reason for a failed or skipped piece); Agent TV has a coordinator scene (`crew/tv-coordinator.ts`, the hub layout in `tv-layout.ts`): the coordinator in the centre, one node per piece around it with the Builder, piece, placement, state and queued-notes badge, including pieces not started yet; the Agent TV list shows the same labels and states; the report names the placement and lists merge conflicts and renumbered migrations. Browser coverage: `pieces-parallel.spec.ts` (board states, TV scene, work panel tabs by keyboard, the piece-list card by keyboard, the merge-conflict card, the phone layout) and `steer.spec.ts`.
- **Budget Continue** resumes cut pieces in their own sessions; pieces that never started begin fresh.
- **Live updates** ride on the orchestration snapshot (`Orchestration.pieces`); there is no separate `pieces` activity type. `GET /api/tasks/:id/pieces` returns the list with a count of queued notes per piece.

Fixed after the first story benchmark (branch `fix/coordinator-bugs`):

- **B1, a rate-limited Codex piece landed empty.** codex-acp 1.13.1 reports a turn that ends on an error (Codex's "exceeded retry limit, last status: 429") as `end_turn` with the failure in the prompt response's `_meta` (`jetbrains.air.sessionFailure`, category `limit`), not as a `session_info_update`, so the turn counted as succeeded. `agents/acp/acp-provider.ts` now reads that meta (`mapper.stopped`), and a turn that ends right after a provider warning (`limit`, `access`, `connection`) with no progress since counts as failed (`mapper.stalled`); `failureError` maps the codex-acp categories (`access` → signed out, `connection` → not available). The failed turn reads as a provider problem, so C6 fallback moves the piece with the handoff.
- **B2, a shared-tree piece "landed" with no files at Full auto → PR.** Nothing deleted P1's files: the gate refused P1's only write, a `cat > file <<'EOF'` heredoc, because `writeTargets` parsed the heredoc text as shell and found redirect targets (`>= 2` gave a file named `=`). `node --test a.ts b.ts` skips a missing file silently, so the scoped check passed, and the piece landed with 0 files. `writeTargets` now strips here-text first (`withoutHereText`; a heredoc fed to a shell stays opaque). A Builder piece that owns files and changes none of them gets one more turn with a note ("changed none of your files"; it counts as a fix turn) and is failed, never landed, if it still changes nothing (`piece-run.ts`, skipped for a resumed piece).
- **B3, piece lists failed the plan-coverage check.** Two causes. In 8 of 16 runs the Claude coordinator, which runs in plan mode, wrote its pieces into a plan file and asked to leave plan mode, so the reply was "No response requested." and the first turn was wasted; the coordinator now takes the pieces block from the plan it proposed in that turn (the stray proposed plan document is rejected), and the prompt says the reply is the plan. And coverage checked every nested plan bullet by word overlap; `coordinator/plan-coverage.ts` now reads the plan as steps with the files their section and parent bullets name, drops grouping bullets and verification steps (run the tests, sanity-check, a Verification section), and counts a step covered when a piece owns or reads one of its files (by path or file name), else by words as before. The prompt lists the files the plan names. A piece that reads another piece's file gets the dependency added (an error only when it would close a cycle). Replaying the 27 coordinator replies from the benchmark transcripts: before, 6 of 16 runs got a valid list; after, 16 of 16 (11 on the first turn), and dropping the CSV piece from any valid list is still caught. The one repair turn with the missing items named stays.

Where the build departs from the design below:

- **Order with the intent flow.** Clarify (when vague) and plan first (for big requests, including most requests that ask to be split up) run before the coordinator. The plan the user approves at "Build this plan?" is the latest approved plan document: its open items count towards engaging, the coordinator prompt carries it as `## Agreed plan`, validation requires every open item to have a piece, and the piece list records that plan version.
- **The coordinator turn is a fresh Ask session** (`${taskId}:coordinator`), not a resume of the session that wrote the agreed plan. The repair re-prompt repeats the full prompt with the validator's errors.
- **The integrator is a Builder turn recorded with the `integrator` role**; after integration every later Builder turn of the task (full-check fixes, Critic fix rounds, continues) runs in that session.
- **Research pieces** run as Scout-role child runs in Ask mode in the main tree; their replies reach later pieces as "Notes from Scouts".
- **Scoped checks** must name a path or package, run a test runner or one of the project's check programs, and not install, format or change files. They still go through the approval gate. `task_pieces.check_status` records each piece's result for the board and the report.
- **Ownership strikes.** In a shared tree a Builder's shell write to a file another piece owns cannot be told from that piece's own edit, so the diff check leaves it (the gate still refuses direct edits).
- **Migration renumbering** renames the colliding file only; references to the old name elsewhere are left to the integrator's full-check fixes.

## Decisions in one place

1. **The default does not change.** A request that fits one Builder runs as the lean harness runs it: one task-scoped Builder, checks with fix turns, the verified cascade, the Critic by rule. The coordinator adds nothing to it, not even a model call.
2. **Decomposition and parallelism are separate decisions.** A story too big for one Builder is split into pieces. Pieces run **in order by one Builder at a time** unless the placement rule finds at least two independent, large pieces. Round 10 showed that small parallel work is not faster (57 s against 60 s).
3. **Builder-sized** means the piece fits one Builder session under the smaller of 50% of the model's context window and 150K tokens. A Builder at 75% of its window hands off to a fresh Builder on the same piece.
4. **Every piece declares the files it owns.** The approval gate refuses a Builder's edit outside its piece's files; a diff check after every turn catches writes that bypassed the gate. Builders never run `git stash`, `checkout`, `switch`, `reset`, `restore`, `clean`, `commit`, `merge` or `rebase`.
5. **One writer integrates.** Builders land their own files; only the integrator merges copies, resolves conflicts and fixes what the full checks find. Pieces run scoped checks only; the full checks run **once on the integrated result**, then the Critic once.
6. **The dependency graph is validated in code.** `dependsOn` must name existing pieces, be acyclic, and cover every file two pieces both touch. The code scan adds edges it can prove; it never removes one.
7. **Approval is bound to a plan version.** The piece list records the `plan_documents` version and a hash of the pieces. A change to ownership, dependencies or pieces is a new version; at Review each step it needs a new approval.
8. **Repair has a budget.** Two fix turns per piece, two integration repair rounds, three Critic rounds, and all repair together at most half of the story's budget (not enforced yet). A budget cut after a passing state keeps that state.
9. **Builders never run on the fast tier** (`model-floor.ts`, `builder-complexity.ts`). The Critic runs on a different provider from the Builders whenever more than one is connected.
10. **Cards follow the harness autonomy.** Review each step sees the piece list and the conflicts it cannot avoid; Automatic sees only risky or failed states; Full auto → PR sees nothing and ships a draft PR with the piece report in its body.
11. **We turn it off on evidence** (section 10).

## 1. The coordinator role

The coordinator is the orchestrator (`orchestration/orchestrator.ts`) with Jev as its advisor. Code owns every decision that has a rule; a model only writes the piece list, and Jev would answer only in unsure bands (not asked yet). There is no Architect: the round-10 lesson was that a separate cold planner cost 34–77% of a planned turn.

- **Coordinator turn.** Role `coordinator`, `resumeKey = ${taskId}:coordinator`, Ask mode, the chat model on Auto with the Builder floor and the complexity rule. Its prompt asks for one fenced `pieces` block (section 8) and nothing else. One repair re-prompt with the validator's errors, which name the uncovered plan steps; still invalid means one Builder in order with the agreed plan, and the reason is recorded. When a Claude coordinator in plan mode proposes its list as a plan instead of replying, the list is read from that proposal.
- **Jev (designed, not asked).** `too_big` ("Is this change too large for one agent session?", only when the size estimate is within 20% of the Builder budget), `split_worth_it` ("Would two agents working at the same time finish sooner without more rework?", only in the placement rule's unsure band) and `same_folder` (only when pieces touch a shared-tree blocker file). Each would act at 0.8 either way, recorded in `run_advice` purpose `parallel`.

**What it owns.** The plan (the latest approved `plan_documents` version); the piece list (`task_pieces`); placement (`coordinator/placement.ts`); provider and model per piece (`coordinator/assign.ts`); scheduling (`coordinator/schedule.ts`, `orchestration/slots.ts`); integration (`coordinator/integrator.ts`, `merge.ts`, `migrations.ts`); the full checks, the verified cascade and the Critic (`checks.ts`, `verify.ts`, `review-loop.ts`); steering (`coordinator/steer-rules.ts`, `notes.ts`); the report (`coordinator/report.ts`).

**When the coordinator engages.** First match, after intake and the risky-change card:

1. The user asks for it ("split this up", "use parallel Builders", "in worktrees", the "Pieces" option in the composer's Plan menu). Recorded as `requested`.
2. The agreed plan has 4 or more open items across 2 or more areas (a workspace package or top-level folder, `areaOf` in `critic-rule.ts`).
3. The code scan's ranked likely files number 12 or more or span 3 or more packages.
4. The size estimate for the whole request is over the Builder budget.
5. Otherwise: the lean path, no coordinator turn, no pieces.

A story that comes back as one piece runs as one Builder with the piece's contract as its brief.

**The report.** One reply at the end, built by code from the records: a table of pieces (title, Builder, placement, provider and model, status, files, scoped check, cost), the integration steps (merges, conflicts and who resolved them, renumbered migrations), the full check lines, the verified cascade's verdict, the Critic's findings and fix rounds, skipped pieces with the reason, and "Incomplete: …" for anything not landed. Full auto → PR puts the same table in the PR body.

## 2. Placement rule

A pure function, `placePieces(pieces, facts)` in `coordinator/placement.ts`. All thresholds are provisional until the story benchmark tunes them.

**Inputs.** The piece list (owned files with globs expanded against `git ls-files` plus new paths, reads, `dependsOn`, scoped checks, the size label S, M or L); the size estimate per piece (`coordinator/size.ts`: `12K + 2 × tokens(owned files) + tokens(read files) + 6K per owned file`, a file's tokens being its line count × 12); the Builder budget per model (`min(0.5 × contextSize, 150K)`); project facts (git or not, `repoBusy`, the autonomy, destructive or migration work, a mode that skips the approval gate); Jev's answers when asked.

**Definitions.** A **large** piece has a size estimate of 40K tokens or more, 5 or more owned files, or label L. A **long** piece has 90K tokens or more. Two pieces are **independent** when no `dependsOn` path joins them and their owned files don't overlap. **Critical-path saving** is `1 − (longest dependency chain by size) / (sum of all piece sizes)`.

**The ladder** (first match wins per story; recorded as a `parallel` decision):

| #   | Placement                                              | When                                                                                                                                                                                                                                                             |
| --- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0   | **One Builder** (no pieces)                            | The coordinator did not engage                                                                                                                                                                                                                                   |
| 1   | **Pieces in order** (one Builder at a time, main tree) | Outside git; fewer than 2 independent large pieces; critical-path saving below 35%; or Jev `split_worth_it` ≤ 0.2                                                                                                                                                |
| 2   | **Worktree Builders**                                  | Parallel is worth it and: another task works in the repo; the agent's mode skips the approval gate; the story deletes, migrates or rewrites data; a piece is long; or a piece owns a shared-tree blocker (manifest, lockfile, generated file, migrations folder) |
| 3   | **Shared-tree Builders**                               | Parallel is worth it and none of row 2 holds (or only a blocker file, and Jev `same_folder` ≥ 0.8)                                                                                                                                                               |
| —   | **Read-only pieces**                                   | Pieces marked `research`: Scouts in Ask mode in the main tree, before the Builders that depend on them                                                                                                                                                           |

**How the plan and the code scan inform it.** A piece list that leaves an agreed-plan item without a piece fails validation once and is re-prompted. The code scan validates ownership (paths exist or sit under an existing folder, none are secret files), expands globs, adds `dependsOn` edges when a piece's owned file imports a symbol another piece changes, and supplies line counts. Scan evidence only adds edges or moves a piece towards isolation.

**When to fall back.**

| Trigger                                           | Fallback                                                          |
| ------------------------------------------------- | ----------------------------------------------------------------- |
| Piece list invalid after one repair               | One Builder in order with the agreed plan                         |
| `git worktree add` or the group base commit fails | That piece and later ones: in order in the main tree              |
| Two ownership violations in one story             | Rest of the story: one piece at a time                            |
| An integrator turn fails twice on a conflict      | The conflict card, except Full auto → PR, which stops and reports |
| A provider becomes unavailable                    | Section 5                                                         |

## 3. Shared-tree Builders

Several Builders work in the same tree (the chat's worktree, or the checkout when the chat works in place), each on its own piece.

- **Ownership in the approval gate** (`approvals/piece-guard.ts`): an edit outside the piece's owned paths is refused with a message naming the owner. Commands whose write targets can be named (redirects, `sed -i`, `mv`, `cp`, `rm`, `touch`, `tee`) are checked the same way. This is the same hard-rule layer as the publish refusal, so it applies in every agent mode and autonomy.
- **Diff check after every Builder turn** (`coordinator/ownership.ts`): changes outside the piece's files are a violation. At Review each step a card asks (keep it in the piece, revert that file, stop); at Automatic and Full auto the file moves into the piece when no other piece owns it and it is not a blocker, otherwise it is reverted and the Builder told. Two violations narrow the rest of the story to one piece at a time.
- **No git operations** (`BUILDER_GIT_REASON`): Builders of a coordinated task can't `stash`, `checkout`, `switch`, `reset`, `restore`, `clean`, `commit`, `merge`, `rebase`, `cherry-pick`, `am`, `worktree` or `branch -d/-D`; read-only git stays allowed. Claude Builder sessions get matching deny rules. Coordinated Builders don't get the `Agent` tool.
- **Scoped checks only.** Whole-project commands (the full check, installs, repo-wide formatters) are refused inside a piece: the coordinator runs the full checks after integration.
- **Per-Builder environment.** Builders and their checks get `SPARK_BUILDER_SLOT` and `SPARK_BUILDER_NAME`. `projects.builder_env` (a map with `{slot}` substitution, such as `TEST_DATABASE_URL=…_test_b{slot}`) gives each Builder its own test database and ports; without it, scoped checks take a per-project Postgres advisory lock (`coordinator/builder-env.ts`).
- **Landing.** A piece lands when its scoped checks pass (or after its 2 fix turns). When every piece has landed or been skipped, the integrator runs if integration needs edits (the piece list's `integration` note or a contract mismatch), then the full checks run once, with at most 2 integration repair rounds, then plan completion, the verified cascade, the Critic and its fix loop (run by the integrator), the keep card, and Ship for Full auto → PR.

## 4. Worktree Builders

Built on the kept worktree code: `projects/worktrees.ts` (`addWorktree`, `commitWorktree`, `groupBase`, `tryMerge` with `git merge-tree --write-tree`, `applyTree` to the working tree never the index, `removeWorktree`), `orchestration/solo-copy.ts` (copy lifecycle, orphan sweep, `Session.copyMerged`), `projects/deps-prep.ts` and `worktree-deps.ts` (`node_modules` beside each copy), and the `run_worktrees` table (the row is written before `git worktree add`). Ship never pushes internal commits or `spark/<id>/<name>` branches.

1. **Base.** Before the first worktree piece, the main tree (uncommitted and untracked files included) is committed through a temporary index as the group base. The orchestration snapshot predates it, so Revert still undoes the whole story.
2. **Copy per piece** at `<root>/.spark/worktrees/<runId>` on `spark/<task>/<name>`; the copy is the Builder's only root; the approval gate and ownership run unchanged inside it.
3. **Land** as soon as the piece's scoped checks pass, in dependency order; dependents then branch from the new main.
4. **Merge main into running copies** at their next turn boundary, then the `merge_main` notice (section 6).
5. **Conflicts** go to the integrator first (two attempts); then the `merge_conflict` card, or a stop with the conflict in the report at Full auto → PR (it never keeps a guess).
6. **Migration renumbering** (`coordinator/migrations.ts`): numbered migration files that collide with a number on main are renamed to the next free number and the rename is reported. Builders never run migrations against a shared database; the full checks run them against the test database.
7. **Cleanup.** Copies and branches are removed after landing, on Stop, on failure and at the end; the orphan sweep handles crashes. Result commits stay under `refs/spark-outpost/builders/<runId>` for the Changes view.

## 5. Multi-provider

**Assignment** (`coordinator/assign.ts`, facts in `provider-state.ts`). Healthy means no `providerIssues` entry in the last 10 minutes (`COORD_PROVIDER_HEALTH_MS`) and no failure earlier in the same task. Another provider gets its floor model (its top non-frontier tier for complex or destructive work), never the fast tier or a retiring model. Among the other providers, the stronger Builder by benchmark pass rate goes first, then the less loaded. Pieces in order stay on the chat provider's routed Builder pick (or the first healthy provider); a pinned model pins every piece; parallel pieces alternate by size, the largest on the chat provider. Jev's provider pick is not used (round 10 found it a coin flip).

**Jev rates each piece; Spark routes it** (`coordinator/piece-jev.ts`, questions in `piece-questions.ts`, composition in `piece-demand.ts`, rules in `piece-routes.ts`). Jev is never asked which model to use. After the piece list validates, one Jev batch call asks at most six independent questions per building piece about its properties: `kind` (choice: implement, debug, refactor, test, migrate, docs, config, ui), `reasoning`, `coding` and `context` (scores 1–5: reasoning needed, how hard the code is, how much of the repo it must understand), `reliability` (noul: must be right the first time) and, when the list runs parallel and placement is not forced, `wide` (noul: long, wide or able to break other pieces in the same folder). State is the request plus an untrusted `<code_evidence>` block with each piece's goal, acceptance, the pieces it waits for, its scoped check, estimated size, whether it touches core or shared Map areas, and its owned and read files with code index and project Map facts, fitted to `JEV_STATE_TOKENS`; no file contents, no secret files. Spark's code then composes a demand (`pieceDemand`): the weighted mean of the expected scores (`PIECE_DEMAND_WEIGHTS` reasoning 0.45, coding 0.35, context 0.2, renormalised when context is unsure) maps to a tier (`PIECE_MID_AT` 2.5, `PIECE_TOP_AT` 3.5), raised to top for a destructive piece (including any piece that owns a migration), kind `migrate`, `reliability` ≥ `PIECE_RELIABILITY_TOP_AT` 0.6 or reasoning ≥ `PIECE_DEEP_REASONING_AT` 4, and to at least mid for a refactor of a core or shared area; a kind below `PIECE_KIND_MIN_CONFIDENCE` 0.5 is ignored. If the reasoning or coding score is below `PIECE_SIGNAL_MIN_CONFIDENCE` 0.5 the rules pick from `assignPieces` stands (an unsure Jev never downgrades a piece), unless a floor already demands the top tier. `pickForDemand` takes the eligible routes (every connected provider's models at or above the Builder floor, minus unhealthy providers) at the demanded tier, stepping up when none is left there and never down, and ranks them by runtime facts Jev does not own: a measured Builder pass rate better by `PIECE_PASS_RATE_MARGIN` 0.1, then model-card strengths that fit the leading capability (reasoning, coding or context, which must lead the others by `PIECE_CAPABILITY_LEAD` 0.75; context also matches a window of `PIECE_LARGE_CONTEXT_TOKENS`), then, for low and mid tiers, a blended card price cheaper by more than `PIECE_PRICE_MARGIN` 10% before the chat's own provider, and for the top tier the chat's own provider before price (top-tier work is where a cheaper unmeasured model is the wrong saving); the pick is floored as before (`floorPick`: never the fast tier). A piece routes below the chat model's tier only when it is clearly simple (`clearlySimple`): Jev's `kind` is docs, config or test (`PIECE_BELOW_CHAT_KINDS`) with confidence ≥ `PIECE_BELOW_CHAT_KIND_CONFIDENCE` 0.8, or reasoning ≤ `PIECE_BELOW_CHAT_MAX_REASONING` 2 and coding ≤ `PIECE_BELOW_CHAT_MAX_CODING` 2, both with confidence ≥ `PIECE_BELOW_CHAT_MIN_CONFIDENCE` 0.6, `reliability` < `PIECE_BELOW_CHAT_MAX_RELIABILITY` 0.3 and no known core or shared area touched; otherwise the demand is raised to the chat model's tier ("not clearly simple, so not below the chat model") and routed again, and demand above it still goes up (live run 3, C2: three Sonnet pieces under a pinned Opus chat needed two fix rounds and cost $0.90 against $0.42 for Opus without Jev). Measured Builder pass rates by task kind override that test once both the lower route and the chat route have `PIECE_BELOW_CHAT_MEASURED_MIN` 10 runs in the matching benchmark category (implement → feature, debug → fix, refactor → refactor): the lower route may go below the chat model only when its rate is within `PIECE_BELOW_CHAT_PASS_MARGIN` 0.05 of the chat route's (`kindPassRates` on the route rules, `belowChatBlock`). Placement: repo-wide isolation (busy repo, gate-skipping mode, destructive story), a long piece or a blocker file keep a piece in its own worktree; otherwise `wide` ≥ `PIECE_WIDE_WORKTREE_AT` 0.5 sends it to its own worktree, `wide` ≤ `PIECE_SHARED_AT` 0.2 to the shared tree, and in between the rules placement stands; two unordered pieces that own the same file never share the tree. A list can mix shared and worktree pieces (`placedGroup` in `run-pieces.ts`). If Jev is not connected, fails, times out (3 s) or answers badly, the rules picks stand. One `piece_route` decision row per list (policy `coord-4`) records each piece's raw Jev signals, the composed demand (score, tier, capability, what raised it), the rules pick, the applied pick, who decided (`jev`, `rules`, `floor`) and why; the piece row carries a short `pick_note` ("Jev: reasoning 2, coding 3, context 2 → mid tier → Codex 6 Sol (best pass rate)", or "Rules: … · Jev was unsure (reasoning 0.42)") shown on the piece board and the Agent TV tooltip. The constants live in `advisor/policy.ts` and are meant to be tuned from recorded decisions. Pieces are routed this way in Auto and pinned chats alike; the chat's own model never changes, it stays the orchestrator.

**Likely files.** The Jev file ranking (`observe-rank.ts`) is now kept on the session; a Builder brief waits for it at most `RANKING_WAIT_MS` (Jev's timeout plus 1 s) and adds "Likely files (a ranking hint, not a limit): a.ts (0.82), …". A piece gets only ranked files it owns or reads; a single Builder gets the top list.

**One PR or separate PRs** (`orchestration/pr-split.ts`, `shipPiece` in `ship/service.ts`). When Full auto → PR ships a list with two or more landed pieces built in their own worktrees, and a draft PR can be opened, Spark asks with a `pr_split` card: One PR (the default, taken when the card auto-continues after the profile's auto-continue seconds, 10 by default), Separate PRs, or either one remembered for the project (`projects.pr_split`, after which the card is skipped). Separate PRs commit each worktree piece's files on `<task branch>-<piece key>` from the current head, push it and open a draft PR; shared-tree pieces and other files go in the main PR (`ShipOptions.exclude`), which is skipped when nothing is left for it.

**The Critic across pieces.** `criticProvider` takes the landed pieces' providers and file counts: the first connected provider that built nothing (the chat provider counts as a builder, since the integrator runs there), else the smallest share; with one provider, the same provider one tier up. It is one turn: over the 24 KB cap the prompt carries "Diff by piece", each landed piece's files with its goal, contract and acceptance, then the integration and other files, and asks for one verdict.

**Fallback.** A failed turn whose error reads as a provider problem (`providerIssueKind`, or "stopped unexpectedly", "could not start", "is not available") moves the piece to `fallbackPick` and records `moved from Codex (rate limited)`. A turn counts as failed when the agent ends it on a session failure, including codex-acp's failure in the prompt response's `_meta` and a provider warning with no progress after it. Before the first edit the new Builder gets the same brief; after it, a `## Handoff` with the files changed, the diff stat, the last scoped check output and the acceptance. A new provider means a new session generation (`:piece:P1:2`). Later pieces avoid a provider that failed in this task. Provider failures don't use the one-tier-up retry budget. Designed but not built: waiting 10 minutes with a retry card when no provider is left, and a Critic fallback to the next candidate.

## 6. Steering running Builders

- **Delivery.** Boundary notes are sent as the follow-up of the piece's next turn under "## Note from the coordinator"; a note that arrives during a piece's last turn gets one more turn in the same session (at most `COORD_NOTE_TURNS` = 3). Urgent notes use `_session/steering` when the adapter advertises it (claude-agent-acp 0.81.2 and codex-acp 1.13.1 both do; `agents/acp/steering.ts`); otherwise `workflow/steer-requests.ts` stops the turn and the piece restarts fresh with the note, the brief and the files changed so far.
- **Note kinds** (`piece_notes`): `merge_main` and `contract_changed` from code after a landing; `requirement_added` (appends an acceptance item and bumps the contract version); `skip`; `stop`; `reassign` (moves the piece to another provider before its next turn); `steer` (free text). Notes to the coordinator (`piece_notes.piece_list_id`, `0070`) reach the integrator, which then runs even without an `integration` note.
- **Notices from code.** When a piece lands, every running piece gets `merge_main` when it runs in a worktree and depends on, reads or imports the landed files, and `contract_changed` when the landed diff changes a symbol named in its contract; urgent when its owned files import a landed file. Main is merged into the copy before the notice (`coordinator/merge-main.ts` for a task copy); a conflicting merge is not applied and the integrator reconciles it.
- **Chat steering.** While a coordinated task has open pieces, the composer shows a "Steer to" picker (Auto, All pieces, each open piece, Coordinator) and sends to `POST /api/tasks/:id/steer`; `POST /api/tasks/:id/pieces/:key/notes` takes one note. Rules classify the text (`skip`, `stop`, "also …", "use <provider> for …", a piece's key, title or Builder name); Auto with no match goes to all open pieces. The reply ("Queued for Rivet: … (next turn)") shows above the composer.
- **Skip** stops a running piece, reverts its files from the tree before it started, and marks its pending dependents skipped; a landed piece can't be skipped (409).

## 8. Data model

`0063_coordinator.sql`:

- `piece_lists`: task, orchestration run, version, the `plan_documents` id and version, `pieces_hash`, placement (`in_order`, `shared`, `worktree`) and its reason, status (proposed, approved, superseded, rejected), approval and `approved_by` (user or level).
- `task_pieces`: key, title, goal, `owns`, `reads`, `depends_on`, contract and its version, acceptance, checks, `research`, size estimate, placement (adds `read_only`), provider, model, Builder run, worktree, status (pending, ready, running, landed, skipped, failed), attempts, fix turns, files changed, violations, `landed_at`, note and `check_status`.
- `piece_notes`: kind (`merge_main`, `contract_changed`, `requirement_added`, `skip`, `stop`, `reassign`, `steer`), body, source (user or coordinator), urgent, delivery time and run.
- `runs.role` and `run_advice.role` add `coordinator` and `integrator`; approval kinds add `pieces` and `ownership`; `projects.builder_env`.

**The `pieces` block** the coordinator writes (`packages/contracts/src/pieces.ts`): `{ "pieces": [{ key, title, goal, owns, reads, dependsOn, contract, acceptance, checks, size }], "integration": "…" }`.

**Validation** (`coordinator/pieces-validate.ts`, pure): keys unique; at most 8 pieces; `dependsOn` names existing keys and is acyclic (the cycle named in the error); owned paths inside the project roots, not secret, not inside `.git`; two pieces owning the same path must be ordered by `dependsOn`; a piece reading a file another piece owns depends on it unless the file is named only in a contract; each piece's size estimate fits the smallest Builder budget among its candidates, else one re-prompt to split it; a piece that reads a file another piece owns gets that dependency added unless it would close a cycle; the list covers the agreed plan's steps (`plan-coverage.ts`: a step is covered when a piece owns or reads a file named in the step, its parent bullets or its section heading, else by words; grouping bullets and verification steps are not steps). The approval hash is SHA-256 over the canonical JSON of keys, owns, dependsOn, contracts and acceptance.

**Persistence** (`persistence/pieces.ts`): list versions, approval bound to the plan version, status transitions guarded by the current status, notes with delivery marking. A crash leaves running pieces `failed` with "outcome unknown", their copies are swept, landed pieces stay landed, nothing is replayed.

## 10. Risks, and when we turn it off

| Risk                                                                                                        | Mitigation                                                                                                   | Watch in the benchmark                              |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| **Parallel is not faster** (round 10: 57 s shared, 60 s worktrees; direct Claude did the same work in 31 s) | Parallel only for 2+ independent large pieces with a 35% critical-path saving; the default stays one Builder | Wall time b and c against a and a2                  |
| The coordinator turn repeats the Architect's cost                                                           | Engage only past the size thresholds; code, not a model, does placement, integration and the report          | Coordinator share of cost; alarm above 20%          |
| Cold Builders re-read what the coordinator read                                                             | Piece contracts name the reads; the 75% handoff sends a summary, not the transcript                          | Reads per Builder, total input tokens against arm a |
| Ownership too tight                                                                                         | The refusal names the owner; unowned files move into the piece at Automatic                                  | Violations and re-plans per story                   |
| Shell writes bypass the gate                                                                                | Diff check after every turn, revert or move, two strikes to one at a time                                    | Violations caught by the diff check vs the gate     |
| Scoped checks miss what full checks find, late                                                              | Full checks once, integrator repair rounds, the Critic                                                       | Integrator repair rounds per story                  |
| Concurrent checks collide on a database or ports                                                            | Per-Builder environment, else the check lock                                                                 | Check failures that pass on rerun                   |
| More agents means more rate limits                                                                          | Spread across providers; fallback with handoff; at most 3 Builders                                           | 429s per run                                        |
| More cards at Review each step                                                                              | The piece-list card offers "in order"; grouped approvals                                                     | Interventions against a                             |
| Anchoring: a detailed contract lowers pass rates                                                            | Contracts hold interfaces and acceptance, not implementation advice                                          | Pass rate a2 against a                              |
| Stale contracts after a steer                                                                               | Contract versions and `contract_changed` notices                                                             | Rework after a notice                               |

**Evidence that turns it off.** After the benchmark (n = 3 per arm), and again after 50 real coordinated tasks:

- **Parallel placement (b, c) goes off** unless it is at least **30% faster** in wall time than the better of a and a2, at **the same or higher pass rate**, with cost per pass including the developer's time at most **1.2×** arm a.
- **Pieces in order (a2) goes off** unless it passes at least as often as one Builder and fixes something one Builder gets wrong. If one Builder passes the story 3/3 at lower cost, the coordinator engages only on explicit request.
- **Keep only worktrees** if ownership violations average more than 1 per story or any run needed a manual repair after a neighbour's edit.
- **Keep only the shared tree** if merge conflicts show in more than 20% of worktree runs or dependency prep adds more than a minute per piece.
- **Multi-provider assignment goes off** (the Critic stays cross-provider) if arm b does not beat the same placement on one provider, or its failures cluster on one provider's pieces.
- **Anything that lowers the pass rate** against arm a is reverted, whatever it saves ([ROUTING_PLAN.md §4](ROUTING_PLAN.md#4-policy-that-stays-in-code)).

**First evaluation (2026-10-01, [story-2026-10-01.md](../benchmarks/story-2026-10-01.md), n = 3–4, $27.58).** Every arm passed every Automatic run, and direct Claude was cheapest ($0.40 per pass against $2.95–4.52). Parallel shared tree: 4% slower than a2, so it fails. Parallel worktrees: 27% faster, under the 30% bar, and mostly load noise, so it fails. Pieces in order: fixed nothing one Builder got wrong, so it fails; one Builder passed 3/3 at lower cost, so the coordinator should engage only on request. The worktrees-only and shared-only rules were not triggered (0 violations, 0 conflicts). Multi-provider could not be judged (there was no one-provider shared arm), but the Codex fallback did not fire at all (B1). Caveats: only 6 of 16 engaged runs actually ran pieces (B3), and wall times were confounded by machine load. Recommended, not applied: `COORDINATOR_MODE` default `in_order` or `off` with engagement on request only, and no parallel default; fix B1–B3 before re-running. B1–B3 are fixed (Status); the user kept `parallel` as the default, and the live re-run is theirs to decide.

If it is turned off, placement rows 2 and 3, the group and merge code, and `piece_notes` go; the ownership guards and git-op refusals stay, since they protect one Builder too.
