## Events emitted today

Built in `apps/server/src/workflow/run-events.ts` unless a row says otherwise.

| Event                                                                                                               | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RUN_STARTED`                                                                                                       | First event of a run, including a queued run stopped before a worker claims it (`stop-run.ts`) and a run recovery marks before it started. A run that fails before it starts begins with `RUN_ERROR`, which the spec allows. A run another run started carries `parentRunId`, the run that started it; a chat turn carries none.                                                                                                                                                                                                                                                                                                                                                                                            |
| `RUN_FINISHED`                                                                                                      | Outcomes `success` and `cancelled`. Carries `usage` (one `TokenUsage` entry: provider, model, `inputTokens` with cache reads and writes counted in, `outputTokens`, `totalTokens`, and the cache and reasoning parts) when the run recorded tokens (`run-usage.ts`). Spark's run columns stay the source for the UI.                                                                                                                                                                                                                                                                                                                                                                                                        |
| `RUN_ERROR`                                                                                                         | Codes `provider_error`, `orchestration_failed`, `outcome_unknown`. No `usage`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `STEP_STARTED`, `STEP_FINISHED`                                                                                     | By `stepName`. A step for a tool call carries `metadata.spark.toolCallId`. Two calls open at once under one name share one step, opened by the first and finished after the last (`turn-events.ts`). A step closed only because the run ended carries `metadata.spark.interrupted` and readers keep it unfinished.                                                                                                                                                                                                                                                                                                                                                                                                          |
| `TEXT_MESSAGE_START`, `TEXT_MESSAGE_CONTENT`, `TEXT_MESSAGE_END`                                                    | The reply, redacted before it is stored.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `REASONING_START`, `REASONING_MESSAGE_START`, `REASONING_MESSAGE_CONTENT`, `REASONING_MESSAGE_END`, `REASONING_END` | One span with one message (same `messageId`) per Thinking step, from ACP `agent_thought_chunk`, redacted like the reply. No `REASONING_ENCRYPTED_VALUE`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `TOOL_CALL_START`, `TOOL_CALL_ARGS`, `TOOL_CALL_END`, `TOOL_CALL_RESULT`                                            | From ACP `tool_call` and `tool_call_update`, with the ACP `toolCallId`; `toolCallName` is the step name. Arguments are sent once, when the agent first reports input (or at the end), redacted and clipped at `COMMAND_TEXT_MAX`; the result is redacted and keeps the last `COMMAND_STORED_CHARS`. A call that names a secret file stores `[redacted:secret_file]` for file content and for its result. A call still running when the run stops has no result.                                                                                                                                                                                                                                                             |
| `ACTIVITY_SNAPSHOT`                                                                                                 | Always `replace: true`. Types: `file_focus`, `task`, `plan`, `link`, `advice`, `plan_document`, `changes`, `check`, `review`, `shortcuts`, `orchestration`, `model_switch`, `member_message`, `browser_screenshot`. No `ACTIVITY_DELTA`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `SUBAGENT_STARTED`, `SUBAGENT_FINISHED`, `SUBAGENT_ERROR`                                                           | Bracket a worker whose reply is copied into the chat's own run (`subagent-events.ts`). A new turn emits none: the one emitter was the answer to a question sent during a build, which is removed, and a provider's own sub-agents arrive as ordinary tool calls of the chat's session. Stored runs still replay them. `subagentRunId` is the worker's run id, `name` is `conversation`, `parentMessageId` is the message it answers. The copied `TEXT_MESSAGE_*` events carry the same `subagentRunId`; the worker's steps, tool calls and reasoning stay in its own run. A stopped worker ends with `SUBAGENT_ERROR` and code `cancelled`, because the event has no cancelled outcome. They carry no cost or check detail. |
| `CUSTOM`                                                                                                            | `approval_requested`, `approval_decided`, `command_started`, `command_output`, `command_finished`. A new name is prefixed `spark.`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

Not emitted: `STATE_*`, `MESSAGES_SNAPSHOT`, `RAW`, the `*_CHUNK` forms.

Before `RUN_FINISHED` or `RUN_ERROR` the run appender closes whatever is still open (reasoning, tool calls, steps, a worker announced with `SUBAGENT_STARTED` and its reply) in the same write (`open-spans.ts`). A run that recovery marks `outcome_unknown` after a crash is not closed this way: its `RUN_ERROR` may follow open steps, which `verifyEvents` accepts.

### An agent's own sub-agents

Spark advertises the adapters' `nativeSubagentSessions` extension (`_meta.jetbrains.air.capabilities`, `client-info.ts`) on a turn's connection, not on the capability probe. Both pinned adapters then send `subagent_spawned` and `subagent_state_update` on the parent session and each sub-agent's updates under its own session id. SDK 1.5.0 has neither update in its schema and drops updates for a session it did not open, so `subagent-stream.ts` rewrites them before the SDK reads the stream: a spawn or an end becomes a marked `session_info_update` on the root session, a sub-agent's `tool_call` and `tool_call_update` move to the root session with a mark naming the sub-agent, and its other updates (text, thoughts, settings) are dropped. The audit records the stream before this rewrite.

`subagent-updates.ts` maps the marked updates with one mapper per sub-agent, so a sub-agent's tool call never closes the main agent's Thinking step. The run stores `SUBAGENT_STARTED` (name, the task as `description`, `parentSubagentRunId` for a nested one, `timestamp`, `metadata.spark.ownSubagent`), then `SUBAGENT_FINISHED` or `SUBAGENT_ERROR` with code `failed` or `cancelled`; the sub-agent's `STEP_*` and `TOOL_CALL_START` carry `subagentRunId`. An `ACTIVITY_SNAPSHOT` of type `subagents` holds `waitingOn`: the number of working sub-agents while the main agent has no step of its own open, else 0 (`subagent-progress.ts`). `packages/contracts/src/subagents.ts` folds these events into the rows the chat, Agent TV and the sidebar show; a stored crew turn's `SUBAGENT_STARTED` has no `ownSubagent` mark and is ignored there.

The main agent's own wait for its sub-agents does not count as an open step: a Codex tool call whose `_meta.codex.collaboration.tool` is `wait`, and a Claude `TaskOutput` call (`_meta.claudeCode.toolName`) whose `task_id` is a working sub-agent. A permission request whose `sessionId` is a sub-agent's carries its name in the approval payload (`subagent`), and the note about the answer is attributed to it. The adapters' placeholder task (`Delegated task`, `Delegated task for <name>`) is stored as no task. After a stop, `subagent_state_update: cancelled` is still recorded; `open-spans.ts` closes whatever the adapter did not.

Chat sessions through the `claude` CLI (Claude and Z.ai) start with `CLAUDE_CODE_FORK_SUBAGENT=1` and without `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` (`subagent-env.ts`), so every sub-agent runs in the background; Terminal sessions build their own environment. While `waitingOn` is above 0, a message sent now that the adapter does not inject is moved to the chat queue instead of cancelling the run (`member-inbox.ts`).

A sub-agent's `agent_message_chunk` also moves to the root session with its mark; it never joins the reply. `subagent-activity.ts` keeps its last message (or the `message` of Claude's `SubagentHandback` call), the paths of its edit, delete and move calls and the commands of its execute calls. With what the patched adapters report when it ends (`subagent-report.ts`: Claude `_meta.claudeCode.usage` and `summary`; Codex `_meta.codex.usage`, `turns`, `model`) these are stored as `CUSTOM` events named `spark.subagent_report` and folded into the row. A cost is added only when the model and the token split are reported and the price table has the model (`reported-output.ts`).

Turn tokens (`turn-tokens.ts`): for the `claude` CLI the prompt response's `usage` covers the main agent loop only, so the total is the larger of the per-model tally in `_meta.quota.model_usage` and `usage` plus the tokens its sub-agents reported; both are sums of reported figures, so neither counts a sub-agent twice. Codex `usage` already adds every thread and is taken as is. The prompts of one run are added up.

On Stop the adapter's process tree is read before `session/cancel` and again when the prompt returns; everything from either reading that is still alive is ended (`agent-process.ts`).

Covered by `subagent-stream.test.ts`, `subagent-updates.test.ts`, `subagent-progress.test.ts`, `acp-subagents.test.ts` and `subagents.db.test.ts` against the fake agent. Not yet run against the real Claude or Codex CLI.

The browser reads the thinking text of a finished run from `GET /api/runs/:id/reasoning/:messageId`; a paired phone may read it like any other run event (no switch governs reading agent output).

The worker writes `TEXT_MESSAGE_CONTENT` and `REASONING_MESSAGE_CONTENT` events in batches: chunks wait at most 50 ms (or 8 KB) and are stored together, each still its own event with its own `seq`. Any other event first stores the waiting text in the same transaction, so the order is the order the agent produced (`apps/server/src/workflow/run-appender.ts`).

Command output events are written by `apps/server/src/workflow/command-recorder.ts`, batched for 100 ms and capped per command; what each adapter provides is in [ACP_AGENTS.md](ACP_AGENTS.md#command-output-in-the-chat-october-6-2026). Evidence: `command-output.test.ts`, `command-recorder.test.ts`, `acp-terminal.test.ts`, `command-terminal.db.test.ts` (fake agent); the live check is reported there separately.

Chat providers run through ACP (Claude, Codex, Z.ai; see [ACP_AGENTS.md](ACP_AGENTS.md)). Separate Terminal sessions run the installed Claude Code or Codex interactive CLI in a Spark-owned PTY, with session-scoped Spark MCP tools. They do not create ACP worker jobs or chat runs. See [native Terminal sessions](NATIVE_TERMINALS.md).

Native Terminal hooks are tested against Claude Code 2.1.280 and Codex CLI 0.153.4. Other versions launch with activity observation marked unsupported. Codex session hooks retain the CLI's own trust requirement. A version match alone does not establish that hooks are active: until an authenticated observation arrives, activity remains unknown. Terminal output stays in the PTY and its bounded memory replay; it is not translated into an AG-UI transcript. Native usage and cost are not inferred from output.

Native lifecycle writes use a session-generation fence rather than a worker lease. Duplicate launch reservations, duplicate event IDs, stale generations, and interrupted recovery are covered by `native-terminal-turns.db.test.ts`; direct process launch and same-process reattachment are covered by `agent-sessions.test.ts`. These fixtures do not establish live provider acceptance. The fake provider, which echoes the message, remains for tests; it is not evidence of any real provider capability.

## A2A: outpost chats (October 9, 2026)

Each chat that belongs to an outpost is served as an A2A 1.0 agent by the API server, with `@a2a-js/sdk` 1.3.0 (exact) and the JSON-RPC binding, and an outpost request is an A2A task. The design is in [A2A_CHATS.md](A2A_CHATS.md). Built as release 1 of outposts; not yet released.

All tests named here are in `apps/server/test/`. The contract tests drive the real router with the SDK's own client; `outposts-e2e.db.test.ts` runs a user's request through the app's own wiring from post to answer.

Limits, which bound any claim:

- **Loopback only.** The server listens on `127.0.0.1`, every A2A route needs the launch token, and both routes are `never` for a paired phone (`apps/server/src/remote/route-rules.ts`). Nothing is served through Tailscale Serve or Funnel.
- **One text message per task.** A message for an existing task is refused (`UnsupportedOperationError`), so a task in `TASK_STATE_INPUT_REQUIRED` cannot be answered over A2A: the user answers it in Spark.
- **A call is never the user.** A `SendMessage` with no stored request behind its `messageId` is accepted only for a chat that is in an outpost and is treated as written by another chat. No message field carries authority.
- **Not served:** push notification configs, `ListTasks`, the extended Agent Card, signed cards, the gRPC and HTTP+JSON bindings, file and data parts. A caller that does not ask for A2A 1.0 is refused.
- **No outside agent has been tried.** The only client that has called the endpoint is the SDK's own, in our tests and in Spark's dispatcher. "Compatible with A2A agents" is not claimed.
- **What the tests prove.** In the contract tests the state of the receiving run is set in the database, not produced by an agent. `outposts-e2e.db.test.ts` runs real turns with the fake provider, which echoes the message. No live provider has run an outpost request.

## Deviations from the AG-UI client model

- The browser uses `EventSource` and our own reducer, not `@ag-ui/client`. Runs start with `POST /api/conversations/:id/messages`, not with an AG-UI `RunAgentInput` request, because the worker owns execution. Evaluating an `AbstractAgent` with `connect()` is task F-17.
- Assistant text is persisted as a message when `TEXT_MESSAGE_END` is written, in the same transaction.
