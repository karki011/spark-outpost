### An agent's own sub-agents

Spark advertises the adapters' `nativeSubagentSessions` extension (`_meta.jetbrains.air.capabilities`, `client-info.ts`) on a turn's connection, not on the capability probe. Both pinned adapters then send `subagent_spawned` and `subagent_state_update` on the parent session and each sub-agent's updates under its own session id. SDK 1.5.0 has neither update in its schema and drops updates for a session it did not open, so `subagent-stream.ts` rewrites them before the SDK reads the stream: a spawn or an end becomes a marked `session_info_update` on the root session, a sub-agent's `tool_call` and `tool_call_update` move to the root session with a mark naming the sub-agent, and its other updates (text, thoughts, settings) are dropped. The audit records the stream before this rewrite.

`subagent-updates.ts` maps the marked updates with one mapper per sub-agent, so a sub-agent's tool call never closes the main agent's Thinking step. The run stores `SUBAGENT_STARTED` (name, the task as `description`, `parentSubagentRunId` for a nested one, `timestamp`, `metadata.spark.ownSubagent`), then `SUBAGENT_FINISHED` or `SUBAGENT_ERROR` with code `failed` or `cancelled`; the sub-agent's `STEP_*` and `TOOL_CALL_START` carry `subagentRunId`. An `ACTIVITY_SNAPSHOT` of type `subagents` holds `waitingOn`: the number of working sub-agents while the main agent has no step of its own open, else 0 (`subagent-progress.ts`). `packages/contracts/src/subagents.ts` folds these events into the rows the chat, Agent TV and the sidebar show; a stored crew turn's `SUBAGENT_STARTED` has no `ownSubagent` mark and is ignored there.

The main agent's own wait for its sub-agents does not count as an open step: a Codex tool call whose `_meta.codex.collaboration.tool` is `wait`, and a Claude `TaskOutput` call (`_meta.claudeCode.toolName`) whose `task_id` is a working sub-agent. A permission request whose `sessionId` is a sub-agent's carries its name in the approval payload (`subagent`), and the note about the answer is attributed to it. The adapters' placeholder task (`Delegated task`, `Delegated task for <name>`) is stored as no task. After a stop, `subagent_state_update: cancelled` is still recorded; `open-spans.ts` closes whatever the adapter did not.

Chat sessions through the `claude` CLI (Claude and Z.ai) start with `CLAUDE_CODE_FORK_SUBAGENT=1` and without `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` (`subagent-env.ts`), so every sub-agent runs in the background; Terminal sessions build their own environment. While `waitingOn` is above 0, a message sent now that the adapter does not inject is moved to the chat queue instead of cancelling the run (`member-inbox.ts`). A message the adapter does take records the reply's text position at delivery, so the chat shows it where the agent took it in. When the user stops the run, a delivered message with no step, thought or text after its delivery and before the stop request, and a send-now message still waiting, are marked `missed` (`markUnreadOnStop`) instead of staying delivered or starting a new turn.

A sub-agent's `agent_message_chunk` also moves to the root session with its mark; it never joins the reply. `subagent-activity.ts` keeps its last message (or the `message` of Claude's `SubagentHandback` call), the paths of its edit, delete and move calls and the commands of its execute calls. With what the patched adapters report when it ends (`subagent-report.ts`: Claude `_meta.claudeCode.usage` and `summary`; Codex `_meta.codex.usage`, `turns`, `model`) these are stored as `CUSTOM` events named `spark.subagent_report` and folded into the row. A cost is added only when the model and the token split are reported and the price table has the model (`reported-output.ts`).

Turn tokens (`turn-tokens.ts`): for the `claude` CLI the prompt response's `usage` covers the main agent loop only, so the total is the larger of the per-model tally in `_meta.quota.model_usage` and `usage` plus the tokens its sub-agents reported; both are sums of reported figures, so neither counts a sub-agent twice. Codex `usage` already adds every thread and is taken as is. The prompts of one run are added up.

On Stop the adapter's process tree is read before `session/cancel` and again when the prompt returns; everything from either reading that is still alive is ended (`agent-process.ts`).

### Background work after the reply (October 19, 2026)

ACP lets an agent send `session/update` outside a prompt turn, and claude-agent-acp 0.81.2 does: one long-lived consumer forwards every SDK message (`dist/acp-agent.js:1997`). It holds `session/prompt` open only while a sub-agent spawned in that turn is itself live (`Turn.deferredSettle`, `:2434-2470`, `:4085-4105`); background shells never hold it. A sub-agent that backgrounds its own command and ends its turn releases the hold, so the prompt returns `end_turn` while work still runs. When that work ends, Claude Code wakes the sub-agent (a new `subagent_spawned` with id `<id>:generation:N`), then the main agent, and the adapter streams that cycle out of turn, closing it with a `usage_update` whose `_meta["_claude/origin"]` names the cycle (`:3792`). Seen live with Claude Code 2.1.301 (two background sub-agents, a background `sleep`): the prompt returned at 20 s and the continuations arrived at 56-76 s. Upstream tracks the missing session-level idle signal in claude-agent-acp #864 and #1285; ACP v2's prompt lifecycle RFD adds `state_update` idle/running for this.

Spark advertises the AIR `asyncTasks` capability on a turn's connection (not the probe) so the adapter announces background shells and monitors, the sub-agents' ones included (`async_task_spawned`, `async_task_state_update`). Spark already sends `_meta.jetbrains.air`, so this flips no other AIR behaviour. `subagent-stream.ts` rewrites them into marked `session_info_update`s like sub-agent spawns, since SDK 1.5.0 has neither in its schema. `background-work.ts` counts the work still running: sub-agents not ended, and background tasks, each counted as the sub-agent whose tool result named its id (`toolResponse.backgroundTaskId` or `taskId`), otherwise as a task of its own.

For Claude chats, when a prompt returns `end_turn` with work still running, the run stays running and the provider keeps reading the session (`turn-loop.ts`): the continuation's text, steps, sub-agent rows, cost (`usage_update`) and tokens (the `_claude/sdkMessage` requests of the cycle) land in the same run, and notifications fire at its real end. The `subagents` activity carries `background: { agents, tasks, names }` while it waits, shown as **Waiting on 2 background agents** in the chat, the list, Agent TV, the island and paired devices. The wait ends at an origin-marked `usage_update` with nothing left running; a background command that never ends (a dev server, a persistent monitor) waits until Stop. While it waits the run is parked (`background-parking.ts`, `ParkedTurns`) so Quit can stop it; the worker has no limit on running turns, so other chats keep running. A message sent during the wait goes to the same session as a new `session/prompt`, never with `session/cancel` first (upstream #976). Stop ends the run, and the process tree with the background work in it; a restart marks the run with `BACKGROUND_OUTCOME_MESSAGE`, since the adapter exits with its stdin and takes the work with it (checked live). Since October 20 the process outlives the turn ([One live session per chat](#one-live-session-per-chat-october-20-2026)). On Quit, `worker.stop()` no longer waits on a parked run: `ParkedTurns.quit()` stops it like Stop (the process tree and its background work end), the run is cancelled with `STOPPED_BY_QUIT` (shown as **Stopped by Quit**) and its provider session is kept, so the next message resumes. Outpost waits and running turns are waited on as before. Codex runs are unchanged. Covered by `background-work.test.ts`, `acp-background.test.ts` and `background-work.db.test.ts` against the fake agent.

### Sleeping until a wakeup (October 22, 2026)

Claude's `ScheduleWakeup` tool is on in chat turns (it was off with the Cron tools). In Claude Code 2.1.280 (SDK 0.3.280) it is a session cron of kind `loop`: `delaySeconds` is clamped to 60-3600, the target is rounded up to the minute, and the result is `{ scheduledFor, clampedDelaySeconds, wasClamped }` (or `{ stopped: true }` for `stop: true`). It is not limited to `/loop`: in the SDK's headless mode the cron scheduler (`isKairosCronEnabled`, on unless `CLAUDE_CODE_DISABLE_CRON`) enqueues the stored `prompt` as a meta prompt once nothing is running, and the model answers it as a new cycle. One-shot fires may come up to 90 s before a :00 or :30 minute (`oneShotMaxMs`). The REPL's 1200 s keepalive is not in the headless path. The wakeup lives in the CLI process only.

claude-agent-acp 0.81.2 forwards the tool result from its PostToolUse hook as `tool_call_update._meta.claudeCode.toolResponse`, then the result text (`Next wakeup scheduled for 10:48:00 (in 67s)…`) as `rawOutput`. The woken cycle reaches the client out of turn, and its closing `usage_update` carries `cost` but no `_claude/origin`, because the cron prompt is not an autonomous origin the adapter marks. Seen with a raw ACP client (the agent asked to sleep 60 s and reply AWAKE): the prompt returned `end_turn` at 9.2 s, the wakeup fired at 75 s and the reply closed at 78 s.

Spark treats a pending wakeup as background work (`scheduled-wakeup.ts`, `background-work.ts`): `scheduledFor` (or, without a tool response, the text's seconds) is the wake time, `stop` or `scheduledFor: 0` clears it, and a cycle that starts while the turn waits, no earlier than 90 s before that time, ends it. A cycle now also ends at a `usage_update` with `cost`, and each cycle that ends with work still pending re-arms the cycle check, so a wakeup that fires after another background cycle (a task that finished earlier) is still seen. The `background_work` output and the `subagents` activity carry `wakesAt`, counted as one thing waited on, so the chat, the list, Agent TV, the island and paired devices show **Sleeping until 10:48** as text, the time formatted in the browser from `wakesAt` (`wait-label.ts`) in the Mac's 12- or 24-hour setting, or the device's locale on a paired device (**Waiting on 1 background task and a wakeup at 10:48** with other work). The run stays running and parked, so it holds nothing in the worker; the live session is not closed while the wakeup is pending. When it fires, the same run records the reply. A message sent during the sleep goes to the session as a new prompt and the sleep goes on. Stop cancels the run and kills the process tree, which takes the CLI's cron with it; Quit stops it as **Stopped by Quit**. A restart cannot keep the wakeup, since it lived in the process: the run ends `outcome_unknown` with "Spark stopped while the agent was sleeping until a wakeup…" (no clock time, since the server can't know the Mac's 12- or 24-hour setting), and Spark sends no prompt of its own. Spark adds no limit or timer; the CLI's own 60-3600 s clamp applies. Ask Spark gets no `ScheduleWakeup`: its hidden chat has no folder, so it runs with the no-project tool list (AskUserQuestion only), which also lacks the ToolSearch a deferred tool like `ScheduleWakeup` needs; it answers at once in the island and has nothing to wait on.

Live through Spark's provider with its own session options (a Do turn in a chat folder, `sleep.live.test.ts`): the prompt returned at 7.9 s with a minute-aligned `wakesAt`, so the tool response arrives even with `disableAllHooks`, and AWAKE came in the same run at 104 s. Asked only to "sleep for 1 minute", the agent picked `ScheduleWakeup` once and a background `sleep 60` once; Spark waits on either.

A foreground `sleep N` in Bash is not blocked by Spark: `script-reads.ts` lists `sleep` only as a command that creates no file. The CLI blocks it itself when its `tengu_amber_sentinel` flag is on: a first command `sleep N` with N ≥ 25 and no `run_in_background` is refused in the tool's input check, before any permission request, with "Blocked: standalone sleep N…", pointing to `run_in_background` or Monitor (seen live under Spark's options for `sleep 30`). A background `sleep` counts as background work as before. codex-acp 1.13.1 and Codex 0.156.1 have no wakeup or cron tool; a Codex agent can only run `sleep` as a command under its mode. Covered by `scheduled-wakeup.test.ts`, `acp-sleep.test.ts`, `background-sleep.db.test.ts` and `agent-sleep.spec.ts` against the fake agent, which sends the same wire shapes.

### One live session per chat (October 20, 2026)

Spark follows ACP v1 and Claude Code's own model: a chat keeps one adapter process and one ACP session across turns. [Session setup](https://agentclientprotocol.com/protocol/v1/session-setup) opens a session once and [prompt turns](https://agentclientprotocol.com/protocol/v1/prompt-turn) are repeated `session/prompt` calls on it; the [stdio transport](https://agentclientprotocol.com/protocol/v1/transports) keeps the process for the connection's life. Message 2 onward is `session/prompt` on the live session, with no new `initialize` and no `session/resume` (`live-connection.ts`, `live-connections.ts`, `live-turn.ts`). Mode, model and effort change on the live session through `session/set_config_option` / `session/set_mode`, and the agent's own `current_mode_update` is carried to the next turn.

`session/resume` (else `session/load`) runs only to reconnect: the first message after a Spark restart, an idle close, a crash, or a change to the connection key. The key (`connection-key.ts`) hashes what is fixed at spawn, `initialize` or `session/new`: agent and launch, cwd and roots, the fs capabilities, the push-blocking env flag, user and repo MCP servers, the Spark instructions and repo options, and Codex's server list. A changed key, or a turn whose stored session is not the live one (Start fresh, compaction, a provider change), closes the live session and opens as before; the worker log names the parts that changed. Child runs, the companion and compaction stay per turn, and a per-turn run that resumes the live session's id closes it first, so two processes never hold one session.

Each run rebinds the connection: the permission and fs handlers, the protocol tap (messages between runs go to the next run's audit), steering and the member inbox read the bound run. The Spark tools grant keeps one key per chat: each run revokes the previous grant and `host.restore`s the key with its own scope, and between runs the key holds a read-only scope whose `beforeToolCall` waits for the next run, so the token in Claude's MCP config or Codex's env stays valid.

ACP says session updates are not limited to prompt turns. An agent cycle that starts between turns (text, thought, a tool call, a plan, a sub-agent or task mark) asks the worker for a run of its own: source `agent_cycle`, no user message (`runs.user_message_id` is nullable for it only, migration 0192), shown as **Continued on its own**. It binds, drains what arrived meanwhile and records until an origin-marked `usage_update` with nothing left running. A permission, fs or Spark tool request that arrives between runs is never answered `cancelled` (upstream #866); it waits and is answered through that run's gate. A message sent during it goes to the live session as in a background wait.

Spark closes a live session (`session/close`, which "MUST cancel ongoing work", then the process tree) only after 30 idle minutes with nothing outstanding, when the chat is archived or deleted (the worker's 5 s sweep), and on quit. A process that exits while idle is dropped quietly and the next message resumes. Stop still cancels the run and kills the process tree with its background work; the next message resumes. An Esc-like Stop that leaves background tasks running is a known gap: with 0.81.2, `_meta.claudeCode.options.perTaskStopAffordance` kept a sub-agent alive but reported it `cancelled` at once, so Spark would lose count of it. That waits for an adapter bump and a choice between the AIR and subagents-RFD paths. Codex stays live too: codex-acp 1.13.1 advertises `resume`, `close`, `list` and `loadSession`.

Measured in the signed dev app (Claude Code 2.1.301, adapter 0.81.2, Opus 5.5, one project chat): send to first text 1.27-1.93 s on the live session (median 1.46 s, 5 turns) against 2.16-4.53 s when the same build reconnected with respawn and `session/resume` (median 2.32 s, 3 turns). An idle chat holds about 465 MB (adapter 125 MB, `claude` 340 MB) until its idle close. Covered by `acp-live-sessions.test.ts`, `acp-background.test.ts`, `live-sessions.db.test.ts`, `live-binding.test.ts`, `agent-cycle.test.ts` and `agent-continues.spec.ts` against the fake agent.

A real fan-out (three sub-agents researching this repo, October 20, 2026) showed why the live session matters. In this SDK mode every Agent call is asynchronous: `session/prompt` is held until the sub-agents end (`subagent_spawned` with `name` and `task`, the sub-agents' own tool calls and messages on their child session ids, `subagent_state_update` `completed` with `tool_uses`, `duration_ms` and `total_tokens`, sent twice), but their results reach the main agent as task-notifications, and it writes its combined summary in an out-of-turn cycle 2-4 s after the prompt returns. A per-turn process would have been killed before that. Claude Code also sends the origin-marked `usage_update` at the start of such a cycle, so a wait ends only at one that follows some work. When sub-agents ended during a turn and nothing else runs, the turn stays open as **Writing up results** for up to 15 s, so the summary lands in the turn the user asked in; a cycle that starts later becomes its own run. The main agent has no tool to stop or message one sub-agent in this mode; a message the user sends while the prompt is held goes in through `_session/steering` and is answered at once. Sub-agents' permission requests go through the gate with the chat's mode, so in Auto they run at once like the main agent's.

Covered by `subagent-stream.test.ts`, `subagent-updates.test.ts`, `subagent-progress.test.ts`, `acp-subagents.test.ts` and `subagents.db.test.ts` against the fake agent. Not yet run against the real Claude or Codex CLI.

The browser reads the thinking text of a finished run from `GET /api/runs/:id/reasoning/:messageId`; a paired phone may read it like any other run event (no switch governs reading agent output).

The worker writes `TEXT_MESSAGE_CONTENT` and `REASONING_MESSAGE_CONTENT` events in batches: chunks wait at most 50 ms (or 8 KB) and are stored together, each still its own event with its own `seq`. Any other event first stores the waiting text in the same transaction, so the order is the order the agent produced (`apps/server/src/workflow/run-appender.ts`).

Command output events are written by `apps/server/src/workflow/command-recorder.ts`, batched for 100 ms and capped per command; what each adapter provides is in [ACP_AGENTS.md](ACP_AGENTS.md#command-output-in-the-chat-october-6-2026). Evidence: `command-output.test.ts`, `command-recorder.test.ts`, `acp-terminal.test.ts`, `command-terminal.db.test.ts` (fake agent); the live check is reported there separately.

Chat providers run through ACP (Claude, Codex, Z.ai; see [ACP_AGENTS.md](ACP_AGENTS.md)). Separate Terminal sessions run the installed Claude Code or Codex interactive CLI in a Spark-owned PTY, with session-scoped Spark MCP tools. They do not create ACP worker jobs or chat runs. See [native Terminal sessions](NATIVE_TERMINALS.md).

Native Terminal hooks are tested against Claude Code 2.1.280 and Codex CLI 0.153.4. Other versions launch with activity observation marked unsupported. Codex session hooks retain the CLI's own trust requirement. A version match alone does not establish that hooks are active: until an authenticated observation arrives, activity remains unknown. Terminal output stays in the PTY and its bounded memory replay; it is not translated into an AG-UI transcript. Native usage and cost are not inferred from output.

Native lifecycle writes use a session-generation fence rather than a worker lease. Duplicate launch reservations, duplicate event IDs, stale generations, and interrupted recovery are covered by `native-terminal-turns.db.test.ts`; direct process launch and same-process reattachment are covered by `agent-sessions.test.ts`. These fixtures do not establish live provider acceptance. The fake provider, which echoes the message, remains for tests; it is not evidence of any real provider capability.

## A2A: outpost chats (October 9, 2026)

Each chat that belongs to an outpost is served as an A2A 1.0 agent by the API server, with `@a2a-js/sdk` 1.3.0 (exact) and the JSON-RPC binding, and an outpost request is an A2A task. The design is in [A2A_CHATS.md](A2A_CHATS.md). Built as release 1 of outposts; not yet released.

All tests named here are in `apps/server/test/`. The contract tests drive the real router with the SDK's own client; `outposts-e2e.db.test.ts` runs a user's request through the app's own wiring from post to answer.

Limits, which bound any claim:

- **Loopback only.** The server listens on `127.0.0.1`, every A2A route needs the launch token, and both routes are `never` for a paired phone (`apps/server/src/remote/route-rules.ts`). Nothing is served through Tailscale Serve or Funnel.
- **One text message per task.** A message for an existing task is refused (`UnsupportedOperationError`), so a task in `TASK_STATE_INPUT_REQUIRED` cannot be answered over A2A: the user answers it in Spark.
- **A call is never the user.** A `SendMessage` with no stored request behind its `messageId` is accepted only for a chat that is in an outpost and is treated as written by another chat. No message field carries authority.
- **Not served:** push notification configs, `ListTasks`, the extended Agent Card, signed cards, the gRPC and HTTP+JSON bindings, file and data parts. A caller that does not ask for A2A 1.0 is refused.
- **No outside agent has been tried.** The only client that has called the endpoint is the SDK's own, in our tests and in Spark's dispatcher. "Compatible with A2A agents" is not claimed.
- **What the tests prove.** In the contract tests the state of the receiving run is set in the database, not produced by an agent. `outposts-e2e.db.test.ts` runs real turns with the fake provider, which echoes the message. No live provider has run an outpost request.

## MCP Apps: Spark's own artifacts (October 22, 2026)

`spark_artifact` on Spark's MCP server (`@modelcontextprotocol/sdk` 1.30.1) returns an MCP `resource_link` per [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp):

- `uri` is `ui://spark/<chat>/<id>`.
- `mimeType` is `text/html;profile=mcp-app` for HTML.
- `_meta.ui.csp` names no connect, resource or frame domains, with `prefersBorder: true`.

On the ACP side (`@agentclientprotocol/sdk` 1.5.0), a `resource_link` content block with that URI, in a tool call update or an agent message, maps to an `artifact` `ACTIVITY_SNAPSHOT` once Spark has checked that the artifact is the chat's own. The card is drawn from Spark's stored versions.

Not implemented:

- `resources/read` for `ui://` URIs.
- The MCP Apps postMessage bridge and tool calls from a page.
- Rendering another server's UI resources.

Design and security model: [ARTIFACTS.md](ARTIFACTS.md).

## Deviations from the AG-UI client model

- The browser uses `EventSource` and our own reducer, not `@ag-ui/client`. Runs start with `POST /api/conversations/:id/messages`, not with an AG-UI `RunAgentInput` request, because the worker owns execution. Evaluating an `AbstractAgent` with `connect()` is task F-17.
- Assistant text is persisted as a message when `TEXT_MESSAGE_END` is written, in the same transaction.
