# Jev

Checked against the TypeSafe docs (https://docs.typesafe.ai/llms.txt), last re-read in full on September 27, 2026. This file is the current design and the open items; earlier rounds are in git history.

## What it is

Jev is TypeSafe's "System One" model. It takes a `state` (text or JSON) and typed questions, and returns typed answers with calibrated probabilities (https://docs.typesafe.ai/introduction):

- **Choice:** one option from up to 255.
- **Score:** a level on a rubric.
- **Noul:** the probability that a statement is true.

Jev is not a chat or coding LLM. It doesn't generate text, stream, call tools, or edit files (https://docs.typesafe.ai/introduction/coding-agents). It has no OpenAI- or Anthropic-compatible endpoint, no CLI, and no ACP support. The "agent skill" is only documentation for coding agents.

## Role

- **Spark off.** With the Spark switch off (Settings → Spark, `profiles.spark_enabled`) Jev is not called at all: no intake, no verdict and no diff observation. See [HARNESS_PLAN.md](HARNESS_PLAN.md#spark-settings-spark-off-and-session-instructions-september-28-2026). The project map is separate: it asks Jev whenever Jev is connected (see [Project map](#project-map)).

- **(a) Chat provider: no.** Nothing in the API can answer a chat.
- **(b) Router: observed only since round 10.** Routing is a documented pattern (https://docs.typesafe.ai/patterns/intent-routing, https://docs.typesafe.ai/patterns/confidence-routing), but rules-only routing was cheaper at the same pass rate, so the rules pick the model and Jev's tier pick is recorded for comparison. Jev acts only on the intake questions listed below.

## API

- **Auth:** `Authorization: Bearer <key>`, with keys from https://console.typesafe.ai/keys. The key format isn't documented, so the app checks nothing locally.
- **Base URL:** `https://api.typesafe.ai`, configurable as `TYPESAFE_BASE_URL` (the SDK's own variable, https://docs.typesafe.ai/sdk/javascript/api/variables/ENV).
- **`GET /v1/models`:** returns `{ models: [{ name, description, release_date }] }` and spends no tokens. The connection check uses it (https://docs.typesafe.ai/models#listing-models).
- **`POST /v1/systemone`:** takes `{ state, model, questions }` and returns `{ model, answers, usage }` (https://docs.typesafe.ai/api).
- **Errors:** 401, 422, 429, and 529.
- **Models:** `jev-latest` and `jev-preview`. Input is text only, up to 64k tokens.

## Cost

The price is $0.042 per million input tokens. Output tokens are free (https://docs.typesafe.ai/models). Responses report tokens, not cost. One routing call is a few hundred to a few thousand tokens, well under $0.0001. Verifying a key spends nothing. Jev gets no "Send test message", because a test would be billed.

## Round 10: what Jev does now (September 27, 2026)

Jev answers a few concrete questions per Do turn, observes routing, edits and diffs, and never grants anything. The flow is in [HARNESS_PLAN.md](HARNESS_PLAN.md#current-architecture-the-lean-harness-round-10-september-27-2026).

- **`need`.** One more Choice in the intake call of a Do turn: question, small change, build or needs you. It sends no new state. At confidence 0.8 or more it chooses how the turn starts; otherwise the rules do. See [HARNESS_SIMPLE.md](HARNESS_SIMPLE.md#3-intake-the-four-needs).
- **Piece questions.** The per-piece questions (`P1_kind`, `P1_reasoning`, `P1_coding`, `P1_context`, `P1_reliability`, …) are asked about the Coordinator's pieces after it writes the list. The Builder count (`builders`) and the `T<n>_…` questions are asked up front only when an agreed plan existed before the build ([HARNESS_SIMPLE.md](HARNESS_SIMPLE.md#4-every-jev-question)). Two more calls happen outside a turn: the [project map](#project-map), and pull request feedback triage while a pull request is watched.
- **One act line per question, at every autonomy.** The harness autonomy only decides whether an unsure answer asks you (Review each step) or falls back to the rules (Automatic, Full auto → PR).
- **Validation before branching.** The key must be present, the type must match, a Choice must be one of the offered options, and every value must be finite and between 0 and 1. A failed intake answer falls back to the rules for that question; a failed policy answer counts as review, and a failed verifier answer as not verified. Only 429 and 529 are retried, once.
- **Distinct options.** Each `intent` option has `what` and `not_for`, so neighbouring categories (Bug fix and Feature, Question and Research) do not split probability. The tier options say what each size is for and not for, with the model's card line.
- **Thresholds are provisional** until tuned on our own labelled data: the observation rows plus the outcome signals. `pnpm jev:thresholds` prints precision and recall per threshold. Promotion to acting follows rule 7 under [Rules for every new use](#rules-for-every-new-use).
- **Records.** Every Jev row stores `policy_version` and the model version that answered (`jevModel`).
- **Removed:** routing that acted (provider, model and effort picks and their gates, the frontier gate), transitions, step checks, the watchdog, parallel and lane questions, the build-style choice, and the complexity, risk, depth, scope and mechanical intake questions. Since September 30 (policy `route-score-1-cache-aware`) four 1–5 ratings are back in the same intake call; they feed a code-owned route score that picks among the models the rules and the floor allow, so Jev still never picks the model; since `route-score-2-escalation-routes` the complexity, stakes and context-dependence ratings also choose how a hard follow-up escalates (ROUTING_PLAN §12), still through code. See [HARNESS_PLAN.md](HARNESS_PLAN.md#removed-in-round-10).

### Project map

The project map (`apps/server/src/map/`) asks Jev outside any turn, while it builds a repository's map in the background. It uses Jev whenever Jev is connected for the project's workspace (`jevAccessFor` in `map/scheduler.ts`); it does not check Spark off or "Check changes with Jev". Calls time out after 20 s (`MAP_JEV_TIMEOUT_MS`) and go through the map's CPU gate, which pauses while any run is queued or running. After 3 failed or timed-out label calls in a row (`LABEL_GIVE_UP_AFTER`) the build stops asking and gives the remaining areas their rules label, so an unreachable Jev costs a build at most a minute; the next build tries again.

**Answer cache** (`map/answer-cache.ts`, migration `0108`). Before an `area_label` call, the labeller hashes the cache version (`jev-answer-cache-1`), the label policy (`MAP_LABEL_POLICY`), the pinned request model and the exact redacted request (state and questions) with SHA-256 and looks the key up in `jev_answer_cache`. A hit younger than 7 days (`ANSWER_CACHE_TTL_DAYS`) is used as the answer and nothing is sent; it still goes through `parseLabel` and the 0.8 line like a fresh answer. The table holds only the key, the answers, the answering model and the time, never the request. A row that is not a valid answer set, or lacks an asked question, is ignored and Jev is asked again. Only answered calls are stored; rows past the TTL are deleted on the next write. A change of policy, model, evidence or question text changes the key. `link_match` calls are not cached.

Each call is a row in `map_jev_calls` (migration `0072`): `purpose` (`area_label` or `link_match`), `subject` (the area id, or `path:line` of the call), status, answering model, input tokens, cost, latency, `policy_version`, `asked` (the full request, passed through `redactValue`) and the answer; an area label's answer also lists the files whose contents were sent. An answer served from the cache is also a row, with `from_cache` true, 0 tokens, 0 cost and the model that first answered; the build's `jevCached` timing counts them and `jevCalls` counts only real calls. Nothing is recorded when Jev is not connected. The label itself is saved in `map_labels` with its source (`jev` or `rules`) and confidence, and the build's timings add the call count, tokens and cost.

### Content-based file ranking (observed since October 3, 2026)

After the code scan, `orchestration/observe-content.ts` asks Jev one Noul per file, "Does the source shown for this file provide concrete implementation, caller or test evidence for `request`?", over short previews of the scan's first 16 sendable candidates (`routing/file-evidence.ts`; the exact content is in [Data sent](#data-sent)). The answer orders the files by probability and is stored as a `rank_content` row next to the `rank` row. Agents still get the current ranking: `CONTENT_RANK.promote` is `false`, and `agentRanking` returns the current ranking without waiting for the previews.

- **Gate.** It runs only when Jev is connected, Spark is on and "Check changes with Jev" is on. Otherwise the row says why (`Jev not connected`, `skipped: diffs off`, the pause message) and nothing is read or sent.
- **Time.** It starts when the scan ends, next to the `rank` call, and has 1.5 s in total (`CONTENT_RANK.deadlineMs`, the same as the code context's ranking grace) for reading files and calling Jev. A timeout or outage here does not count toward the Jev pause (`pauseOnFailure: false`), so a short deadline cannot switch off the acting calls.
- **Cache.** Each file's answer is stored in `jev_answer_cache` under the hash of the policy (`rank-content-1`), the request model and that file's redacted single-file request. A file with the same preview and the same request is not sent again for 7 days; the row lists `sent` and `cached` paths, and a fully cached ask records 0 tokens.
- **Record.** The row holds the status, tokens and cost, each request's files, bytes, tokens and latency, the probabilities, the order (first 12) and the `state` sent. Migration `0110` adds the purpose and the `content_files`, `content_status`, `content_tokens` and `content_rank` columns to `routing_labels`.
- **Comparison.** `routing:labels` adds `files.content` (precision and recall at 5 against the files the task changed) next to `files.predicted`. `pnpm jev:content-rank` prints scan order, the current ranking and the content ranking side by side, per-turn wins and losses, tokens per turn and the cached share. It supports promotion at 50 or more labelled turns when recall@5 is at least 0.05 higher, precision@5 is not lower, and more turns improved than got worse.

Diffs are sent only by the edit gate, the verifier and the Critic findings call. File contents are sent by those, by the file previews (only while "Check changes with Jev" is on) and by the project map, which also sends the repository folder name; the map does not depend on "Check changes with Jev".

TypeSafe doesn't train on customer data. Zero data retention is enterprise-only (https://docs.typesafe.ai/legal).

The key lives only in the OS keychain (`jev:api_key`). The database and the UI see only a masked `…abcd`.

## Turn categories and auto titles (built September 26, 2026)

- **Categories.** The `intent` question offers ten intents: Question, Research, Plan, Bug fix, Feature, Refactor, Docs, Tests, Config, Review (October 1, 2026; Debugging, Setup and Chat read as Bug fix, Config and Question). The pick is stored on the top-level run (`runs.category`) when its confidence is at least 0.5; otherwise, and without Jev, a Do turn stores the rules' intent from the wording (`intentByRule`). A chat's category is its most recent non-question turn, else Question.
- **UI.** A quiet chip on each turn header and the crew dispatch line, the category in the sidebar row tooltip, an `is:<category>` filter in sidebar search (ids, labels, and aliases such as `is:bugfix` or `is:config`), and cost and turn counts by category in Settings → Usage and the audit summary. Child runs count toward their turn's category.
- **Auto titles.** `conversations.title_source` is `message`, `auto`, or `user`. While it is not `user`, the main agent is asked to end its reply with `Title: …`; that line is held back from the stream and the saved message and stored as `runs.suggested_title`. When the top-level run succeeds, the same transaction retitles a `message` chat with the agent title, or with a fallback of category plus main file or topic ("Refactor · format.ts"). An `auto` title changes again only when a later turn's confident category differs from the one it was titled under. Renaming sets `user`; the ⋯ menu can stop or resume auto titles. The title and its origin are recorded in the run's advice.

## Rules for every new use

These follow the TypeSafe docs and our authority rules in [HARNESS_PLAN.md](HARNESS_PLAN.md#jev-can-never-grant-permissions).

1. **Code owns the flow.** Jev answers atomic questions, and a pure function turns the answers into the decision. A question that reads like "what should we do?" is split into facts (https://docs.typesafe.ai/concepts/how-to-build-with-system-one).
2. **One call per event.** Every question on the same state goes into one batch, speculative ones included (https://docs.typesafe.ai/patterns/fan-out). Split only when a question needs a different state.
3. **Noul criteria use `true` and `false`**, and a high value means the thing we check for. Where several checks guard against a bad result, frame each as bad = true and act on the `max` (https://docs.typesafe.ai/cookbooks/sde_cascade). `noulQuestion` in `advisor/questions.ts` only accepts these keys.
4. **No arithmetic for Jev.** Counts, times, token budgets and prices stay in code. Jev gets named buckets such as "checks failed" or "no retries left".
5. **Gate every answer.** Use a Noul band per action, or a confidence line for a Choice. Below the line the existing rules decide. See [Reading confidence](#reading-confidence).
6. **Jev never grants anything.** It never answers an approval, loosens a mode, skips a safety check, or marks work verified. It can make the harness do more (continue, review, ask), and less only where a rule already allows it.
7. **Observe first.** Each new decision first records Jev's answer next to the rule's as a `run_advice` row with its own `purpose`. It acts only after our own labelled rows support it (`pnpm jev:thresholds`; `pnpm jev:content-rank` for the content-based file ranking). A decision that can be promoted has one constant that turns acting on, off by default (`CONTENT_RANK.promote` in `routing/file-evidence.ts`).
8. **Store `response.model`** on every row, so a change of Jev version shows up in the analytics.

## Reading confidence

- For Choice and Score, Jev reports `confidence = (n·p_max − 1) / (n − 1)`, where `n` is the number of options offered (https://docs.typesafe.ai/confidence). It puts every option count on one scale: 0 is no better than an even guess, 1 is certain. We gate on it. For a Noul, `optionConfidence` in `advisor/gate.ts` applies the same formula with n = 2.
- Calibration holds across groups of answers, not for any one answer.
- Low confidence means the options overlap, the question measures more than one thing, or the state lacks the evidence. It is a reason to ask or fall back, not a verdict.
- Pick a Noul line per action: 0.5 when both errors cost the same, higher when a false yes is expensive, lower when a missed yes is. Middle values go to review.
- For a result built from several answers, use the weakest one (`min`). For "any serious problem" checks, use the `max` of the bad-is-true Nouls.
- Repeated calls are not bit-identical (a probability moves by about 0.01). Use abstention bands, not repeated voting.

## API limits

From the TypeSafe docs (https://docs.typesafe.ai/models, https://docs.typesafe.ai/api, https://docs.typesafe.ai/model-jaggedness/jev-1.13):

- **Rate limits:** 1,200 requests per minute and 250,000 tokens per second per account, adjusted dynamically; over either returns 429. Cookbooks hit 429 at about 8 concurrent requests on one key.
- **Context:** 64k tokens for the state plus all questions, and 32k for the state plus the longest single question. Accuracy falls as irrelevant state grows.
- **Per question:** up to 255 Choice options, 2 to 10 Score levels. No documented limit on questions per call (the docs show up to 62).
- **Latency:** about 100 ms typical, 70 to 500 ms end to end; we measured 150 to 360 ms.
- **Structured questions:** `instructions`, option descriptions, Score levels and Noul criteria can be objects, which is how we pass `what`, `not_for` and `examples`. Score levels should describe situations, not degrees.
- **Known weak spots (jev-1.13):** literal reading, numbers and counting, dates, indirection, large irrelevant state, adversarial content, contradictory instructions, no consistency between separately asked questions, and generation. English is the primary language.
- **Our handling:** at most 4 calls in flight per process (`JEV_CALLS_IN_FLIGHT`, `advisor/jev-limiter.ts`); a 429 or 529 is retried once, honouring `retry-after-ms` or `retry-after`, only when at least 1 s of the budget would be left; `jev-latest` is sent as `jev-1.13.0` (`requestModel` in `advisor/jev.ts`), the version the lines were tuned on.

## Where Jev is a poor fit

- **Anything that writes:** plans, fix instructions, summaries, titles, commit and PR text, explanations. The docs say generation "will not work well and will be very slow".
- **Arithmetic, counts and dates:** token counts, when to compact, time windows, anomaly maths (the analytics detectors stay deterministic).
- **Deep code judgment:** whether a diff is correct, finding bugs or vulnerabilities, resolving merge conflicts. The Critic and the checks do this.
- **Permissions and safety:** approvals, allowlists and secret-file rules.
- **Decisions code already makes exactly:** `package.json` script detection, retry counts.
- **Adversarial text as a boundary:** the `injection` Noul is recorded, never used to relax a check (the docs call such a check "a filter, not a security boundary").

## Risks

- **Latency.** Orchestration calls time out after 3 s (`ORCHESTRATION_JEV_TIMEOUT_MS`) and fall back to the rules. After 3 calls in a row that time out, cannot reach TypeSafe or get a 5xx (`JEV_PAUSE_AFTER`, `advisor/jev-breaker.ts`), every Jev call in the process is skipped for 30 s (`JEV_PAUSE_MS`) and answers at once with "Jev is not answering, so Spark is using its rules for a moment.", so a silent Jev costs a turn a few seconds, not 3 s per question; the first call after the pause tries again, and any answer resets the count. A rejected key (401), 422 and a caller that stopped waiting do not count. Keep batches under about 60 questions and 10k state tokens.
- **Rate limits.** Several orchestrations and the map can call at once; the process limiter and the single retry cover this today. Record 429s so they can be told apart from other failures.
- **Data sent.** Any new field goes in the [Data sent](#data-sent) table and a pinned test. File paths and contents beyond today's, chat history, or text across chats need the user's yes. Send diffs only while "Check changes with Jev" is on, never send tool output or credentials, and don't route through OpenRouter or Vercel AI Gateway (a third party). Zero data retention is enterprise-only.
- **Quality drift.** `jev-latest` will move. Keep the pinned version and re-run `apps/server/test/jev-intake.live.test.ts` and a period of observation before moving to a new one.
