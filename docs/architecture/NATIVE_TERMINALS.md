# Native Terminal sessions

Terminal sessions run the installed Claude Code or Codex interactive CLI in a pane of a tmux server that Spark owns ([tmux](#tmux)); without a usable tmux they run in a Spark-owned PTY as before. Chat sessions continue through ACP. Terminal sessions do not start chat runs and cannot switch a live Chat conversation into a native terminal.

## Ownership and lifecycle

The desktop starts an independent local runtime under the channel's app-data directory. That runtime owns embedded PostgreSQL, the Node API, and the workflow worker. Electron controls the windows and connects to this runtime over a Unix domain socket, `runtime/control.sock` (mode 0600) in the channel's private `runtime` directory (mode 0700), so only the same user can reach it. The host creates a new control token on every start (`runtime/token`, mode 0600) and records its pid and app version in `runtime/endpoint.json`; it removes a stale socket and endpoint on start after checking that no live host answers, and removes the endpoint and token on shutdown. The token never crosses the socket: the client sends a nonce, the host answers with an HMAC of the token over both nonces, the client verifies it and answers with its own, and the host serves no request before that. The API launch token stays in runtime memory and is read only over this proven connection. The host starts only the app's own API, worker and migration entries through its own `server-entry.js`; the server folder is fixed when the host is spawned. Service environments are passed through whole, because agents need the user's login-shell environment. Development and installed channels have separate directories and credentials. A data folder whose socket path exceeds 103 bytes is refused with an error.

On reconnect, Electron adopts a runtime of the same app version: its database port, API port, launch token, and running services. It does not migrate an already-running API or start duplicate agents. A runtime of a different app version, or one that reports no version, is replaced: Electron asks it to shut down over the proven connection (API and worker, their PTYs, then PostgreSQL), waits up to 30 seconds for the process to exit, then starts a host of the current version and continues the normal start, migrations included. A host that does not answer, such as one from the earlier loopback protocol or one that ignored the request, receives SIGTERM (the same ordered shutdown) and after another 30 seconds SIGKILL, but only when the recorded pid is a `runtime-host.js` process started for this runtime directory; any other process is left alone. Terminal sessions under tmux are kept through the replacement: the earlier API is asked to detach, and the new API re-adopts them in its startup recovery (`nativeTerminals.recover()`). Sessions that ran without tmux are lost and recorded as interrupted. Normal updates still use explicit shutdown before restarting the updated app; replacement covers a runtime left headless by a crash, a force quit or an update.

| Event                                                         | Terminal behavior                                                                                                                       |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Hide a terminal, close a window, refresh, or lose its socket  | PTY continues; a fresh one-use attach token reconnects to the same process                                                              |
| Electron renderer or main-process crash                       | Runtime and services continue; reopening reattaches                                                                                     |
| Explicit Quit                                                 | Services stop, Terminal sessions and their tmux server stop, grants are revoked, then PostgreSQL stops                                  |
| API or runtime crash, API restart, update relaunch            | The CLI keeps running under tmux; the next API re-adopts the session and the view says Spark restarted                                  |
| Mac restart or logout, tmux server gone, session without tmux | Session history remains; running state is reconciled as interrupted and resume is explicit                                              |
| Native CLI exits                                              | Session records its exit and does not restart automatically; the view offers Resume session, or Start again with no provider session ID |
| Provider reports `SessionEnd` (`/clear`, `/resume`, logout)   | PTY continues; an open turn closes; the next `SessionStart` may carry a new session ID                                                  |
| Launch fails before the agent starts                          | Run fails with the reason; a plain launch starts again with the saved first message                                                     |
| Dock shell (not an agent) loses its socket                    | Shell ends; only agent sessions are kept for reattachment                                                                               |
| Reopen with another app version after a crash or update       | The earlier runtime is shut down and replaced; its tmux sessions are kept and re-adopted                                                |

Only the CLI's own exit marks a session exited: the PTY's exit, or under tmux the dead pane's status. A provider `SessionEnd` hook is an observation: Spark closes the open turn as outcome unknown, records the provider's reason when it is a plain token, and keeps the process. After a `SessionEnd`, the next `SessionStart` from the same hook credential and generation may replace the recorded provider session ID; any other event carrying a different session ID is refused.

A provider session ID is accepted from a hook only when it is 1–100 letters, digits, `_` or `-` and does not start with `-`. It is checked again when the resume command line is built, so a stored value can never be read as an option. Anything else is refused and not stored.

A session with no provider session ID has nothing to resume. When its launch failed (terminal limit, CLI probe, worktree), its run is failed with the reason and a plain launch is allowed again: the saved first message's run is re-queued, and the session view offers Start again. The same plain launch is allowed when the CLI exited, or the host stopped, before any provider session ID was recorded: the run's outcome is unknown, it is re-queued the same way, and the view offers Start again for every ended session that has nothing to resume. A launch or session the user stopped stays cancelled and offers neither action without a provider session ID. Startup recovery fails Terminal runs that were queued but never launched, so they do not count as active work.

An attach token is single-use: after its socket disconnects, reattaching needs a token newly issued by the authenticated attach route. Agent sessions keep a replay buffer; ordinary dock shells end when their socket closes.

Terminal output replay is bounded to 256,000 JavaScript characters in memory. It is not a durable terminal transcript; after a re-adoption it starts from what tmux still holds of the screen and scrollback. Reattachment preserves a running process; provider-native resume creates another process from provider history and does not restore an interrupted shell command exactly.

Spark manages only its own child processes, the tmux server on its own socket, and recorded session IDs. It never adopts or kills an external terminal by executable name, and never talks to the default tmux socket. PTYs start in the session's project workspace; a working directory does not provide a filesystem sandbox. Native CLI permission modes continue to govern native execution.

## tmux

A Terminal session's CLI runs in a tmux session so it outlives the API process. The code is in `apps/server/src/terminal/tmux/`. Plain shells, previews and agent terminal tabs (`spark_terminal_run`) are not under tmux.

| Piece          | How                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Binary         | tmux 3.8 with a static libevent, built from pinned tarballs and bundled per architecture ([Releases](RELEASES.md#bundled-tmux)). `SPARK_TMUX_BIN` overrides it from source; `SPARK_TERMINAL_TMUX=off` turns it off                                                                                                                                                                                                                                                                                                                                   |
| Private server | Socket `tmux/s` and config `tmux/tmux.conf` under the channel's data folder (mode 0700/0600), always passed with `-S` and `-f`, with `-u`. Never `~/.tmux.conf` or the default socket. Run from source, the folder is per API port. The server starts with a small fixed environment and that folder as its working directory                                                                                                                                                                                                                        |
| Config         | Status off, no prefix, no key bindings, mouse off, `escape-time 0`, focus events and extended keys on, 50,000 lines of history, `window-size latest`, renaming off, clipboard off, `remain-on-exit on`                                                                                                                                                                                                                                                                                                                                               |
| Launch         | `new-session -d` is read from a 0600 file that exists for the length of the call, so the environment (the Codex tools token among it) is never in a process's arguments. The whole pane environment is passed explicitly; the token is removed from the session environment once the CLI has started. A `/bin/sh` wrapper waits for one line, restores what tmux overrides (`SHELL`, `TERM_PROGRAM`), unsets `TMUX` and `TMUX_PANE`, changes folder and `exec`s the CLI, so the CLI is the pane's process and sees `TERM=xterm-256color` and no tmux |
| Stream         | One `tmux -C attach` client per session. `%output` bytes are unescaped and sent down the existing WebSocket, so xterm.js renders the CLI's own output and keeps scrollback, selection and mouse state. Input is `send-keys -H`; resize is `refresh-client -C`. The wrapper is released only after the client is attached, so no output is missed                                                                                                                                                                                                     |
| Exit           | A `pane-died` hook renames the window; the client then reads `pane_dead_status` and `pane_dead_signal`. That status decides exited or error exactly as a PTY exit does. A control client that ends while the pane lives is reopened once                                                                                                                                                                                                                                                                                                             |
| Stop           | The pane's process tree is signalled as before (`killProcessTree`), then the tmux session is killed. The server exits with its last session                                                                                                                                                                                                                                                                                                                                                                                                          |

### Re-adoption

On start, `recover()` lists the sessions on the socket (`readopt.ts`). A session whose row is live is rebuilt: new hook credentials are written to its `observer.json`, which the hook script reads on every event; the Spark tools grant is restored from the sha256 digest kept in `adopt.json` beside it, on the same port (`terminal-sessions/mcp-port`), so the token the CLI already holds keeps working; the open turn gets its context back and Spark tools stay read-only until the next hook reports the mode. A session with no row is killed. A row with no session, or a tmux server that is gone, goes through the existing interrupted recovery. A pane whose command ended while Spark was down is adopted so its real exit status is recorded. Recovery runs once per API process.

The terminal is seeded from `capture-pane -e -p -N` (scrollback, the saved screen under an alternate screen, the visible screen) and `pane_private_modes` (cursor, mouse, focus, bracketed paste, keypad). OSC 8 hyperlinks survive the capture. The Kitty and modifyOtherKeys key modes are not replayed.

Hook events fired while the API was down are lost. For Claude Code the open turn's steps and tokens are read back from the session file, from the offset stored when the turn began, with each step's own time; sub-agent steps from that gap are not. Codex steps from the gap are not read back and the view says so. A turn that ended during the gap stays open until the next hook event, as an unobserved completion always has; a turn that was open shows **Open** until then.

The view shows one line, "Spark restarted at 7:14. This session kept running.", from `readopted` on the session (in memory, so it ends with that API process), and reconnects by itself.

### Quit, restart and update

| What happens                                                                  | Terminal sessions                                                                                                                                                                                                        |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The user quits Spark, or quits with an update that installs without reopening | Stopped: the API gets SIGTERM, stops every session and kills the tmux server                                                                                                                                             |
| **Restart to update**                                                         | Kept: the desktop notes `install(relaunch)` and `before-quit-for-update` (`quit-policy.ts`), the stop request carries `keepTerminals`, and the runtime host sends the API a message instead of SIGTERM; the API detaches |
| A newer app replaces a runtime left running                                   | Kept, the same way                                                                                                                                                                                                       |
| The API or the runtime host is killed, or the supervisor restarts the API     | Kept: nothing told tmux to stop                                                                                                                                                                                          |
| The API keeps failing and Spark gives up                                      | Kept until the next start                                                                                                                                                                                                |

### Not durable

A Mac restart or logout ends the tmux server; so does killing it. A bundled tmux that cannot speak to a server left by another tmux version cannot re-adopt its sessions. If the tools port is taken at the next start, a re-adopted session keeps running without Spark tools. A session that fell back to a direct PTY is interrupted by a restart as before.

### Fallback

Without a binary, with one that fails `tmux -V`, with a socket path over 103 bytes, or when `new-session` fails, the session runs in a direct PTY and one log line says so.

### Start timing

The API writes one line to its log when it starts, naming the tmux that runs sessions by file name and version (`Terminal sessions run under tmux (tmux, tmux 3.8).`) or the fallback reason. Each Terminal session start then writes one line, when the session prints its first output, ends before printing, or fails:

```
Terminal start session=<session id> provider=claude outcome=started total_ms=2059 tmux=yes worktree=created locate_cli_ms=3 prepare_session_ms=2016 worktree_ms=1939 grant_ms=0 prepare_launch_ms=9 spawn_ms=21 new_session_ms=20 attach_ms=8 first_output_ms=40
```

`total_ms` is the launch request, which is what "Starting terminal…" waits for. `worktree_ms` is inside `prepare_session_ms` and covers placing the chat: the fetch, `git worktree add` and dependency preparation. `spawn_ms` is the synchronous start of the process and holds `new_session_ms` (tmux `start-server` and `source-file`, then `display-message`); without tmux the line says `new_session=direct`. `attach_ms` runs from opening the control client to tmux acknowledging the release of the held start, and `first_output_ms` from the spawn to the first bytes. A failed start adds `failed_in`, the error class, and its status and code when it has them. The line holds durations, the provider, the session id and these fixed words only: no path, command, prompt, name or error message (`start-timing.ts`).

## Tools and observation

With Use Spark workflow enabled, Terminal agents receive a revocable session-scoped Spark MCP grant and prepared task context. Turning it off omits Spark tools and workflow prompts from new launches. Custom instructions remain available in either mode. Spark tools use the existing backend permissions, confirmations, audit, and run events. The native interface owns native questions and permission prompts; Spark action confirmations remain Spark cards.

Native commands run outside Spark's command gate. Terminal sessions do not run automatic separate publish turns or automatic PR follow-up turns; the native agent owns that interaction. The Chat-only autonomy control is omitted from Terminal sessions. Automatic Full auto → PR remains a Chat workflow feature.

Provider-specific launch adapters supply hooks and MCP configuration for the individual launch without rewriting global CLI settings. Hook events are authenticated, scoped to the session and generation, and treated as observations. They never grant authority. Compatibility is verified through isolated CLI capability probes rather than an exact version allowlist. Missing observations show Open rather than inferring idle from terminal silence.

Claude Code fires no hook when the user interrupts a turn with Esc: `Stop` "does not run if the stoppage occurred due to a user interrupt", and no `Notification` or `SessionEnd` follows. While a Claude turn is open, Spark therefore follows the session transcript that the hooks name in `transcript_path` and treats the record Claude Code appends on an interrupt (a `user` record whose only content is `[Request interrupted by user]` or `[Request interrupted by user for tool use]`, carrying the turn's `promptId`) as an `interrupt` observation: the run closes as cancelled ("Interrupted in the native terminal.") and the session shows Idle, as for the Codex `Interrupt` hook. The path is accepted only when it is absolute and named `<session id>.jsonl` for the session ID the same authenticated hook reported. The first read of a session file starts at its end and later reads continue from the stored position; lines are parsed as untrusted data, and only token counts, model names and the CLI's own cost total are stored from the file ([Terminal usage](TERMINAL_USAGE.md)). The observation is fenced like a hook event: it applies only when its `promptId` equals the open turn's prompt ID, its event ID is derived from the session, generation and prompt ID so a repeat is a no-op, and the watcher closes when the turn closes or the session ends. Esc pressed before Claude Code has received any part of a reply writes no record (the CLI puts the prompt back in the input box), so that turn stays Running until the next prompt closes it as outcome unknown.

Spark tool permissions never exceed the mode selected at launch, even if a hook reports a broader native mode. Until a recognized permission observation arrives, Spark tools remain read-only. Widening Spark tool permissions requires a new session with the intended launch mode.

The terminal view and Island share a session identity and activity state. The terminal companion stays outside PTY output, does not intercept typing, and honors reduced motion.

The Browser bridge is forwarded independently for the API and worker while a desktop is attached. Pending and new Browser requests fail explicitly when the desktop disconnects; background non-Browser work can continue. Reopening restores the bridge. Terminal and native-terminal routes are refused by the phone gateway, including Terminal creation through otherwise-shared conversation and ticket endpoints.

## Validation boundaries

`runtime-client.test.ts` exercises real detached host processes in temporary directories: socket and token permissions, token rotation, a stale endpoint and socket taken over by another listener, connections without proof, a controller killed with SIGKILL, identity adoption, explicit shutdown of owned children, replacement of a host of another version, without a version, or of the earlier loopback protocol, and refusal of entries outside the app. `runtime-retire.test.ts` covers the pid identity check and the SIGTERM and SIGKILL fallback against fixture processes. Replacement after a real auto-update or a crash of the packaged app has not been exercised. `agent-sessions.test.ts` exercises immediate native spawn, duplicate launch prevention, bounded replay, fresh tokens, stale attachment handling, and exit reporting. Existing setup terminal tests retain their disconnect/timeout behavior. `native-terminal-runtime.db.test.ts` checks real authenticated hook HTTP, native MCP calls and backend confirmations, cancellation/resume fencing, and eight simultaneous fixture sessions. These use a fake PTY and do not measure live provider performance.

These checks do not establish native packaged Electron crash acceptance, embedded-PostgreSQL survival under every OS termination scenario, or live Claude/Codex activity delivery. Provider claims remain tied to adapter contract tests, local capability probes, and explicit live acceptance. Release validation must exercise the packaged application, actual provider prompts and approvals, interrupted recovery, and 5–10 concurrent sessions.

If PostgreSQL is unavailable while the native process exits, durable exit status may require service restart reconciliation. Process cleanup and grant revocation still proceed.

### Review follow-up

Terminal sessions have no Spark safety floor: the provider's CLI runs under the agent's own permission mode, and Spark's approval cards, protected-path rules and ran-without-review audit do not apply inside the PTY. Spark records that the session started, its mode and its observed state, and, since the Terminal usage change, the tool names and times of its steps, token counts, model and cost per turn read from the CLI's own session file, and the CLI's own session total; never commands, paths, prompts, replies or tool output (see [Terminal usage](TERMINAL_USAGE.md)). The owner chose to document this rather than build a floor; AGENTS.md and the guide say so.

Runs of a Terminal session are recorded at the non-publishing level (`hands-off`) whatever the profile default is, so the Spark MCP scope has publish authority only when the user's message asks for it or the agent's mode would run it. A Terminal conversation with no terminal row and no messages is a draft: the app shows the new-session picker again, and the chat list and pruning treat it like an empty chat.

An instruction file that can no longer be read does not fail a run: preferences load without its text, a chat run records one note with the reason, and the profile reports the reason for Settings. A Terminal launch goes on without the text but records no note yet. The file check refuses credential locations by full resolved path, and a paired phone sees that a file is set but not its path.
