## Current architecture: the lean harness (round 10, September 27, 2026)

Everything below this section up to "Evidence, kept distinct" is history: it records how the harness grew in rounds 1 to 9. This section is what runs today. The plan, the decisions and the inventory are in the round-10 plan the user approved, and the evidence is in the independent review and `docs/benchmarks/harness-e2e-live-2026-09-26.md`.


- **Intake** (`advisor/intake-questions.ts`, `orchestration/intake.ts`). One batched call per turn. The acting questions are Nouls, each worded as one concrete fact with structured `true`/`false` descriptions: `question`, `vague` (first message only), `review`, `destructive` and `continues_task` (only when the chat has a task to continue, with the previous request and a short task summary as evidence). `intent` stays for the category chips, the clarify readings and the auto-title fallback; its options carry `what` and `not_for` so neighbouring categories do not share probability. `injection` is judged over attached text only and never relaxes anything. `tier` is a Choice over the chat provider's small, mid and top models, recorded and never applied. Removed from intake: complexity, risk score, depth, scope, mechanical, provider, per-provider model and effort, and the speculative build style.
- **Validation.** Before anything branches, every answer is checked: the key is present, its type matches the question, a Choice is one of the offered options, and every probability and Noul is finite and between 0 and 1. A failed intake or routing answer falls back to the rules for that question only. A failed policy-gate answer counts as "review", never "allow"; a failed verifier answer counts as not verified. Only 429 and 529 are retried; a malformed request is never sent again unchanged.
- **Gates** (`advisor/gate.ts`, `advisor/policy.ts`). Each question has one act line, the same at every autonomy; the autonomy only decides whether an unsure answer asks you (Review each step) or falls back to the rules (Automatic, Full auto → PR). For Nouls the line is a probability band: 0.8 or more acts as yes, 0.2 or less as no. Before round 10, `decide()` acted at the level's clarify line, so Balanced acted at 0.6 and Hands-off at 0.5 even for destructive work.
- **Destructive work** is destructive when Jev says so at its act line or the keyword rule matches (`orchestration/risk-rules.ts`): the larger of the two wins, so a keyword match is never cleared by Jev. Destructive work gets the top tier on Auto, a Critic and a worktree copy.
- **Routing** (`orchestration/routing.ts`). Rules only. A pinned model always wins. Auto means the rules choose the tier: the chat's model, the middle tier for a trivial edit (at most 25 words, at most one named file, a wording or formatting verb) and the top tier for destructive work. Session-keep (`session-keep.ts`) keeps the task session's model when the rules would change the tier mid-task, except for a move to the top tier. Jev's tier pick is stored as `autoWouldUse` and shown as "Jev would have used …".
- **Model floor and complex work** (`orchestration/model-floor.ts`, `orchestration/builder-complexity.ts`, policy `fixturn-3-devday-rerun-nohaiku`). The harness never picks the fast tier or a retiring model (a card with `retiresNotBefore` on or before today + 30 days) for any role: a small-tier or retiring pick moves to the lowest model at tier 1 or above in the provider's live list, with a note such as "raised to Sonnet 5: Builders don't run on the fast tier". A model the user pins for a chat still runs, with a retiring note. On Auto a Builder gets the top tier only for complex work (the user asks for it, a migration, security work or several packages, a broad request whose code scan spans 15+ files or 3+ packages, or Jev's intake tier top at 0.8 or more); everything else runs on the middle tier. Rules, notes and evidence: [ROUTING_PLAN.md §4](ROUTING_PLAN.md#4-policy-that-stays-in-code) and [routing-live-2026-09-27.md](../benchmarks/routing-live-2026-09-27.md).
- **One task-scoped Builder** (`members.ts`, `member-routes.ts`). A Do task runs as a child run with `resumeKey = ${taskId}:builder`, not in the chat's own session. The chat only keeps compact results: the Builder's reply plus the check, "Incomplete" and review lines. A follow-up in the same task resumes the task session (M6) and sends only the new message; a new task starts a fresh, small-context Builder with the request and the recent chat, never the whole transcript. Questions are still answered in place by the chat's agent (Scout). The Builder prompt asks for one small increment: do the change, and for a whole feature do the first useful slice, say what is left and stop. Claude Builders get `TodoWrite`, so their own plan is recorded as the task plan.
- **Follow-up or new task.** `continues_task` decides; when Jev is unsure the rule counts a message as a follow-up when it has at most 15 words and refers back ("it", "that", "also" and so on), or arrives within 10 minutes of the task's last reply. A new task closes the previous one and its session.
- **Task sessions close** on Revert, a failure, Stop, the 30-minute idle timeout, or when a new task starts in the chat. Keep does not close them: Keep marks the task done for outcomes, and a follow-up after Keep continues the same session.
- **Worktrees** (`solo-copy.ts`, the kept `projects/worktrees.ts`, `snapshot.ts`, `worktree-deps.ts`, `deps-prep.ts`). One copy per orchestration, reused by retries, fixes and continues. It is used for every Full auto → PR task (it ships from its own branch), for a provider mode that skips the approval gate (Codex Approve for me and Full access, `modeNeedsWorktree`), for a second task running in the same repo at the same time (`repoBusy`), for destructive work, and for risky work at Automatic (`copiesRiskyWork`). It merges back after each Builder turn; if your files changed meanwhile, a card offers Keep your version, Keep Bolt's or Stop (no reconciling Builder). Copies are removed before the turn finishes, and the worker still sweeps orphans. "One Do run per project" (M4) was never enforced by `claimNextJob`; the copy is how two tasks share a repo now.
- **Verification loop.** Project checks after every Builder turn that changed files, then up to 2 resumed fix turns (`CHECK_FIXES`). The plan-completion rule reads the Builder's own ACP plan: open entries get a resumed "continue" (at most `PLAN_CONTINUES`, 2); still-open entries end the reply with "Incomplete: …".
- **Critic.** Runs on the other connected provider (same provider one tier up when alone) with the request, the Builder's plan, the agreed plan, the diff (24 KB cap) and the check results, for destructive work or a migration, a review request (the `review` Noul or the review phrase rule) or, judged on the finished diff (`orchestration/critic-rule.ts`, since September 28, 2026): a large diff (`LARGE_DIFF_LINES` 400, `LARGE_DIFF_FILES` 10), a build from an agreed plan, or a feature over 3 or more source files or 2 or more areas (a workspace package or top-level folder, such as a migration plus the code). A one-liner (one source file, at most 10 changed lines) never gets one. Tests, docs, lockfiles and generated files are not counted as source. In the developer's-day benchmark no Critic ran on the plan build (s04) or the three-layer story (s11). Findings go into the reply.
- **Risky work asks first** (`checkpoint-policy.ts`, since September 28, 2026). Destructive work or a migration (`complexByRule`) shows "Start this risky change?" (checkpoint kind `plan`: Build it, Stop) before the first Builder at Review each step; Automatic builds it in a worktree copy instead and asks at keep time if the diff adds a destructive migration. Full auto goes ahead in its worktree copy and puts "Risky change: …" at the top of the PR body. The developer's-day s10 (a column rename) had no card before the Builder. Since the developer's-day rerun (N3): only destructive schema work asks. A migration asks when the request is destructive (Jev or the rule) or its wording drops, renames, retypes, truncates or rewrites existing data; an additive migration (CREATE TABLE, a nullable ADD COLUMN, CREATE INDEX, like s11's tags table) builds without the card and still gets the Critic. After the Builder the migration diff decides (`destructiveMigrationInPatch`: DROP TABLE/COLUMN, RENAME, ALTER … TYPE, TRUNCATE, DELETE or UPDATE without WHERE, knex drops and renames): when a change nobody flagged adds such a statement, Auto-edit asks with the keep card ("Auto-edit asks because the migration it added can lose or rewrite existing data (…)") and Full auto puts the risky note in the PR body.
- **Builders never publish** (since September 28, 2026). The approval gate refuses `git push`, `git remote add/set-url/remove/rename`, `git send-email`, `gh`, `hub` and `glab` from a Builder at every level (`BUILDER_PUBLISH_REASON`; Codex Do actions all go through the gate), Claude Builder sessions carry matching `permissions.deny` rules, and the Builder prompt says the harness commits, pushes and opens the PR. Ship refuses to push a branch that carries internal commits (authored `snapshots@spark-outpost.local`, such as "Spark Outpost: parallel base …") and only pushes its own one-level `spark/<slug>-<id>` branches, never a worktree branch `spark/<id>/<name>`. In the developer's-day s12 the Builder pushed its worktree branch with the parallel-base commit and told the user it could not open a PR while the harness opened it.
- **Critic → fix rounds** (`advisor/finding-questions.ts`, `orchestration/critic-fix.ts`, `review-loop.ts`, `transitions.ts`, policy `fixturn-1`, since September 28, 2026). In the live routing round the Critic named the exact bug both times a Haiku Builder failed scenario e (`"((5.00)"` accepted; `-$5.00` read as +500), but Balanced (now Review each step) kept the change and no fix ran ([routing-live-2026-09-27.md](../benchmarks/routing-live-2026-09-27.md)). Now, when the verdict is concerns, each finding (up to 10) is classified as a concrete correctness bug or not: a rule on the text (bug words such as wrong, regression, crash; or behaviour words such as returns, accepted, missing, should throw, unless the finding is labelled a nit or is about naming, style, comments or readability) and, when Jev is connected and diffs may be sent, one `finding_N` Noul per finding, "Is this finding a concrete correctness bug in the change?", with the task and diff as state. Jev decides a finding at 0.8 or more either way (`ACT_AT.finding`); below that, or without Jev, the rule decides. Each review is a `finding` row in `run_advice` (`0045_critic_findings.sql`) with the per-finding readings, the review number, the fix round and the action, and shows as a decision in the crew view. With correctness findings at Automatic and Full auto → PR, the same Builder session gets one resumed fix turn (`resumeKey`, the findings as `route.followUp`), the checks run again (with their own fix turns), and the Critic reviews the new diff, told which findings the Builder was asked to fix. The loop stops when a review is clean (looks good, or only style findings), when every correctness finding repeats the previous review (normalized text, line numbers ignored), when checks still fail after the fix and its check-fix turns, when the budget check refuses the next spawn (the budget card asks as usual, and every fix turn counts against the task budget), or after `CRITIC_FIX_ROUNDS` (3) fix rounds. At Review each step nothing runs by itself: the keep card adds "Fix these findings" (then "Fix again") after Keep, which stays the primary option; each answer runs one round. Automatic asks with the keep card (and "Fix again") when concerns remain after the loop, and keeps by itself when the last review is clean; Full auto goes on to ship with them in the reply and the PR body. The keep card reason and the final reply say how it ended: "Fixed after 2 review rounds: the Critic's last review found no correctness problems; checks pass", "Still concerns after 3 rounds: …", "Still concerns after 1 round: the same findings came back after the fix: …", or "Stopped after 1 fix round: the checks failed after the fix …". A user's "Fix again" after the cap runs one more round; the cap limits only rounds the harness starts itself. Since the developer's-day rerun (N2, September 28, 2026): (a) the loop acts only on correctness bugs against the request or the agreed plan. The rule reads hardening, security and robustness advice the request didn't ask for (spreadsheet formula injection in an export, quoting `\r` for "some CSV readers", when to revoke a blob URL; hedges such as "may lose", "some browsers", "safety concern") as a suggestion unless it names a missed requirement, a concrete wrong result, or a real vulnerability the change adds (SQL injection, XSS, an auth bypass, a leaked secret). Jev can't turn a suggestion into a fix turn, its question now says so and gets the agreed plan as state. Suggestions are reported ("Not fixed automatically: …") and don't stop Automatic from keeping. (b) Each fix round has its own budget: a quarter of the run's tool calls (at least 20) and 4 minutes of active time (`FIX_ROUND_*` in `policy.ts`), and the harness starts a round by itself only when that much of the run's budget is left. (c) When a limit (the round's or the run's) cuts a fix round short and the change before it passed the checks, the run doesn't fail and no budget card shows: the files go back to the last state that passed the checks (the pre-fix state, or the fixed state when only the re-review was cut), and the flow ends on the keep card at Automatic and Review each step ("Stopped fix round 1: … Still open: …"; Full auto ships). Stop on a budget card that refused a fix turn now ends on the keep card as well.
- **Failures and the loop guard.** A failed Builder is retried one tier up by rule, at most twice; then the retry card offers Retry or Stop and report, and its auto-continue picks Stop and report (it used to finish). The loop guard (`loop-guard.ts`) stops a Builder after 5 identical non-edit tool calls in a row: at Review each step a card offers Continue (resume with a note to try another way) or Stop and report; at Automatic and Full auto → PR the turn stops with a report.
- **Observation mode, phase 2** (`advisor/policy-gate.ts`, `advisor/verify-questions.ts`, `orchestration/observe.ts`). Hard rules in `approvals/decide.ts` still decide first and are unchanged. For every proposed edit with a diff, the approval gate calls an observer after deciding and without waiting for it; one batched call asks four bad-is-true Nouls (`beyond_request`, `destroys_work`, `weakens_tests`, `unsupported_file`), takes the maximum, and records what the policy would do (block at 0.85 or more, review at 0.5 or more, otherwise allow; a missing or invalid answer is review) next to what the rules did and the approval id, so your later answer joins. The edit gate's rows (`policy`) never act. The verifier acts since the verified cascade (below). The workspace setting "Check changes with Jev" (on by default, `profiles.jev_diffs`) turns them off; then nothing is sent and a row records "skipped: diffs off".
- **Verified cascade** (`advisor/verify-questions.ts`, `orchestration/verify.ts`, `transitions.ts`; measured in `docs/benchmarks/verifier-2026-09-27.md`: unsupported precision 0.91, recall 0.83 on 24 labelled diffs). When the Builder and its checks and fix turns finish green with files changed, one Jev call gets the task, the Builder's plan, the check lines and the full uncommitted diff (`changesForReview`, 24,000 characters), and answers a Choice `verdict` (supported, unsupported, declined) plus one `unmet_N` Noul per requirement line. A verdict counts at confidence 0.8 or more. Accepted unsupported reruns the Builder once, one tier up (`escalate`), in the same task session and worktree, with the unmet requirement lines as the follow-up, then runs its checks again; accepted declined raises a "Jev could not verify the change" card (Finish as it is, Retry one tier up, Stop; auto-continue picks Finish); supported or below 0.8 goes on as before (Critic, keep card). At most two verdicts per turn and only the first acts. Every verdict is a `verify` row in `run_advice` with the answer, the action (`escalate`, `ask`, `finish`) and the escalation target. Without Jev, or with diffs off, the flow is checks and fix turns only. The retry one tier up for a failed Builder is unchanged: it handles agent failures, which the verdict never sees.
- **Plan capture** (`plans/`, `workflow/plan-recorder.ts`, `orchestration/plan-agreement.ts`, `0044_plan_documents.sql`). Plans the user agrees to are kept per conversation as versioned `plan_documents` (proposed, approved, rejected, superseded; source `claude_plan_mode`, `codex`, `chat` or `user`; approval time, who, which option and run, and the git HEAD at approval). They come from Claude's plan mode, from a `<proposed_plan>` block in an agent reply (stored as proposed), from the chat (below), or from "Save as agreed plan" under a reply that looks like a plan. Writes happen in code; a failed save shows as "Error: Could not save the plan: …" in the work log. The latest approved plan goes into every Builder prompt and every new session in the conversation as a short `## Agreed plan` block (goal, up to 12 open items, up to 6 key decisions, 2,000 characters), and the Critic gets it with a request to say whether the change follows it. When files the plan names changed since its approval commit, the block and the Plan tab say it may be out of date. There is no approval gate: nothing waits for a plan unless the agent asks.
- **Plans agreed in chat.** When the turn has a previous assistant reply, intake adds the Noul `plan_agreed` ("Is this message approving a plan or set of steps proposed in the previous assistant reply?") with the end of that reply (4,000 characters) as `previous_reply`. At 0.85 or more the reply is saved as an approved plan (or a proposed Codex plan from that reply is approved); from 0.6 a "Save the plan above as the agreed plan?" card offers it; below, nothing. Every such turn writes a `plan_agreed` row in `run_advice` with Jev's value, the action and a keyword baseline (`yes`, `go ahead`, `do that`, `sounds good`, `let's do it`, at most 20 words) for comparison. Without Jev only the button exists.
- **Audit.** Every Jev record carries `policy_version` (now `fixturn-3-devday-rerun-nohaiku`; earlier `cascade-1`, `lean-1`, from `advisor/policy.ts`, which holds every threshold) and the Jev model version that answered.
- **Analytics.** The Harness tab keeps the rule-vs-Jev comparison, adds cost per verified completion by routing agreement (total turn cost including Jev over turns whose outcome is good), and an "Observation mode: would have asked or blocked" card with the edit gate's and verifier's would-be actions against what happened. `pnpm jev:thresholds` prints precision and recall per threshold from the observation rows and the outcome signals. Every threshold is provisional until tuned on that data.
- **Kept unchanged:** approvals and the autonomy levels, the Codex Do patch and rules, session resume (M6), outcomes and thumbs, model cards (prices, tiers and the tier question's text), analytics, the digest, the companion, slash commands, the Home screen, the audit log, Lean build (default lean, now a rule only), Keep and Revert, run snapshots and the changes view.

### Ship: branch, commit, push, draft PR (September 28, 2026)

After Keep, the keep card and the Changes tab offer **Ship** (`ship/`, `api/ship-routes.ts`, `web/src/ship/`, `0048_ship.sql`). It turns a finished task into a branch, a commit, a push and a draft pull request, one step further each time the user asks.

- **Git is the user's own.** Every local step runs the system `git` with the user's identity, hooks, signing, SSH keys and credential helper (`GIT_TERMINAL_PROMPT=0`, so nothing prompts). Commit and push need no GitHub connection. Without git the preview shows the install hint (`GIT_INSTALL_HINT`).
- **What is committed.** Only the task's own files: the union of files its non-reverted runs changed (`taskChanges`, both sides of a rename), filtered to paths that still differ from `HEAD`. Secrets files (`isSecretPath`, such as `.env`) are left out and listed. Unrelated edits and anything the user staged stay as they were: Ship runs `git add` on the task's paths and `git commit --only -- <paths>`. Attribution is per file, so a task file the user also edited is committed whole.
- **Branch.** `${BRANCH_PREFIX}/<task-slug>-<task-id-8>` (`spark/…`, `spark-dev/…` in the dev channel), created with `git switch -c` from the current `HEAD`, so the user ends up on the branch with their other uncommitted changes carried along. The base for the PR is the current branch when the remote has it, otherwise the remote's default branch (then the repository's `default_branch` from the API). A second Ship on the same task commits on top of the same branch; if the user has switched away and the task has new changes, Ship asks them to switch back.
- **Push.** `git push --set-upstream <remote> refs/heads/<b>:refs/heads/<b>`: never forced (a moved remote branch fails with git's message), never the base or default branch (`safeToPush` only accepts Ship's own prefixed branch), never a merge.
- **Draft PR.** Needs GitHub API access, in this order: the user's `gh` login when `gh auth status --hostname <host>` succeeds (calls go through `gh api`; Spark never runs `gh auth token`), then a pasted fine-grained token, then a GitHub App later. All three sit behind `GitHubConnection` (`whoami`, `defaultBranch`, `findPullRequest`, `createPullRequest`, `updatePullRequest`), built by `restConnection` over a transport, so an App transport can be added without changes elsewhere. The host comes from the remote URL, so GitHub Enterprise works through `https://<host>/api/v3` or a `gh` login for that host. The PR body has the summary (the task's last reply), changed files, check lines, Critic findings, cost, the agreed plan's outline, and the footer "🤖 Generated with Spark Outpost". An open PR for the branch is updated instead of opening another.
- **Records.** The PR goes into `task_links` with source `ship`; `task_ships` keeps the branch, base, remote, last commit, push time and PR per task. Every Ship, successful or not, writes a hash-chained `ship` entry (redacted) to the audit log of the task's latest run.
- **Tokens.** A pasted token is checked with `GET /user` (login, scopes for classic tokens, the expiry header for fine-grained ones) and with repository access for linked projects on that host, then stored only in the keychain under the channel's `KEYCHAIN_SERVICE` (account `github:token`). The database keeps the login, host, scopes, expiry and repository access, never the token. Tokens never go into prompts, agent environments or logs; `redact.ts` also hides `Authorization: token …` headers and passwords in push URLs.
- **UI.** The Ship button reads "Open draft PR", "Push branch" or "Commit" depending on what is possible, and opens a confirm panel with the branch, the base, the files and an editable title. After shipping the card shows the PR link (the Links tab has it too) and the button becomes "Update draft PR". Settings → Connectors → GitHub shows which method is active (gh detected as a user, a token with its scopes, expiry and repositories, and Remove), and the GitHub App as "Coming later".
- **Not built.** The GitHub App (device flow) needs the final app name and a registered app; neither exists yet. Full auto → PR is wired (next section). PR status, CI results and merging are not read.
- **Tests.** Unit: branch naming, remote parsing, file selection, PR and commit messages, status parsing, token headers, redaction. DB (`ship.db.test.ts`): a temp repository whose `origin` points at `github.com/acme/widgets` for parsing and at a local bare repository for pushing (`remote.origin.pushurl`), a fake GitHub API server (`test/fake-github.ts`) and a fake `gh` on the path (`tests/browser/bin/gh`), covering the gh path, the token path, push-only, commit-only, no force-push, and the blocked cases. Browser (`ship.spec.ts`): Ship from the keep card, push-only without a connection, and the Settings card.

### Tickets: Linear and Jira connectors (September 28, 2026, backend only)

The backend for Tickets (`tickets/`, `api/ticket-routes.ts`, `0054_tickets.sql`); the Tickets view keeps its "coming soon" placeholder until the chosen design is built: the inbox layout with smart views, search across all tickets with Assign to me, attention rules and a Home brief (`docs/design/tickets/TICKETS_SCREEN_PLAN.md`, decided September 28, 2026).

- **Sources.** `TicketSource` (`whoami`, `listAssigned`, `getTicket`, `transition`, `comment`, `linkPullRequest`) with Linear (GraphQL, personal API key) and Jira Cloud (REST v3, site URL + email + API token, `search/jql`, ADF read and written as text). Jira Server and Data Center with a personal access token come later.
- **Status.** Four buckets: To do, In progress, In review, Done. Linear state types and Jira status categories map by default (a started state named like "review" is In review); `ticket_connections.status_map` maps a status name per Linear team or Jira project. A move never goes backwards (except to Done); with no matching state it is skipped with a message that points at Settings.
- **Connections.** `PUT /api/tickets/connections/:source` validates with `whoami` before saving; the key goes only to the keychain under `KEYCHAIN_SERVICE` (account `ticket:<source>:token`); the database keeps the account, site, email and settings. `PATCH` changes `moveOnShip` and the status map; `DELETE` removes the row and the keychain entry.

## Principles

A simple harness lets people see, control, and trust what the agent does, without learning how the harness is built.

- **See it.** Every tool call is a step with a record of what happened: the diff, the command, its output, and its exit code.
- **Approve it.** Risky actions pause the run on a card. The backend enforces the decision, not the model.
- **Stop it.** Stop always works, even while an approval is waiting.
- **Survive restarts.** Postgres is the source of truth. After a crash the run shows `outcome_unknown`, and nothing is replayed automatically.
- **Trust the result.** The "what changed" card comes from the harness's own records and `git`, not from what the agent says it did.
- **Keep the output.** Plans, changes, checks, and reviews are durable run artifacts that can be opened, compared, and exported after the run, even after a restart.
- **Choose per chat.** Provider, model, effort, and mode live in `conversations.overrides`. Advice can suggest; only the user and the fixed rules decide.

**Why not always planner, executor, then reviewer.** Running all three on every run means three cold starts (8–10 s each for Claude), about three times the tokens, and a stuck run whenever a review fails, even for "what does this function do?". Both agents already plan natively and stream ACP `plan` updates, so the harness records the agent's own plan as an artifact instead of running a planner. It picks a **mode**, not a pipeline.

## Run lifecycle

Run statuses: `queued → running ⇄ awaiting_approval → succeeded | failed | cancelled | outcome_unknown`.

- **Approvals** (M2). The permission handler calls a pure `decide(mode, request, runRules, allowlist)` that returns allow, reject, or ask. Ask inserts a pending `approvals` row, emits `approval_requested`, and waits on `NOTIFY approvals` with a 1 s poll as backup. The ACP request stays open and the lease keeps renewing. `POST /api/approvals/:id/decision {optionId}` only succeeds while the row is `pending`; a changed `payload_hash` needs a new approval. Stop answers `cancelled`. After 30 minutes the harness answers reject-once, marks it `expired`, and fails the run with "Approval timed out".
- **Recovery.** A crashed run becomes `outcome_unknown`, and its pending approvals expire. If it was waiting, the message says the action never ran. The plan and every other artifact written so far stay readable. Nothing is replayed.
- **Budgets** (M4). A pure `budgets.ts`: 15 minutes of active time (approval waits don't count), 60 tool calls, and an optional cost cap from Settings (Decision 4). A spent budget sends `session/cancel` and ends with `RUN_ERROR` `budget_exceeded`, naming the limit.
- **Concurrency** (M4). 2 jobs at a time by default (`WORKER_CONCURRENCY`). "One Do run per project" was planned here but never enforced at claim time; since round 10 a second Do task on the same repo builds in a worktree copy instead. Ask and Chat runs run in parallel.

## Run artifacts

One model for everything a run leaves behind that a person wants to open again: the plan, what changed, check results, the review, and advice.

### Storage

`0010_run_artifacts.sql`:

```sql
CREATE TABLE run_artifacts (
  run_id uuid NOT NULL REFERENCES runs (id) ON DELETE CASCADE,
  kind text NOT NULL CHECK (kind IN ('plan', 'changes', 'check', 'review', 'advice')),
  version integer NOT NULL CHECK (version > 0),
  body jsonb NOT NULL,
  source_run_id uuid REFERENCES runs (id) ON DELETE SET NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (run_id, kind, version)
);
ALTER TABLE runs ADD COLUMN mode text;
```

- **Append-only versions.** Each write adds the next version for `(run_id, kind)`. The latest version is the current artifact; earlier ones are its history.
- **Why a table and not only run events.** Run events are fenced by the worker's lease, so nothing can be appended once the run ends. A review, a check the user runs later, or advice that arrives late must still attach to the run. The table also makes "latest plan for each run in this chat" a single query.
- **Live updates.** While the worker holds the lease, an artifact is written in the same transaction as an AG-UI `ACTIVITY_SNAPSHOT` event (`activityType` is the kind, `messageId` is `artifact:<kind>`, `content` is `{ version, body }`, `replace: true`). This goes through `appendRunEvent` with a new `artifact` option, like `assistantMessage` today. Writes after the run are plain inserts with `pg_notify('run_artifacts', runId)`; the web refetches the run on that notice once F-10's status stream exists, and on focus until then.
- **Bodies** are validated by zod schemas in `packages/contracts/src/artifacts.ts`, both on write and on read. Each body is capped at 256 KB; longer diffs and outputs are cut with a `truncated` flag.

| Kind      | Written by and when                                      | Body                                                                                                                        |
| --------- | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `plan`    | Worker, on each ACP `plan` update that differs (S1)      | `entries: [{ content, priority, status }]`                                                                                  |
| `advice`  | Worker, before the prompt and after a Do run (S2, M5)    | `purpose` (route or review), `rules` and `jev` advice, `jevError`, `applied`, `latencyMs`, `usage { inputTokens, costUsd }` |
| `changes` | Worker, when a Do run ends; recovery, after a crash (M3) | `base` (git ref or recorded writes), `files [{ path, change, additions, deletions }]`, `patch`, `agentClaim`                |
| `check`   | Worker or the check endpoint (M4)                        | `command`, `exitCode`, `durationMs`, `outputTail` (8 KB), `approvalId`                                                      |
| `review`  | The review run, attached to the reviewed run (M5)        | `reviewer { provider, model, effort }`, `changesVersion`, `verdict` (looks good, concerns, unclear), `text`                 |

### API

- `GET /api/conversations/:id` adds a small `artifacts` summary per run, for example `plan: { version, done, total }`, so the thread renders without extra requests.
- `GET /api/runs/:id/artifacts` returns the latest version of each kind.
- `GET /api/runs/:id/artifacts/:kind` returns every version, oldest first, for the history view.
- `GET /api/runs/:id/artifacts/:kind.md` returns Markdown with `Content-Disposition: attachment`. The Markdown for each kind comes from one pure `artifactMarkdown(kind, versions)` in contracts, shared by the server and "Copy as Markdown".

### Plans in detail

- **Capture.** `session-updates.ts` stops turning plan entries into work-log steps. It emits a new provider output `{ kind: 'plan', entries }` with content, priority, and status. The worker drops an update identical to the latest version, then writes a new version. After 200 versions in one run, the latest version is overwritten instead, so a looping agent can't grow the table without bound.
- **Replacement.** ACP plan updates replace the whole plan, and entries have no IDs. The history compares versions by entry text in a pure `planChanges(previous, next)`: added, removed, and status changed.
- **In the thread.** A Plan card sits at the top of the turn, above the work log: a checklist with ○ pending, a spinner for in progress, ✓ done, and a small "high" tag (low priority is dimmed). The header reads "Plan · 3 of 5 done". While the run works the card updates live; afterwards it is collapsed to its header. If the run was cancelled or crashed, unfinished entries show as "not finished".
- **The Plan panel.** "Plan" in the turn footer opens a side panel that works for any run, live or finished. It shows the checklist, a "History" toggle with a timeline ("10:02 added Run tests · 10:04 Fix divider done · 10:05 removed Update docs"), and "Copy as Markdown" and "Download .md". The same panel shows Changes, Checks, and Review as tabs when they exist.
- **Links.** The panel state is in the URL: `/c/:conversationId?run=:runId&panel=plan`. It's a local link to reopen or bookmark, not a public share.
- **Claude's plan mode** (since plan capture, September 28, 2026; see [Plan capture](#plan-capture-september-28-2026)). Claude Builders get `EnterPlanMode` and `ExitPlanMode`; entering plan mode is allowed at every autonomy. The exit request (`kind: switch_mode`, the plan in `rawInput.plan`) is an approval (M2) titled "Approve the plan?" with the plan rendered as Markdown, and it is also stored as a `proposed` plan document, separate from the ACP `plan` checklist. The card shows every option the agent sent, including the ones that switch to Auto or Bypass permissions (see [Provider permission modes](#provider-permission-modes-september-28-2026)). Any `exit-plan-*` choice the user allows marks the document `approved`, clear-context ones included even though claude-agent-acp answers them with a deny; a rejection marks it `rejected` and the agent keeps planning.

### When it's called

1. **Before a run (phases 1 and 3).** In `execute-run.ts`, after the job is claimed and before the provider starts, when Jev is connected.
   - Phase 1 doesn't wait. The call runs next to the provider's 4–10 s cold start. If advice arrives while the run works, it is written with an `ACTIVITY_SNAPSHOT`. If it arrives after the run ends, it is inserted without an event. After 10 s it is recorded as timed out.
   - Phase 3 waits at most 2.5 s, then uses the chat's settings and records `applied: 'rules'` with the reason.
2. **After a Do run (phase 2).** After the `changes` artifact is written and before `RUN_FINISHED`, with the change counts and whether a check ran. It waits at most 3 s. On timeout or error it uses `reviewSuggested` and the other connected provider (Decision 3). Jev's review answer is used only when its probability is at least 0.6 or at most 0.4; in between, the rules decide.
3. **During a run only as the watchdog** (round 9): every 10 tool calls or 2 minutes of silence per active member, to flag a stuck or looping agent. **Never** for approvals, for Chat runs in phase 2, or when only one provider is connected and there is nothing to route (phase 1 still records effort advice).

### Data sent, minimised

- **Sent:** the task text (the new message only, capped at 8,000 characters), the mode, whether a folder is linked, the connected providers with their model and effort IDs, and for review only the counts: files changed, files deleted, and whether a check ran.
- **Attached text** on the new message is sent (capped at 8,000 characters, without names) only for the injection question, since S2.
- **Since then** (harness round 3 onwards, confirmed by the user on September 27, 2026): plan step text and file paths in the routing, parallel, lane, transition and step-check calls, the end of each agent's reply, and in round 9 the titles of a running member's recent tool calls. [JEV.md](JEV.md#data-sent) lists exactly what each call sends.
- **Never sent:** history, image attachments, file contents, diffs, tool and command output, project names, and credentials. Free text is passed through the audit log's secret redaction first.
- Unit tests pin the exact `state` keys, so any new field is a visible change.

### Cost, storage, and display

- **Cost.** `askSystemOne` already receives `usage.input_tokens`; the `Advice` type gains `usage`. Cost is estimated at $0.042 per million input tokens from the catalog and stored as `usage.costUsd`. `GET /api/usage/summary` and the chat's `usageTotals` gain an `advisors` line (calls, tokens, estimated cost), so Settings shows Jev next to the providers.
- **Storage.** Every call writes an `advice` artifact: both the rules' and Jev's answers, the error if any, which one was applied, and the latency. This replaces the `runs.advice` column proposed in JEV.md.
- **Display.** One muted line under the turn header: "Jev suggested Codex · high effort · review by Claude". When it differs from what ran: "Jev suggested Codex · high effort (ran Claude · medium)". Hover or focus shows the reason, confidence, latency, and cost. On failure: "Jev unavailable · used the fixed rules". With Jev disconnected, nothing is shown.

### Jev can never grant permissions

- `Advice` has no mode, permission, or approval field, and `decide()` takes no advice argument.
- A routed run keeps the mode the user picked. If Jev routes to another provider, the run uses the same mode class (Ask or Do), never a looser one, even if that provider's picker is looser.
- Advice cannot start a Do run, skip an approval, extend a budget, or mark work verified. Phase 2 offers a review; it doesn't start one (see Open questions).
- Tests assert that every possible Jev answer leaves `runs.mode`, the approval decisions, and the budgets unchanged.

## Project folders and safety

- **Linking** (M1, `0009_projects.sql`, `0010_conversation_projects.sql`): `projects (id, workspace_id, name, root_path)` with symlinks resolved, and an ordered `conversation_projects` list per chat whose first entry is the primary repo. The server refuses `/`, `$HOME`, and anything that isn't an existing directory.
- **File access** goes through `fs-handlers.ts` and the pure `projects/path-policy.ts`: absolute paths only, inside the root after symlinks are resolved, reads capped at 1 MB, writes (M2) create missing folders and record hashes before and after plus a diff.
- **Secret files are refused** for reads and writes, each shown as a step: the list in `projects/secret-files.ts` (`.env*` except `.env.example`, SSH key names, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `.npmrc`, `.netrc`, `.pgpass`, `.pypirc`, `.git-credentials`, credential files), writes under `.git/`, and `.sparkignore` entries.
- **Approval buttons.** "Allow", "Allow for this run" and "Always allow in this project" all answer the agent with `allow_once`; the harness keeps the run rule and the allowlist itself, so the agent never switches to a looser mode and every later action still gets a receipt. "Deny" answers `reject_once`. `reject_always` isn't shown.
- **Commands.** Claude's shell tool goes through `request_permission`, and the card says the command isn't sandboxed. Codex Do runs in our patched `ask-every-action` mode, where every command and patch reaches `request_permission`. Its commands run in Codex's sandbox without network unless Codex escalates, and the card says so ([CODEX_DO.md](CODEX_DO.md)). A command on the project's allowlist runs without asking at the Balanced and Hands-off levels (Decision 2). So does a safe read-only command inside the project. Package installs always ask unless they only restore the lockfile.
- **Sandbox.** No `sandbox-exec` (Decision 5). Tools that reach the disk without our handlers are listed as known gaps.
- **Worktrees** (M7): an opt-in git worktree per task under `.spark/worktrees/<runId>`, merged or discarded by the user. Required before "Full access".

#### M6 status (September 26, 2026)

Resumable sessions landed. The `/` menu, @-mentions, `session/delete` and compaction are still open.

- **What the adapters support.** claude-agent-acp 0.81.2 and codex-acp 1.13.1 (with our read-only patch) both advertise `loadSession`, `sessionCapabilities.resume` and `close`, and both resume a session in a **new agent process**: Claude reads the transcript Claude Code keeps under `~/.claude/projects` (`session/resume` recreates the SDK query with `resume: <id>`), and Codex calls `thread/resume` on its stored thread. So agent processes stay per run and there is no warm process pool; nothing extra stays in memory between turns. Claude's `closeSession` only knows sessions in its own process.
- **Storage.** `0026_provider_sessions.sql`: `provider_sessions (conversation_id, provider, agent_key, session_id, cwd, workdir, additional_dirs, settings_hash, last_message_id, last_reply_hash, reported_cost_usd, created_at, last_used_at, closed_at, close_reason)`, at most one open row per conversation and agent key. A chat turn's key is `chat:<mode>`; a child's is `key:<resumeKey>`.
- **When a turn resumes** (`decideResume` in `workflow/session-decision.ts`, pure): the latest row for the key is open, used within the idle time, its settings hash matches (provider, model, effort, run mode, planning tools, linked repos in order), its last turn finished, and, for chat turns, the message just before the new one is the reply it wrote with the same text (so a queued message or text appended by the orchestration, such as a Critic's verdict, forces a fresh start). The provider then also needs `resume` (preferred) or `loadSession` advertised and the same `cwd` and extra directories; otherwise, or if the resume call fails, it opens a new session with the history as before. The work log gets a quiet step: "Continued session" or "Fresh session (settings changed)" (also "chat changed since", "last turn did not finish", "idle", "started fresh", "chat archived", "repos changed", "couldn't resume"). An agent that can't resume at all gets no note.
- **What a resumed turn sends.** Only the new message and its attachments (plus the title request on untitled chats): no project note and no history. Chats without a project get a stable folder per conversation and key (`$TMPDIR/spark-outpost-sessions/<hash>`) instead of a new temp folder, so `cwd` matches on the next turn.
- **`session/load`.** Used only when `resume` isn't advertised. The SDK's update routing is attached after the load response, so replayed `user_message_chunk`, `agent_message_chunk` and tool updates never reach the mapper, and the audit tap drops `session/update` notifications while the load is pending, so they aren't stored or counted as tool calls.
- **Cost.** Claude's `usage_update` cost is cumulative over the session, so a resumed run records the reported cost minus the cost stored at the end of the previous turn (`reported_cost_usd`). Token counts on the prompt response are per turn for both agents.
- **Lifecycle.** At the end of each tracked turn the provider sends `session/close` (when advertised, 3 s cap) before stopping the process, so the adapter shuts down cleanly. A stored session is closed (a database state) when: the chat's provider, model, effort, permission, routing or repos change (`PATCH /api/conversations/:id/settings`, only when a value really changed); the chat is archived; the user picks **Start fresh** in the chat header's ⋯ menu (`POST /api/conversations/:id/fresh-session`); a turn fails or is stopped; it has been idle for `SESSION_IDLE_MINUTES` (default 30); or more than `SESSION_OPEN_LIMIT` (default 8) are open, least recently used first. The worker sweeps idle, archived and excess sessions on start and with every recovery pass, and removes a chat's session folder once no open session uses it and it has been idle; deleting a chat removes its folders.
- **Orchestration children: the `resumeKey` contract.** A child run resumes only when the orchestrator stores `route.resumeKey` on it (and optionally `route.followUp`). Use a key scoped to the task and the member, for example `${taskId}:builder:${name}`, and reuse it for that Builder's retries and fix follow-ups. The same rules apply (same provider, model, effort, mode and repos, same `cwd`, last turn finished), except that chat messages aren't checked. So a retry one tier up, or a Builder moved into a worktree copy, starts fresh by design. When the session continues, the agent receives `followUp` instead of the full `prompt` (it already has the plan, notes and earlier steps), so write `followUp` as the short instruction, such as the review findings to fix; without it the full prompt is sent again. Never give the same key to two runs at once. Children without a key behave exactly as before.
- **Measured** (`claude` Haiku 4.5, `codex` 6 Luna · low, turn 2 of a two-message chat without a project, time to first reply text including process start):

  | Agent  | Run   | Turn 2 fresh (history resent)                 | Turn 2 resumed                                      |
  | ------ | ----- | --------------------------------------------- | --------------------------------------------------- |
  | Claude | cold  | 7.9 s, 6,715 tokens written to cache, $0.0155 | 4.8 s, 6,669 read from cache + 187 written, $0.0013 |
  | Claude | warm  | 3.4 s, 6,715 read from cache, $0.0026         | 2.4 s, 6,669 read + 440 written, $0.0020            |
  | Codex  | first | 4.5 s, 11,227 uncached input + 4,864 cached   | 4.5 s, 970 uncached + 15,104 cached                 |
  | Codex  | again | 3.7 s, 11,227 uncached + 4,864 cached         | 3.2 s, 2,665 uncached + 15,104 cached               |

  In a two-message chat the history is small, so the win is mostly the cache: Claude reuses its cached transcript, and Codex's uncached input drops by 76–91%. The saving grows with the history that a fresh turn resends (up to the 36 KB budget), and a resumed agent also keeps its own tool results, which the text history never carried.

Provider with the fake agent: `session/resume` sends only the new message and closes at the end, `session/load` replay is hidden from outputs and the audit, no capability, a missing session and a moved folder start fresh, the harness's reason is noted, and `followUp` replaces the prompt. #### M7 status (September 26, 2026)

Worktrees landed first for parallel Builders. "Full access" inside a worktree and the `terminal` capability are still open.

- **When steps run in parallel.** The Architect is told to end its reply with a line such as `Parallel: 2, 3` naming consecutive steps that touch different files and need nothing from each other (groups separated by `;`), and to start read-only steps with `Research:`. A plan entry ending in a tag such as `[parallel A]` works too. `parallel.ts` keeps only consecutive groups, maps them through the batching of long plans, then splits a group wherever two steps name the same file, so the file list is a safety check rather than the trigger. The check is conservative: a step that names a file it only imports from counts as touching it. Plans without hints run exactly as before. Jev is not asked per step pair.
- **Read-only parallelism.** A `Research:` step runs as a Scout (Ask mode, in the main copy). Scouts in one group run together, a group may mix Scouts and Builders, and each Scout's reply is passed to later Builders as "Notes from Scouts". Since round 4 the Critic reviews each Builder's diff while the next Builder works (see round 4).
- **Limits.** At most 3 members of one orchestration run at once (`ORCHESTRATION_PARALLEL_LIMIT`, `OrchestratorDeps.parallelLimit`) and at most `PARALLEL_AGENT_LIMIT` (default 6) across the worker. The worker's own `WORKER_CONCURRENCY` still counts orchestrations only.
- **Worktrees.** A group with two or more Builders in a git project first commits the main working tree (uncommitted and untracked files included, through a temporary index) as the group base. Each Builder gets `git worktree add -B spark/<task>/<name> <project>/.spark/worktrees/<runId> <base>`, and the worktree is its `cwd` and only project root. `.spark/` is added to `.git/info/exclude` once; `.gitignore` is never touched. `run_worktrees` records the path, branch, base and result commits, and when each copy was merged and removed. The row is written before `git worktree add`, so every copy on disk has a row.
- **Approvals.** M2's gate runs unchanged inside each copy, so paths are relative to the worktree, and titles end with "· Bolt's copy". A Builder in a copy cannot write to the main copy: it is outside its roots.
- **Merging.** When the group finishes, each successful Builder's copy is committed onto its branch (its result commit is also kept under `refs/spark-outpost/builders/<runId>`). Copies merge back in plan order: the main working tree is committed on top of the base, `git merge-tree --write-tree` merges it with the branch, and the difference is applied to the working tree with `git apply` (never the index, never a forced checkout). Each merged step is marked completed in the plan; the group's steps were marked in progress together.
- **Conflicts.** A conflicting merge asks a `merge_conflict` checkpoint titled like "Rivet and Tack both changed notes.txt.", with both sides' changes per file (base and each side's text, shown as Shiki diffs; unified diff text when a file is over 64 KB or binary). Keep Rivet's (the main copy's version of the conflicting files), Keep Tack's (the copy's version), Ask a Builder to reconcile (non-conflicting parts are applied, the main copy keeps the first version, and a new Builder runs in the main copy with both diffs in its prompt), or Stop.
- **Failures and Stop.** A failed member is not merged; its step is retried one tier up in the main copy through the normal retry rules. A stopped or budget-stopped group merges nothing, and Continue restarts the group's open steps. Worktrees and branches are removed after the merge, on Stop, on failure and at the end of every orchestration; the worker's recovery pass removes copies whose orchestration has ended (a crash leaves it `outcome_unknown`).
- **Outside git.** No worktrees: groups keep their Scouts, one Builder carries the Builder steps in order, and the orchestration records why in `parallelNote`.
- **Snapshot and revert.** The orchestration's snapshot is taken before the first copy, so "Revert to before this run" undoes every merged change. Just before a copy merges, its run's snapshot is re-pointed at the main copy's pre-merge commit, so the Changes view ends the previous run's diff there.
- **Budgets.** Tool calls and cost add up across all children. Active time is wall-clock time minus the union of approval waits, so two Builders waiting at once are counted once.
- **API and UI.** Crew members carry `parallelGroup` and `copy` (the branch); `GET /api/tasks/:id/changes` gives each copy's own branch diff with `name` and `copy`; task list items carry `name` and `group`. The thread shows a group as "Working in parallel: Rivet and Tack" with side-by-side mini headers (live members open, finished ones fold), the Tasks tab lists the group under "In parallel", and the Changes tab labels a copy "Rivet's copy".
- **Tests.** Unit: grouping from tags and files, members with and without worktrees, the parallel flow (group, merge, retry after a failed member, Stop at a conflict, budget continue, sequential fallback), crew ordering, overlapping waits, name pools, and real git copies (uncommitted files, disjoint merge without touching the index, conflict and keeping either side). DB with the fake ACP roles (`#parallel`, `#research`, `#collide`, `#slowstep N`): a 3-step plan where steps 2 and 3 merge cleanly and the plan ends all completed, parallel Scouts, each conflict option, Stop during a group, crash recovery removing orphans, and a non-git folder. #### Harness tuning (September 26, 2026)

The first harness-vs-direct benchmark ([results](../benchmarks/harness-vs-direct-2026-09-26.md)) showed the harness at 1.9× the cost of one direct agent, almost all of it from planning and cold Builders on multi-file work. These rules came out of it; the re-run is in [the tuned results](../benchmarks/harness-vs-direct-2026-09-26-tuned.md).

- **A request that is already a plan skips the Architect.** When the depth would be `plan_execute`, the trusted risk is `multi-file`, the request names between 1 and 6 files (`namedFiles`, which now also sees a path at the end of a sentence), and Jev's intake confidence is at least 0.7, the depth becomes `execute` with one in-place Builder (`refineDepth` in `depth.ts`). The reason is stored as `depthNote` on the intake advice (an optional field of `adviceSummarySchema`) and shown in the intake decision's summary.
- **The Critic stays when Jev asks for review.** If the rules would plan without review but Jev's depth answer is `plan_execute_review` with a depth confidence of at least 0.5, the depth keeps the review. A review only reads, so this needs less confidence than acting on Jev's depth. Destructive risk still always reviews. This is checked before the skip, so a reviewed request keeps its Architect.
- **The Architect's tier follows the plan's size.** On Auto, a short plan gets the middle tier (Sonnet 5) at high effort: the request names 1 to 4 files, or Jev scores complexity moderate or lower (trusted at 0.5 confidence or more). Opus stays for vague requests (no named files), destructive risk, and complex ones. A pinned chat still uses its pinned model, and records what Auto would have used. The route decision's rule reads "short plan" or "top tier".
- **One Builder per run of sequential steps.** After planning, consecutive steps outside a parallel group go to one Builder in one ACP session (`carry` on the spawn, `spans.ts`). Its prompt lists every step, marks each "<- your step", and asks for a "Step N done." line after each one. `stepTicker` in `plan-progress.ts` watches the streamed text and ticks each step completed (and the next one in progress) as its marker arrives, so the plan still moves one step at a time. Anything not ticked is completed when the Builder is judged done. A failed or budget-stopped Builder is retried or resumed with only its unticked steps, one tier up for a retry. The planned route asks Jev once per span, with the span's steps as its work. Outside git every Builder step is carried by one Builder.
- **Builders get the Architect's notes.** The Architect is asked to end with "Notes for Builders:" (signatures, imports, short excerpts with paths). The Builder prompt gains "Notes from the Architect": the files the Architect read (from its `Read` tool calls) and that notes section (or its whole reply when there is none), capped at 4,000 characters (`ARCHITECT_NOTES_LIMIT`).
- **Parallel only when it pays.** A parallel group keeps its own Builders only if every Builder step in it names at least 2 files or the Architect lists it on a "Large: 2, 3" line (a step it expects to take more than about 20 seconds). Otherwise the group's steps are carried by one Builder. Research groups are unaffected.
- **Lower bar for cheaper picks.** The routing gate acts at 0.8 instead of 0.9 when Jev's pick is the same tier or cheaper than the fallback (same provider, model tier and effort no higher) and the risk is `edits`. Upgrades and `multi-file` or `destructive` risk keep 0.9; read-only keeps 0.75. `autoWouldUse` now records Jev's pick for every Builder and Critic route, on Auto as well as pinned, whether or not the gate acted, so a benchmark can measure the threshold.
- **Tests.** Unit: the gate thresholds, `refineDepth`, the Architect tier and complexity trust, the cheaper-pick gate and `autoWouldUse`, carried spans in the flow (retry and budget resume with only the open steps, rules after a carried span), the Large line and the worth-splitting filter, step markers, and the Builder prompt with carried steps and the Architect's notes. DB with the fake ACP roles: a request that names its files runs one Builder and records why, a less certain one plans with a Sonnet Architect whose notes reach the Builder, small tagged steps stay in one Builder, and the plan-progress, flow and level scenarios with one carrying Builder. Browser: the crew specs expect one Builder carrying the plan.

#### Harness round 3: Jev scope, Architect and parallelism (September 26, 2026)

Results: [round 3](../benchmarks/harness-vs-direct-2026-09-26-round3.md).

- **Scope question.** The intake batch asks one more choice, "How much of the codebase does `task` touch?", with the options one spot, one module, a few modules and across the codebase (`SCOPE_QUESTION` and `SCOPE_CRITERIA` in `intake-questions.ts`). The answer is stored as `scope` on the intake (an optional field of `jevIntakeSchema`) with its confidence in `confidences.scope`, and the dispatch tooltip shows it. A missing or unoffered answer leaves the scope unknown instead of failing the intake.

- **Stuck or looping detection** (`watchdog.ts`, `watchdog-rules.ts`, `watchdog-questions.ts`). Each member is watched through the same output stream that counts its tool calls. Every 10 tool calls, or after 2 minutes with no output (not while it waits on a permission approval), code flags obvious repeats (an identical tail, the most frequent call, an A-B-A-B back-and-forth) and one batched Jev call asks four bad-is-true Nouls over the member's step titles and last 12 tool-call titles: `repeating`, `off_step`, `waiting` (on a missing tool, permission, install or input) and `finished` (done but not stopping). The worst answer decides at 0.85 (stuck) or 0.3 (fine); in between, or without Jev, the rule decides (5 identical non-edit calls in a row).
- **Actions by level.** Hands-on and Balanced: a `stuck` checkpoint, "Bolt looks stuck: repeating Read src/dates.ts", with Nudge Bolt, Let it continue and Stop; the usual auto-continue picks Let it continue, and the card closes by itself when the member ends. Hands-off and Full auto: a nudge. There is no mid-turn injection in ACP, so the nudge is queued for the member's next turn (continue, fix or check-fix follow-up in the same session) as "## Note from the harness". Never an automatic stop.
- **Limits.** 20 watchdog calls per orchestration (`WATCHDOG_CALL_BUDGET`), the process-wide Jev limiter, one call in flight per member, and a cooldown of two checks after acting. `OrchestratorDeps.watchdog` tunes the settings or turns it off (`false`).
- **Records and display.** Each check is a `run_advice` row with `purpose = 'watchdog'` next to what the rule would have done (migration `0036_watchdog.sql` also adds the `stuck` approval kind). The crew turn and Agent TV show "looks stuck: …" on the member and a line under its work log; a pending watchdog checkpoint is a "Looks stuck" attention state in the sidebar, Home and the companion. Watchdog checkpoint time does not count as waiting for the active-time budget, since the member keeps working.
- **Unchanged.** The per-step "did the Builder finish" check keeps acting.
- **Also decided today.** File paths stay in what Jev is sent, and are no longer redacted anywhere (secrets still are); JEV.md's data-sent list and the in-app Jev details say exactly what goes. The frontier gate is 0.90, the same as the normal upgrade gate ([MODEL_CARDS.md](MODEL_CARDS.md)).
- **Tests.** Unit: heuristics, when to check, verdicts, actions per level, cooldown, question building and parsing, the per-orchestration budget and one-in-flight rule. DB with the fake agent (`orchestration-watchdog.db.test.ts`): a looping Builder triggers the checkpoint at Balanced and a nudge (delivered on its next turn) at Full auto; a healthy one triggers nothing. Web: row state, Agent TV lines and notes.

### Tasks

- A **task** is one piece of work in a chat. It can span several turns: "continue" or "also add a test" joins the open task. It owns the plan, the live task list, the agents that worked on it, links such as a PR, what changed, and the cost.
- **Storage:** `tasks (id, conversation_id, title, status, created_at, closed_at)`, plus `runs.task_id`.
- **Plans are versioned per task.**
  - An updated plan is a new version of the same plan.
  - A replaced plan supersedes the old one, which is kept and marked superseded.
  - Each run records `plan_version`, so "Builder worked from plan v2" stays true after v3 exists.
- **Links:** `task_links (task_id, kind, url, title, source, created_at)`. PR URLs are captured from ACP resource links, from tool output (`gh pr create`), or pasted by the user. PR status through `gh` comes later.
- **Live task list:** built by the harness from what it records, never by asking the agent. It shows plan entries plus the harness's own stages (understood, planned, each step, waiting for you, checks, review, PR). Each item names its agent, model, effort, tokens, and cost.
- **Built in S1b (`0014_tasks.sql`):**
  - **Task rule.** One pure `chooseTask(latest, didWork)` in `apps/server/src/tasks/rules.ts`. A new message joins the chat's open task when it is sent. A run without a task opens one on its first tool call, client action, or non-empty plan. Chit-chat stays taskless, and nothing closes a task yet.
  - **Artifacts are keyed per task**, not per run: `run_artifacts (task_id, kind, version, body, source_run_id, superseded_by, created_at)`, so a plan's versions span the task's runs. Only `plan` is written today. A plan write goes through `appendRunEvent` with the `artifact` option and an `ACTIVITY_SNAPSHOT` (`messageId` `artifact:plan`, `activityType` `plan`, `content { version, body }`), fenced by the lease. Opening a task and capturing a link add `task` and `link` snapshots so the web refetches.
  - **Plans.** `nextPlanWrite` drops identical updates, writes status-only changes (step progress) and every further update from the run that wrote the latest version into that version, and overwrites the latest version after 200; only a plan change from another run (a new Architect, an edited plan, a follow-up turn) adds a version. Inside a crew only the Architect, or a Builder when there is no plan, records its agent plan as the task plan. `planChanges(previous, next)` in contracts marks the previous version `superseded_by` when added plus removed entries are more than half of all entries; status changes alone are an update. `runs.plan_version` is the version a run started from or last wrote.
  - **Links.** `findPullRequests` normalises `github.com/<owner>/<repo>/pull/<n>` from tool text content, `resource_link`s, `rawOutput`, and the final reply text (only when the run has a task). `POST /api/tasks/:id/links` adds a user link; duplicates return the existing row.
  - **Task list.** `taskList(task, runs, events, plan)` and `taskSummary` in `packages/contracts/src/tasks.ts`: understood, made a plan, each plan entry, harness events, one item per run (follow-ups labelled with the request), and each PR. A run in `awaiting_approval` shows as waiting for you. The conversation detail carries `tasks` (list and summary); `GET /api/tasks/:id` adds `runs`, `planVersions` with `usedBy`, and `links`; `GET /api/tasks/:id/artifacts/plan.md` downloads `artifactMarkdown`.
  - **UI.** A task card under the task's latest turn and a work panel toggled from the chat header: the task list by default with waiting items pinned and done items folded, then Plan (version, used by, history, copy and download), Links (chips and Add link), and Cost tabs. It docks on wide screens, overlays below 1100 px, and is a bottom sheet on phones.
  - **Left:** per-approval waiting items and check or review stages once M2 and M4 write them as `events`; closing a task (PR merged, or Jev); a Plan card in the turn; a Changes tab; per-item tokens for plan steps; model and effort from S1a's `used_model` instead of the requested ones.

### Audit

The model is CloudWatch-like: everything an agent does is recorded.

- **Hierarchy:**
  - The chat session is the log group.
  - Each agent run is a log stream, with its role, provider, model, effort, and mode.
- **Raw protocol log:** every ACP message in both directions, with timestamp, method, size, and redacted payload.
- **Also kept:** the full agent stderr, receipts, approvals, artifacts, and Jev decisions.
- **Metrics per agent run:** input, output, cached, and thinking tokens, plus cost, context, duration, and tool calls. Cost is labelled reported or estimated.
- **Integrity and privacy:**
  - Records are append-only, with sequence numbers and a hash chain.

- **Retention:** raw logs are kept for 90 days by default, and summaries are kept forever.
- **Recorded today (S1a, `0013_audit.sql`):**
  - `run_protocol_log`: every JSON-RPC message of an agent run, tapped at the transport in both directions, plus the agent's stderr (up to 1 MB per run), redacted and hash-chained per run
  - on `runs`: the model, effort, and mode the agent actually used, `duration_ms`, `tool_call_count`, and `cost_source`
  - not yet: receipts, approvals, artifacts, Jev decisions, and a role per run
- **Audit view:**
  - a summary by model, role, and provider
  - a timeline waterfall
  - logs you can filter by agent, type, and text
  - JSONL and CSV export

### Harness autonomy

Since September 28, 2026 (provider permission modes, below) the agent's own mode decides what the agent asks, and the harness autonomy decides what the harness does around it. The stored ids stay `balanced`, `hands-off` and `full-auto` in the `level` columns.

| Checkpoint           | Review each step                                                                                    | Automatic (default)                                                                                                | Full auto → PR                                                                                |
| -------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| Clarify the request  | When Jev is unsure; a vague request asks "What should change?"                                      | A vague request asks "What should change?" (Jev `vague` ≥ 0.8 or the vague rule); otherwise the fixed rules decide | Never; a vague request assumes the likeliest reading and says so in the reply and the PR body |
| Risky work           | "Start this risky change?" card before the first Builder (destructive work, destructive migrations) | No card: the Builder works in a worktree copy; an unconfirmed destructive migration in the diff asks at keep time  | No card: worktree copy, "Risky change" at the top of the PR body                              |
| Edits and commands   | Whatever the agent's mode asks (see the posture table below)                                        | Same                                                                                                               | Same                                                                                          |
| Critic findings      | Offered on the keep card ("Fix these findings")                                                     | Fixed in a loop (at most 3 rounds)                                                                                 | Fixed in a loop, then shipped with what's left in the PR body                                 |
| Retry or escalate    | Rule retries (at most 2), then the retry card                                                       | Same; the card auto-continues to Stop and report                                                                   | Same; the card auto-continues to Stop and report                                              |
| Keep, fix, or revert | Always, unless you approved every changed file's edit yourself (never ask twice)                    | Kept by default; asks when checks fail, the Critic still has concerns or a destructive migration nobody confirmed  | Kept by default, then shipped to a draft PR from its own branch; the card shows it            |

- **Read-only commands** (both providers, `approvals/command-kinds.ts`) run without asking in every mode. A read-only command is one simple command, with no pipes, redirects or wrappers:
  - `ls`, `pwd`, `stat`, `tree`, `wc`, `find` without actions
  - `cat`, `head`, `tail` and non-recursive `grep` without globs
  - `sed -n N,Mp`
  - `git status`, `git diff`, `git log`, `git show` and `git branch`, without `rev:path` or `--output`

  Its working directory and every path must be inside the project. Secret file names always ask, and recursive searches (`grep -r`, `rg`) ask because they can reach secret files.

- **Package installs always ask**, in every mode. The exception is an install that only restores the lockfile: `npm ci`, or `--frozen-lockfile`, `--immutable` or `--offline` with no package named.
- **Budgets and Stop** apply at every autonomy.

#### Safety floor under the permissive modes (verified offline, September 28, 2026)

Method as in [REPO_AGENT_CONFIG.md](REPO_AGENT_CONFIG.md#step-1-what-loading-the-project-settings-source-would-do-claude): the real claude-agent-acp 0.81.2 against a fake Anthropic API on 127.0.0.1 that answers with canned tool calls, a trap repo with a `.env` canary and a local bare remote, our session `_meta`, and every permission request answered "reject". Scripts and logs stayed in the session scratchpad.

| Check (Claude)                                               | Manual                                    | Accept edits | Auto       | Bypass permissions  |
| ------------------------------------------------------------ | ----------------------------------------- | ------------ | ---------- | ------------------- |
| Read tool on `.env`                                          | denied                                    | denied       | denied     | denied              |
| Bash `cat .env`, `grep -r SECRET .`                          | denied                                    | denied       | denied     | denied              |
| `git push`, `gh`                                             | denied                                    | denied       | denied     | denied              |
| `git -C . push`, `/usr/bin/git push` without a Bash ask rule | asked                                     | ran unasked  | classifier | **pushed unasked**  |
| Write outside the repo without Edit/Write ask rules          | asked                                     | asked        | classifier | **written unasked** |
| With `ask: ['Bash', 'Edit', 'Write']`                        | everything reaches our gate in every mode |

- The secret-file `Read` deny rules hold in every mode and also block `cat .env` and writes to `.env`. The publish deny rules miss `git -C … push` and absolute paths when Bash doesn't ask; our gate's `publishesCode` catches those and `sh -c "…"` wrappers. Bypass writes outside the repo unasked, and Auto hands decisions to Anthropic's classifier. The blanket ask rules beat every mode.
- **So Claude Do sessions keep `ask: ['Bash', 'Edit', 'Write']` in every mode**, and the gate applies the chosen mode's posture after the floor. Claude's modes therefore never need a worktree, and Bypass permissions on the real checkout only gets a warning. Do sessions set `allowDangerouslySkipPermissions` so the adapter offers Bypass permissions (and its plan-exit options); chats and Ask sessions keep it off. `dontAsk` is not offered by claude-agent-acp 0.81.2 (`set_mode` and `set_config_option` both refuse it).
- **Codex's Approve for me and Full access** don't send requests to our gate (an auto reviewer, or `never`), so secret reads, pushes (Full access has network) and writes outside the repo aren't gated. They run only in a worktree copy (`modeNeedsWorktree`), a live switch to them on the real checkout is refused, and unknown future modes of an ungated provider count the same. The offline check of Codex could not be run (see the report); the earlier live probe in [CODEX_DO.md](CODEX_DO.md) showed `on-request` modes reading `.env` unasked.
- **Builders' environment** (defence in depth, every provider): `GIT_CONFIG_COUNT`/`url.spark-outpost-no-push:///.pushInsteadOf` rewrites every push URL, `GH_CONFIG_DIR` points at an empty folder and hosting tokens are removed (`withoutPublishing` in `agent-env.ts`). Verified offline for Claude's Bash: `git push` failed, `git fetch` and `git commit` worked, `gh` was logged out. A command that resets `GIT_CONFIG_COUNT` undoes it, so it is a speed bump, not a boundary; the gate refuses those commands for Builders.
- **Migration** (`0050_provider_modes.sql`): Ask → Claude Plan / Codex Read-only; Ask before edits → Manual / Ask every time + Review each step; Auto-edit → Accept edits / Approve for me + Automatic; Full auto → Bypass permissions (Claude, gated) / Approve for me (Codex) + Full auto → PR. The new default autonomy is Automatic.

## Decisions (September 25, 2026)

1. **Default mode in a linked folder** follows the user's default permission for that provider (set in onboarding or Settings, and overridable per chat). There is no separate folder default.
2. **Commands with auto-accept.** Each project gets its own allowlist, for example `pnpm test`, stored on the project. A command on the list runs without asking. Any other command asks. The card offers "Always allow in this project", which adds the command to the list.
3. **Reviewer.**
   - Use the other connected provider when there is one.
   - Once Jev is connected, it chooses whether to review and which provider, model, and effort to use.
   - Jev's advice is recorded on the run. The harness still enforces approvals, and Jev's choice can never grant permissions.
4. **Cost.** No default cost cap. Show usage and cost for each run, totals for the chat, and totals per provider, including context use per provider. The per-run cap stays optional in Settings.
5. **OS sandbox.** Follow the ACP guidance.
   - The client's file handlers and permission requests are the boundary the client controls.
   - Each agent's own sandbox covers the rest: Claude's permission modes with its tools limited. Codex runs a patched codex-acp 1.13.1 whose `read-only` mode is a true `readOnly` sandbox (upstream codex-acp#480), so it may read linked repos in Ask. Its sandbox can read the whole disk, a known gap.
   - M1 ships without `sandbox-exec`. Tools that reach the disk without our handlers are listed as known gaps.
6. **Crash during a Do run.**
   - Take a snapshot when the run starts: a git ref of the working tree, or, outside git, copies of the files the harness writes.
   - After a crash, show what changed and offer "Revert to before this run" as well as "Keep changes".
   - Revert only touches files changed during the run, and it needs one confirmation.
