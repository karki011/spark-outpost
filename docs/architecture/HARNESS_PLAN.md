# Harness plan

The harness around every agent turn: how a request is routed, built, checked, reviewed, kept and shipped, and what the user sees and controls. This file describes what runs today and what is still open; the rounds that led here are in git history. Jev itself is described in [JEV.md](JEV.md), the coordinator in [COORDINATOR_PLAN.md](COORDINATOR_PLAN.md), routing rules in [ROUTING_PLAN.md](ROUTING_PLAN.md), and the ACP details in [ACP_AGENTS.md](ACP_AGENTS.md) and [ACP_COVERAGE.md](ACP_COVERAGE.md). The user's Decisions, at the end, are binding.

## Current architecture: the lean harness (round 10, September 27, 2026)

What runs today. Round 10 (September 27, 2026) cut the harness down to one task-scoped Builder with rules-only routing; the coordinator (September 28–30) adds pieces on top for work too big for one Builder. The evidence for round 10 is in `docs/benchmarks/harness-e2e-live-2026-09-26.md`.

- **Intake** (`advisor/intake-questions.ts`, `orchestration/intake.ts`). One batched call per turn. The acting questions are Nouls, each worded as one concrete fact with structured `true`/`false` descriptions: `question` (an answer, a plan or feedback, nothing to change yet), `vague` (every Do turn; a follow-up is judged against the previous reply and request), `review`, `destructive` and `continues_task` (only when the chat has a task to continue, with the previous request and a short task summary as evidence). `intent` stays for the category chips, the clarify readings and the auto-title fallback; its options carry `what` and `not_for` so neighbouring categories do not share probability. `injection` is judged over attached text only and never relaxes anything. `tier` is a Choice over the chat provider's small, mid and top models, recorded and never applied. Removed from intake: complexity, risk score, depth, scope, mechanical, provider, per-provider model and effort, and the speculative build style.
- **Validation.** Before anything branches, every answer is checked: the key is present, its type matches the question, a Choice is one of the offered options, and every probability and Noul is finite and between 0 and 1. A failed intake or routing answer falls back to the rules for that question only. A failed policy-gate answer counts as "review", never "allow"; a failed verifier answer counts as not verified. Only 429 and 529 are retried; a malformed request is never sent again unchanged.
- **Gates** (`advisor/gate.ts`, `advisor/policy.ts`). Each question has one act line, the same at every autonomy; the autonomy only decides whether an unsure answer asks you (Review each step) or falls back to the rules (Automatic, Full auto → PR). For Nouls the line is a probability band: 0.8 or more acts as yes, 0.2 or less as no.
- **Destructive work** is destructive when Jev says so at its act line or the keyword rule matches (`orchestration/risk-rules.ts`): the larger of the two wins, so a keyword match is never cleared by Jev. Destructive work gets the top tier on Auto, a Critic and a worktree copy.
- **Routing** (`orchestration/routing.ts`, `route-score.ts`, `cache-switch.ts`, `task-signals.ts`; since September 30, 2026, policy `route-score-1-cache-aware`). A pinned model always wins, destructive work gets the top tier and the model floor holds. Otherwise a Builder on Auto is picked by a legible score: expected quality (card tier × complexity, raised for ambiguity and context dependence, never above measured Builder failures) and the whole task's cost (card prices incl. cache-read pricing), combined in dollars as token cost + (1 − pass rate) × repair cost, the repair cost growing with stakes and complexity. The signals are Jev's four intake ratings when confident, else rule estimates (trivial, complex, destructive, vague, follow-up); with the rules alone the score picks exactly what the old rules did (the chat's model, the middle tier for a trivial edit, the top tier for complex work). A follow-up in the same task anchors on the resumable session's model: the route never steps below it and steps up only when the stronger model is worth re-reading the session's context at its cache-write price ("kept Sonnet 5: warm session, 48K context"). A hard follow-up (complexity or stakes ≥ 4) in a session holding 100K+ tokens escalates through a handoff instead (`escalation.ts`, `handoff.ts`, policy `route-score-2-escalation-routes`): a stronger Builder in its own session (`${taskId}:escalated`) with a structured brief while the cheaper session stays warm, or, when the follow-up depends on the context (4+), compact then switch the session; complexity 3 raises effort on a warm session whose cache survives it; once escalated a task doesn't step back down; an escalated result with stakes ≥ 4 gets the Critic. The route decision stores the signals, the top three scores and the escalation route with its inputs, and the why line shows them ("hard follow-up at 180K → Opus 5.5 Builder with brief; Sonnet 5 session kept warm"). The thresholds are provisional and pass-rate evidence for the routes is pending. Jev's tier pick is still stored as `autoWouldUse` and shown as "Jev would have used …". Details and calibration: [ROUTING_PLAN.md §12](ROUTING_PLAN.md#12-cache-aware-routing-and-the-route-score-september-30-2026-policy-route-score-1-cache-aware).
- **Model floor and complex work** (`orchestration/model-floor.ts`, `orchestration/builder-complexity.ts`, policy `fixturn-3-devday-rerun-nohaiku`). The harness never picks the fast tier or a retiring model (a card with `retiresNotBefore` on or before today + 30 days) for any role: a small-tier or retiring pick moves to the lowest model at tier 1 or above in the provider's live list, with a note such as "raised to Sonnet 5: Builders don't run on the fast tier". A model the user pins for a chat still runs, with a retiring note. On Auto a Builder gets the top tier only for complex work (the user asks for it, a migration, security work or several packages, a broad request whose code scan spans 15+ files or 3+ packages, or Jev's intake tier top at 0.8 or more); everything else runs on the middle tier. Rules, notes and evidence: [ROUTING_PLAN.md §4](ROUTING_PLAN.md#4-policy-that-stays-in-code) and [routing-live-2026-09-27.md](../benchmarks/routing-live-2026-09-27.md).
- **One task-scoped Builder** (`members.ts`, `member-routes.ts`). A Do task runs as a child run with `resumeKey = ${taskId}:builder`, not in the chat's own session. The chat only keeps compact results: the Builder's reply plus the check, "Incomplete" and review lines. A follow-up in the same task resumes the task session (M6) and sends only the new message; a new task starts a fresh, small-context Builder with the request and the recent chat, never the whole transcript. Questions are still answered in place by the chat's agent (Scout). The Builder prompt asks for one small increment: do the change, and for a whole feature do the first useful slice, say what is left and stop. Claude Builders get `TodoWrite`, so their own plan is recorded as the task plan.
- **Follow-up or new task.** `continues_task` decides; when Jev is unsure the rule counts a message as a follow-up when it has at most 15 words and refers back ("it", "that", "also" and so on), or arrives within 10 minutes of the task's last reply. A new task closes the previous one and its session.
- **Task sessions close** on Revert, a failure, Stop, the 30-minute idle timeout, or when a new task starts in the chat. Keep does not close them: Keep marks the task done for outcomes, and a follow-up after Keep continues the same session.
- **Worktrees** (`solo-copy.ts`, the kept `projects/worktrees.ts`, `snapshot.ts`, `worktree-deps.ts`, `deps-prep.ts`). One copy per orchestration, reused by retries, fixes and continues. It is used for every Full auto → PR task (it ships from its own branch), for a provider mode that skips the approval gate (Codex Approve for me and Full access, `modeNeedsWorktree`), for a second task running in the same repo at the same time (`repoBusy`), for destructive work, and for risky work at Automatic (`copiesRiskyWork`). It merges back after each Builder turn; if your files changed meanwhile, a card offers Keep your version, Keep Bolt's or Stop (no reconciling Builder). Copies are removed before the turn finishes, and the worker still sweeps orphans. "One Do run per project" (M4) was never enforced by `claimNextJob`; the copy is how two tasks share a repo now.
- **Chat worktrees** (since September 29, 2026; `orchestration/chat-place.ts`, `place-decision.ts`, `projects/chat-worktrees.ts`, `chat-worktree-cleanup.ts`, `persistence/chat-worktrees.ts`, table `chat_worktrees` in `0067`). A Do turn in a git project gets the chat's own worktree at `<repo>/.spark/worktrees/<id>` on a new branch named like Ship's (`spark/<title or request slug>-<chat id>`), started from HEAD (the default branch when HEAD is detached). Every later turn of the chat, Ask turns included, runs there (`loadRunInput` swaps the project root), so several chats work on one repo in parallel and never touch your checkout or each other; `repoBusy` ignores them. Dependencies are prepared at creation with the kept `worktree-deps.ts` strategy; repo agent config, trust, `.mcp.json` and project checks read the worktree like any root. Uncommitted changes in your checkout are not in it (the start note says so). Exceptions, decided once per chat (`decidePlace`): a branch you picked in the composer's branch menu or named in the request ("on branch x", "the x branch") is used as is: in place when it is the checked-out branch and the tree is clean, otherwise in a worktree on that branch (a remote-only branch is fetched and tracked; a branch that is checked out with uncommitted changes, or open in another worktree, gets a new chat branch started from it). "Work in my checkout" in the same menu keeps today's in-place flow (and its per-run copies) and is remembered per project (`projects.work_place`); the menu is closed once the chat has a branch. Non-git folders are unchanged. Inside a chat worktree no per-run copy is made (it already isolates the work, so modes that skip the gate may run there). The kept card shows "Kept on spark/… in this chat's worktree" with **Bring changes into <your branch>** (a three-way `merge-tree` from the last brought commit, applied as uncommitted edits to your checkout only on click; refused with the reason when your checkout has uncommitted changes or the same lines changed on both sides) next to Ship (Open draft PR, or Commit on the branch). Ship and Full auto use the chat branch (never switching your checkout; the PR base is the branch the chat started from when the remote has it). Revert restores the worktree. The chat header shows `spark/… · worktree` with an Open folder button, and Agent TV shows the branch. Archiving removes a clean worktree; deleting saves uncommitted work as a commit on the branch first; the owned branch is deleted only when it has nothing new, or is pushed or merged, otherwise it is kept. The worker sweep (once a minute) also removes worktrees whose branch was merged into your checkout's HEAD or `origin/HEAD`; Reset removes them with the same rules.
- **Verification loop.** Project checks after every Builder turn that changed files, then up to 2 resumed fix turns (`CHECK_FIXES`). The plan-completion rule reads the Builder's own ACP plan: open entries get a resumed "continue" (at most `PLAN_CONTINUES`, 2); still-open entries end the reply with "Incomplete: …".
- **Critic.** Runs on the other connected provider (same provider one tier up when alone) with the request, the Builder's plan, the agreed plan, the diff (24 KB cap) and the check results, for destructive work or a migration, a review request (the `review` Noul or the review phrase rule) or, judged on the finished diff (`orchestration/critic-rule.ts`, since September 28, 2026): a large diff (`LARGE_DIFF_LINES` 400, `LARGE_DIFF_FILES` 10), a build from an agreed plan, or a feature over 3 or more source files or 2 or more areas (a workspace package or top-level folder, such as a migration plus the code). A one-liner (one source file, at most 10 changed lines) never gets one. Tests, docs, lockfiles and generated files are not counted as source. Findings go into the reply.
- **Risky work asks first** (`checkpoint-policy.ts`, since September 28, 2026). Destructive work or a migration (`complexByRule`) shows "Start this risky change?" (checkpoint kind `plan`: Build it, Stop) before the first Builder at Review each step; Automatic builds it in a worktree copy instead and asks at keep time if the diff adds a destructive migration. Full auto goes ahead in its worktree copy and puts "Risky change: …" at the top of the PR body. Only destructive schema work asks. A migration asks when the request is destructive (Jev or the rule) or its wording drops, renames, retypes, truncates or rewrites existing data; an additive migration (CREATE TABLE, a nullable ADD COLUMN, CREATE INDEX) builds without the card and still gets the Critic. After the Builder the migration diff decides (`destructiveMigrationInPatch`: DROP TABLE/COLUMN, RENAME, ALTER … TYPE, TRUNCATE, DELETE or UPDATE without WHERE, knex drops and renames): when a change nobody flagged adds such a statement, Automatic asks with the keep card ("… the migration it added can lose or rewrite existing data (…)") and Full auto puts the risky note in the PR body.
- **Builders never publish** (since September 28, 2026). The approval gate refuses `git push`, `git remote add/set-url/remove/rename`, `git send-email`, `gh`, `hub` and `glab` from a Builder at every level (`BUILDER_PUBLISH_REASON`; Codex Do actions all go through the gate), Claude Builder sessions carry matching `permissions.deny` rules, and the Builder prompt says the harness commits, pushes and opens the PR. Ship refuses to push a branch that carries internal commits (authored `snapshots@spark-outpost.local`, such as "Spark Outpost: parallel base …") and only pushes its own one-level `spark/<slug>-<id>` branches, never a worktree branch `spark/<id>/<name>`.
- **Critic → fix rounds** (`advisor/finding-questions.ts`, `orchestration/critic-fix.ts`, `review-loop.ts`, `transitions.ts`, policy `fixturn-1`, since September 28, 2026). When the verdict is concerns, each finding (up to 10) is classified as a concrete correctness bug or not: a rule on the text (bug words such as wrong, regression, crash; or behaviour words such as returns, accepted, missing, should throw, unless the finding is labelled a nit or is about naming, style, comments or readability) and, when Jev is connected and diffs may be sent, one `finding_N` Noul per finding, "Is this finding a concrete correctness bug in the change?", with the task and diff as state. Jev decides a finding at 0.8 or more either way (`ACT_AT.finding`); below that, or without Jev, the rule decides. Each review is a `finding` row in `run_advice` (`0045_critic_findings.sql`) with the per-finding readings, the review number, the fix round and the action, and shows as a decision in the crew view. With correctness findings at Automatic and Full auto → PR, the same Builder session gets one resumed fix turn (`resumeKey`, the findings as `route.followUp`), the checks run again (with their own fix turns), and the Critic reviews the new diff, told which findings the Builder was asked to fix. The loop stops when a review is clean (looks good, or only style findings), when every correctness finding repeats the previous review (normalized text, line numbers ignored), when checks still fail after the fix and its check-fix turns, when the budget check refuses the next spawn (the budget card asks as usual, and every fix turn counts against the task budget), or after `CRITIC_FIX_ROUNDS` (3) fix rounds. At Review each step nothing runs by itself: the keep card adds "Fix these findings" (then "Fix again") after Keep, which stays the primary option; each answer runs one round. Automatic asks with the keep card (and "Fix again") when concerns remain after the loop, and keeps by itself when the last review is clean; Full auto goes on to ship with them in the reply and the PR body. The keep card reason and the final reply say how it ended: "Fixed after 2 review rounds: the Critic's last review found no correctness problems; checks pass", "Still concerns after 3 rounds: …", "Still concerns after 1 round: the same findings came back after the fix: …", or "Stopped after 1 fix round: the checks failed after the fix …". A user's "Fix again" after the cap runs one more round; the cap limits only rounds the harness starts itself. Details: (a) the loop acts only on correctness bugs against the request or the agreed plan. The rule reads hardening, security and robustness advice the request didn't ask for (spreadsheet formula injection in an export, quoting `\r` for "some CSV readers", when to revoke a blob URL; hedges such as "may lose", "some browsers", "safety concern") as a suggestion unless it names a missed requirement, a concrete wrong result, or a real vulnerability the change adds (SQL injection, XSS, an auth bypass, a leaked secret). Jev can't turn a suggestion into a fix turn, its question now says so and gets the agreed plan as state. Suggestions are reported ("Not fixed automatically: …") and don't stop Automatic from keeping. A re-review (the Critic checking a fix round) runs at medium effort on the same Critic (`CRITIC_REREVIEW_EFFORT`, `rereviewCritic` in `routing.ts`, since October 1, 2026); the first review keeps high effort. (b) Each fix round has its own budget: a quarter of the run's tool calls (at least 20) and 4 minutes of active time (`FIX_ROUND_*` in `policy.ts`), and the harness starts a round by itself only when that much of the run's budget is left. (c) When a limit (the round's or the run's) cuts a fix round short and the change before it passed the checks, the run doesn't fail and no budget card shows: the files go back to the last state that passed the checks (the pre-fix state, or the fixed state when only the re-review was cut), and the flow ends on the keep card at Automatic and Review each step ("Stopped fix round 1: … Still open: …"; Full auto ships). Stop on a budget card that refused a fix turn now ends on the keep card as well.
- **Failures and the loop guard.** A failed Builder is retried one tier up by rule, at most twice; then the retry card offers Retry or Stop and report, and its auto-continue picks Stop and report. The loop guard (`loop-guard.ts`) stops a Builder after 5 identical non-edit tool calls in a row: at Review each step a card offers Continue (resume with a note to try another way) or Stop and report; at Automatic and Full auto → PR the turn stops with a report.
- **Observation mode, phase 2** (`advisor/policy-gate.ts`, `advisor/verify-questions.ts`, `orchestration/observe.ts`). Hard rules in `approvals/decide.ts` still decide first and are unchanged. For every proposed edit with a diff, the approval gate calls an observer after deciding and without waiting for it; one batched call asks four bad-is-true Nouls (`beyond_request`, `destroys_work`, `weakens_tests`, `unsupported_file`), takes the maximum, and records what the policy would do (block at 0.85 or more, review at 0.5 or more, otherwise allow; a missing or invalid answer is review) next to what the rules did and the approval id, so your later answer joins. The edit gate's rows (`policy`) never act. The verifier acts since the verified cascade (below). The workspace setting "Check changes with Jev" (on by default, `profiles.jev_diffs`) turns them off; then nothing is sent and a row records "skipped: diffs off".
- **Verified cascade** (`advisor/verify-questions.ts`, `orchestration/verify.ts`, `transitions.ts`; measured in `docs/benchmarks/verifier-2026-09-27.md`: unsupported precision 0.91, recall 0.83 on 24 labelled diffs). When the Builder and its checks and fix turns finish green with files changed, one Jev call gets the task, the Builder's plan, the check lines and the full uncommitted diff (`changesForReview`, 24,000 characters), and answers a Choice `verdict` (supported, unsupported, declined) plus one `unmet_N` Noul per requirement line. A verdict counts at confidence 0.8 or more. Accepted unsupported reruns the Builder once, one tier up (`escalate`), in the same task session and worktree, with the unmet requirement lines as the follow-up, then runs its checks again; accepted declined raises a "Jev could not verify the change" card (Finish as it is, Retry one tier up, Stop; auto-continue picks Finish); supported or below 0.8 goes on as before (Critic, keep card). At most two verdicts per turn and only the first acts. Every verdict is a `verify` row in `run_advice` with the answer, the action (`escalate`, `ask`, `finish`) and the escalation target. Without Jev, or with diffs off, the flow is checks and fix turns only. The retry one tier up for a failed Builder is unchanged: it handles agent failures, which the verdict never sees.
- **Plan capture** (`plans/`, `workflow/plan-recorder.ts`, `orchestration/plan-agreement.ts`, `0044_plan_documents.sql`). Plans the user agrees to are kept per conversation as versioned `plan_documents` (proposed, approved, rejected, superseded; source `claude_plan_mode`, `codex`, `chat` or `user`; approval time, who, which option and run, and the git HEAD at approval). They come from Claude's plan mode, from a `<proposed_plan>` block in an agent reply (stored as proposed), from the chat (below), or from "Save as agreed plan" under a reply that looks like a plan. Writes happen in code; a failed save shows as "Error: Could not save the plan: …" in the work log. The latest approved plan goes into every Builder prompt and every new session in the conversation as a short `## Agreed plan` block (goal, up to 12 open items, up to 6 key decisions, 2,000 characters), and the Critic gets it with a request to say whether the change follows it. When files the plan names changed since its approval commit, the block and the Plan tab say it may be out of date. There is no approval gate: nothing waits for a plan unless the agent asks.
- **Plans agreed in chat.** When the turn has a previous assistant reply, intake adds the Noul `plan_agreed` ("Is this message approving a plan or set of steps proposed in the previous assistant reply?") with the end of that reply (4,000 characters) as `previous_reply`. At 0.85 or more the reply is saved as an approved plan (or a proposed Codex plan from that reply is approved); from 0.6 a "Save the plan above as the agreed plan?" card offers it; below, nothing. Every such turn writes a `plan_agreed` row in `run_advice` with Jev's value, the action and a keyword baseline (`yes`, `go ahead`, `do that`, `sounds good`, `let's do it`, at most 20 words) for comparison. Without Jev only the button exists.
- **Audit.** Every Jev record carries `policy_version` (now `laws-1-universal-laws`; earlier `overhead-1-spec-plan-rereview`, `route-score-2-escalation-routes`, `route-score-1-cache-aware`, `intent-3-tagged-findings-prose-plans`, `intent-2-clarify-plan-first`, `intent-1-answer-first`, `fixturn-3-devday-rerun-nohaiku`, `cascade-1`, `lean-1`, from `advisor/policy.ts`, which holds every threshold) and the Jev model version that answered.
- **Analytics.** The Harness tab keeps the rule-vs-Jev comparison, adds cost per verified completion by routing agreement (total turn cost including Jev over turns whose outcome is good), and an "Observation mode: would have asked or blocked" card with the edit gate's and verifier's would-be actions against what happened. `pnpm jev:thresholds` prints precision and recall per threshold from the observation rows and the outcome signals. Every threshold is provisional until tuned on that data.
- **Universal laws** (October 1, 2026, policy `laws-1-universal-laws`, `apps/server/src/laws/`): five small guardrails around every Builder, described in [UNIVERSAL_LAWS.md](UNIVERSAL_LAWS.md): unexplained removals ask "why?" on the keep card (Chesterton), Spark's own check run beats the Builder's claim and weakened tests or config edits are flagged (Goodhart), plan cards show a time and cost estimate learned from the user's runs (Hofstadter), each Builder gets a turn budget scaled to the task's complexity (Parkinson), and a model whose recent pass rate for a task kind falls below its tier peers stops getting that work (Peter principle). Agents read all of it through `spark_laws`.
- **Also in place:** approvals and the autonomy levels, the Codex Do patch and rules, session resume (M6), outcomes and thumbs, model cards (prices, tiers and the tier question's text), analytics, the digest, the companion, slash commands, the Home screen, the audit log, Lean build (default lean, now a rule only), Keep and Revert, run snapshots and the changes view.

### Coordinator

Built September 28–30, 2026 (phases C0–C7); design, status and open items in [COORDINATOR_PLAN.md](COORDINATOR_PLAN.md).

- **When it engages.** After intake, clarify and plan first: the user asks for pieces, the agreed plan has 4+ open items across 2+ areas, the code scan's likely files number 12+ or span 3+ packages, or the size estimate is over one Builder's budget. Otherwise the one-Builder path above runs unchanged, with no extra model call.
- **What it does.** A read-only coordinator turn (`${taskId}:coordinator`) writes a `pieces` block (owned files, dependencies, contract, acceptance, scoped checks), validated in code. The placement ladder picks pieces in order, shared-tree Builders or worktree Builders; each piece's Builder may only edit its own files and can't run git state changes; pieces run scoped checks only; one integrator (`${taskId}:integrator`) merges, resolves conflicts and fixes what the full checks find; then the full checks, the verified cascade and the Critic run once on the integrated result. A report built by code lists the pieces.
- **Mode.** `COORDINATOR_MODE` defaults to `parallel` (`apps/server/src/config.ts`); `in_order`, `shadow` and `off` override it. Settings → Projects → "Builders at once" (`projects.piece_slots`, 1–3) caps parallel pieces per task. Spark off never engages it.
- **Not evaluated.** The story benchmark (phase C8) that should decide whether parallel placement stays on has not run.

### Lean build style

Adapted from [ponytail](https://github.com/dietrichgebert/ponytail) (MIT); our own wording, no ponytail file is copied or run.

- **The style** (`orchestration/lean.ts`, `build-style.ts`). Rules only, no setting and no Jev call (the project `build_style` column was dropped in `0068`): a Do turn in a linked project builds `lean`; a request that asks for a complete, production-ready or polished version builds `lite`; anything else is `off`.
- **Builder prompt.** Lean gives the ladder (does it need to exist, is it already in this codebase, the standard library, a native platform feature, an installed dependency, one line, and only then the minimum code), root cause over symptom, the safety floor (never simplify away validation at trust boundaries, data-loss handling, security, accessibility or anything requested), `lean:` markers for deliberate shortcuts with a limit and an upgrade, and one runnable check for non-trivial logic. Lite builds all of it and names the smaller option in one line.
- **Critic.** When a Critic runs anyway, it adds a complexity lens (`delete:`, `stdlib:`, `native:`, `yagni:`, `shrink:` findings and a `net: -N lines possible` line). Complexity alone never makes the verdict "concerns".
- **Shortcuts.** At wrap-up the diff is scanned for added `lean:` comments (no model call) and stored as a `shortcuts` artifact, shown in the Tasks list.
- **Open questions.** (1) Should the lean prompt name "validate the full format, including calendar ranges" for dates and similar, or leave that to the Critic? (2) Projects that forbid comments, like Spark Outpost's own AGENTS.md, conflict with `lean:` markers: should Builders list shortcuts in their reply instead? (3) Most lean runs have no Critic: should large diffs get a complexity-only pass?

### Ship: branch, commit, push, draft PR (September 28, 2026)

After Keep, the keep card and the Changes tab offer **Ship** (`ship/`, `api/ship-routes.ts`, `web/src/ship/`, `0048_ship.sql`). It turns a finished task into a branch, a commit, a push and a draft pull request, one step further each time the user asks.

- **Git is the user's own.** Every local step runs the system `git` with the user's identity, hooks, signing, SSH keys and credential helper (`GIT_TERMINAL_PROMPT=0`, so nothing prompts). Commit and push need no GitHub connection. Without git the preview shows the install hint (`GIT_INSTALL_HINT`).
- **What is committed.** Only the task's own files: the union of files its non-reverted runs changed (`taskChanges`, both sides of a rename), filtered to paths that still differ from `HEAD`. Secrets files (`isSecretPath`, such as `.env`) are left out and listed. Unrelated edits and anything the user staged stay as they were: Ship runs `git add` on the task's paths and `git commit --only -- <paths>`. Attribution is per file, so a task file the user also edited is committed whole.
- **Branch.** `${BRANCH_PREFIX}/<task-slug>-<task-id-8>` (`spark/…`, `spark-dev/…` in the dev channel), created with `git switch -c` from the current `HEAD`, so the user ends up on the branch with their other uncommitted changes carried along. The base for the PR is the current branch when the remote has it, otherwise the remote's default branch (then the repository's `default_branch` from the API). A second Ship on the same task commits on top of the same branch; if the user has switched away and the task has new changes, Ship asks them to switch back.
- **Push.** `git push --set-upstream <remote> refs/heads/<b>:refs/heads/<b>`: never forced (a moved remote branch fails with git's message), never the base or default branch (`safeToPush` only accepts Ship's own prefixed branch), never a merge.
- **Draft PR.** Needs GitHub API access, in this order: the user's `gh` login when `gh auth status --hostname <host>` succeeds (calls go through `gh api`; Spark never runs `gh auth token`), then a pasted fine-grained token, then a GitHub App later. All three sit behind `GitHubConnection` (`whoami`, `defaultBranch`, `findPullRequest`, `createPullRequest`, `updatePullRequest`), built by `restConnection` over a transport, so an App transport can be added without changes elsewhere. The host comes from the remote URL, so GitHub Enterprise works through `https://<host>/api/v3` or a `gh` login for that host. The PR body has the summary (the task's last reply), changed files, check lines, Critic findings, cost, the agreed plan's outline, and the footer "🤖 Generated with Spark Outpost". An open PR for the branch is updated instead of opening another.
- **Records.** The PR goes into `task_links` with source `ship`; `task_ships` keeps the branch, base, remote, last commit, push time and PR per task. Every Ship, successful or not, writes a hash-chained `ship` entry (redacted) to the audit log of the task's latest run.
- **Tokens.** A pasted token is checked with `GET /user` (login, scopes for classic tokens, the expiry header for fine-grained ones) and with repository access for linked projects on that host, then stored only in the keychain under the channel's `KEYCHAIN_SERVICE` (account `github:token`). The database keeps the login, host, scopes, expiry and repository access, never the token. Tokens never go into prompts, agent environments or logs; `redact.ts` also hides `Authorization: token …` headers and passwords in push URLs.
- **UI.** The Ship button reads "Open draft PR", "Push branch" or "Commit" depending on what is possible, and opens a confirm panel with the branch, the base, the files and an editable title. After shipping the card shows the PR link (the Links tab has it too) and the button becomes "Update draft PR". Settings → Connectors → GitHub shows which method is active (gh detected as a user, a token with its scopes, expiry and repositories, and Remove), and the GitHub App as "Coming later".
- **Not built.** The GitHub App (device flow) needs a registered app. Merging is not built; PR state, reviews and checks are read only for the Tickets view.

## Principles

A simple harness lets people see, control, and trust what the agent does, without learning how the harness is built.

- **See it.** Every tool call is a step with a record of what happened: the diff, the command, its output, and its exit code.
- **Approve it.** Risky actions pause the run on a card. The backend enforces the decision, not the model.
- **Stop it.** Stop always works, even while an approval is waiting.
- **Survive restarts.** Postgres is the source of truth. After a crash the run shows `outcome_unknown`, and nothing is replayed automatically.
- **Trust the result.** The "what changed" card comes from the harness's own records and `git`, not from what the agent says it did.
- **Keep the output.** Plans, changes, checks, and reviews are durable run artifacts that can be opened, compared, and exported after the run, even after a restart.
- **Choose per chat.** Provider, model, effort, and mode live in `conversations.overrides`. Advice can suggest; only the user and the fixed rules decide.

**Why not always planner, executor, then reviewer.** Running all three on every run means three cold starts (8–10 s each for Claude), about three times the tokens, and a stuck run whenever a review fails, even for "what does this function do?". Both agents already plan natively and stream ACP `plan` updates, so the harness records the agent's own plan as an artifact instead of running a planner. It picks a **mode**, not a pipeline.

## Run lifecycle

Run statuses: `queued → running ⇄ awaiting_approval → succeeded | failed | cancelled | outcome_unknown`.

- **Approvals** (M2). A request the gate decides to ask about waits on a card; see [M2 status](#m2-status-september-26-2026).
- **Recovery.** A crashed run becomes `outcome_unknown`, and its pending approvals expire. If it was waiting, the message says the action never ran. The plan and every other artifact written so far stay readable. Nothing is replayed.
- **Budgets** (M4). A pure `budgets.ts`: 15 minutes of active time (approval waits don't count), 60 tool calls, and an optional cost cap from Settings (Decision 4). A spent budget sends `session/cancel` and ends with `RUN_ERROR` `budget_exceeded`, naming the limit.
- **Concurrency** (M4). 2 jobs at a time by default (`WORKER_CONCURRENCY`). "One Do run per project" was planned here but never enforced at claim time; since round 10 a second Do task on the same repo builds in a worktree copy instead. Ask and Chat runs run in parallel.

### M2 status (September 26, 2026)

The approval gate as it stands (built in M2, extended since):

- **Storage.** `0015_approvals.sql`: the `approvals` table with a receipt for every decision, the `awaiting_approval` status, `runs.mode`, the snapshot columns and `reverted_at`, `projects.command_allowlist`, `run_file_backups`.
- **Decisions.** The pure `approvals/decide.ts` takes the mode's posture, the request, the run rules and the allowlist (details under [Provider permission modes](#provider-permission-modes-september-28-2026)). Once the chat has read sensitive data, anything that sends data out asks in every mode (see [Read, then send](#read-then-send-september-30-2026)). Always asks, in every mode: deleting outside the repo, secret files (`projects/secret-files.ts` and `.sparkignore`, in paths and command words), changing files outside the repo, and package installs. A push by the chat's own agent follows the mode's posture and otherwise asks unless allowlisted; a Builder's push is refused. Refused: plain force pushes (`--force`, `-f`, `+refspec`), `--mirror`, lease force pushes that don't name a branch or target `main`, `master` or the default branch, reads outside the project and edits inside `.git`. A `--force-with-lease` push to a named working branch always asks with a hold-to-confirm card and no "Always allow" (September 30); a Builder of a coordinated task is still refused. An allowlist entry covers the same command with more arguments, never a chained one.
- **Waiting.** `workflow/approval-gate.ts` inserts the pending row, emits `approval_requested` and waits on `NOTIFY approvals` with a 1 s poll. `POST /api/approvals/:id/decision {optionId, scope, payloadHash}` only succeeds while pending and when the hash matches. Stop answers `cancelled`; 30 minutes answers `reject_once`, marks it `expired` and fails the run; recovery expires pending approvals and says the action never ran.
- **Snapshot and revert.** A Do run starts with a git snapshot built in a temporary index (`read-tree HEAD`, `add -A -- .`, `commit-tree`, kept under `refs/spark-outpost/runs/<runId>`), which never touches the user's index or working tree. Outside git, the harness copies each file before an approved edit. `GET /api/runs/:id/changes` and `POST /api/runs/:id/revert` restore only files changed since the run started, once.
- **Known gaps.** Git snapshots skip ignored files, so changes to them aren't reverted. Outside git, changes made by commands aren't backed up.
- **Codex Do** runs in our patched `ask-every-action` mode, where every command and patch reaches the gate ([CODEX_DO.md](CODEX_DO.md)).

## Task artifacts

What a task leaves behind that a person wants to open again. `run_artifacts` is keyed per task since `0014_tasks.sql`: `(task_id, kind, version, body, source_run_id, superseded_by, created_at)`, so a plan's versions span the task's runs. Kinds (`packages/contracts/src/artifacts.ts`): `plan`, `check`, `review` and `shortcuts` are written today (`changes` and `advice` are in the enum; Jev advice is per run in `run_advice`, and changes are computed from the run snapshots).

- **Append-only versions.** The latest version is the current artifact; earlier ones are its history. A write while the worker holds the lease goes through `appendRunEvent` with an `ACTIVITY_SNAPSHOT` (`messageId` `artifact:<kind>`), so the web updates live.
- **Bodies** are validated by the zod schemas in `packages/contracts/src/artifacts.ts` on write and on read.
- **Plans.** `nextPlanWrite` drops identical updates, writes status-only changes and further updates from the same run into the current version, and overwrites the latest version after 200; a plan change from another run adds a version. `planChanges(previous, next)` marks the previous version `superseded_by` when added plus removed entries are more than half of all entries. `runs.plan_version` is the version a run started from or last wrote. `GET /api/tasks/:id/artifacts/plan.md` downloads the Markdown.

### Plans in detail

- **Capture.** `session-updates.ts` turns each ACP `plan` update into a provider output `{ kind: 'plan', entries }` with content, priority and status; the worker versions it as above, so a looping agent can't grow the table without bound.
- **Replacement.** ACP plan updates replace the whole plan, and entries have no IDs. The history compares versions by entry text in a pure `planChanges(previous, next)`: added, removed, and status changed.
- **The Plan tab** of the work panel (`tasks/PlanPane.tsx`) shows the checklist, the version and which runs used it, a "History" toggle with a timeline of the versions, and "Copy as Markdown" and "Download .md". The agreed plan shows beside it (`AgreedPlan.tsx`).
- **Claude's plan mode** (since plan capture, September 28, 2026; see [Plan capture](#plan-capture-september-28-2026)). Claude Builders get `EnterPlanMode` and `ExitPlanMode`; entering plan mode is allowed at every autonomy. The exit request (`kind: switch_mode`, the plan in `rawInput.plan`) is an approval (M2) titled "Approve the plan?" with the plan rendered as Markdown, and it is also stored as a `proposed` plan document, separate from the ACP `plan` checklist. The card shows every option the agent sent, including the ones that switch to Auto or Bypass permissions (see [Provider permission modes](#provider-permission-modes-september-28-2026)). Any `exit-plan-*` choice the user allows marks the document `approved`, clear-context ones included even though claude-agent-acp answers them with a deny; a rejection marks it `rejected` and the agent keeps planning.

Jev is an advisor, never an executor or an authority. ## Project folders and safety

- **Linking** (M1, `0009_projects.sql`, `0010_conversation_projects.sql`): `projects (id, workspace_id, name, root_path)` with symlinks resolved, and an ordered `conversation_projects` list per chat whose first entry is the primary repo. The server refuses `/`, `$HOME`, and anything that isn't an existing directory.
- **File access** goes through `fs-handlers.ts` and the pure `projects/path-policy.ts`: absolute paths only, inside the root after symlinks are resolved, reads capped at 1 MB, writes (M2) create missing folders and record hashes before and after plus a diff.
- **Secret files are refused** for reads and writes, each shown as a step: the list in `projects/secret-files.ts` (`.env*` except `.env.example`, SSH key names, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `.npmrc`, `.netrc`, `.pgpass`, `.pypirc`, `.git-credentials`, credential files), writes under `.git/`, and `.sparkignore` entries.
- **Approval buttons.** "Allow", "Allow for this run" and "Always allow in this project" all answer the agent with `allow_once`; the harness keeps the run rule and the allowlist itself, so the agent never switches to a looser mode and every later action still gets a receipt. "Deny" answers `reject_once`. `reject_always` isn't shown.
- **Commands.** Claude Do sessions keep `ask` rules for Bash, Edit and Write in every mode (`CLAUDE_DO_ASK_RULES`), so Claude's shell tool reaches `request_permission` and our gate; the card says the command isn't sandboxed. Codex Do runs in our patched `ask-every-action` mode, where every command and patch reaches `request_permission`. Its commands run in Codex's sandbox without network unless Codex escalates, and the card says so ([CODEX_DO.md](CODEX_DO.md)). A command on the project's allowlist runs without asking (Decision 2). So does a safe read-only command inside the project. Package installs always ask unless they only restore the lockfile.
- **Sandbox.** No `sandbox-exec` (Decision 5). Tools that reach the disk without our handlers are listed as known gaps.
- **Worktrees.** Each chat gets its own worktree by default (see "Chat worktrees" above); per-run copies cover the in-place cases, and Codex modes that skip the gate run only in a worktree.

## Sessions

### M6 status (September 26, 2026)

Resumable sessions (`workflow/session-decision.ts`, `0026_provider_sessions.sql`). The `/` command menu and @-mentions of project files ship; `session/delete` and compaction are still open.

- **What the adapters support.** claude-agent-acp 0.81.2 and codex-acp 1.13.1 (with our read-only patch) both advertise `loadSession`, `sessionCapabilities.resume` and `close`, and both resume a session in a **new agent process**: Claude reads the transcript Claude Code keeps under `~/.claude/projects`, and Codex calls `thread/resume` on its stored thread. So agent processes stay per run and there is no warm process pool. Claude's `closeSession` only knows sessions in its own process.
- **Storage.** `provider_sessions (conversation_id, provider, agent_key, session_id, cwd, workdir, additional_dirs, settings_hash, last_message_id, last_reply_hash, reported_cost_usd, created_at, last_used_at, closed_at, close_reason)`, at most one open row per conversation and agent key. A chat turn's key is `chat:<mode>`; a child's is `key:<resumeKey>`.
- **When a turn resumes** (`decideResume`, pure): the latest row for the key is open, used within the idle time, its settings hash matches (provider, model, effort, run mode, planning tools, linked repos in order), its last turn finished, and, for chat turns, the message just before the new one is the reply it wrote with the same text. The provider then also needs `resume` (preferred) or `loadSession` and the same `cwd` and extra directories; otherwise, or if the resume call fails, it opens a new session with the history. The work log gets a quiet step: "Continued session" or "Fresh session (…)" with the reason.
- **What a resumed turn sends.** Only the new message and its attachments: no project note and no history. Chats without a project get a stable folder per conversation and key (`$TMPDIR/spark-outpost-sessions/<hash>`) so `cwd` matches on the next turn.
- **`session/load`.** Used only when `resume` isn't advertised; replayed updates never reach the mapper or the audit log.
- **Cost.** Claude's `usage_update` cost is cumulative over the session, so a resumed run records the reported cost minus the cost stored at the end of the previous turn (`reported_cost_usd`).
- **Lifecycle.** At the end of each tracked turn the provider sends `session/close` (when advertised, 3 s cap) before stopping the process. A stored session is closed when the chat's provider, model, effort, permission, routing or repos change; the chat is archived; the user picks **Start fresh** in the chat header's ⋯ menu; a turn fails or is stopped; it has been idle for `SESSION_IDLE_MINUTES` (default 240); or more than `SESSION_OPEN_LIMIT` (default 16) are open, least recently used first. The worker sweeps idle, archived and excess sessions and removes unused session folders.
- **The `resumeKey` contract for child runs.** A child run resumes only when the orchestrator stores `route.resumeKey` on it (and optionally `route.followUp`). Use a key scoped to the task and the member (`${taskId}:builder`, `${taskId}:integrator`, `${taskId}:piece:P1:1`) and reuse it for that member's fixes and continues. Chat messages aren't checked for children. When the session continues, the agent receives `followUp` instead of the full `prompt`. Never give the same key to two runs at once.
- **Measured** (Claude Haiku 4.5 and Codex 6 Luna · low, turn 2 of a two-message chat, time to first reply text including process start): Claude cold 7.9 s and $0.0155 fresh against 4.8 s and $0.0013 resumed; Codex uncached input dropped by 76–91% on resume. The saving grows with the history a fresh turn resends.

### Tasks

- **Model picker.** Auto lets the rules pick the tier; a pinned model is always used, and the record says what Auto would have used.
- **Context for members** comes from the harness, never from another agent: Builders get the request, the recent chat, the agreed plan and, in pieces, their contract; the Critic gets the request, the plans, the diff and the check results.

### Audit

Everything an agent does is recorded, CloudWatch-like: the chat is the log group and each agent run a log stream with its role, provider, model, effort and mode.

- **Raw protocol log** (`run_protocol_log`, `0013_audit.sql`): every ACP message in both directions plus the agent's stderr (up to 1 MB per run), redacted and hash-chained per run. Harness entries (checks, Ship, Codex developer instructions) are in the same chain with direction `harness`.
- **Also kept:** approvals with their receipts, task artifacts, Jev decisions (`run_advice`, with `policy_version`), and on `runs` the model, effort and mode the agent actually used, `duration_ms`, `tool_call_count` and `cost_source`.
- **Metrics per agent run:** input, output, cached and thinking tokens, cost (labelled reported or estimated), context, duration and tool calls.
- **Audit view:** a summary by model, role, provider and run, a per-turn timeline with approval waits, logs you can filter by agent, type and text, and JSONL and CSV export.
- **Retention:** raw logs 90 days by default, summaries forever.

### Provider permission modes (September 28, 2026)

The four-level picker is gone (user decision). Agent permissions now come from the provider: the picker's Permissions section lists the modes the live session advertises (its `mode` config option, or legacy `modes`), with the agent's own names and descriptions, and the harness autonomy sits next to it in the same section ("Sonnet 5 · Accept edits · Automatic"). One plain line under it says what the two do together (`combinationLine` in `contracts/agent-modes.ts`, e.g. "Agent won't ask · kept automatically · Revert available"), and a warning shows only for a bypass-type mode on the real checkout or a mode that runs only in a worktree copy.

- **Storage.** `provider_connections.agent_mode` is the "default mode for new chats" (Settings and onboarding; a new connection gets the provider's own default: Claude `default` "Manual", Codex `agent` "Approve for me"). A chat overrides it in `overrides[provider].agentMode`. `runs.agent_mode` records the mode a Do run starts in, crew members inherit it (translated to the closest mode when a member runs on another provider, `translateMode`), and `runs.used_mode` records what the agent reported. `permission` is derived: a read-only mode (Claude Plan, Codex Read-only, or any mode whose `_meta.kind` is `plan`) makes an Ask run; every other mode a Do run. Generic config options (a Fast mode boolean, `model_config`, unknown categories) are stored per chat in `overrides[provider].options` and per run in `runs.config_values`, and applied with `session/set_config_option` (booleans with `type: "boolean"`).
- **Applying.** Do runs send the chosen mode with `session/set_config_option` (or `session/set_mode` for agents with only legacy modes). A mode the agent doesn't offer falls back to the asking mode (Claude Manual, Codex Ask every time) with a note. Ask runs, Scouts and Critics use the provider's read-only mode as the harness role: Codex `read-only`; Claude keeps `default` with only Read, Glob and Grep, because Claude's Plan mode prompt tells the model to write a plan file with Write and to call ExitPlanMode, tools Ask sessions don't have (verified offline, below).
- **Mode changes.** A mode you pick while a turn runs is switched live (`runs.requested_mode`, polled by the worker, then `set_config_option` on the open session); queued runs start in it; the agent session is kept (mode, autonomy and options are not part of the session shape). An agent's own `current_mode_update` or `config_option_update` shows as a step ("Claude switched to Accept edits mode") and updates `used_mode`, model, effort and options live. A switch to a mode that may not run where the run is (a worktree-only mode on the real checkout; anything but read-only in Ask) stops the run, as before.
- **Approval cards** show every option the agent sent (`allow_once`, `allow_always`, `reject_once`, `reject_always`) with the agent's labels, and the chosen option goes straight back. An `*_always` choice is also recorded as a run rule (`scope = 'run'`), so the harness never asks twice in the run: an allow covers the same command, edits or tool again, a reject refuses it before asking. The harness keeps one extra, "Always allow in this project", for commands. On actions that always ask (secret files, package installs, changes or deletes outside the repo) the agent's `allow_always` options are hidden, because an agent-side always rule (Codex's command approval for the session) could let the next one skip the gate. Claude's plan approval (`ExitPlanMode`) now shows all of its options, including the ones that switch to Auto or Bypass permissions.
- **The gate follows the live mode** (`decide(posture, …)`, posture from `modePosture`): `asks` (Manual, Ask every time, unknown modes) asks you for edits and commands not on the allowlist or read-only; `edits` (Accept edits) lets edits through; `auto` and `full_access` (Auto, Bypass permissions, Approve for me, Full access) let everything through, as does Automatic or Full auto in the chat's own worktree (except pushes, September 30); `denies` (Don't ask) refuses what isn't pre-approved. The safety floor applies first in every mode: plain force pushes and a Builder's publishing are refused (a solo Builder's lease force push asks), reads outside the project and edits inside `.git` are refused, and deleting outside the repo, secret files, package installs and changes outside the repo always ask. Commands that read files (`cat`, `head`, `grep`, `sed`, `awk`, `cp`, `tar`, `curl -F @file`, `source`, `python -c`, `node -e` and the like, including inside `sh -c`, `eval` and `find -exec`) are checked by what they can reach (`approvals/file-reads.ts`, September 29): a literal glob, a loop over a literal list and a recursive read (`grep -r`, `rg --hidden`, `tar`, `cp -r`, `find -exec`) are expanded on disk, and a match with the secret file list asks as a secret file. An argument Spark can't resolve (`$(…)`, backticks, variables other than a loop over a literal list, `xargs` input, `read`, inline code that opens a computed path or lists folders) asks with "Spark can't tell which files this reads", at every mode and ahead of run rules and the allowlist. Shell keywords (`do`, `then`, `if`…) no longer hide the command after them from the other checks. Scripts and piped code are checked too (`approvals/script-reads.ts`, `script-runs.ts`, September 30): a script run by name (`python x.py`, `node`/`tsx`/`bun`/`deno run`/`ruby`/`perl`/`php`, `bash x.sh`, `source`, `./x` by its shebang, and through `npx`, `pnpm exec`, `uv run`, `poetry run`) is read from disk. A script that git shows as committed and unchanged is the user's own code and runs like `pnpm test` does, unscanned; any other script (new, edited, untracked, ignored or outside a repository) is scanned like `python -c`: a secret path it names, a `.env` loader (`dotenv`, `load_dotenv`, `--env-file`) or `--env-file` pointing at a secret asks as a secret file, and computed reads ask with "Spark can't tell which files this reads". Code fed to an interpreter on stdin is scanned the same way when Spark can see it (`echo '…' |`, `printf`, `cat file |`, `<<EOF`, `<<<`, `< file`); code it can't see (`curl … | python3`, `git show … | node`, a subshell or `$(…)` feeding the pipe, `<(…)`, a remote `deno run https://…`, a binary or oversized script, or a missing script that an earlier command could have created) asks with "Runs code Spark can't see". A shell reading its script from a pipe (`curl … | bash`, `bash -s`) asks as a command Spark can't see inside. Limits: only the named file is scanned (not its imports, nor code run by test runners or package scripts), a script the agent commits before running it counts as committed, and a missing script run on its own is allowed because it can't run. Codex also blocks secret reads at the OS level (patch part 7 in PATCHES.md: Seatbelt denies `SECRET_FILE_PATTERNS` under the project roots for every process, scripts and pipes included); it does not cover `.sparkignore` entries or secret files outside the project roots.
- **Never ask twice.** At Review each step, when every changed file's edit was approved by you one by one during the turn (`approvedEveryEdit`), the keep card is skipped and the change is kept ("Kept: you approved every edit."), unless checks fail, the Critic still has concerns or a destructive migration nobody confirmed shows up.

- **UI.** The composer picker's Permissions tab has two lists, "Agent mode" (the live modes, the provider default tagged) and "Harness autonomy", with the one-line summary and the warning under them (`ModeOptions.tsx`); read-only modes read just "Plan" or "Read-only" since autonomy doesn't apply. An Options tab renders every other config option generically: booleans as switches, selects as radios with group headings (`ConfigOptions.tsx`). The model list hides models whose card retires within 30 days (a "Show retiring models" switch reveals them, labelled "Retiring Oct 15, 2026"; the chat's current model always shows). Settings and onboarding show "Default mode for new chats" and "Harness autonomy" (`ProviderDefaults.tsx`), and capabilities refresh after each run so modes a run reports show up. Approval cards list the agent's options in its order with its labels and say "Chose: …" once decided.

| Write outside the repo without Edit/Write ask rules          | asked                                     | asked        | classifier | **written unasked** |
| With `ask: ['Bash', 'Edit', 'Write']`                        | everything reaches our gate in every mode |

- The secret-file `Read` deny rules hold in every mode and also block `cat .env` and writes to `.env`. The publish deny rules miss `git -C … push` and absolute paths when Bash doesn't ask; our gate's `publishesCode` catches those and `sh -c "…"` wrappers. Bypass writes outside the repo unasked, and Auto hands decisions to Anthropic's classifier. The blanket ask rules beat every mode.
- **So Claude Do sessions keep `ask: ['Bash', 'Edit', 'Write']` in every mode**, and the gate applies the chosen mode's posture after the floor. Claude's modes therefore never need a worktree, and Bypass permissions on the real checkout only gets a warning. Do sessions set `allowDangerouslySkipPermissions` so the adapter offers Bypass permissions (and its plan-exit options); chats and Ask sessions keep it off. `dontAsk` is not offered by claude-agent-acp 0.81.2 (`set_mode` and `set_config_option` both refuse it).
- **Codex's Approve for me and Full access** don't send requests to our gate (an auto reviewer, or `never`), so secret reads, pushes (Full access has network) and writes outside the repo aren't gated. They run only in a worktree copy (`modeNeedsWorktree`), a live switch to them on the real checkout is refused, and unknown future modes of an ungated provider count the same. The offline check of Codex could not be run (see the report); the earlier live probe in [CODEX_DO.md](CODEX_DO.md) showed `on-request` modes reading `.env` unasked.
- **Builders' environment** (defence in depth, every provider): `GIT_CONFIG_COUNT`/`url.spark-outpost-no-push:///.pushInsteadOf` rewrites every push URL, `GH_CONFIG_DIR` points at an empty folder and hosting tokens are removed (`withoutPublishing` in `agent-env.ts`). Verified offline for Claude's Bash: `git push` failed, `git fetch` and `git commit` worked, `gh` was logged out. A command that resets `GIT_CONFIG_COUNT` undoes it, so it is a speed bump, not a boundary; the gate refuses those commands for Builders.

#### Read, then send (September 30, 2026)

Automatic, Full auto and the agents' Auto and Bypass modes run commands such as `curl` unasked. To close the read-then-send (exfiltration) gap, the harness tracks what a chat has **observed** and, once it has seen sensitive data, asks before anything that sends data off this computer, at every level and mode.

- **What is tracked** (`observations/`, table `run_observations` in `0080_run_observations.sql`, keyed by run and chat): a secret or `.sparkignore`d file the user allowed on a "Secret files always ask" card (source `secret_file`, the file's path in the project, `secretLabels` in `decide.ts`); secret values in a tool's output or in a file read through the client (`secret_output`: the project's own `.env` values or a redaction rule hit such as a token, a private key or `KEY=value` with a sensitive key and a real-looking value, placeholders like `your-key` or `changeme` excluded; `observations/output-scan.ts` taps the ACP stream next to the audit recorder, so `env`, `printenv` and config dumps count); and private work data from Spark's own read tools (`private_data`: `spark_tickets`, `spark_chat`, `spark_chats`, `spark_audit`, `spark_pr`, `spark_pull_requests`, `spark_brief`, `spark_activity`, flagged `privateData` on the tool). Only names are stored, never values. Each observation is kept in memory for the turn, written to the table and to the run's protocol log as `spark/observed`. The scope is the chat: every later turn, Builder and piece of the same conversation reads the stored observations, so a resumed session stays guarded.
- **What counts as sending data out** (`approvals/egress.ts`, `egress-hosts.ts`): network clients (`curl`, `wget`, `http`/`xh`, `ssh`, `scp`/`rsync` to a remote, `sftp`, `ftp`, `telnet`, `nc`, `dig`, `nslookup`, `ping` and the like), `git push`/`send-email` and `git clone`/`fetch`/`pull` of a URL, `gh`/`glab`/`hub`, cloud and deploy CLIs (`aws`, `gcloud`, `az`, `kubectl`, `terraform`, `vercel`, …), mail tools, package publishing (`npm publish`, `cargo publish`, `docker push`/`run`/`build`, …), `/dev/tcp`, python/node/ruby/perl/php one-liners, heredocs and uncommitted scripts whose code opens connections (`requests`, `urllib`, `fetch(`, `socket`, `http.request`, …; the same inline-code scanning as file reads), commands Spark can't see inside, every tool of a user or repo MCP server (`mcpServer` on the request, from Claude's `_meta.claudeCode.mcpServer`, an `mcp__server__tool` title or Codex's MCP approval), and web fetch tools (`toolKind: fetch`). Requests that only reach `localhost`, `127.0.0.1`, `::1`, `0.0.0.0` or `*.localhost` stay exempt; a host Spark can't resolve (`curl "$URL"`) counts as remote.
- **Decision** (`decide.ts`, `taintedEgress`): after refusals, run reject rules and the force-push card, and before the always-ask list, run allow rules, the allowlist, the chat worktree's Automatic and the mode's posture: a tainted chat plus an egress request asks with "This run read .env earlier; sending data to example.com needs your OK" (names only, the host, or "out through `gh`"). The card drops the agent's `allow_always` options, shows no "Always allow in this project", and the server refuses any scope but once (`validateDecision`). The card adds a "Read sensitive data earlier: …" line (`ObservedNote`), and Spark's own action cards (create or comment on a ticket, open a PR), which always confirm, show the same line. Each ask is logged as `spark/egress` with the approval id, subject and observed names. Untainted chats behave exactly as before.
- **Codex.** Codex Do runs in `ask-every-action`, where every command reaches the same gate, so the rule applies to Codex exec approvals too. Switching to a network-disabled permission profile once tainted was checked and not done: the profile is chosen per turn at `turn/start` (patch part 7 in [PATCHES.md](PATCHES.md)), so it could only take effect on the next turn, and it would not stop the case that matters, because a command Codex escalates runs outside the sandbox profile altogether ([CODEX_DO.md](CODEX_DO.md)); the gate is what stops it. Approve for me and Full access never reach the gate and still run only in a worktree copy; the guard can't see them.
- **Limits.** Data the agent writes into files that you later commit and push yourself, or that Ship pushes, isn't followed. DNS lookups and other covert channels inside allowed commands (a test runner, a committed script, package scripts, a build that downloads) aren't classified; committed scripts are trusted like `pnpm test`. Secret-looking values are detected by pattern, so an unusual secret format can be missed and a realistic fixture can taint a chat (the cost is an extra card). A command Spark lets through as "can't tell which files this reads" after you allow it does not taint by itself; its output is still scanned. Observations last for the whole chat; Start fresh does not clear them.

- **Migration** (`0050_provider_modes.sql`): Ask → Claude Plan / Codex Read-only; Ask before edits → Manual / Ask every time + Review each step; Auto-edit → Accept edits / Approve for me + Automatic; Full auto → Bypass permissions (Claude, gated) / Approve for me (Codex) + Full auto → PR. The new default autonomy is Automatic.

## Decisions (September 25, 2026)

1. **Default mode in a linked folder** follows the user's default permission for that provider (set in onboarding or Settings, and overridable per chat). There is no separate folder default.
2. **Commands with auto-accept.** Each project gets its own allowlist, for example `pnpm test`, stored on the project. A command on the list runs without asking. Any other command asks. The card offers "Always allow in this project", which adds the command to the list.
3. **Reviewer.**
   - Use the other connected provider when there is one.
   - Superseded: whether to review is decided by the Critic rule (`orchestration/critic-rule.ts`) and the `review` Noul, not by Jev choosing a reviewer.
   - Jev's advice is recorded on the run. The harness still enforces approvals, and Jev's choice can never grant permissions.
4. **Cost.** No default cost cap. Show usage and cost for each run, totals for the chat, and totals per provider, including context use per provider. The per-run cap stays optional in Settings.
5. **OS sandbox.** Follow the ACP guidance.
   - The client's file handlers and permission requests are the boundary the client controls.
   - Each agent's own sandbox covers the rest: Claude's permission modes with its tools limited. Codex runs a patched codex-acp 1.13.1 whose `read-only` mode is a true `readOnly` sandbox (upstream codex-acp#480), so it may read linked repos in Ask. Its sandbox can read the whole disk, a known gap.
   - M1 ships without `sandbox-exec`. Tools that reach the disk without our handlers are listed as known gaps.
6. **Crash during a Do run.**
   - Take a snapshot when the run starts: a git ref of the working tree, or, outside git, copies of the files the harness writes.
   - After a crash, show what changed and offer "Revert to before this run" as well as "Keep changes".
   - Revert only touches files changed during the run, and it needs one confirmation.
