# Windows support: feature inventory

Status: draft for planning, written 2026-11-22 from a code scan of `otel-export`. Nothing here is built.

## Summary

- **Most of Spark ports as-is.** The web app, the Express API, ACP agents, tickets, Slack, GitHub, sub-chats, Sparks and workflows, telemetry and the Browser pane are Node, web or Electron code.
- **The blocker is the safety floor.** The approval gate parses commands with tree-sitter **bash** and checks POSIX paths. On Windows, if agents run PowerShell or cmd, or paths use drive letters and backslashes, the floor, the publish rules and the secret-send check would weaken without any error. This has to be fixed before anything ships.
- **Four features need a new implementation:** Mac control, Voice, macOS Calendar (EventKit) and Touch ID. **Terminal sessions** also need a new design, because tmux does not run on Windows.
- **Goal: the same experience as on the Mac.** Every Mac-only feature gets a Windows equivalent or, where none exists (macOS Calendar), a replacement, listed in "Parity design" below. Earlier "Drop v1" verdicts mean "ships in a later phase", not "never".
- **Packaging is new work:** an NSIS or MSIX installer, Authenticode signing, a Windows update feed and CI.

"Mac only" in `AGENTS.md` usually means "on the host computer, not on a paired device". Those features (Settings, Sparks, the GitHub page, Telemetry, shell tabs and so on) are host-only, not macOS-only. On a Windows host they work like any other host feature.

## Parity design

### One Windows helper

The Mac has four signed Swift helpers (Mac control, Voice, Calendar) plus the `no-activate` addon. Windows gets **one signed helper, `spark-win-helper.exe`**, written in C# with .NET Native AOT. It is a single self-contained executable with no .NET install needed.

C# is chosen because UI Automation, WinRT (Windows Hello, speech, media) and WASAPI all have first-party bindings there. It keeps the Mac helpers' stdin/stdout JSON protocol, so the Node hosts in `apps/desktop/src/*/host.ts` stay one code path with a platform switch. Small window-style calls such as no-activate can go in a Node-API addon or in the helper itself.

## Order of work

Each phase ends with the real-machine tests used on the Mac, on a Windows 11 x64 and an ARM PC.

1. **Ground truth.** Add a manual `windows-latest` CI job; install on a Windows VM; confirm ACP sessions and which shell commands reach the gate.
2. **Safety floor.** Windows paths and temp folders, ACLs, Claude on Git Bash with the PowerShell tool off, and the Windows test matrix for `approvals/`.
3. **Foundations.** Postgres, Credential Manager with chunking, named pipes, ConPTY, PATH.
4. **Shell and packaging.** Fluent shell, tray, taskbar, toasts, island, privacy screen with Windows Hello, NSIS installer, signing, update feed. **First Windows alpha.** Windows ships as an alpha, named so in the installer and the About panel, until it has had real use.
5. **Terminal session host.** Restart survival to match tmux.
6. **Helper part 1.** Calendar (Microsoft Graph) and Voice with meeting loopback.
7. **Helper part 2.** Mac control on UI Automation, as "Computer control" on Windows.
8. **Codex PowerShell reader.** Codex on Windows reaches the same safety floor as Claude.

Until a phase lands, its features are hidden on Windows with "Coming to Windows" in Settings, never broken.

## Answered (2026-11-22)

From the npm registry and official docs:

- **Embedded Postgres:** `@embedded-postgres/windows-x64` exists at 17.10.0-beta.17. There is no Windows ARM build. On the Windows CI runner the server refused to start as administrator ("Execution of PostgreSQL by a user with administrative permissions is not permitted"), because embedded-postgres starts `postgres.exe` directly. On Windows Spark now starts and stops it with `pg_ctl` (`apps/desktop/src/postgres-windows.ts`), which drops administrator rights.
- **Keychain library:** `@napi-rs/keyring` 2.1.0 ships `win32-x64`, `win32-ia32` and `win32-arm64` builds.
- **Agent backends:** the Claude agent SDK and `@openai/codex` 0.166 both ship Windows x64 and arm64 binaries.
- **Credential Manager size:** a blob is at most 2560 bytes (`CRED_MAX_CREDENTIAL_BLOB_SIZE`, [Microsoft docs](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)).
  - `telemetry:headers` allows up to 20 × (128 + 4096) bytes, so one entry can't hold it, and even a single long header can fail.
  - Fix: split large secrets into chunks, or keep an encrypted file whose key lives in Credential Manager.
  - Checked on the Windows runner: keyring stores UTF-16, so about 1,200 characters fit (see Phase 3 progress).
- **Claude Code shell** ([setup docs](https://code.claude.com/docs/en/setup)):
  - With Git for Windows installed, the Bash tool runs in Git Bash (`CLAUDE_CODE_GIT_BASH_PATH` sets the path). Its PowerShell tool also runs alongside by default for claude.ai and Console accounts.
  - Without Git, every command goes through the PowerShell tool.
  - `CLAUDE_CODE_USE_POWERSHELL_TOOL=0` turns the PowerShell tool off.
  - Sandboxing is not supported on native Windows.
- **Codex shell** ([Windows docs](https://developers.openai.com/codex/windows)): Codex runs commands in PowerShell, with its own Windows sandboxes (`mxc` recommended, `elevated` and `unelevated` as fallbacks). The `unelevated` sandbox does not support denied read paths.
- **Command parser:** `tree-sitter-bash.wasm` loads through `require.resolve`, which is platform-independent.

**What this means for the parser:**

- **Claude:** require Git for Windows and turn the PowerShell tool off in Spark's sessions with `CLAUDE_CODE_USE_POWERSHELL_TOOL=0`. The bash parser and the existing rules then still apply.
- **Codex:** it only uses PowerShell, so the gate needs a PowerShell reader before Codex on Windows can get the same safety floor. The bash parser does not reject PowerShell: it reads `Get-Content C:\Users\me\.ssh\id_rsa` as an ordinary command, so its decisions on PowerShell can't be trusted. Until the reader exists, Spark must not claim the safety floor for Codex there. An always-ask fallback needs implementing: today an unreadable command does not always ask, since `approvals/decide.ts` can allow a command before its unreadable-command check, and that check depends on the run kind. Even with it, the Codex modes that run commands without sending them to the gate (Workspace access, Auto review, Full access) stay uncovered on Windows, as they are seen only after the fact on the Mac.

## Phase 2 progress

- **Gate paths (done):** the approval gate (`apps/server/src/approvals/`) reasons about paths with POSIX semantics on every platform (`gate-path.ts`). On Windows, native paths entering the gate are converted to Git Bash form (`C:\\x` → `/c/x`): roots, home, the working folder, tool paths, git folders, and the temp, data and crew folders (`gate-request.ts` at the entry points). Windows paths written in commands are read the same way. Git Bash `/tmp` maps to the Windows temp folder. File access converts back, and a POSIX path with no Windows equivalent is treated as missing. Claude permission rules use the same `/c/...` form.
- **Claude on Windows (done):** Spark's Claude sessions set `CLAUDE_CODE_USE_POWERSHELL_TOOL=0`, so every command runs in Git Bash.
- **Windows CI:** safety-rule unit tests went from 95 failing to 0. All unit tests went from 318 failing to about 235; the rest are terminal, worktree, desktop and tooling tests for later phases.
- **Codex on Windows (always ask):** until the PowerShell reader lands (phase 8), every Codex command the gate sees on Windows asks, in every mode but those that skip anything not pre-approved, with the reason "Spark can't read PowerShell commands yet". Its edits are decided as before. Codex modes that run commands without sending them to the gate (Workspace access, Auto review, Full access) stay uncovered.
- **Private data folder:** on Windows the desktop app makes Spark's data folder private at start (`apps/desktop/src/private-folder.ts`): PowerShell from System32 replaces the folder's whole rule list (`Set-Acl` with SDDL) with full control for the current user (by SID, Microsoft Entra accounts included), SYSTEM and Administrators only, with inheritance off and inherited by everything inside, so an explicit grant to someone else does not survive, so the Postgres password, `app-lock.json`, the launch token and the database are covered without changing each file's `0o600`. Files Spark puts in the temp folder are already private, since Windows keeps it under the user's profile. A failure is logged and Spark still starts. The Windows CI check gives a test folder an explicit grant to Everyone, then confirms the folder is private by its security descriptor and that Postgres starts inside it. The desktop runtime pipe's rules come with named pipes in phase 3.
- **Letter case:** on Windows, instruction files and git control match in any case (`agents.md`, `.GIT/hooks/…`), a path inside a project counts as inside when it differs from the project folder only in case, and Sparks' folders compare case-insensitively, as Spark's data folder already did. macOS keeps exact case for instruction files, matching Claude's own ask rules.
- Project folders on a network share (`\\server\share`) are not supported yet: POSIX path joins collapse the share's leading `//`, so a folder the gate can no longer map reads as unknown, and a server named with one letter would map to that drive. Keeping the share prefix through every join is a follow-up.

## Phase 3 progress

- **Credential Manager size (done):** keyring stores UTF-16, so one entry holds about 1,200 characters. On Windows, `nativeKeyring` splits a longer secret into parts of 1,000 characters (`apps/server/src/setup/keyring-chunks.ts`): each save writes its parts under new names (`<account>#<generation>-<n>`, a random generation per save) and then switches the main entry's marker to them, so a save that fails part way leaves the old secret whole. The old parts are removed after the switch. A missing part is an error, never a short secret. The Mac keychain is unchanged.
- **Browser pane project files (done):** the file check that lets a chat's pane load only its own project files compares paths in any letter case on Windows (`insideRoots` in `apps/desktop/src/browser/request-guard.ts`). A `file:` address on another computer (`file://server/share`) stays refused.
- **Stopping processes (done):** Windows has no process groups or `ps`. `signalGroup` and `killProcessTree` (`apps/server/src/terminal/process-group.ts`) end a whole tree with `taskkill /T /F`, and the process table and a process's start time come from `Win32_Process` through PowerShell. Checks, pushes, clones, agent terminal tabs and previews use it, so Stop and time limits work, and a leftover installer is ended only when its start time matches the recorded one.
- **Default shell (done):** shell tabs, `spark_terminal_run` and previews start Git Bash on Windows (`CLAUDE_CODE_GIT_BASH_PATH`, then Git under Program Files or the user's programs folder; `setup/default-shell.ts`), never a WSL `bash.exe`. The approval gate reads bash, so it can still judge what an agent runs there. A user's `SHELL` from Git Bash is ignored on Windows, since it is a POSIX path.
- **Secret and sign-in paths (done):** on Windows, the secret-file, sign-in folder, `.sparkignore` and protected-path checks read a backslash as a folder separator (`apps/server/src/projects/path-policy.ts`), so `C:\Users\me\.ssh\config` counts as sign-in details. macOS keeps a backslash as part of a name.
- **Claude path rules (done):** a project's `.claude/settings.json` path rule (`Edit(/src/**)`) is anchored in Claude's Windows form, `Edit(//c/work/app/src/**)` (`agent-config/permission-rules.ts`).
- **Login shell (done):** Windows has no login shell, so Spark asks none for `PATH` or the push environment (`setup/login-path.ts`, `desktop/src/shell-path.ts`). The packaged app keeps the `PATH` it was started with.
- **Company rules file (read done):** on Windows Spark reads `%ProgramData%\SparkOutpost\managed-settings.json`. Writing it through a UAC prompt is not built yet; the card says an administrator can edit the file. Checking that only administrators can write it is still to do.
- **Worktree `node_modules` (gap):** Windows has no clone-copy command, so a new worktree gets its packages from an offline install or a fresh install, not a copy of the main checkout's `node_modules`.
- **Git Bash process tree (done):** a command Git Bash starts can outlive the Windows process that launched it, so Spark also reads Git's own `ps` (`usr\bin\ps.exe`) and links each process to its Git Bash parent (`terminal/msys-processes.ts`). A shell tab then reports and stops what it started.
- **Privacy screen file (done):** saving it retries the rename while another save holds the file on Windows.
- **Shell tab commands (done):** the running command of a shell tab looks past Git Bash's `bin\bash.exe` wrapper to the shell it starts, and reads Windows program paths with spaces or quotes. Closing a tab ends its whole process tree before the console closes.
- **Chats with no project (done):** the check that keeps a chat with no project inside its own private folder compares paths in one form, so on Windows it no longer treats that folder as outside Spark's data folder (`approvals/crew-folders.ts`).
- **Codex sandbox paths (done):** Codex's permission profiles name folders (browser data, Sparks and workflows, a worktree's git data) as native Windows paths (`agents/acp/codex-permissions.ts`); macOS is unchanged.
- **Shell tab folder (done):** Git Bash starts with `CHERE_INVOKING=1`, so its login profile stays in the tab's folder instead of moving to the home folder.
- **Test temp folder:** the unit tests' temp sandbox sets `TEMP` and `TMP` as well as `TMPDIR` on Windows.
- **Folders in use (done):** Windows won't remove a folder a running shell is in, so "ends a shell when its folder is removed" can't happen there; Deleting a chat waits for its shells to stop before removing its worktree, and archiving keeps a worktree while a shell, agent terminal tab, Terminal session or preview is still open in it or a folder below it, comparing paths in Windows form (`persistence/folder-in-use.ts`). The crash-recovery installer test uses a POSIX script and runs only off Windows.
- **Git and keychain wording (done):** a missing Git points Windows at Git for Windows instead of Apple's command line tools (`gitInstallHint`), and the keychain wait names Windows Credential Manager.
- **Line endings:** the Windows CI job turns off `core.autocrlf` so tests that read files back see the committed bytes.

- **Desktop runtime connection:** on Windows the desktop app and its background service talk over a named pipe (`\\.\pipe\spark-outpost-runtime-<hash of the data folder>`) instead of a Unix socket (`runtime-handshake.ts`). The token and endpoint files stay in the private data folder, and every connection still proves it holds the token before anything else is sent, so the pipe's default access rules are not relied on. Finding a leftover service reads its command line through `Win32_Process` instead of `ps`, allowing for quoted paths (`runtime-retire.ts`).

## Phase 4 progress

- **Mark-of-the-Web (done):** a download the user saves gets a `Zone.Identifier` stream with `ZoneId=3` on Windows (`apps/desktop/src/browser/quarantine.ts`), as the Mac writes `com.apple.quarantine`; the Windows unit run writes and reads it back.
- **Hour cycle (done):** times follow the Windows short time format (`sShortTime` under `HKCU\Control Panel\International`: `H` is a 24-hour clock, `h` a 12-hour one), read with `reg.exe` from System32 at start and again whenever a Spark window gains focus (`apps/desktop/src/hour-cycle.ts`).
- **Unsigned installer (test only):** `pnpm desktop:package -- --platform win` (the default on Windows) builds a per-user NSIS installer for x64 (`apps/desktop/release/<version>/Spark-Outpost-<version>-windows-alpha-x64.exe`) with the app, server, web and Postgres, and none of the Mac helpers (tmux, Mac control, calendar, voice, no-activate). Postgres keeps its whole `bin` folder on Windows (its DLLs sit beside `pg_ctl.exe`, `initdb.exe` and `postgres.exe`), and node-pty keeps its `win32-x64` prebuild with ConPTY. `--release` is refused on Windows until Authenticode signing and a Windows update feed exist. The **installer** job in `.github/workflows/windows.yml` builds it, installs it silently, starts Postgres from the installed files, launches the installed app with a temporary data folder, uninstalls it, and keeps the installer as a 3-day CI artifact; it is never published.
- **Taskbar, tray and notifications (done):** on Windows the app sets its AppUserModelID to the channel's app id (the id the installer gives its shortcut), so notifications show and group under Spark Outpost; the waiting count shows as a red overlay dot on the taskbar button with the count as its description (`apps/desktop/src/app-badge.ts`), where the Mac sets the Dock badge; and the tray uses the colour app icon at 32 px, since the Mac's black template icon disappears on a dark taskbar. Windows builds say Alpha in the About panel and in Help and Updates, where the Mac says Beta.
- **Deep links (done):** the packaged app registers its link scheme with `setAsDefaultProtocolClient`, a link to a running app arrives through `second-instance`, and a chat link that starts the app is read from its launch arguments (`launchChat` in `apps/desktop/src/deep-link.ts`), where the Mac gets `open-url`.
- **Coming to Windows (started):** the desktop preload exposes the Mac control and Voice bridges only on macOS, so their Settings pages, the mic button and the island's voice entry are absent on Windows instead of reporting a missing helper. Terminal sessions show **Coming to Windows** in the session type menu and can't be chosen there, and the ticket dialog offers only a chat, until phase 5. The web reads the platform from `window.sparkDesktop.platform` (`onWindows()` in `apps/web/src/desktop/desktop-bridge.ts`).
