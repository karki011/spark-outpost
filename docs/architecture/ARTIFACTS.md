# Artifacts

An artifact is a page an agent makes for the user: HTML, Markdown or SVG. The user opens it beside the chat in the Work panel. Spark keeps every version. It runs sandboxed on its own origin and never reaches Spark, the network or the user's files. Built October 22, 2026, on top of the chat folders in [ACP_AGENTS.md](ACP_AGENTS.md).

## The tool

`spark_artifact` is a Spark action tool (`apps/server/src/spark-mcp/tools/artifact-tool.ts`). It is offered to every chat turn that may use action tools, project or not, and to Terminal sessions through the API's Spark tools host, on the same action path as the other Spark action tools there (not yet tried in a live Terminal session). It is not offered to Ask Spark or to read-only scopes.

| Action                           | What happens                                                                                                                                 |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `publish {title, kind, content}` | Starts a new artifact at version 1                                                                                                           |
| `update {id, content, title?}`   | Adds the next version of an artifact in this chat                                                                                            |
| `read {id, version?}`            | Returns a version that was shown in this chat (the latest by default), as stored. It is Spark's own data about the chat, so it asks nothing. |

`publish` and `update` follow the agent's mode like other Spark action tools (`publish_artifact`, `action-policy.ts`). They run at once in Auto, Bypass permissions, Auto review and Full access, and in Accept edits when the user's message asked for a page, chart, dashboard or similar. Otherwise they show a card with the title, kind, version and size.

Before the card, the content is checked and stored:

- **Boundary checks:** the content is at most 2 MB of UTF-8 (`ARTIFACT_MAX_BYTES`), an SVG must be one `<svg>` document, and the title is cleaned to 120 characters.
- **Scrubbing:** the content is scrubbed of saved sign-in values for the chat's project and of values from the secret files in the chat's projects and its own folder, as the browser tools do.
- **Storage:** it is written once (`wx`, 0600) to `<data>/<channel>/chats/<chat>/artifacts/<id>/<version>`, beside the chat's work folder and never inside it, so the safety floor keeps the agent from changing it. Each version gets a row in `artifact_page_versions` (migration 0204) with its sha256 and a random 256-bit view key.

The version is shown, and gets `published_at`, only when the action runs. A declined card leaves an unshown version that nothing serves, and keeps its number, so the picker can skip one (v1, v3). The audit holds the action with the artifact id, version, size and sha256, never the content. Deleting the chat removes the folder, and the rows go with the chat.

## MCP Apps and ACP mapping

The tool result is a text block and an MCP `resource_link` describing the artifact as an MCP Apps resource:

- `uri`: `ui://spark/<chat>/<id>`
- `mimeType`: `text/html;profile=mcp-app` for HTML, `text/markdown` or `image/svg+xml` otherwise
- `_meta.ui.csp`: `{ connectDomains: [], resourceDomains: [], frameDomains: [] }`, with `prefersBorder: true`

This follows [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp) and the [ext-apps draft](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/draft/apps.mdx). Spark's MCP server does not serve `resources/read` for these URIs; the agent reads a version with `read`. Spark renders no other server's `ui://` apps, and nothing in an artifact can call tools: there is no `window.claude` and no postMessage bridge.

An ACP `resource_link` in a tool call's content or in the agent's message whose URI parses as `ui://spark/<chat>/<id>` becomes an `artifact_link` output (`agents/acp/artifact-links.ts`). The worker turns it into an `ACTIVITY_SNAPSHOT` of type `artifact` only when the artifact belongs to the chat (`artifacts/activity.ts`). The tool also appends that activity itself when it shows a version, and the activity refreshes the chat.

The card under the turn is drawn from Spark's own record (`artifactPages` in the chat detail, per version's run). It never uses a title or kind the agent put in a link.

Whether the pinned adapters pass an MCP `resource_link` through to ACP tool call content has not been checked against a live Claude or Codex session. The fake agent does (`fake-acp-spark.ts`), and the card does not depend on it.

## Where it renders

The Work panel gets a third tab beside Work and Browser while an artifact is open. It has the title, a version picker, **Copy**, **Save as…**, **Share…** (see [Sharing](#sharing)) and **Close artifact**.

- **HTML** runs on its own origin, `http://127.0.0.1:<API_PORT + 10000>`, or `API_PORT - 10000` when the sum is above 65535 (`artifactPortFor`, worked out the same way by the server, Vite and the Mac app). This is a separate loopback server in the API process (`artifacts/origin-server.ts`) that serves only `GET /v/<view key>` for a shown HTML version. If its port can't be bound, the API logs it and runs on: the view has no address and the tab says the page can't be shown; Markdown, SVG, Copy and Save as… still work.
- **Markdown** renders in the app with the chat's Markdown renderer, which shows no raw HTML, images or non-web links.
- **SVG** renders as an `<img>` from a `data:` URL, so its scripts never run.

The artifact origin:

- Answers only `Host: 127.0.0.1:<port>`, `GET` only.
- Checks the stored sha256 on every serve. A changed file is not served.
- Sets no cookies and asks for no launch token, so it has nothing that reaches Spark's API.
- Sends `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; media-src data: blob:; connect-src 'none'; frame-src 'none'; child-src 'none'; worker-src 'none'; object-src 'none'; form-action 'none'; base-uri 'none'; sandbox allow-scripts; frame-ancestors <the app's origins>`.
- Also sends `nosniff`, `no-referrer`, a Permissions-Policy that turns off camera, microphone, location, clipboard and the like, and `no-store`.

The app's frame is `sandbox="allow-scripts"` with no `allow-same-origin`, so the page has an opaque origin. The app's own CSP gains `frame-src 'self' <artifact origin>` (`appContentSecurityPolicy`, built per launch from the API port in the server and in Vite).

The Mac app adds four guards (`apps/desktop/src/artifact-frames.ts`):

- The artifact port is in the Browser pane's blocked ports.
- A subframe of a Spark window may load only artifact pages (`will-frame-navigate`); every other navigation is refused, and the app's `frame-src` already stops one to another site in the renderer.
- A request from the artifact frame never gets the launch token added.
- Downloads and permission requests from the artifact origin are refused.

### Links

The artifact origin puts one script before the page (after a leading doctype, `artifacts/link-clicks.ts`). On a real click (`isTrusted`) of an `http(s)` link that the page did not handle itself, whatever its `target`, it stops the click and moves the frame to `/open?to=<address>` on the artifact origin. The Mac app catches that navigation (`artifactLinkRequest`, `guardSubframes`) and:

- refuses it unless it comes from an artifact frame, within 1 second of a real mouse-up (`before-mouse-event`) or Enter or Space (`before-input-event`) in that window, with no other link question open; one click allows one question;
- reads only `http(s)` addresses without a user name or password, shown as the parsed address (punycode for other scripts);
- shows a dialog naming the address, **Open in Spark** or **Open in Browser** (by **Open links in**) or **Cancel** (the default), and only then opens it through the shell's `openLink`, so it follows **Open links in** ([BROWSER.md](BROWSER.md#the-shells-chokepoint)); an address on the API origin still goes to the external-link path, never a viewer window with the launch token.

A page script cannot open anything on its own: popups are blocked by the sandbox, a direct navigation is blocked by `frame-src`, and an `/open` request without a real click in the last second is dropped. A script that runs at the moment the user clicks somewhere in the window can still ask, but only the dialog, with the address in it, opens a link. The origin itself answers `/open` with 404, so outside the Mac app (a browser in development) a link opens nothing. On paired devices the `page` route gets no script: links there behave as the device's browser treats a sandboxed frame.

**Save as…** fetches `GET /api/artifacts/:id/versions/:version/file` (an attachment, `default-src 'none'; sandbox`) and saves it with the shared `ExportButton`, as the audit export does. **Copy** copies the stored text.

## Sharing

**Share…** uploads one shown version to Spark's share service, a Cloudflare Worker in `infra/share-worker/`, and gives the user a link anyone can open in a browser. Only the user's own click on the Mac shares: there is no agent tool, no Ask Spark action, and every route is `never` for paired devices, where the button is hidden.

- **Configuration:** the service origin is build configuration, as the heartbeat is. `SHARE_URL` in `apps/desktop/scripts/builder-config.ts` is empty; `SPARK_SHARE_URL` sets it per build and lands in the packaged `package.json` as `shareUrl`. The Mac app hands it to the API as `SPARK_SHARE_URL` (`share-url.ts`), which dev and tests set directly. It must be an https origin with no path, query or login, or http on loopback (`shareServiceOrigin` in contracts). Without it the status route says unavailable and the button is not shown; a link made earlier still shows, and Stop sharing and the sweep still work, because they use the origin in the share's own stored `url`. `--release` refuses an http loopback origin.
- **What is sent:** the stored version file, read with its sha256 checked (`readVersionFile`), only for a version with `published_at`. HTML goes as is. SVG goes inside a minimal page that shows it as an `<img>` from a `data:` URL, so its scripts never run; the wrapped page must still fit 2 MB. Markdown is not shared: the server has no renderer that matches the app's, so the button is off with a reason. Before the upload the stored text is checked again with the publish scrubbers (`share-scrub.ts`: the project's saved sign-ins, and the secret files in the chat's projects, worktrees and own folder). A page that now holds such a value, for example one added to a secret file after the page was made, is refused with a reason and nothing is uploaded; an unreadable keychain refuses too.
- **The call:** `POST <origin>/v1/shares` with `{ id, deleteToken, title, html, expiresInDays, passcode?, theme? }` and only `content-type`, `redirect: 'error'` and a 20-second timeout (`share-service.ts`). Spark makes the delete token (32 random bytes, base64url) and derives the id from it (`share-id.ts`: base64url of the first 16 bytes of SHA-256 of `spark-share-id:` + token; `ARTIFACT_SHARE_ID_PATTERN`, `ARTIFACT_SHARE_ID_DOMAIN` and `ARTIFACT_SHARE_DELETE_TOKEN_PATTERN` in contracts), so it can take a page down even when the answer is lost. The upload has no account, and the worker refuses with 400 any create whose id is not the one its token gives, so only the holder of a share's key can ever store a page at its address, and a link that stopped working can never show someone else's page. The service answers 201 `{ id, url, expiresAt }`, again 201 for a repeat of the same id and token while that share is live, and 409 for an id its owner deleted or asked to delete (the worker keeps an empty `gone/<id>` marker for good, which only that key can write for an id with nothing stored; it stops the owner's own late upload). The answer is checked: the id Spark sent, an ISO expiry and exactly `<origin>/a/<id>` as the `url`. Any non-201, a timeout or a bad answer is a one-line error in the sheet.
- **Theme:** the pane reads the current skin's computed colours (`share-theme.ts`: background, panel, text, muted, strong line, accent and its ink, success, danger, raise) as `#rrggbb` plus `light` or `dark` from the background, and sends them as `theme`; the route validates them with `artifactShareThemeSchema` and the worker again, so only plain colours reach its pages. The unlock, Verified, report and viewer strip pages use them whatever the viewer's own system look is; a share without a theme, or with a colour the pane couldn't read, gets the worker's neutral light and dark look. The theme is stored with the page on the share service, never in Spark's database or audit.
- **Passcode:** **Require a passcode** (off by default) makes 8 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` with `crypto.randomInt` on the server, sent bare and shown as `XXXX-XXXX`. It is in the create response once (`no-store`) and in the sheet's state, never in a row, the query cache, the audit, an event or a log.
- **Storage:** `artifact_page_shares` (migration 0257) holds share id, artifact id, version, `state` (`pending` or `live`), url, `expires_at`, `has_passcode` and `created_at`, one row of either state per version. It has no foreign key, so it outlives a deleted version, artifact or chat as an orphan for the sweep below. The delete token is a keychain item (`share:<id>`), deleted when the page is gone. Only a live row reads as shared; a row whose `expires_at` has passed reads as not shared and is cleared when that version is shared again or by the sweep.
- **Create order** (`shares.ts`): make the token and the id it gives, save the token in the keychain, insert the row as `pending` (its `expires_at` is the chosen days plus an hour, so it outlasts the service's own expiry), upload, then in one transaction mark the row live with the service's expiry and write the audit entry. If anything fails after the row exists, including the audit entry, Spark sends one `DELETE` and the user sees the error: a 204, or a 404 after a definite answer, removes the row and the token. After a timeout or an unreachable service the lost upload may still land, so only a 204 or a 404 with the header `x-share-final: 1` (`ARTIFACT_SHARE_FINAL_HEADER`: no page is stored at the id and none can arrive from that key) removes them; a 404 without it is not trusted, and an unconfirmed page keeps its pending row and token for the sweep. A pending row never shows as **Shared**. A new Create for a version whose pending row is younger than a minute is refused ("still removing an earlier try"); an older one is taken down first, claimed as the sweep claims it. Each try makes a fresh key and id; a row's old pair is never uploaded again.
- **One link per version:** a second Create for a live version answers 409 with `{ error, share }` and no passcode; the pane opens the Shared sheet for that link with "This version is already shared. Stop sharing to make a new link with different settings." and updates its cached status. An identical Create that arrives while the first uploads gets the same answer with no second upload; a different one waits and then gets the 409. Another version gets its own link.
- **Stop sharing:** `DELETE <stored origin>/v1/shares/:id` with `authorization: Bearer <token>`, where the origin is the one in the row's `url` (checked with `shareServiceOrigin`), never the configured one: after `SPARK_SHARE_URL` changes, or in a build with none, the request still goes to the service that holds the page, and another service's 404 is never asked for. A stored `url` with no usable origin is a one-line error and keeps the row. A 204 or 404 removes the row, writes the unshare audit entry and then deletes the token. Any other answer or an unreachable service is a one-line error, and a missing keychain item says Spark can't remove the page and that it ends on its end date. In each case the row stays, the pane keeps showing **Shared** with its link and nothing is audited; the sweep clears the row at `expires_at`.
- **Sweep:** `sweepShares` (`shares.ts`) runs with the startup and hourly prune (`startup-prune.ts`, after empty chats and builder chats) and once, without waiting, after `DELETE /api/conversations/:id`, one sweep at a time (a request during a sweep runs one more after it). A row past `expires_at` loses its keychain item and then the row, with no call (the service has already removed the page). A live row whose artifact version no longer exists, however it was deleted (the delete route, reset, crew and test-run chats, empty-chat pruning, builder chats), is taken down: a 204 or 404 deletes the row and then the keychain item; any other answer, an unreachable service or an unreadable keychain keeps both for the next sweep. A pending row older than a minute is claimed first (`takeDownPending`): one transaction locks the row while it is still `pending`, sends the `DELETE`, and deletes the row, so marking it live waits for that transaction. If the create finished first the row is live and the sweep leaves it alone; if the sweep won, the create finds no pending row, answers "The link could not be saved" and sends its own `DELETE`. For a pending row only a 204 or a 404 with `x-share-final: 1` counts: the worker sends that header when it has retired the id for its own key (an upload that lands later is refused with 409) or when the key does not give the id (an upload of that pair is always 400). A 404 without the header, which is what a worker older than the header answers and such a worker may not retire ids, keeps the row and the key and is asked again each sweep until `expires_at`, after which no page can remain; until then a new Create for that version is refused ("still removing an earlier try"). A 429 (the worker limits retiring ids with nothing stored to 60 per hour per address) is any other answer: kept for the next sweep. Rows made before ids were derived (random ids) need no migration: a live one is deleted by its stored token hash as before, and for a pending one with nothing stored the worker's 404 has the header, since the worker refuses any upload to an id its key does not give. An orphan or pending row whose keychain item is missing is kept until `expires_at`, since nothing can take its page down before then. Takedowns go to each row's stored origin, whatever origin is configured now.
- **Audit:** `spark/artifact_share` and `spark/artifact_unshare` entries on the version's run (or the chat's latest run) with artifact id, version, size, sha256, share id, expiry and whether it has a passcode. The link is not recorded: it opens the page, unlike a pull request address. Never the content, the passcode or the token.
- **What a shared page can reach:** the worker shows the page in an `<iframe sandbox="allow-scripts">` on its own shell page. The content's policy has no `connect-src`, forms, frames or workers, and the sandbox blocks popups and navigating the tab. A script can still navigate its own frame; the shell's `frame-src 'self'` stops that for any address outside the worker before a request is sent (checked in Chromium with a local copy of both policies; Firefox and Safari were not run), so inside the viewer a page has nowhere to send what it shows. There is no CSP directive for a document's own navigation (`navigate-to` was dropped from the standard), so a content address opened as a tab of its own could navigate away. The worker therefore serves `/content` only to a frame: a request whose `Sec-Fetch-Dest` is present and not `iframe` gets the 404 page. A browser too old to send that header (before Safari 16.4, Chrome 80, Firefox 90) is not covered, and there only for someone who copies the frame's address out of the shell within its 60 seconds. As on a paired device, WebRTC is outside CSP.

## Paired devices

**Open artifacts** (Remote control, off by default) allows `GET /api/artifacts/:id/versions/:version/view` and `/page`. The page route serves the same HTML with the same policy and `frame-ancestors 'self'`, in the same sandboxed frame. The `file` route is `never`.

On a phone the frame is on the Serve origin, still opaque. A device's browser has no Electron guard, so a script's own navigation or WebRTC (which CSP does not cover) could send data from the page off the device. The page holds only what the agent wrote, scrubbed of secret values, and no Spark data. With the switch off the tab says it is turned off.
