# Repo agent configuration

How Claude and Codex use a linked repo's own agent setup (instructions, skills, commands, subagents, hooks, MCP servers) without letting the repo loosen Spark Outpost's rules. Checked September 28, 2026 against `@agentclientprotocol/claude-agent-acp` 0.81.2 (Claude Agent SDK 0.3.280, Claude Code CLI 2.1.280) and `@agentclientprotocol/codex-acp` 1.13.1 (Codex 0.156.1, patched); Spark's own tools section checked September 30, 2026.

## Trust

A project folder with hooks, allow rules, MCP servers or key and traffic settings gets a "Trust this folder?" decision, like Claude Code's trust prompt. It is asked once: the context bar shows a small "Trust this folder?" button next to Agent setup until the user trusts the folder or picks "Not now". Both choices are stored; "Not now" and "Stop trusting" leave the folder untrusted and stop asking, and the folder can be trusted later from the popover.

- **Trusted**: hooks, every MCP server in `.mcp.json` and the allow rules below load as the repo configured them, without per-item switches. They go through our own settings layer, never `settingSources`: hooks as flag `settings.hooks`, MCP servers as ACP `mcpServers` (each tool still asks, `mcp__<server>` ask rule), allow rules as `RepoRootLaunch.allowRules`, which `claudeSessionMeta` puts in flag `permissions.allow`. The safety floor stays: secret-file deny rules, the publish deny rules (`CHAT_RUN_DENY_RULES`), `blockReadsOutsideWorkingDirectories`, the floor's ask rules (`floorAskRules`), the WebFetch and Monitor ask rules, and audit.
- **Allow rules that are never applied**, even when trusted, shown as "Not applied: <reason>" (`agent-config/allow-rules.ts`): plain `Bash`, `Edit`, `Write`, `MultiEdit`, `NotebookEdit` or with `*`, `**`, `:*`; Bash rules that match `git push`, `git remote add/set-url/remove/rm/rename`, `git send-email`, `git request-pull`, `gh`, `hub`, `glab`, `tea` or a prefix of one (`Bash(git:*)`); Bash rules that start with a shell or wrapper (`bash`, `sh`, `sudo`, `env`, `xargs`, `eval`, …), chain or redirect commands, or have a wildcard before the end; `Read` rules naming secret files (`.env`, `*.pem`, `id_rsa`, …); edit rules outside the project (`/`, `~`, `..`) or on secret files.
- **Approval gate**: Claude checks deny, then ask, then allow; Spark adds no blanket Bash, Edit or Write ask rule (`claudeSessionMeta` in `agents/acp/agents.ts`). `commandAllowlistFromRules(rules)` turns the applied Bash rules into project command-allowlist entries (`Bash(npm test:*)`, `Bash(npm test)` and `Bash(npm test *)` all become `npm test`, which `allowlistCovers` matches for `npm test` plus arguments, never chained commands). `Bash(npm test)` is an exact match in Claude but a prefix in our allowlist.
- **Fingerprint**: trusting stores a fingerprint of the hooks, allow rules and MCP servers, and a snapshot of each item. When the repo's set changes (for example after a pull), the folder counts as not trusted for these parts until the user trusts it again; the popover and context-bar button say "Folder setup changed" and list added, removed and changed hooks, allow rules and MCP servers. Instructions, skills, commands and subagents follow their own switches whether trusted or not.
- **Key and traffic settings** are never applied by trusting alone. The "Keys and traffic" card lists them (values of key, token, auth and header variables are hidden) and has its own switch, available only while the folder is trusted. Turning it on stores a fingerprint of the list with values; any change turns it off. When on, Claude sessions get exactly those `env` keys as flag `env` and those helper commands (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`, `otelHeadersHelper`, `proxyAuthHelper`), primary repo first. Other `env` keys are still ignored. Step 1 shows why: the CLI hot-reloads `.claude/settings.json`, which `settingSources: []` still avoids because we pass a copy.
- **Codex**: trust gives Codex the `.mcp.json` servers. `.codex/config.toml` is still ignored (its MCP servers aren't parsed) and codex-acp still marks session roots untrusted; key and traffic settings don't apply to Codex.
- **Audit**: `agent_config_audit` rows with subject `trust` (granted: fingerprint, hook lines, MCP names and fingerprints, applied and dropped allow rules; withdrawn: previous fingerprint and `revoked` or `declined`) and `redirects` (fingerprint and the setting names).
- **Revoke**: "Stop trusting" in the popover, or Settings → Projects, which lists every linked folder as Trusted, Not trusted or Not asked yet.

## Step 1: what loading the project settings source would do (Claude)

Method: a fake Anthropic API on 127.0.0.1 records every request the real CLI makes (system prompt, tools, auth header) and answers with canned text or tool calls, so no tokens are spent. A trap repo holds each file type plus hooks, `apiKeyHelper`, `statusLine`, `otelHeadersHelper`, `awsAuthRefresh`, `env` (including `ANTHROPIC_BASE_URL` pointing at a second recording server and `BASH_ENV`), `permissions.allow: [Bash, Edit, Write, Read]`, `defaultMode: bypassPermissions`, `additionalDirectories` outside the repo and a `.mcp.json` server. Every command touches a marker file. The real `claude-agent-acp` is driven over ACP with our session `_meta`. Scripts are not committed (they lived in `.local/verify/`).

| Question                                                                                      | Result with `settingSources: ['project', 'local']`                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Loads CLAUDE.md, CLAUDE.local.md, skills, commands, subagents?                                | Yes, all five appear in the first model request. Nested `sub/CLAUDE.md` does not (it loads lazily). AGENTS.md is not read.                                                                                                                                      |
| Does flag `disableAllHooks: true` win over the repo's `disableAllHooks: false` and its hooks? | Yes. No project or local hook ran. The adapter's own SDK callback hooks (`PostToolUse`, `UserPromptSubmit`) still fired.                                                                                                                                        |
| Permission merge                                                                              | Our flag `ask: [Bash, Edit, Write]` still asked for Bash and Write despite the repo's `allow` rules and `bypassPermissions` default (deny, then ask, then allow). `blockReadsOutsideWorkingDirectories` refused a read into the repo's `additionalDirectories`. |
| Command-executing settings                                                                    | **`apiKeyHelper` ran.** Flag `apiKeyHelper: ""` stops it. `statusLine`, `otelHeadersHelper` and `awsAuthRefresh` did not run in these sessions.                                                                                                                 |
| Project `env`                                                                                 | **Applied.** `ANTHROPIC_BASE_URL` sent every model request, with our API key, to the second server. A flag `env` entry overrides a key it names, but keys we don't know about reach the CLI and Bash.                                                           |
| Mid-session changes                                                                           | **The CLI hot-reloads `.claude/settings.json`.** An env key added after the session started reached the next Bash command.                                                                                                                                      |

Because a repo's `env` can't be neutralized (unknown keys, hot reload), `settingSources` stays `[]` and `strictMcpConfig` stays on. Instead:

- Instructions go through `_meta.systemPrompt.append`, with a header saying they are repository content that can't grant permissions. Verified: appended text reaches the system prompt.
- Skills, commands and subagents go through the SDK `plugins` option, pointing at a generated plugin folder under `$TMPDIR/spark-outpost-repo-plugins/<content hash>` (`agent-config/plugin-dir.ts`). Frontmatter is reduced to an allowlist, so `allowed-tools`, `hooks`, `mcpServers` and `permissionMode` are dropped. Verified: all three appear, namespaced as `<repo>:<name>` (for example `/app:greet`).
- `disableSkillShellExecution: true` is always set. Verified: a command's `` !`touch …` `` became "[shell command execution disabled by policy]".
- Hooks off: `disableAllHooks: true`. Hooks on: the reviewed hooks object goes in flag `settings.hooks`. Verified both: flag hooks ran; with `disableAllHooks` they didn't.
- MCP: enabled servers go in ACP `session/new` `mcpServers`, plus an `ask` rule `mcp__<server>`. Verified with a local stdio echo server: each call to its tool raised `session/request_permission` in both Ask and Do sessions, even without the rule. Ask declines every request; Do sends it to the approval gate, where an MCP call is an `other` action: it asks unless the agent's mode lets everything through (Auto, Bypass permissions, Approve for me, Full access); Don't ask refuses it, and "allow for this run" covers that tool only.

Also noted: the adapter's own `SettingsManager` reads the project's `permissions.defaultMode` whatever `settingSources` says (escalating modes are filtered). This predates this change; we set the mode explicitly and a run stops if the mode changes unsafely.

## Turning agent tools off

Checked October 22, 2026 against the same adapter and SDK versions, with the SDK driving the real CLI against a scripted Anthropic API on `127.0.0.1` (no tokens spent).

Spark gives agents their own tools and leaves turning them off to the files users and companies already use for Claude Code and Codex. There is no Spark setting for it.

- **Claude tools.** `agents/acp/claude-tools.ts` lists every built-in tool the pinned SDK declares (`sdk-tools.d.ts`) as on for a turn kind (AskUserQuestion in every session, for its question cards), repo-dependent (Skill, Agent) or off with a reason; `claude-tools.test.ts` fails on an unclassified name. Off tools are also in `disallowedTools`, so a subagent's own `tools` list can't bring one back. ScheduleWakeup is on in chat turns, since Spark keeps the turn open until the wakeup (see [Sleeping until a wakeup](PROTOCOL_ALIGNMENT.md#sleeping-until-a-wakeup-october-22-2026)), and not in the no-project tool list Ask Spark's hidden chat uses. Off: EnterWorktree and ExitWorktree (they move the session out of the place Spark chose, and `remove` deletes a branch), CronCreate/Delete/List, RemoteTrigger, Workflow and ProposeGoal (work outside a turn, or a re-prompting loop Spark's run state doesn't see), PushNotification, Artifact, ArtifactComments, ArtifactData, DesignSync, ClaudeDesign, Projects, ReadNotifications, SendFeedback (claude.ai and Anthropic services: sends outside Spark's rules), SendMessage and ListAgents (they reach other Claude sessions, through Anthropic's servers for other machines), ProposeSkills (writes outside the project) and ShowOnboardingRolePicker. TodoWrite no longer exists in CLI 2.1.280; the Task* tools replace it and the adapter shows both as the plan.
- **Tools the adapter shows as `other`.** claude-agent-acp has no case for NotebookEdit and Monitor, so `approvalRequestFrom` reads the tool name (`toolCall.name`, or `_meta.claudeCode.toolName`): a NotebookEdit is an edit of `notebook_path`, a Monitor with `command` is a command, and a WebFetch `url` or a Monitor `ws.url` is the request's `address`. The rail watch uses the same function, so flag-after sees them too. Claude Code checks a Monitor command against the Bash rules (a `Bash(git push:*)` ask and a `Bash(npm publish:*)` deny both caught one in Bypass permissions), but its socket form asked nothing in Bypass permissions, so `WebFetch` and `Monitor` are session ask rules: with them, the CLI raised `canUseTool` for each call in Bypass permissions. Without the WebFetch rule, a WebFetch to `http://127.0.0.1:1` was attempted in Bypass permissions (`ECONNREFUSED`).
- **Web addresses.** `approvals/web-address.ts` refuses, in every mode, a scheme other than http(s) or ws(s), an address with a login in it, and this computer: `localhost`, `*.localhost`, `*.test`, `127.0.0.0/8` (the URL parser turns `127.1`, `2130706433` and `0x7f.0.0.1` into `127.0.0.1`), `0.0.0.0`, `[::]`, `[::1]` and IPv4-mapped loopback. A value from a project secret file in the address, plain or percent-encoded, asks with hold-to-confirm (`secretSend`), and the gate then works from a copy of the request with the address cut to its origin and every secret value (plain or percent-encoded) redacted from the title, the agent's reason and every other field, so no card, note, step, audit entry or event stores it. A second layer of `WebFetch(domain:…)` deny rules (`localhost`, `*.localhost`, `*.test`, `127.0.0.1`, `0.0.0.0`, `[::1]`, `[::]`) is checked by the CLI itself; it matched `http://127.1/`, `http://[::1]/` and `http://LOCALHOST/`. A public name that resolves to 127.0.0.1 is not caught; Spark's API still needs the launch token.
- **Reading turns.** Ask and Plan turns sent only commands to the gate and declined everything else; WebFetch, WebSearch and Monitor now reach the gate there too (`readingTurnReviews`), which follows the mode. They are offered only in turns that have the gate (`CLAUDE_GATED_TOOLS`), so a reading turn without one isn't handed a tool every request of which would be declined.
- **Web reads.** A completed WebFetch, WebSearch or Codex web search item records a `web_page` observation (`web page <origin>` or `web search`, `agents/acp/web-reads.ts`) in every turn, chats included, so later sends carry the note as after `spark_browser_read`. Claude names a WebFetch before its address streams in, so `session-updates.ts` holds that step until the address arrives and names it `Fetched <host>`; a web search is `Searched the web`. Live, October 22, 2026 (Haiku, Manual, a real Do turn with Spark's gate): the search ran after the gate allowed it, `https://example.com/` showed as `Fetched example.com` and recorded `web page https://example.com`, `http://127.0.0.1:9` was stopped by the CLI's domain deny, and `http://127.0.0.2:9` reached the gate and was refused (`apps/server/test/web-tools.live.test.ts`).
- **User and project rules.** `agent-config/permission-rules.ts` reads `$CLAUDE_CONFIG_DIR/settings.json` (default `~/.claude/settings.json`) and each opened root's `.claude/settings.json` and `.claude/settings.local.json`, takes only `permissions.deny` and `permissions.ask` (strings shaped like `Tool` or `Tool(spec)`, up to 512 characters and 200 per list per file), and anchors a file rule's `/path` to that file's folder (`//<root>/path`), since the CLI anchors `/path` to the settings file's root while Spark passes the rules as flag settings anchored to the session's cwd. `turn-launch.ts` loads them for Claude and Z.ai turns and puts them in the connection key; `claudeSessionMeta` puts the deny rules first in `disallowedTools` and `permissions.deny`, the ask rules first in `permissions.ask`, then Spark's own. Env, hooks, `apiKeyHelper`, allow rules and every other key of those files stay unread, so the key-safety findings in Step 1 still hold. Deny and ask rules only take away, so they apply whether the folder is trusted or not and are not part of the trust fingerprint. The Agent setup popover no longer lists them as ignored.
- **Managed settings.** The CLI loads the policy tier (`/Library/Application Support/ClaudeCode/managed-settings.json`, its drop-in folder, MDM and server-managed settings) with `settingSources: []`: the SDK's `resolveSettings` documents it and `managed-settings.test.ts` checks it with the SDK's `managedSettings` input. `CLAUDE_CODE_MANAGED_SETTINGS_PATH` is compiled out of this CLI build, so there is no path override for a test; the manual check is to put `{"permissions":{"deny":["WebSearch"]}}` in that file and see WebSearch missing from a Do turn's tools. Probe: a policy-tier `deny: ["WebSearch"]` removed WebSearch alongside Spark's flag deny of Monitor. With `allowManagedPermissionRulesOnly: true`, the CLI drops Spark's flag `permissions.ask` and `permissions.deny` (a protected-path or WebFetch ask no longer reaches the gate) but keeps `disallowedTools`, so Spark's deny rules (secret-file edits, force pushes, the publish commands, the local WebFetch domains) hold. That is the company's choice; Spark doesn't detect it.
- **Codex.** `CODEX_CONFIG` becomes codex-acp's `thread/start` config, layered over the user's `$CODEX_HOME/config.toml` and the managed config, so a key Spark doesn't set comes from them. Spark no longer sets `web_search`; Codex's own default or the user's or company's value applies. Spark still sets, for its floor: `features.shell_tool` (off in chats), `features.unified_exec = false` (unified exec keeps a shell open and `write_stdin` types into it with no new approval request, which the gate would never see), `features.skill_mcp_dependency_install = false`, `features.apps = false`, `default_permissions` and the permission profiles, `mcp_servers` (the user's own turned off, Spark's added), the project trust patch, and, only when the user turned a repo switch off, `project_doc_max_bytes` and `skills.include_instructions`. Approval and sandbox are sent per turn from the agent's mode. Not checked live: whether Codex sends its web search tool by default in a read-only session (a scripted Responses API saw no tools in Codex's first request).

## Discovery

`agent-config/discovery.ts` lists, per repo root, instruction files (root files by name, nested ones from `git ls-files`), skills with frontmatter name and description, commands (`ops/deploy.md` becomes `ops:deploy`), subagents, hooks (event, matcher, command preview, source file), MCP servers (name, transport, command and args or URL, env and header names) and ignored settings (allow rules, env names, command settings, other keys, `.codex/config.toml`). Files are only read and parsed, never run; files over 256 KB are skipped; bad JSON becomes a warning. Results are cached per root by `git HEAD` plus the path, mtime and size of every candidate file, so a new untracked nested `AGENTS.md` shows up once HEAD or a watched file changes.

## Storage (migration 0047)

- `project_agent_settings`: per project, `instructions`, `skills`, `commands`, `subagents` (default true) and `hooks_fingerprint` (null means off). Hooks count as on only while the repo's current hooks hash to that fingerprint.
- `mcp_servers`: `source` (`project`, `user` or `imported:<tool>`), `project_id` (required for `project`, never set otherwise), name, transport, a config snapshot with env and header names but no values, and a fingerprint of the full config. Project servers are scoped to their project and never listed globally.
- `mcp_server_enablements`: per server and scope (`global`, `project`, `chat`) with the reviewed fingerprint. Repo servers use `project` scope; user-level servers use all three (see [User-level MCP servers](#user-level-mcp-servers)). Migration 0053 adds `mcp_servers.last_check` (the last connection test) and an index on scope.
- `agent_config_audit`: every switch change, with the hook commands or MCP config that was approved, plus trust and key-and-traffic decisions.
- `project_trust` (migration 0052): per project, `trusted`, the executable-config `fingerprint` and item `snapshot` at trust time, `redirects_fingerprint` (null means key and traffic settings are off) and `decided_at`. A row with `trusted = false` records "Not now" or a revoke.
- `runs.followed_instructions`: the files a run was given, shown as "Following: …" in the turn header.

MCP env values like `${HOME}` are expanded from the server's environment with secret-looking names removed (`childEnvironment`), so `${GITHUB_TOKEN}` expands to an empty string.

## Launch

`workflow/agent-turn.ts` calls `loadRepoLaunch` with the chat's project roots. Settings are matched to roots by the chat's project order, so a chat worktree in place of the first root uses the first project's switches; its MCP servers and hooks still have to match the approved fingerprints. `acp-provider.ts` turns the launch into Claude `_meta` (`claudeSessionMeta`) or Codex `CODEX_CONFIG` (`codexConfig`) and the `mcpServers` list.

## UI

The context bar's sliders button ("Agent setup for <project>") opens a popover with cards for instructions, skills, commands, subagents, hooks (with command previews and a warning), MCP servers (per-server switches, command or URL, env names, warning) and ignored settings. A dot marks the button when something found is off, changed or unreadable. When trust is needed, the popover starts with a trust card, and cards for allow rules and key and traffic settings follow the hooks and MCP cards. Settings → Projects lists trust per folder with "Stop trusting". Focus stays inside while open; Escape returns focus to the button.

## User-level MCP servers

Servers that belong to the user rather than a repo: added by hand or from a pasted config in Settings → MCP servers, and turned on for all chats, per project or per chat.

### Did agents already load the user's global MCP servers?

Checked September 28, 2026 with the marker technique above: a temporary `HOME` and `CODEX_HOME`, a fake model endpoint, and MCP servers whose only job is to write a marker file when started. The real adapters were driven over ACP; the user's own config was never read.

| Agent  | Setup                                                                                       | Did the user-level server start?                                                   |
| ------ | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Claude | Our meta (`settingSources: []`, `strictMcpConfig: true`), `~/.claude.json` has `mcpServers` | No. The ACP server did.                                                            |
| Claude | Same, `strictMcpConfig: false`                                                              | No: with no user settings source, `~/.claude.json` servers are not loaded.         |
| Claude | Control: `settingSources: ['user', 'project', 'local']`                                     | Yes, so the check can see a start.                                                 |
| Codex  | `$CODEX_HOME/config.toml` has `[mcp_servers.*]`                                             | **Yes, at `session/new`, in every Codex chat and in the capability probe.**        |
| Codex  | Same, `CODEX_CONFIG` sets `mcp_servers.<name>.enabled = false`                              | No.                                                                                |
| Codex  | Same, plus one ACP server (unpatched codex-acp)                                             | **Yes**: the ACP servers replaced the `CODEX_CONFIG` table. Fixed by patch part 6. |
| Codex  | ACP server with the same name as a user-level one                                           | codex-acp drops ours and runs the user's (its dedupe filter).                      |

So Claude was already consistent; Codex was not. Now, for every Codex process (chats, the capability probe), `agent-env.ts` reads the names under `[mcp_servers]` in `$CODEX_HOME/config.toml` (default `~/.codex`) and sets each to `enabled = false` in `CODEX_CONFIG`; codex-acp keeps those entries next to the ACP servers ([PATCHES.md](PATCHES.md) part 6). A Spark server whose name clashes with one of them is renamed `<name>_spark`, so it is never dropped or merged with the user's entry. `APP_SERVER_LOGS` is removed from Codex's environment because codex-acp logs the full `thread/start` config there. We kept the user's `CODEX_HOME` rather than a harness-managed copy: Codex rotates refresh tokens in `auth.json` and keeps session rollouts there, so a copy would break sign-in and resume.

### Adding servers

Users add servers by hand in Settings → MCP servers, or paste a README-style JSON config into the add form, which fills the fields in the browser. Spark does not read other apps' MCP config files (Claude Code, Claude Desktop, Cursor, VS Code, Codex, Windsurf). Servers imported by an earlier version keep their `imported:<tool>` source and "From <app>" label; they can be tested, switched and removed but not edited. Project `.mcp.json` files are not shown here; they stay in each project's Agent setup.

The only user-level file Spark reads for MCP is `$CODEX_HOME/config.toml`, for the server names it turns off in Codex sessions (above).

### Secrets

The database keeps env and header names only (`config.envNames`, `headerNames`, plus `secretNames` for names with a stored value). Values live in the keychain under `KEYCHAIN_SERVICE`, one entry per server (`mcp:<server id>`, JSON of env and headers). The fingerprint of a user-level server covers name, transport, command, args, URL and value names, not values, so rotating a token needs no review. Values are resolved in the worker when the agent starts; `session/new`, `session/load` and `session/resume` audit entries have every MCP env and header value replaced with `[redacted:mcp_secret]`. Removing a server deletes its keychain entry.

### Scopes

A user-level server runs in a chat when the first switch found, in this order, is on and matches the current fingerprint: the chat's (`/mcp`), the chat's projects' (in link order), then all chats (`global`). Clearing a chat or project switch falls back to the next. Every change is written to `agent_config_audit` with the scope and the reviewed config (names, never values).

### Test connection

Settings → Test connection starts the server through the MCP SDK client with a 20-second limit, in a temporary working folder, with only the SDK's default variables (`HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER`) plus the server's own env, then lists its tools. HTTP and SSE servers get their headers. The result (tool names or a redacted error, with the fingerprint tested) is stored on the server. It is not an OS sandbox: the command runs with the user's permissions, which is why it only runs when the user clicks.

### Launch

`workflow/agent-turn.ts` loads the chat's enabled user servers (`mcp/launch.ts`) next to the repo launch; `acp-provider.ts` resolves their keychain values and puts them first in `session/new` `mcpServers`, followed by the repo's, with names made unique. Claude gets an `mcp__<name>` ask rule for each (in project chats), so MCP tool calls ask unless the agent's mode lets everything through, as above. HTTP and SSE servers are skipped with a note when the agent does not advertise them (Codex has no SSE). User servers also reach chats without a project, where every tool call is declined like any other action.

### /mcp

`/mcp` in the composer opens "MCP servers in this chat": each user-level server with its source, which switch decides it and its last test, a switch for this chat and Reset (back to the project or all-chats setting); the linked repos' servers read only, with their state; and "Manage in Settings".

## Spark's own tools (`spark` MCP server)

Every agent session Spark launches (chat, Ask, Do; Claude, Z.ai and Codex) gets a built-in MCP server named `spark`, read-only except for actions the user confirms on a card, so agents can answer questions about Spark itself.

- **Tools**: `spark_providers`, `spark_connectors`, `spark_settings`, `spark_projects`, `spark_map`, `spark_find`, `spark_chats`, `spark_chat`, `spark_audit`, `spark_tickets`, `spark_analytics`, `spark_activity`, `spark_brief` (`apps/server/src/spark-mcp/tools/`). Each reuses the functions behind the matching API route. These read tools carry `readOnlyHint: true` and change nothing, except that `spark_tickets` refreshes the same ticket cache the Tickets page refreshes.
- **Action tools**: `spark_create_ticket`, `spark_comment_ticket`, `spark_transition_ticket`, `spark_assign_ticket` (Jira and Linear through Spark's connectors) (pull requests need no card: an authorized agent calls `spark_push` and runs `gh pr create`, or `spark_pull_request` when `gh` is not signed in, and Spark records the PR from the output). They never act on their own: each inserts a `spark_action` approval with a preview of exactly what will change (source, project or ticket, current status or assignee, branch, base and files), the call waits for the user's answer, and only a confirm runs it. The user can edit the text fields first (title, description or comment, type, priority, labels, target status); edits are validated against the action's editable fields and stored in `approvals.edits` (migration 0073). There is no "Always allow", the scope is always once, levels never decide these cards, and assigning shows the current owner so taking someone else's ticket is explicit. Results go back to the agent (key and URL, PR URL and number, or "declined"), each action is written to the run's protocol log as `spark/<action>` (redacted), and ticket actions also to `ticket_events` (new action `create`). Sessions without a run to show the card in refuse these tools. Codex gets `tool_timeout_sec = 3600` for the Spark server so a waiting card doesn't time the call out.
- **Guide and GitHub reads**: `spark_guide` searches a curated index of how Spark works (`spark-mcp/guide/sections.ts`); `spark_pull_requests` and `spark_pr` read open PRs, CI, reviews, mergeability, files and comments through Spark's GitHub connection (gh CLI or saved token; the token never leaves the server).
- **Transport and auth**: the worker starts one Streamable HTTP MCP listener on `127.0.0.1` with a random port (`spark-mcp/host.ts`, stateless, JSON responses). Each agent turn gets a fresh 32-byte bearer token scoped to the workspace, chat and run; it is revoked when the turn ends. Requests need the exact `127.0.0.1:<port>` Host, no `Origin` header, POST only, and a live token. The Spark API launch token is never shared.
- **No agent-side approval asks**: the agents never raise their own permission request for Spark tools (reads need none; actions get Spark’s own card instead). Claude and Z.ai get the server in ACP `mcpServers` and an `allow: ["mcp__spark"]` rule. User and repo servers can't take the name: `spark` is reserved (a clash becomes `<name>_spark`) and runs of `_` in server names collapse to one, so `spark__x` can't pose as `mcp__spark__…`. Codex gets it in `CODEX_CONFIG` `mcp_servers.spark` with `default_tools_approval_mode = "approve"` (not through ACP, which would replace that entry); if the user's own Codex config has a `spark` server, ours is `spark_outpost`. Agents without HTTP MCP skip it without a note.
- **Private work data**: the read tools that return tickets, Slack, pull requests, the brief or data across chats (`privateData` on the tool: `spark_tickets`, `spark_slack`, `spark_pr`, `spark_pull_requests`, `spark_pr_follow_up`, `spark_chats`, `spark_brief`, `spark_activity`, `spark_attention`, `spark_spend`, `spark_terminals`, `spark_sparks`) mark the chat as having seen private work data when they succeed (`spark_pr` and `spark_pull_requests` only for another project, `spark_pr_follow_up` only for another chat's pull request). From then on a send elsewhere is noted on the mode's card or flagged, never asked about by itself ([HARNESS_PLAN.md, Read, then send: a note, not a card](HARNESS_PLAN.md#read-then-send-a-note-not-a-card-october-6-2026)), and the action tools' cards show "Read sensitive data this turn: …". The tools that return this chat's own context (`spark_task`, `spark_chat`, `spark_chat_history`, `spark_run`, `spark_laws`, `spark_audit`) do not mark the chat, and labels earlier builds stored for them are ignored (`RETIRED_LABELS` in `observations/run-observations.ts`).
- **Output**: compact JSON, passed through `redactValue`, with lists and texts cut until the result fits 20,000 characters, and paging (`offset`, `nextOffset`) where lists grow. Chat messages are clipped per message.
- **Instructions**: when the server is attached, the Spark instructions add one line pointing at the `spark_*` tools (649 of 1,024 characters at the longest).
- **Audit**: tool calls are ordinary ACP tool calls, so they land in the run's protocol log and steps like any other; the session token in `session/new` is redacted like other MCP header values.
- **Tests**: `spark-mcp/format.test.ts`, `test/spark-mcp-actions.db.test.ts` (card, edits, decline, stop, both sources, takeover), `test/spark-mcp-open-pr.db.test.ts`, `test/spark-mcp-github.db.test.ts`, `web/.../SparkActionCard.test.tsx`, `tests/browser/spark-actions.spec.ts` (fake agent asks to create a ticket; the user edits and confirms), `spark-mcp/host.test.ts`, `agents/acp/spark-tools.test.ts`, `test/spark-mcp-setup.db.test.ts`, `test/spark-mcp-chats.db.test.ts`, `test/acp-spark-tools.db.test.ts` (fake agent calls a tool over HTTP; Claude allow rule; Codex config; token revoked after the turn).

## Spark's rules

October 24, 2026. Spark's own rules (the safety floor, the publish rules and the `gh` rules) used to be code with two database switches (Settings → Spark rules). They are now a JSON file shaped like Claude Code's settings, read by pure code in `apps/server/src/spark-rules/` with the file I/O at the edge (`rules-store.ts`). This change keeps every verdict as it was with the seeded file; the Settings page for the file (PR 2) and an agent tool to edit it with a session grant (PR 3) are not built.

- **Files.** The user file is `<data>/<channel>/settings.json` (`sparkDataDir`, `BRANCH_PREFIX`), or `SPARK_RULES_FILE`; the company file is `/Library/Application Support/SparkOutpost/managed-settings.json`, or `SPARK_MANAGED_RULES_FILE`, and Spark never writes it. Both are read on every gate decision and at every turn launch, up to 256 KB. Unit, DB and browser tests point both variables at their own temp folders (`vitest.config.ts`, `test/support.ts` `createTestDb`, `playwright.config.ts`; `resetTestDatabase` removes them), so no test reads the real data folder or `/Library`.
- **Shape.** `{"permissions": {"allow": [], "ask": [], "deny": []}}`, validated like `agent-config/permission-rules.ts`: strings up to 512 characters, 200 per list. Unknown keys, non-text entries and unrecognised rule strings are kept in the file, never applied, and reported (`GET /api/spark-rules` returns them as `problems` for a later page). A file that is not JSON, not an object, has a non-object `permissions` or a non-list `allow`/`ask`/`deny`, or can't be read, means the recommended rules for that tier plus a report: fail safe, never "no rules".
- **Resolution** (`resolve.ts`). Each file gives a candidate: for a floor id, the strongest list naming it; for a `gh` command, `Gh(<group> <verb>)` if that file names it, else that file's `Gh(*)`. The strongest candidate across files wins, deny, then ask, then allow, ties to the company file. So deny wins anywhere, the user file can tighten the company file but never loosen it (a user `allow Gh(release create)` doesn't escape a company `deny Gh(*)`), and within one file a named `gh` command escapes that file's `Gh(*)`. No rule and allow both leave the call to the agent's mode; allow exists to carve a command out of `Gh(*)`. `Gh(*)` is the one place where a more specific rule beats a general one, because the recommended rules must say "other `gh` commands are refused unless added", which deny-wins-anywhere can't express otherwise.
- **Seed once.** At startup the API writes `recommendedRulesText(gh)` when the file and the `.settings-seeded` marker beside it are both absent, then writes the marker, so a deleted rule, or the whole deleted file, never comes back (deleted file: no user rules). The old `profiles.gh_workflows` and `gh_allowed` columns seed the `Gh` rules and are read only for that; Settings → Spark rules and the refused-card's **Allow … and retry** now edit the file (`changeSparkRules`: serialized in the API process, seeded first, atomic temp file and rename, unknown keys and entries kept, a malformed file refused rather than overwritten). Before the seed, the worker uses the same recommended rules in memory. The per-turn Allow once list stays in `approvals` and joins the file's rules in `sparkRulesForRun`.
- **Recommended rules** (`recommended.ts`): deny `Push`, `Push(other)`, `PullRequest`, `GitRemote`, `Gh(*)` (and the three workflow ids when **Run a workflow** was Refused); ask `Push(force)`, `SecretFile(edit)`, `SecretFile(read)`, `InstructionFile(edit)`, `GitConfig`, `WriteOutside`, `SecretSend`; allow the three workflow ids (when it followed the mode) and each allowed command.

- **Applying a rule.** At each point, the recommended effect runs today's code unchanged. deny refuses with today's reason (an ask becomes a refusal); ask asks with today's reason and fields, so hold-to-confirm stays where it was; allow or no rule skips that check and the call goes on to the next check and then to the agent's mode. A lifted publish stop (`kind: 'mode'`) makes the publish verdict "mode", so the publish basis can't run a lifted command at once in Manual. Rails are checked twice, deny-ruled rails first, so a deny on a later rail still wins. `decideRuled` returns the rule id beside the decision; `decide` drops it, so decisions and the existing tests are unchanged, and the gate's refused step reads "Refused <command> — Spark rules: <id>".
- **Agent flags.** `floor-flags.ts` reduces the resolved rules to `SparkFloor` (secret edits, force push, remotes, instruction files, git config). `claudeSessionMeta` builds the flag `deny`/`ask` rules from it (a removed rule drops its flag rule, a deny adds one, `PUBLISH_ASK_RULES` stay so the gate still sees `git push` and `gh`), and `codexConfig` keeps the project secret denies only while `SecretFile(edit)` holds. `turn-launch.ts` loads the floor at each launch and puts it in the connection key, so a live session reopens with resume when the rules change.
- **Fixed in v1.** Agents never read or change the rules file or its marker (`browser-data.ts` `touchesSparkRules`, refused in every mode, with Claude `Read`/`Edit` denies), and never reach Spark's ports. Ask Spark's own refusal to merge, approve or dismiss reviews stays. The Mac control, Browser pane, Calendar and web address floors, `--no-verify`, a stacked parent not yet pushed, reads outside the project, `.git` internals, Spark's browser data and Ask turns' read-only rule are not rule ids. Observed rail flags in modes the gate can't see follow the resolved rules too: `rail-crossings.ts` (outside writes and deletes, secret files, instruction files, git config, force pushes), `send-watch.ts` (`Push(other)`) and the run-end check in `workflow/rail-flags.ts` raise a flag only while that rule asks or denies; a stacked push, a send after reading work data and Spark's browser data always flag. Terminal session records keep the recommended rules. `spark_push` has no card, so a `SecretSend` ask or deny refuses there and only a lifted rule lets it push.
- **`gh` global flags.** `gh-reads.ts` `ghArgs` moves leading `-R`/`--repo`/`--hostname` and their values after the command, in `ghOnlyReads` and `hostingCommands`, so `gh -R owner/repo pr checks 512` is a read and `gh -R owner/repo pr create` still meets the publish rules (the moved `-R` still marks another repo).
- **Tests.** `spark-rules/equivalence.test.ts` runs a corpus of 201 cases (50 commands and edits, each under three publish grants and with no task branch, and a secret send) in six postures, 1,206 decisions, against the seeded file read back from disk, and compares each decision with `approvals/fixtures/spark-rules-verdicts.json`, recorded from `origin/main` before this change (`decide` with the database default `gh` rules); the whole existing decide, gate and publish suite runs unchanged. `rule-removal.test.ts` checks each rule id: the recommended verdict, that removing it gives the same decision as no rules at all (the mode's verdict, in Manual and Auto), that deny refuses and ask asks in every mode it covers, and the two-file cases. `rules-file.test.ts`, `rules-store.test.ts` (seed once, deleted rule, deleted file, malformed and unreadable files, serialized changes), `agents/acp/spark-floor.test.ts` (flag rules, Codex profile, connection key), `approvals/gh-global-flags.test.ts`, `browser-data.test.ts` and `test/spark-rules.db.test.ts` (seeding from the old columns, Settings writing the file, a deleted rule in the gate, problems).

## Limitations

- Off means "not given to the agent", not "hidden": with instructions off, the live Claude run read CLAUDE.md with its Read tool and still answered with the codeword.
- CLAUDE.md `@imports` are not expanded, and nested instruction files are listed rather than loaded when the agent enters a folder.
- Plugin names namespace skills and commands (`/app:greet`, not `/greet`). A skill's supporting files stay in the repo; the skill text names that folder.
- When hooks are on, a `PreToolUse` hook can approve or block tool calls; the popover says so.
- Repo MCP servers that need secrets from the shell don't get them; user-level servers get theirs from the keychain.
- Removing and restoring a project drops its agent settings and MCP approvals.
- Instructions text is capped at 48 KB per session (24 KB per file).
- A hook's change list line shows the first 200 characters of its command; a change past that shows as the hook being changed with the same text.
- Trust follows a project by its order in the chat, so a chat worktree is trusted only while its executable config matches the fingerprint the user trusted.
