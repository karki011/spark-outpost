# PR follow-up

After Spark opens a pull request from a chat, the worker watches it through the user's existing GitHub connection (GitHub App sign-in for covered repos, token, or gh CLI; see `GITHUB_APP.md`) and handles failing checks and review feedback. Code: `apps/server/src/pr-follow-up/`, storage in `persistence/pr-watches.ts` (migration 0087).

## Ready for review by default

Settings → Work → Pull requests → **Open pull requests as**: Ready for review (default) or Draft (`profiles.pr_ready_for_review`). Ship passes the choice to GitHub (`NewPullRequest.draft`). The one exception: a Full auto PR whose checks still fail, when **When checks still fail in Full auto** says to open it anyway, always opens as a draft marked "Checks failing" (`ShipOptions.draft`). The ship mode id stays `draft_pr`; user-facing copy says "PR" and only says "draft PR" when GitHub got `draft: true`. The setting is global: Ship has no per-project settings today.

## Watching

Ship registers a `pr_watches` row for every PR it opens or updates (chat, task, repo, number, branch). `startPrFollowUp` in the worker ticks every 15 s and polls due watches:

- `watching` / `needs_you`: read the PR; stop (`done`) when merged or closed. Otherwise gather, triage and maybe start a round. The interval starts at 2 minutes and doubles while nothing changes, up to 30 minutes; any new item resets it.
- `fixing` / `confirming`: no GitHub reads; check the round run or the confirm card every 20 s. A decided card also wakes the poller through the `approvals` notification.

Webhooks would replace most polling; they need a public endpoint or the GitHub App, so they are left for later.

## Every pull request of a chat

`pr_watches` (extended in migration 0132) holds every pull request opened in a chat, not only the ones Ship opened. `follow_up` together with a task decides whether the fix loop applies (`Watch`); the wider row is `TrackedPull` (`persistence/tracked-pulls.ts`) and is polled for status only. Rows are unique per workspace, host, repository (case-insensitive) and number, and record `opened_via` (`ship`, `agent`, `terminal`, `discovery`), who opened it and the run.

| Source                        | Code                                                       | Notes                                                                                                                                                          |
| ----------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The agent's `gh pr create`    | `tasks/agent-pull-request.ts`                              | Always tracked; followed up only when the repository is the chat's and the head is the chat's own branch. Audited as `ship/agent_pr`.                          |
| The publish step              | `workflow/publish-step.ts`                                 | Spark asks GitHub for a pull request with the branch as head after the turn and records it.                                                                    |
| A tool in a chat terminal tab | `terminal/pull-request-scan.ts`, `pr-tracking/terminal.ts` | Output is scanned for github.com pull request links; a link counts only when GitHub confirms its head is a branch of the chat or the user opened it meanwhile. |
| Discovery                     | `pr-tracking/discover.ts`                                  | Pull requests whose head is the chat's own branch, or the branch checked out in its worktree. Runs on chat open, focus and run start or finish, once a minute. |

Terminal and discovery sightings are audited as `ship/pr_tracked` and never take a pull request another chat tracks. A pull request in a repository the chat is not linked to is marked `outside`.

Status per row: state, title, head and base, checks with the failing check names and links, and the review verdict. Checks follow one rule (`ship/github/check-runs.ts`), shared with the tickets screen: pending while any run is incomplete, failing only when all are complete and at least one failed. Missing access sets a plain reason and reads as unknown; a rate limit pauses every row on that host for 30 minutes. The web asks `POST /conversations/:id/pull-requests/refresh` on chat open, focus, run start and finish, and on a 1 to 10 minute timer; the worker is woken through the `pr_poll` channel.

Not covered: a Tasks row for terminal and discovery pull requests.

## When a pull request opens

Three things follow a pull request Spark records for a chat through the publish step, Ship, the agent's `gh pr create` or `spark_pull_request` (`opened_via` `ship` or `agent`; the tool tracks its pull request itself through `tasks/agent-pull-request.ts`). Migration `0236_pr_post_open.sql` adds their columns and marks every existing row's tickets as handled.

- **Ticket move** (`tickets/ship-sync.ts`, `tickets/pull-ticket-keys.ts`). `syncPullTickets` claims the row (`ticket_sync_claimed_at`, set once by an `UPDATE … WHERE … IS NULL`), so the publish step and Ship (which start it without waiting, so a slow ticket source never holds up the turn or the ship) and the poller (which awaits it after saving the poll; each ticket request has the ticket client's 20-second timeout), which runs it for any open, unclaimed `ship`/`agent` row that is not `outside`, move a ticket at most once per pull request, across duplicates and restarts. The chat's tickets are the task's `task_tickets` (started from, or linked by the user, as before) plus tickets named in the branch or title: a key with no letter or digit on either side, matched case-insensitively against cached Jira or Linear tickets of a connected source, or, when written in capitals, looked up with `getSummary` (at most five keys). Key matches are not written to `task_tickets`, so they never move on merge. Each ticket gets the existing link and, when the source's **Move tickets to In review when a PR opens** is on, the existing `moveTicket` to the `in_review` group; ServiceNow never has that switch, so it never moves. Moves run without a card in every mode and are audited as ticket events. Each outcome is kept in `ticket_sync`; the chat shows a line for every one that did not succeed ("WEB-4 was not moved to review: …"), under the turn's **Opened pull request** line, or under the PR row for a pull request the Ship panel opened (it has no run). The claim comes before the move, so a crash between them loses that one move rather than repeating it. A failure never fails the publish, the poll or follow-up. Terminal, discovered and adopted pull requests move nothing.
- **Follow-up offer** (`web/src/chat/pull-request/post-open-model.ts`). Under the turn's **Opened pull request** line, a `ship`/`agent` pull request that is open and followable shows "Follow up on this PR?" while **Follow up on pull requests** is off or **Ask before pushing and replying** is on. **Turn on** sets `pr_follow_up` on and `pr_follow_up_ask` off for the workspace, and its note names the one that changes: there is no per-pull-request switch. A pull request the Ship panel opened shows it under its PR row instead. It is not an approval card and not an attention item; × dismisses it in that browser (`use-dismissed-pulls.ts`).
- **Clean** (`pr-tracking/clean.ts`). After each poll the worker checks a followed, open, non-draft pull request: checks `passing` (Spark can't tell required checks from optional ones, so every run must pass, and no checks at all is never clean), no `changes_requested` verdict, no round or confirm card, no `review_comment:` thread among the stored open threads (plain PR comments don't count; more threads than stored counts as open), and no feedback item queued, needing the user, planned or in a round (held items don't count). The first clean poll on a head sets `clean_head_sha` and `clean_since`; anything that breaks it clears `clean_since` but keeps the head, so the same head never shows clean again and a new head can. While `clean_since` is set for the current head, the PR row shows "PR is clean · ready to merge" and `/api/attention` has a non-blocking `pr-clean:<pull>:<head>` update, which never counts, chimes or pushes. Spark still never merges.

## Gathering and dedup

Per poll (`gather.ts`): the pull request itself (head, base, `mergeable_state`, requested reviewers and teams), failing check runs on the head commit with the check title, summary and up to 5 failure annotations; inline review comments; reviews that request changes or comment with a body; PR comments. Bots (Copilot, CodeRabbit) are included. Each item has a source key (`check:<name>:<sha>`, `review_comment:<id>`, `review:<id>`, `issue_comment:<id>`) and `pr_feedback_items` is unique per watch and key, so nothing is processed twice; a check that fails again on a new head is new. Spark's own replies carry a hidden marker and are skipped. Lists read up to 5 pages of 100.

Check logs are not downloaded: the excerpt is what the Checks API returns (output title, summary, annotations). Fetching job logs is a possible follow-up.

## Trust and triage

An item is trusted when it is a failing check on the PR's head (the PR's own CI), its author has write, maintain or admin permission (`GET /collaborators/:login/permission`), or its author is one of the **Review bots to act on** (`profiles.pr_follow_up_bots`, migration `0237`, matched by exact login ignoring case, so `coderabbitai[bot]` and `gitar-bot` are entered as GitHub shows them). Other bots and failed lookups are untrusted. A listed bot's text is untrusted data like any reviewer's: it goes through the same triage and prompt, and the agent judges it and may push back. The list applies to items gathered after it changes; an item already held stays held. Untrusted items are shown (state `held`) and never acted on automatically; the user can include them through `spark_pr_follow_up_round`.

Jev triages new comments in one batch of Choice questions (`triage.ts`): fix, question, disagree (needs a human), nit, already addressed, information. Answers below 0.6 confidence, and everything when Jev isn't connected, use the rules. Checks are always "fix".

States: disagreements → `needs_user` (always the user's call); addressed/information → `done`; untrusted, or switched off by the sub-settings → `held`; questions with replies off → `needs_user`; the rest → `queued`.

## Rounds

When items are queued, follow-up is not stopped (below), and the branch is in sync, Spark sends one chat message (`source = 'pr_follow_up'`, `startAs = 'change'`) so an ordinary chat turn runs in the chat's worktree on the chat's own session and model. The turn's publish step uses the follow-up prompt: push fixes to the same branch, no new pull request, no replies and no resolved threads.

Before a round starts (`round.ts`, `rounds.ts`):

- **Busy chat.** A chat with a queued, running or waiting run, or a card waiting for the user, is never interrupted: the items stay `queued`, the watch says "New feedback is waiting for the chat's current turn to finish", and the next poll tries again. Everything that arrives meanwhile goes into the same round.
- **Same failure.** A check that fails on the new head with the same name and the same excerpt as the check the previous round fixed is not tried again: it goes to the user with "CI still fails the same way after the fix". A different excerpt is a new failure.
- **Repeated request.** A comment by the same author on the same file and line (or, for PR comments, the same author) as an item the agent already pushed back on goes to the user. Spark does not argue twice.
- **A round that changes nothing.** There is no round cap. When a round ends with no pushed commit and no reply posted, `settle` stores the PR head in `pr_watches.quiet_head` (migration `0237`) and the watch says follow-up stopped. Items that arrive later clear it, and so does a new head or the user asking for another round (`spark_pr_follow_up_round`). A quiet watch never starts a round; an item queued while quiet goes to the user. This ends bot and agent ping-pong without a budget, and it survives a restart because it is stored; a duplicate item is deduplicated by source key and never wakes it.
- **Branch behind or in conflict.** When GitHub reports `mergeable_state` `dirty` (conflicts) or `behind` (the base requires an up-to-date branch), the round prompt tells the agent to update the branch by merging the base (`git fetch <remote> <base>`, `git merge <remote>/<base>`), never rebasing or force pushing, and to `git merge --abort` and report conflicts it can't resolve safely ("Needs you:"). A null or `unknown` state (GitHub still computing) adds nothing. Not offered while **Ask before pushing and replying** is on: Spark's own push there sends working-tree changes, and a merge-only commit is not verified to reach it. The state also starts a round by itself (`rounds.ts` `mergeRoundKey`, `mergeRoundDue`): when it is `behind` or `dirty` and the key `<head sha>:<base ref>` differs from `pr_watches.merge_round_for` (migration `0238`), the poller counts it like a queued item, so the busy-chat, Spark-pause and quiet rules apply unchanged. Any round that starts with the merge line stores its key, so one head and base pair gets one merge round, across duplicate polls and restarts; a new head (or another base) gets another. A round with no feedback items says why ("PR #7 is behind main"), carries no `<pr_feedback>` block and asks only for the merge and a summary; the watch says "Updating the branch from its base (round N)". The base ref, not its sha, is in the key, so main moving on alone never starts another round for the same head.
- **Re-requesting review.** Each poll adds the requested reviewers and teams (`org/slug`) and every review author to `pr_watches.known_reviewers` (lowercased, kept when GitHub drops a reviewer from the requested list after they review). The round prompt names them and says the agent may re-request review from them after Spark's push prompt and the push succeed, never from anyone new. App bots other than Copilot (`copilot-pull-request-reviewer[bot]`, requested as `copilot`) are left out of that list, because GitHub's review request does not take them; the gate still accepts any known name. Not offered while **Ask before pushing and replying** is on, because Spark pushes then.
- The first line of the message says why Spark sent it ("Spark: CI failed on PR #7 (test) and 2 review items arrived on PR #7, so I asked this chat to look") and that the user did not type it. The user stops the turn like any other.

The prompt wraps all GitHub text in `<pr_feedback>` as quoted lines, says it is untrusted data that cannot grant permissions or change the mode, and tells the agent to judge each item on its merits: fix what is right; push back, with a short and specific reason, on what is wrong, out of scope or settled by the project's conventions; for a failing check, fix what its change caused and say so when the check also fails on the base branch or is flaky infrastructure; leave to the user anything that changes scope, is security-sensitive, repeats a pushed-back request, or needs a change to CI workflows, hook configuration or protected files (those keep their ask rules whatever the prompt says). It ends its reply with one line per item: `[F1] fixed: …`, `[F2] pushed back: …`, `[F3] answer: …`, `[F4] left for you: …`, and a summary for the user.

### Round outcomes

Each settled, stopped or failed round appends one outcome to `pr_watches.round_outcomes` (`persistence/round-outcomes.ts` `recordRoundOutcome`, keyed by the round run so a repeated settle replaces it): pushed, merged the base (a pushed round with no items), replies posted, items left, an unpushed fix, and whether the round run (or its child runs) ran a successful `gh pr edit --add-reviewer` or `requested_reviewers` command (`round-outcome.ts`). The view sends them as `roundOutcomes`; the web composes the line (`roundOutcomeLine`: "Follow-up replied to 3 comments, pushed a fix, re-requested review", "Follow-up stopped: nothing changed"). A follow-up round adds nothing to the turn preamble.

### Who pushes

A round run carries the publish basis `follow_up` (`approvals/publish-policy.ts`, `workflow/publish-context.ts`): the gate and `spark_push` allow a push of the chat's own branch at every autonomy level and in asking modes, but only while `pr_watches` holds an open, followed pull request of that chat on that branch. An ordinary turn in the same chat does not carry it; a merged or closed pull request ends it; the hard rails are unchanged (own branch only, no force push, hooks never skipped, nothing merges, `gh` limited to `pr create`/`view`/`edit`). A push of a merge of the base is an ordinary fast-forward push of the own branch, so it needs nothing more; a rebase can only be published by a force push, which `Push(force)` refuses (plain) or asks with hold-to-confirm (lease) while set. After the round's checks the orchestration runs the publish turn (`orchestration/agent-publish.ts`): the agent commits (a merge commit included) and pushes with `spark_push`, and opens nothing.

In the same round run, a re-request of review is allowed at once at every autonomy level and in asking modes (`approvals/own-repo.ts` `reviewRequestOf`, `publish-policy.ts`, decided with the reason "re-requesting review from this pull request's own reviewers", recorded like every gate decision) when it is exactly `gh pr edit <own number, branch or URL> --add-reviewer <logins>` (comma-separated or repeated, `@` allowed, `@copilot` for Copilot's reviewer bot) or `gh api [-X POST] repos/<own repo or {owner}/{repo}>/pulls/<own number>/requested_reviewers` with only `-f`/`-F`/`--field`/`--raw-field` `reviewers[]=` and `team_reviewers[]=` values, every name already in `known_reviewers`, on the chat's own open followed pull request while follow-up is on and not set to ask first. A new reviewer, another pull request, `--input`, another field, `-R`/`--repo` or `--hostname` is refused with the reason, under `PullRequest` (`gh pr edit`) or `Gh(api write)` (the API), so with no rule set it follows the agent's mode like any publish stop. Outside a round nothing changed: the API form stays under `Gh(api write)`, and `gh pr edit` on the own pull request keeps its publish basis. An allowed re-request is work on the chat's own pull request, not a send.

When the run ends, `settleRound` compares the branch with its remote-tracking ref. A new pushed head is the commit of the round; a new head that was not pushed sends the fixed items to the user ("The fix is in the chat but was not pushed"). Then, per item: fixed → reply "Fixed in <sha>: <note>"; pushed back → reply "Not changed: <reason>", and the thread stays open; answer → the answer; left for you, or no line → `needs_user`. Replies go out through Spark's GitHub connection (the agent's `gh` rail has no comment verb), pass the secret redaction, carry the hidden Spark marker, and each is audited on the round run as `ship/pr_reply` with its text.

**Ask before pushing and replying** (`profiles.pr_follow_up_ask`, off by default) keeps the earlier flow: the fix stays in the working tree, one `spark_action` card (`pr_follow_up`) lists the push and each reply, and on confirm Spark pushes with Ship's `push` mode (no agent turn is running by then) and replies.

Spark never force-pushes, merges, approves, resolves threads or dismisses reviews.

## Where it shows

- Chat: a one-line PR row above the message box (`PrCard`), in the composer stack above the context bar: `#number` link, title, then only the facts that matter (Checks failing or running, N need you, N new comments, Round r while a round runs) and the state (Open, Draft, Merged, Closed). It has a fixed height (32 px, 44 px on phones) so live updates never move the composer, and a polite status line announces a change of state or facts. Clicking it opens a panel upward (`PullPanel`) with what Spark is doing, the gathered items, and the same checks, reviews and comments sections the Links tab shows (`PullDetails`). More than two pull requests collapse to one "N pull requests" row. A merged or closed row can be dismissed with ×; the dismissal is kept per chat in the browser (`use-dismissed-pulls.ts`, keyed by pull and state, so a reopened pull shows again). It refreshes on the `pull_request` change event. There is no PR chip in the chat header.
- Details: each poll stores `pr_watches.details` (migration `0139_pr_details.sql`): every check run once by name with its state (failing, running, passing, cancelled, skipped, neutral) and the check's own output title; each reviewer's latest verdict (a later plain comment never replaces an approval or a change request); and up to 50 open threads, newest first (review threads GitHub marks resolved are left out, read with one GraphQL call that fails open; replies and Spark's own replies are skipped). Summaries and excerpts are reduced to plain text (`pr-tracking/plain-text.ts`: Markdown and HTML removed, secrets redacted, cut to 160 and 220 characters), are rendered as text only, and are never logged. The view adds Spark's follow-up status to a thread from the feedback item with the same source key (fixed, pushed back, answered, left for you, fixing). The aggregate check state is unchanged: a cancelled run still counts as failing there, and is listed as Cancelled.
- Watching indicator: the PR row, its panel and the Links card show one eye icon with who is on the pull request (`watch-indicator-model.ts`, `WatchIndicator.tsx`). The state is derived, in this order, from facts the server already holds: a running round (`phase = fixing`: "Agent is on it", with the round and the crew member read from the chat's orchestration for `roundRunId`), something for the user (a confirm card, items left, `needs_you`), no access (`pollProblem` `not_connected` or `no_access`, or a status reason), a pause (`rate_limit`, `offline`, `error`, with the last error in brief and the next try), Follow up off (from the profile), stopped after a round that changed nothing (`quiet` in the view), checks running, no review yet, then "Spark is watching" (followed) or "Spark is tracking" (status only). Merged and closed pull requests show no indicator. The view adds `nextPollAt`, `pollProblem` (`pr_watches.poll_problem`, migration `0142_pr_poll_problem.sql`, set from the error class when a poll fails and cleared by the next good one) and `roundRunId`. The same migration makes an idle poll that only moved `last_polled_at` send the `pull_request` change event, so "checked 20s ago" stays current; polls during a round do not. The eye pulses only while a round or checks run, never with reduced motion; the row shows a short word on wide screens and the icon alone on phones; the full sentence is the icon's name and tooltip, and the row's polite status line carries the label without the times. When Follow up is off, or asks first, the panel shows that same profile switch. Not known to the server, so never shown: an agent polling the pull request with its own command inside a turn.
- Round lines: a round's user message is headed "Follow-up sent this round; you did not type it" (from `Run.prFollowUp`), and the turn ends with the outcome line for that run (`RoundLines.tsx`). The PR row's panel leads with the last round's outcome.
- Sidebar, Home and the desktop island: a pending `pr_follow_up` card shows as "PR feedback" (`ConversationAttention.prFeedback`).
- Tickets inbox: a ticket whose PR has items waiting for the user gets the `pr-feedback` attention flag.
- Spark tools: `spark_pr_follow_up`, `spark_pr_follow_up_round` (see `SPARK_TOOLS.md`).

## Settings

Settings → Work → Pull requests: Follow up on pull requests (on), with Ask before pushing and replying (off), Fix failing checks, Handle review comments and Reply on GitHub threads (all on), and **Review bots to act on** (empty; up to 50 GitHub logins; disabled while follow-up or Handle review comments is off). These are workspace settings; there is no per-chat or per-pull-request switch yet, so the offer's **Turn on** changes the workspace setting. The bot list is Mac only: `PATCH /api/profile` refuses `prFollowUpBots` from a paired device (403, "Choose review bots on your Mac."), which sees the list read-only, and no Spark tool writes it, so a bot comment can't add itself.
