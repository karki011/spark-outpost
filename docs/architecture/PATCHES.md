# Dependency patches and adapter workarounds

What we change in third-party code, why, what guards it, and when each part can go. Checked September 27, 2026; upstream status checked September 30, 2026. Spec conformance and what each adapter advertises are in [ACP_COMPLIANCE.md](ACP_COMPLIANCE.md).

## Patch files

| File                                                          | Package                                                                   | Applied by                                                        |
| ------------------------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `patches/@agentclientprotocol__codex-acp@1.13.1.patch`        | `@agentclientprotocol/codex-acp` 1.13.1 (bundles `@openai/codex` 0.156.1) | `patchedDependencies` in `pnpm-workspace.yaml`, on `pnpm install` |
| `patches/@agentclientprotocol__claude-agent-acp@0.81.2.patch` | `@agentclientprotocol/claude-agent-acp` 0.81.2                            | The same                                                          |

There are two patches. The codex-acp patch edits the bundled `dist/index.js` (about 40 changed lines in seven parts). The claude-agent-acp patch edits `dist/permissions/effects.js` (three changed lines, one part). pnpm refuses to install if a hunk no longer applies, so a version bump always forces a decision.

## claude-agent-acp 0.81.2 patch

### A reject carries Spark's reason to Claude

|             |                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Changes     | `dist/permissions/effects.js`. `parseClaudePermissionSelection` reads `_meta.denyMessage` from the permission response when it is a string and returns it with the selection. `applyCommonSelection` passes it to `deny()` for the `reject` option. Without `_meta.denyMessage` the adapter behaves as upstream.                                                                                                                                                              |
| Why         | When Spark's policy, not the user, rejects a tool call, Spark answers `session/request_permission` with the reject option and `_meta.denyMessage` (`permissionResponse` in `apps/server/src/agents/acp/permission-request.ts`; `declineInConversation` in `permissions.ts`). Unpatched, Claude is told "User refused permission to run tool" and reports that the user said no. Patched, the tool's denial message is Spark's reason, for example "Spark's policy blocked …". |
| Upstream    | Not checked. No upstream issue or pull request is recorded for this change.                                                                                                                                                                                                                                                                                                                                                                                                   |
| Guard tests | `apps/server/src/agents/acp/permission-request.test.ts` › "reaches Claude as the tool's denial message instead of 'User refused'" (runs the installed adapter's `decodeClaudePermissionResponse`).                                                                                                                                                                                                                                                                            |
| If removed  | Nothing is allowed that was refused before: the call is still denied. Claude hears "User refused permission to run tool" for a policy denial and may tell the user they refused it.                                                                                                                                                                                                                                                                                           |
| Remove when | claude-agent-acp passes a deny message from the permission response on its own, or Spark stops sending `_meta.denyMessage`. Verify with the same guard test against the unpatched package.                                                                                                                                                                                                                                                                                    |

On a claude-agent-acp bump: rename the patch file and its `patchedDependencies` key in `pnpm-workspace.yaml` to the new version, re-create the hunk with `pnpm patch` and `pnpm patch-commit` if upstream still lacks it, then run the guard test.

## codex-acp 1.13.1 patch, part by part

### 1. `read-only` is a real read-only sandbox

|             |                                                                                                                                                                                                                                                                                                                                      |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Changes     | `dist/index.js`, `class _AgentMode`, `static ReadOnly`: the sandbox becomes `{ type: "readOnly", networkAccess: false }` (was `workspaceWrite` rooted at `cwd`, with `/tmp` and `$TMPDIR` writable), its sandbox mode is `read-only`, and the label reads "Read-only". Approval policy stays `on-request` with the user as reviewer. |
| Why         | Ask runs and chats use `read-only`. Unpatched, Codex could edit the project and run writing commands in Ask without any `session/request_permission`. With `readOnly`, extra repos passed as `additionalDirectories` also stay read-only, because the adapter only widens `workspaceWrite` policies.                                 |
| Upstream    | [codex-acp#480](https://github.com/agentclientprotocol/codex-acp/pull/480) "restore read-only mode and clarify access presets", merged September 23, after 1.13.1. It is in the 1.13.2 previews (1.13.2-preview.5, September 25), not in a release yet. #480 also adds a separate `workspace-write` mode.                            |
| Guard tests | `apps/server/src/agents/acp/agents.test.ts` › "the codex-acp patch" › "makes read-only a readOnly sandbox" (reads the installed `dist/index.js`).                                                                                                                                                                                    |
| If removed  | Codex Ask and chat runs can write to the project and `/tmp` without asking. Codex extra repos become writable.                                                                                                                                                                                                                       |
| Remove when | codex-acp ≥ 1.13.2 (or the first release containing #480) is released and its `read-only` mode has `type: "readOnly"`. Verify with the same guard test against the unpatched package.                                                                                                                                                |

### 2. `ask-every-action` mode

|             |                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Changes     | `dist/index.js`, `class _AgentMode`: new `static AskEveryAction` (`"ask-every-action"`, "Ask every time") with `approvalPolicy: "untrusted"`, `approvalsReviewer: "user"` and a `workspaceWrite` sandbox with `writableRoots: []`, `networkAccess: false`, `excludeSlashTmp: true`, `excludeTmpdirEnvVar: false`. `_AgentMode.all()` lists it after `ReadOnly`.                                                                     |
| Why         | Codex Do needs every command and patch to reach `session/request_permission`, so `decide()` and the approval gate see each action. Every upstream mode uses `on-request`, which runs sandboxed reads and in-sandbox edits unasked, including `cat .env` ([CODEX_DO.md](CODEX_DO.md#results)).                                                                                                                                       |
| Used by     | `agents.ts`: `CODEX_DO_MODE`, `doMode` on the Codex definition; `session-modes.ts` uses it as Codex's asking mode: chosen for Ask every time, and the fallback when a chosen mode is unavailable or needs a worktree the run doesn't have.                                                                                                                                                                                          |
| Upstream    | #480's `workspace-write` mode is still `on-request`, so it doesn't replace this. Filed as [codex-acp#555](https://github.com/agentclientprotocol/codex-acp/issues/555), with draft PR [#557](https://github.com/agentclientprotocol/codex-acp/pull/557) offered in the issue, from the fork [karki011/codex-acp](https://github.com/karki011/codex-acp). Open as of September 30, 2026.                                             |
| Guard tests | `agents.test.ts` › "adds an ask-every-action mode: untrusted, user-reviewed, sandboxed without network"; `test/acp-codex-do.test.ts` (fake agent with Codex's option ids); `test/codex-crew.db.test.ts`; live: `test/codex-do.live.test.ts` (every Codex tool call must have an approval receipt).                                                                                                                                  |
| If removed  | Codex Do can't be gated: `set_config_option` to `ask-every-action` fails and the run stops before prompting (the mode can't be applied), so Codex Do becomes unavailable rather than unsafe.                                                                                                                                                                                                                                        |
| Remove when | codex-acp ships a mode whose per-turn policy asks before every command and file change (for example an `untrusted` or granular "ask always" preset) and `test/codex-do.live.test.ts` shows `ls` and `cat` asking under it. Then point `CODEX_DO_MODE` at that mode id. Also watch `@openai/codex`: if it drops `untrusted` from the app-server protocol, this part stops working even while the patch applies (CODEX_DO.md "Risk"). |

### 3. `decline` option, ordered before `cancel`

|             |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Changes     | `dist/index.js`, `commandDecisionOptions(params)`: inserts Codex's `decline` decision before `cancel` when Codex doesn't offer it. `fileChangeDecisionOptions()`: adds `decisionOption(ApprovalOptionId.Decline, "No, continue without it", "reject_once", "decline")` before the `cancel` option.                                                                                                                                                                                                              |
| Why         | Under `untrusted`, Codex offers only accept variants and `cancel`, and `cancel` ends the turn (`stopReason: cancelled`). Our gate answers a denial with the first `reject_once` option (`permissions.ts`, `workflow/approval-gate.ts`), so putting `decline` first makes a denial "skip this and carry on", as with Claude.                                                                                                                                                                                     |
| Relies on   | Option order: both `decline` and `cancel` are `reject_once`. ACP_COMPLIANCE lists this as adapter-specific.                                                                                                                                                                                                                                                                                                                                                                                                     |
| Upstream    | Filed as [codex-acp#556](https://github.com/agentclientprotocol/codex-acp/issues/556), with draft PR [#558](https://github.com/agentclientprotocol/codex-acp/pull/558) (opt-in: `decline` is offered only when the client sets `clientCapabilities._meta.continueOnReject: true` at `initialize`, which our code doesn't set, so #558 as drafted needs a code change before it replaces this part). The app-server already accepts `decline`; the adapter just doesn't offer it. Open as of September 30, 2026. |
| Guard tests | `agents.test.ts` › "offers decline before cancel for commands and file changes"; `test/acp-codex-do.test.ts`.                                                                                                                                                                                                                                                                                                                                                                                                   |
| If removed  | A denied Codex action would end the whole turn as cancelled instead of letting Codex continue.                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Remove when | codex-acp offers a continue-on-deny `reject_once` option ahead of `cancel` for command and file-change approvals. Verify with the guard test and one denied command in `test/codex-do.live.test.ts`.                                                                                                                                                                                                                                                                                                            |

### 4. Usage summed per turn

|             |                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Changes     | `dist/index.js`: new helpers `TOKEN_USAGE_FIELDS`, `tokenUsageStep`, `addTokenUsage` and `turnPromptUsage` next to `toTokenCount`. `handleTokenUsageUpdated` adds each request's step (the change in the thread total, or `last` when no total was seen) to `sessionState.turnTokenUsage`. The two turn starts reset it. The four prompt responses (end turn, cancelled, failure) report `buildPromptUsage(turnPromptUsage(sessionState))` instead of the last request only. |
| Why         | Unpatched, `PromptResponse.usage` holds only the turn's last model request, so tool-heavy Codex turns were undercounted and our cost estimates too low.                                                                                                                                                                                                                                                                                                                      |
| Upstream    | No new issue or PR: commented on the existing [codex-acp#447](https://github.com/agentclientprotocol/codex-acp/issues/447#issuecomment-5856984813), backing the more complete open PR [#486](https://github.com/agentclientprotocol/codex-acp/pull/486) (also open: #353, #367). `PromptResponse.usage` is itself an unstable ACP field (SDK 1.5.0 unstable schema).                                                                                                         |
| Guard tests | `agents.test.ts` › "reports the whole turn's tokens, not only the last model request" (runs the patched helpers on a two-request turn and a repeated update).                                                                                                                                                                                                                                                                                                                |
| If removed  | Codex runs report only the last request's tokens; usage and estimated cost are too low. Nothing breaks functionally.                                                                                                                                                                                                                                                                                                                                                         |
| Remove when | codex-acp reports per-turn usage on the prompt response (check its changelog and the `buildPromptUsage(...)` call sites). Verify with the guard test's arithmetic against the unpatched helpers, or compare `thread/tokenUsage/updated` totals with the response in one live run.                                                                                                                                                                                            |

### 5. Session roots are untrusted

|             |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Changes     | `dist/index.js`, `createSessionConfig(...)`: the `projects` entry written for each session root sets `trust_level: "untrusted"` (was `"trusted"`).                                                                                                                                                                                                                                                                                                                                                                                        |
| Why         | Codex loads a project's `.codex/config.toml` only for trusted projects. Marked trusted, a repo's config applied inside our sessions: a checked-in `[mcp_servers.*]` entry was started at `session/new` (verified offline, see [REPO_AGENT_CONFIG.md](REPO_AGENT_CONFIG.md#codex)), and `notify`, `shell_environment_policy`, `model_providers` and hooks would apply too. Approval and sandbox are set per turn from the ACP mode, so they were already ours. AGENTS.md and `.agents/skills` / `.codex/skills` still load when untrusted. |
| Guard tests | `agents.test.ts` › "marks session roots untrusted so a repo's .codex/config.toml is never loaded".                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| If removed  | A repo's `.codex/config.toml` configures Codex in our sessions, including MCP servers that start without the user turning them on.                                                                                                                                                                                                                                                                                                                                                                                                        |
| Remove when | codex-acp stops writing trust for session roots, or offers a way to load project config without trusting it. Verify by starting a session in a repo whose `.codex/config.toml` defines an MCP server that writes a marker file.                                                                                                                                                                                                                                                                                                           |

### 6. `CODEX_CONFIG` MCP entries survive ACP servers

|             |                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Changes     | `dist/index.js`, `createSessionConfig(...)`: when a session has ACP `mcpServers`, the thread's `mcp_servers` is the `CODEX_CONFIG` table plus those servers (was: those servers only).                                                                                                                                                                                                                      |
| Why         | Codex starts every `[mcp_servers.*]` in the user's own `~/.codex/config.toml` (or `$CODEX_HOME`). We turn each of them off with `mcp_servers.<name>.enabled = false` in `CODEX_CONFIG` (`agent-env.ts`), so only servers the user turned on in Spark Outpost run. Unpatched, a session with any ACP server replaced that table and the user's servers started again (marker test through the real adapter). |
| Guard tests | `agents.test.ts` › "keeps CODEX_CONFIG mcp_servers next to ACP servers so user-level ones stay off"; `test/acp-user-mcp.test.ts`.                                                                                                                                                                                                                                                                           |
| If removed  | In a Codex chat with any MCP server turned on, the user's own Codex MCP servers start too, without review.                                                                                                                                                                                                                                                                                                  |
| Remove when | codex-acp merges its config with the ACP servers, or offers a way to ignore user-level MCP config. Verify with a temporary `CODEX_HOME` whose `config.toml` defines a server that writes a marker file, plus one ACP server.                                                                                                                                                                                |

### 7. Named permission profiles per turn

|             |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Changes     | `dist/index.js`, `CodexAcpClient`: new `turnSandbox(agentMode, cwd, additionalDirectories)`, used by `sendPrompt`. When `CODEX_CONFIG` has a `permissions` profile named after the mode id, `turn/start` sends `permissions: <mode id>` and `runtimeWorkspaceRoots: [cwd, ...additionalDirectories]` instead of the legacy `sandboxPolicy`. Otherwise it sends the legacy policy as before.                                                                                                                                                                                                                                                                                         |
| Why         | Secret files must be unreadable in every Codex mode, not only when a command names them (e2e 2026-09-29, B1: a read-only Ask turn ran `sh -c "cat .env"` without a permission request). `codex-permissions.ts` gives each mode a profile that denies `SECRET_FILE_PATTERNS` under `:project_roots`, enforced by Seatbelt for every command. A per-turn `sandboxPolicy` replaces the configured profile (checked with `command/exec`: `cat .env` is denied under the profile and readable under `{type: "readOnly"}`), so the adapter must select the profile instead. `default_permissions` is the read-only profile, so turns that set no policy (goals, reviews) fall back to it. |
| Guard tests | `agents.test.ts` › "gives every Codex mode a permission profile, so no turn falls back to a bare sandbox" and "selects the named profile for a turn instead of the legacy sandbox policy"; `codex-permissions.test.ts`; `test/acp-codex-secrets.test.ts` (runs the real `codex sandbox` with each mode's profile, macOS only); `test/acp-codex-profile-contract.test.ts` (the bundled Codex accepts every mode profile, also on a thread that got no session config).                                                                                                                                                                                                               |
| If removed  | Codex can read `.env` and other secret files in read-only, Approve for me and Full access without any request, and in Ask every time whenever the command doesn't name the file.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Remove when | codex-acp selects a configured permission profile per mode itself. Verify with `test/acp-codex-secrets.test.ts` and one live `cat .env` per mode.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

## Upgrade checklist for codex-acp

1. Read the codex-acp changelog and the diff since 1.13.1 for #480, a stricter approval mode, a continue-on-deny option and per-turn usage. Decide which of parts 1 to 7 are now upstream. On 1.13.2-preview.5 (rechecked September 27, 2026), 11 of 13 hunks still applied unchanged; only part 1's `read-only` hunk was a no-op (superseded by #480) and needed one line added by hand to `AgentMode.all()`. `untrusted`, the `ask-every-action` behaviour, the missing `decline` option and the last-request-only usage were all unchanged from 1.13.1.
2. Bump `@agentclientprotocol/codex-acp` in `apps/server/package.json` to the exact version. Rename the patch file and the `patchedDependencies` key in `pnpm-workspace.yaml` to the new version, or remove them if nothing is left.
3. Re-create the remaining parts against the new `dist/index.js`: `pnpm patch @agentclientprotocol/codex-acp@<new>`, apply the still-needed hunks by hand (the function names above are stable anchors), then `pnpm patch-commit <dir>`. Drop the part-1 hunk if #480 is in.
4. `pnpm install`, then run the guard tests: `pnpm vitest run --project unit apps/server/src/agents/acp/agents.test.ts apps/server/test/acp-codex-do.test.ts`. A removed part's test must now pass against upstream code; if upstream renamed a mode or option id, update `agents.ts` (`conversationMode`, `CODEX_DO_MODE`) and the test together.
5. Check the mode meanings: the capability probe (`GET /api/providers/codex/capabilities?refresh=1`) lists the modes; `read-only` must still be read-only and the Do mode must still be `untrusted` with the user as reviewer.
6. Live: `pnpm test:live apps/server/test/codex-do.live.test.ts` (uses the ChatGPT login, about $0.03 at `gpt-6-luna` · low). Every Codex tool call must have an approval receipt, and a denied command must let the turn continue. For a deeper check, repeat the raw-ACP probe in [CODEX_DO.md](CODEX_DO.md#how-the-probe-ran) for `ls`, `cat .env`, `apply_patch` and an outside write.
7. Run `pnpm test`, `pnpm acp:coverage`, and the Codex rows of `test/acp.live.test.ts` (context recall, blocked write, cancel). Update this file, CODEX_DO.md and ACP_COMPLIANCE.md.
