# Spark tools coverage

Every agent session (Ask, Do, chats without a project) gets the `spark` MCP server from `apps/server/src/spark-mcp/`. Goal: an agent can answer any question about Spark through these tools. This table maps each user-facing area to the tool that answers it. Tool code lives in `spark-mcp/tools/`; `spark_guide` section `spark-tools` is the agent-facing version of this table and a test keeps it naming every read tool.

## Rules every tool follows

- Grants are per turn: a bearer token scoped to one workspace, chat and run, revoked when the turn ends. Every query filters by that workspace.
- Results pass through `renderResult`: secrets and tokens are redacted, long text and lists are clipped, and paging is explicit.
- Tools marked private record a `private_data` run observation, so the read-then-send guard (`approvals/egress.ts`, `taint.ts`) notes a later send out of that run: a non-blocking flag, or a note on the card when the mode asks.
- Tools never return file contents, terminal output, secrets or API keys. Two exceptions: `spark_browser_preview` returns the recent output of the preview server Spark runs, and `spark_terminal_run` returns the recent output of a command Spark runs for the agent; both are redacted, clipped and marked untrusted.
- Read tools change nothing. Actions follow the agent's mode (`actionPath`): at once in Auto, Bypass permissions, Approve for me and Full access, and in Accept edits when the user's message asked; otherwise a `spark_action` confirm card, and Spark does it after the user confirms.

## Gaps

- Onboarding progress and the setup checklist (`/setup`): providers and connectors are covered; there is no single "what is left to set up" answer.
- Repo agent config and trust (`/projects/:id/agent-config`): which repo instructions, skills and MCP servers reach agents is not readable.
- Status companion (desktop): its preferences live in the web app only.
- Git state of a project (`/projects/:id/git`, branches): only the default branch and live worktree count are exposed.
- Ship preview (`/tasks/:id/ship`: what a commit or PR would include and why it is blocked) is not exposed; it runs git and GitHub calls.
- Feedback comments and reasons are not shared; only counts (thumbs up and down) per group.
- Revert and ship stay in the UI; answering cards and stopping a chat are Ask Spark's only (below). Any new action must follow `actionPath` and use the `spark_action` confirm card when it asks. `spark_pr_follow_up_round` only queues items and lets the follow-up worker start the round; the push and GitHub replies still go through their own card (or Full auto).

## Ask Spark

Ask Spark's hidden chat gets every tool above except the chat-turn tools (`CHAT_TURN_ONLY` in `spark-mcp/server.ts`: `spark_push`, `spark_pull_request`, `spark_pr_follow_up`, `spark_pr_follow_up_round`, `spark_terminal_run`, `spark_outpost_ask`, `spark_outpost_start`, `spark_browser_sign_in`, `spark_artifact`), plus its own tools (`assistantOnly`): `spark_start_chat`, `spark_send_to_chat`, `spark_stop_chat`, `spark_archive_chat`, `spark_answer_card`, `spark_pause`, `spark_start_ticket`, `spark_post_outpost`, `spark_clear_finished`, `spark_set_aside` and `spark_meeting`. Its tools that ask follow **When Ask Spark acts** (Manual: a card; Act: at once) instead of an agent mode (`assistantPath` in `actions/ask-spark-limits.ts`).

## User guide

`spark_docs` reads the same Markdown pages the Docs page bundles (`docs/guide/`, parsed by `packages/contracts/src/guide.ts`). In development it reads `docs/guide` from the repo; the desktop package copies the pages (not the images) to `server/guide`. Image references come back as `[Screenshot: alt]`. Pages that say "Coming soon" are flagged `comingSoon`.

## Agent terminals

`spark_terminal_run` (`spark-mcp/tools/terminal-run-tool.ts`, `terminal-run-start.ts`, `terminal-run-folder.ts`) is offered only in a chat with a linked project and never to a read-only session. It has four actions and none that sends input. The design is in `AGENT_TERMINAL.md`.

- `start` resolves the folder (the chat's first root, or a folder under a linked root; a link that leads outside is refused), then asks `reviewSparkCommand` (`workflow/command-gate.ts`) with the mode the session is in now (`runs.used_mode`). A refusal comes back as `{ action: "start", refused: true, reason }`, not as an error. An ask raises the gate's card through `createApprovalGate(...).raise`, the same insert, wait and settle the agent's own commands use, so the run waits in `awaiting_approval` and a timeout stops the turn. Then it inserts the `agent_terminals` row (`decided_by` `card` or `mode`), appends the `agent_terminal_started` run event anchored in the reply, and returns the terminal's brief. The API process spawns the command from the row.
- A second `start` with the same MCP request id, command and folder returns the terminal that is still live instead of starting another.
- `status` lists this chat's agent terminals, newest first. `output` returns the last lines of one (60 by default, 200 at most, 16,000 characters) in a `<terminal_output>` block after the facts. `stop` asks for the stop as `agent`. `output` and `stop` answer only for a terminal of this chat.
- Audit: `spark/terminal_start` holds the redacted command, folder, mode, decision (`mode`, `card` or `refused`), reason, approval id and terminal id, and is marked ran without review when no card approved the start. `spark/terminal_stop` holds the terminal id, its name and who asked. The tool writes the entry for `agent`; `workflow/stop-terminals.ts` writes it for `turn_stopped`.
- Stopping a turn (`workflow/stop-run.ts`) stops the terminals that run and its member runs started. A start that lands after the stop was asked is stopped at once.

## Terminal sessions

Terminals live in the API process and Spark tools run in the worker, so the API records each open chat shell in `terminal_shells` (migration 0083: id, workspace, chat, label, folder, pid) when it attaches and removes it when it ends; startup clears the table. `spark_terminals` skips rows whose process is gone and reads the running program from the process table.

## PR follow-up

`spark_pr_follow_up` reads `pr_watches` and `pr_feedback_items` (migration 0087) for the chat's PRs or a PR number: phase, what Spark is doing, checks, rounds used of 3, and each item with author, write access, triage (Jev or rules) and state. Item excerpts come from GitHub reviewers and CI and are marked as data. `spark_pr_follow_up_round` shows a `pr_follow_up_round` card listing the items; on confirm it queues them (including held items from people without write access, or items past the round limit) and asks the worker to start a round. See `PR_FOLLOW_UP.md`.

## Chat history and compaction

`spark_chat_history` reads `messages` for one chat (this chat by default) as numbered turns, by range (`from`, `to`) or by a case-insensitive search, and lists the chat's `compactions` (migration 0088): method (`agent`, `spark`, `agent-auto`), tokens before and after, and the summary. A compacted session's preamble and the note after an agent's `/compact` tell the agent the tool exists. Compaction itself has no action tool: the card or the autonomy level decides. See `COMPACTION.md`.

## Sparks (named teammates)

`spark_chat` marks each user message an @mention handed to Sparks (`handedToSparks`) and lists `sparkReplies`: per Spark subagent the Spark, role, status, whether the main agent ran, cost and the full reply read from the child run's events, since the main agent only received a short hand-off note. `spark_sparks` adds `mentionJobs` (count, last chat, last time) from child runs with role `spark`. `spark_sparks` reads `teammates` and their linked chats (migration 0095) through `teammateList`: each Spark's face, role, state across its chats (idle, working, needs_you, done, failed), home chat id, chat count, last activity, defaults with project names, the standing instructions, whether the blob follows the name (`look`) and the instructions file path when the user set one, plus which starter Sparks are still offered. It is private because instructions and chat titles are the user's work data. `spark_create_spark` and `spark_update_spark` build a `create_teammate` or `update_teammate` card with every field the Spark will have (the update card also lists `changed`); a Spark made without `face` keeps a name-based blob, and `face: null` on an update puts one back; they refuse a duplicate name, an unknown project or an unconnected provider before asking, and save only after the user confirms. Saving new instructions, a name or a role closes the Spark's chat sessions so the next turn gets the new brief. See `TEAMMATES.md`.

**Sharing a chat with another chat.** A chat's reference is its id or its deep link (`spark-outpost://chat/<id>`, `spark-outpost-dev://` on the dev channel; `parseChatReference` in `packages/contracts/src/chat-share.ts`). `spark_chat`, `spark_chat_history`, `spark_task`, `spark_run` and `spark_audit` accept either in `chat`. The scope is the workspace, as before: any chat on this computer, in any project. `spark_chat` with `digest: true` returns `chatDigest` (`apps/server/src/chat-share/digest.ts`): state as of the call with a `live` line (a running chat says it is a snapshot), goal, last reply, latest task, changed file paths, PR links, pending approvals, queued count and the last turns (`limit`, at most 8). Results about a chat other than the session's own carry an `untrusted` note; text is redacted before it is cut. The composer turns a pasted chat link, or a pick from **Add another chat…**, into a text attachment built by `POST /api/chat-context` (`chatContextDocument`, at most 4,000 characters): the same digest without turns, plus the exact tool calls to read more. Nothing in this path writes to the shared chat; `chat-share.db.test.ts` holds the row counts steady.

## MCP servers

`spark_mcp_servers` (`tools/mcp-tool.ts`) lists the user's own MCP servers from `mcp_servers` and `mcp_server_enablements`: id, name, where it came from, transport, the exact command and arguments or URL, the names of its environment variables and headers, which names still have no saved value (`valuesMissing`), where it is on (all chats, this chat, projects), whether it changed since it was reviewed, and the last connection test. Secret values are never read.

Four action tools (`actions/mcp-actions.ts`, performed by `actions/mcp-perform.ts`) follow the same policy as every Spark action (`actionPath`): Spark does it at once in Auto, Bypass permissions, Approve for me or Full access, and in Accept edits when the user's message asked for it; otherwise the tool returns `waiting_for_user` and the user confirms a card.

| Tool                      | Action              | Does                                                                                                                                 |
| ------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `spark_add_mcp_server`    | `add_mcp_server`    | Saves a new user server. With no values to fill it is turned on for this chat (or `turnOn`: `all_chats`, `off`)                      |
| `spark_update_mcp_server` | `update_mcp_server` | Changes a user-added server; only passed fields change. Places where it was on and reviewed stay on (`keepEnabledAfterChange`)       |
| `spark_switch_mcp_server` | `switch_mcp_server` | Turns it on, off, or back to inherit for all chats, this chat or one project. Refused if the server changed after the card was built |
| `spark_remove_mcp_server` | `remove_mcp_server` | Deletes the server, its keychain values and its enablements                                                                          |

Hard rails, in `actions/mcp-config.ts` and the tool schemas:

- The tools take only the names of environment variables and headers. Each name is saved as a placeholder with no value; the user fills it in Settings → MCP servers. A server with missing values is never turned on by a tool.
- The command, each argument and the URL are refused when they look like a secret (`redactText` changes them, a `--token=…`, `--api-key value` or `KEY=value` form with a sensitive name, URL credentials, or a sensitive query parameter).
- A stdio command must be one program (arguments go in `args`), single-line, with no control characters. The card and the audit carry the exact command and arguments.
- Imported servers cannot be edited, only switched or removed, as in Settings.
- Every add, update and removal writes an `agent_config_audit` row (`subject` `mcp`, `detail.change`, `detail.by` `agent`, the run id) next to the run-audit entries `spark/<action>` that every Spark action writes; switches are audited by `setUserEnablement`.
- Changes reach new agent sessions only. Running sessions are not restarted, and every result says so.
