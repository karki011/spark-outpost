# Simple orchestration

Plan and inventory for removing Spark's harness. Written October 9, 2026 on `spark/simple-orchestration`, cut from `main` at 0.1.0-beta.11 (`dcb421dd`). No feature code was changed for this document. Nothing here was run: every statement about behaviour was read from the code, and is marked where it could not be confirmed that way.

**The owner's decision (October 9, 2026).** "Remove our harness completely and just do simple orchestration driven work, subagent or worktree, let the LLM decide." "Strip down and keep it simple." And, the same day: "We will delete all unwanted and we don't need an option for Spark workflow or not; everybody gets it."

What that means, as agreed:

- One chat is one provider agent session. The user's message goes to the agent as typed.
- The agent decides whether to plan, use its own sub-agents, or (Outposts release 2, not on `main` yet) propose sub-chats in an outpost that the user starts.
- Spark stays a moderator. It keeps only what only Spark can do: the approval gate and safety floor, the audit and ran-without-review marking, worktrees and branches per chat, the publish rules and the publish step for Full auto → PR, pull request tracking and follow-up rounds, Spark action tools, Outposts, Terminal sessions, model and usage display.
- There is one path. No setting chooses between the old and the new one, and **Use Spark workflow** is removed.
- Nothing new replaces what is removed: no new heuristics, caps, timers or cards.

This file supersedes [HARNESS_SIMPLE.md](HARNESS_SIMPLE.md) and [HARNESS_PLAN.md](HARNESS_PLAN.md) for where the product is going. Those two still describe what runs on `main` today. Paths without a prefix are under `apps/server/src/`. Line counts are non-test lines at `dcb421dd`.

## Recommendation

1. Replace `orchestrate` with one small turn function that calls the existing `runAgentTurn` on the chat's own run. That function already carries the gate, the audit, the session, tasks, plans and usage.
2. Give the chat's run the three publish guards that only a solo Builder has today. This is the one place where safety enforcement must move.
3. Keep the publish step as a second prompt to the same session, sent only when there is unpublished work and a reason to publish.
4. Delete the Coordinator, pieces, Builder and Critic child runs, intake, routing, Spark-run checks, the laws and every Jev call inside a turn. Jev stays for the Map, pull request feedback sorting and the companion.
5. Keep old chats readable with no migration: stored rows, the read schemas and a read-only crew view stay.
6. Build it on this branch in an order that compiles and passes at every commit, using a test-only seam that is deleted before the merge. Ship it in one release.
7. Ask the owner to approve the visible removals in section 3 and the `AGENTS.md` wording in section 2.4 before the deletion lanes start.
8. Estimated removal: about 55,000 lines, of which about 20,000 are server source.

## 1. Inventory of today's harness

### 1.1 The path of a turn today

`workflow/worker.ts` claims a job and calls `orchestrate` (`orchestration/orchestrator.ts`, 499 lines). In order:

1. Start the run, record an outpost request in the audit, note a project move.
2. Find the chat's place (`chat-place.ts`); the worktree is created later, when a build starts.
3. Offer compaction if the chat is almost full (`compaction/prepare-turn.ts`).
4. Hand an `@Spark` mention to that Spark as a child run (`spark-handoff.ts`).
5. Decide whether this is a plan turn (`/plan`, or a Plan-mode chat).
6. **Shortcut:** with Spark off and no changing project turn, or for a short "push it" message on an open task (`instruction-turn.ts`), call `runAgentTurn` on the chat's own run and finish. This is the only direct path today.
7. Otherwise: start a code scan, run intake (one batched Jev call, up to 3 s, rules as fallback), read the need, save a plan agreement, link a ticket, create the worktree, load the project's checks, write an orchestration row.
8. Drive the state machine (`transitions.ts`): a Reader in place, or a Builder child run, or the Coordinator and pieces; then Spark-run checks and a fix turn; a Jev verdict; a Critic and fix rounds; the laws review; keep or ship; a publish child run.
9. Compose the final text from every helper's reply plus Spark's notes, close copies and task sessions, record kept changes, send the next queued message.

## 2. The target

### 2.1 The path of a turn

One function, `runChatTurn`, replaces `orchestrate`. Every turn:

1. Start the run. Record an outpost request in the audit. Note a project move.
2. Place the chat. In a mode that can change files, create the chat's worktree and branch now if it has none.
3. Offer compaction if the chat is almost full (unchanged).
4. Hand an `@Spark` mention to that Spark (unchanged).
5. If the message starts with `/plan`, or the chat is in the agent's Plan mode, start the turn in the agent's own plan mode (`asPlanTurn`, as today).
6. Call `runAgentTurn` on the chat's own run. The prompt is the user's message.
7. If files changed: write the "Changes kept" record with Revert, link a mentioned ticket, and run the publish step when it applies.
8. Finish the run. Record kept changes. Send the next queued message.

There is no orchestration row, no child run, no retry and no Spark text added to the reply except the publish result line.

| Case                             | What differs                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| (a) Chat with no project         | Step 6 only. No gate is needed because there is no folder; Spark action tools still ask by the agent's mode. This is today's Spark-off path                                                                                                                                                                                                                                                                                                                                                                                                |
| (b) Project chat in a worktree   | In a read-only mode the turn gets the read-only gate (`prepareAskRun`). In any other mode it gets the full gate with a snapshot (`prepareDoRun`), so Changes, Revert and the audit work as today                                                                                                                                                                                                                                                                                                                                           |
| (c) Full auto → PR               | After step 6, if the chat's branch has work that is not pushed or has no pull request, Spark sends one publish prompt (`publishTurnPrompt`) to the same session. With no project or git repository it says "No pull request" in one line. With no remote, Spark's ship service (the Ship button's code) commits on the chat's branch. A chat working in the user's checkout has no branch of its own: the change is kept, nothing is pushed and the reply says so in one line. Without a GitHub connection the push gives a Create PR link |
| (d) Pull request follow-up round | The poller starts a run with the round prompt and `followUpRound` set, as today. The turn is the same function. The follow-up basis allows a push to the chat's own branch. The publish step uses the follow-up prompt. `finishRound` reads the reply and Spark posts the per-item replies. Nothing here changes                                                                                                                                                                                                                           |
| (e) Outpost request              | The request is wrapped with its label by `asAgentReads` and audited, as today. A request that is not from the user counts as no user text, so it can never be a publish request (`userText`)                                                                                                                                                                                                                                                                                                                                               |
| (f) Terminal session             | Unchanged, except that every launch now gets Spark tools and the session note, because the off switch is gone                                                                                                                                                                                                                                                                                                                                                                                                                              |

**The publish step in detail.** Today it is a Builder child run that resumes the chat's session. In the target it is a second `runAgentTurn` call on the chat's own run. Two things must be built for that, both in lane B3: the run's snapshot is taken once, not once per prompt, and one run may close two assistant messages. If either proves fragile, the fallback is today's mechanism unchanged: a child run that resumes the chat's session, labelled "Publish" instead of "Builder".

**Tasks.** Each changing turn joins the chat's open task (`taskForWorkingRun`, already called inside `runAgentTurn`). Intake no longer starts a new task when a message looks unrelated.

### The prompt

Spark appends one block to the agent's system prompt for a chat turn. It is built by `chatPrompt(facts)` in `apps/server/src/workflow/chat-prompt.ts` (wording in `chat-prompt-text.ts`) from plain facts, with no I/O. `publishPrompt(facts)` in `publish-prompt.ts` builds the second prompt of the publish step. `withChatPrompt` in `chat-turn-prompt.ts` gathers the facts and sends the block for the chat's own run; `publish-step.ts` sends the second prompt. The owner approved this wording on October 9, 2026:

```
You are working for the user in Spark Outpost.
Folder: <path> · Branch: <branch> (a worktree of <repo>)

How to split work
- Small or single-area change: do it yourself.
- Independent parts inside this repo and branch (searching, reviewing, edits to separate files): use your own sub-agents.
- Work that spans repos, needs separate branches or pull requests, or is big enough that the user should steer each part: propose sub-chats with spark_outpost_draft and say why. The user starts them; you don't.
- If the request is unclear, ask one question and stop.

Engineering
- Change files with your file-editing tools, not shell commands such as heredocs, cat > or sed -i, so the user sees each change as a diff.
- The repo's own instructions (AGENTS.md, CLAUDE.md) take priority over these.
- Read the code your change touches before deciding anything.
- Before writing code, stop at the first of these that works: it doesn't need to exist · the codebase already has it · the standard library has it · the platform has it · an installed dependency has it · it can be one line · otherwise write the minimum that works.
- Never cut: validation at trust boundaries, data-loss handling, security, accessibility.
- Logic with a branch, loop, parser, money or security in it gets one small test.
- Small, coherent changes that match the surrounding code. No unrelated cleanup.
- Run the checks that cover what you changed.

Reporting
- Lead with the result: what changed, what you verified.
- End with what you skipped or didn't check, and any risk.

Publishing
- <one line from the chat's autonomy and state>
```

The block holds no safety rules, no role names and nothing about when to plan. It grants nothing: the gate and the publish rules decide, and the Publishing line only tells the agent what to expect.

In a Do turn (not a Plan-first turn) the last How to split work line reads instead: "- When the user should choose, or a detail you need is missing, call AskUserQuestion (Codex: request_user_input) with the options instead of writing them in your reply, and use the answer it returns." Ask, read-only and Plan turns keep "ask one question and stop". This line was added on October 22, 2026 for question cards (ACP form elicitation) and needs the owner's confirmation.

Why, measured with real Claude Opus 5.5 through the whole Spark path (worker, Spark tools, a Manual Do chat in a repo; `apps/server/test/ask-tool-choice-app.live.test.ts`), 3 runs per prompt, counting turns that raised a question card. ## 6. Decisions for the owner

1. **A push with no reason to publish, in a mode that asks.** Today a Builder is refused and a run without a role gets a card. Recommended: refuse, as for a Builder, so no outcome changes. The other choice is the agent mode's ordinary card; the own-branch rule would still refuse any other branch.
2. **Spark stops running the project's checks.** Then "a draft when checks still fail" cannot be decided by Spark. Recommended: strip, and open a draft only when Settings says so. The other choice keeps one check run before publishing, with no fix turn, which keeps the sentence and about 1,200 lines.
3. **`/plan` and Plan-mode chats.** Recommended: keep both. `/plan` starts one turn in the agent's own plan mode; in a Plan-mode chat every message does. Tickets' and Slack's "Plan first" keep sending `/plan`.
4. **The "Plan saved" line.** Recommended: only for a plan the user approved.
5. **Jev.** Recommended: no Jev call in any turn; keep it for the Map, pull request feedback sorting and the companion; remove "Check changes with Jev". "Ask Jev about this change" as a button is new work and is not built here.
6. **Auto in the model picker.** Recommended: keep the entry, meaning the agent's default model.
7. **Agent TV.** Recommended: keep the window and the rail, showing the chat's agent and Sparks; it is where provider sub-agents will appear. The other choice removes it now.
8. **The category chip.** Recommended: remove. The other choice keeps a rules-only chip that reads the wording and changes nothing in the turn.
9. **The "act as a coordinator" line in "Working with the user".** Recommended: keep as written; it is the only nudge toward sub-agents and the agent is free to ignore it.
10. **Showing a provider's sub-agents as their own rows.** Recommended: a follow-up after this release, starting with a check against real adapters.
11. **The compaction card.** Recommended: unchanged here. Both agents compact themselves, so it can be looked at later on its own.
12. **Old turns.** Recommended: show each helper's reply, model and cost read-only; do not show old piece boards.
13. **Order against Outposts release 2.** `spark/outposts-r2` edits only files this plan keeps. Recommended: merge release 2 first, or keep the four files named in phase A at their paths until it merges.
14. **Chats working in the user's checkout** lose the isolated copy and its merge card. Recommended: accept; the worktree per chat is the default and the checkout was the user's choice.
15. **Dead settings columns.** Recommended: leave them one release, then drop.

Raised by phase B:

16. **A Plan-mode chat makes a worktree.** Every message in a Claude Plan-mode chat is now a plan turn, which is a changing run: it gets a worktree, a snapshot and the full gate, even for a question. The outcome is read-only until the plan is approved. The other choice is a read-only run that cannot build after approval. Measured on this repository (4,223 tracked files): `git worktree add` takes about 1.5 s and 41 MB of checkout, with objects shared; cloning `node_modules` into it took about 25 s on a busy machine and near-zero new disk (APFS clones). It is paid once per chat, at its first turn in any mode that can change files, not per question. The worktree is the session's folder, so it stays while the chat lives; deleting or archiving the chat removes it, and its branch too when it has no commits beyond its base.
17. **Codex plans are never approved.** A `<proposed_plan>` reply is saved as proposed; only the Jev agreement approved it, and that is gone. Until the Codex adapter's own approval is confirmed, a Codex plan gets no "Plan saved" line. Since October 11, 2026 nothing presents such a plan as agreed: the Work panel heads it **Proposed plan**, and `spark_task` returns it as `proposedPlan` with `agreedPlan` null.
18. **Full auto → PR publishes earlier unpublished work.** The publish step acts on whatever is unpublished on the chat's branch, also after a turn that only answered a question.
19. **A publish prompt that fails or is stopped** ends the run as failed or cancelled, with the first reply stored and the kept record written. The other choice ends it as succeeded with a "not published" line. **The publish block leads with Spark's line (October 11, 2026).** The agent's reply to the publish prompt is held (`workflow/publish-step-lead.ts`) until `publishedState` is read, then the second message is written as Spark's result line followed by what the agent said, in the stream and in storage alike; commands still stream live. The prompt says the user does not see it and asks for a statement of the result. A message that asks only for the push still gets the prompt when the agent pushed before it committed: the change is not on the remote.
20. **The publish note.** `withPublishNote` still adds "The user asked for this to be pushed…" to a changing run whose message asked, and repeats it on the publish prompt. The Publishing line of the chat prompt and the publish prompt say the same. Recommended: delete the note in phase C.
21. **The Publishing line is fixed when the session opens**, a read-only turn at Full auto → PR is told to push, and so is a worktree on a branch the chat does not own (the gate refuses that push; `ChatPromptFacts` has no field for it). Recommended: leave the Publishing section out of a read-only turn; accept that the line reflects the turn that opened the session, since the publish prompt arrives each time it applies.
22. **No basis, Codex Approve for me or Full access.** Those modes are a basis and never reach the gate, so nothing here limits which branch such a run pushes. `spark/push-floor` flags it after the fact (`other_push`).
23. **Ticket suggestions.** A ticket named in a turn that changed nothing is no longer saved as suggested, and the chat's first branch no longer carries the ticket key (the worktree exists before the ticket is linked; the ship title still gets the key).
24. **New wording to approve.** `CHAT_PUBLISH_REASON` ("This chat's agent pushes and opens a pull request only when the user's message asks for it, the chat is at Full auto → PR, or its mode is Auto or Bypass permissions (Full access)"), "The change is kept but was not committed: …", the three Publishing lines in "The prompt", and the empty reason on the kept record (the web shows "Kept automatically." or "Kept by Full auto → PR.").

## 7. Risks

- **The publish guards are the one safety change.** If lane B2 misses one of the three places, the chat's agent could push a branch that is not its own in a mode the gate cannot see. The tests named in B2 are the control, and a real-provider pass in Bypass permissions and Full access before release.
- **The tests are built on the harness.** 78 server test files and 53 browser specs reach their subject through the orchestrator's support code. Porting is most of the work, and a test ported carelessly can stop testing what it claims.
- **Quality may drop on large or risky work.** There is no second reviewer, no Spark-run checks and no retry on a stronger model. What the user gets depends on the agent and on the repository's own checks.
- **Codex has less to fall back on.** The "Working with the user" text for Codex says to keep a checklist because it has no sub-agents; the pinned adapter does carry sub-agent events, but whether Codex uses them for a given sign-in is unknown. Large Codex builds lose parallel pieces.
- **Cost can move either way.** No per-role cache writes and no doubled Coordinator turns; but no cheap model for small work on a chat pinned to a top model.
- **Two prompts in one run** (the publish step) is new for the run and message code. The fallback is named in section 2.1.
- **The `gh` read question** in section 2.3 may be a present bug that the move makes visible to every turn.
- **A worktree is created on the first changing-mode turn**, even for a question, because nothing classifies the message any more.
- **Visible removals are many.** Agent TV, the Crew tab, the model why-line and three guide pages change at once. The owner's approval of section 3 is needed before phase D.
- **Sub-agents are invisible as agents** until the follow-up in decision 10. Their tool calls are gated and audited, but the user sees one agent.
- **Merge order.** Deleting 55,000 lines on a long-lived branch collides with anything else that touches `orchestration/`. Release 2 touches only kept files; other open branches were not checked.
- **This plan was read, not run.** Line counts are exact; the behaviour claims come from the code and its tests. The first lane to touch each area should confirm them.
