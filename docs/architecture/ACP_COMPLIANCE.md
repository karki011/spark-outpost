# ACP compliance audit

Checked on September 27, 2026 against the official spec at agentclientprotocol.com (overview, initialization, session setup, prompt turn, content, tool calls, file system, terminals, agent plan, session modes, session config options, slash commands, extensibility, schema), the stable v1 schema in [`docs/reference/acp/schema.json`](../reference/acp/schema.json) and the unstable v1 schema bundled with `@agentclientprotocol/sdk` 1.5.0. Pinned: `@agentclientprotocol/sdk` 1.5.0, `claude-agent-acp` 0.81.2 (Claude and Z.ai), `codex-acp` 1.13.1 with our patch. Per-surface status lives in [ACP_COVERAGE.md](ACP_COVERAGE.md).

Verdicts:

- **compliant**: meets every MUST and SHOULD we are subject to.
- **deviation**: departs from a MUST or SHOULD, or from the spec's intent. Each has a fix or a justification.
- **extension**: vendor or unstable surface, used the way the spec allows (`_meta`, advertised capabilities, unstable schema).

Code paths are relative to `apps/server/src/agents/acp/`.

## Summary

- No MUST is broken. Every optional method we call is gated on the capability the agent advertised, and we only advertise client capabilities we implement.
- `session.notices` / `notice` are not our extension. They are the unstable session notices field from the RFD, defined in the SDK's unstable schema, and both adapters check exactly `clientCapabilities.session.notices`. They stay where they are. The coverage check now verifies them against the SDK's unstable schema instead of warning "Not in the schema".
- Adapter-specific reliance: `_meta.claudeCode.options` hardening (Claude, Z.ai), `_meta.jetbrains.air` `sessionFailure` (both adapters), the codex-acp patch's `ask-every-action` mode, its `decline` option order, its untrusted session roots and its named permission profiles per turn (parts 2, 3, 5 and 7 in [PATCHES.md](PATCHES.md)), and `--hide-claude-auth` (Z.ai).

## Slash commands

Spec: commands are advertised with `available_commands_update` (name, description, optional input hint) and invoked as ordinary prompt text that starts with `/name`. The spec puts no MUST on clients.

**How the adapters detect a command.** codex-acp 1.13.1 (`CodexCommands.parseCommand`) reads only the first prompt block, trims it and checks for a leading `/`; the name is lowercased. claude-agent-acp 0.81.2 passes the text to Claude Code, which treats a message whose text starts with `/` as a command (`LOCAL_ONLY_COMMANDS` and `REPLAY_HIDDEN_COMMANDS` check `firstText.startsWith("/")`). A leading space doesn't help against Codex, because it trims. So escaping means the first block must not start with `/` after trimming.

**What we do** (`slash-commands.ts`, `session-commands.ts`, `apps/web/src/chat/composer/`):

- `available_commands_update` becomes a `commands` output, stored on `provider_sessions.available_commands` (migration `0035_session_commands.sql`) and read back when the session is resumed. `GET /api/conversations/:id/agent-commands` returns the current chat session's commands without the blocked ones.
- The `/` menu lists Spark Outpost's commands first, then the agent's. It filters as you type (name prefix first, then name or description), and is keyboard navigable (arrows, Enter or Tab to pick, Escape to close). It reuses the file picker's listbox styles and passes axe WCAG 2.1 AA.
- Our commands run in the browser and are never sent raw: `/fresh` (start a new agent session for this chat, dropping the resumed context), `/model [name]` and `/effort [level]` (set it directly when the name matches an offered option, otherwise open the picker on that tab), `/plan …` (sends the text `/plan …`, which the server turns into a plan turn in the agent's own plan mode; [HARNESS_SIMPLE.md](HARNESS_SIMPLE.md#5-plans-the-plan-line-and-plan-mode)), `/review …` (sends a review request, which the orchestrator reads as review intent in Do, so a Critic reviews). Our names win a clash with an agent command or a blocked name (Codex's own `/review` and `/plan` are hidden).
- Helper text: each row shows `/name`, its argument hint (for example `/effort low|high|max`, built from the agent's efforts), a one-line description, and where it runs ("Spark" or the agent's name). An agent command without a description reads "No description from {agent}". The highlighted row's example or longer explanation shows under the list. A typed blocked command shows why it is blocked, and a typed unknown command says it will be sent as text.
- Sending: in a continued session, an advertised, unblocked command is sent unchanged as the first text block, with a "Sent /name to …" step. Anything else that starts with `/` (unknown, blocked, or in a fresh session, where our note already comes first) is sent with a first line saying it is text, not a command, plus a "Sent … as text" or "Blocked …" step. The title request is not appended to a command.
- Blocked names are refused in the composer with a notice and never sent. The server escapes them too, as a backstop.

## Recommendations (not done here)

1. **Cancellation SHOULDs.** Mark open tool steps cancelled on Stop and keep reading updates until the prompt response (ACP_COVERAGE M1 item 2).
2. **Refusing without a reject option.** If a future agent offers no reject option, consider a JSON-RPC error instead of `cancelled` outside a cancellation, and record it.
3. **SDK private API.** Replace the `attachSession` cast when the SDK exposes a public way to open a session from a `session/resume` or `session/load` response.
4. **Client info.** Send the real app version; record `agentInfo` (name, version) on the run for the audit view.
5. **Schema tracking.** Keep `docs/reference/acp/schema.json` on the stable v1 schema; the coverage check now reads the SDK's unstable schema for the entries outside it.
