## Analysis

### Method

Each cell starts from a fresh git repo of the Ledger Lite fixture under the session scratchpad, runs through the server's real code path against an isolated PostgreSQL schema (the same setup as `apps/server/test/*.live.test.ts`), then verifies the result with the visible `node --test` suite, task-specific hidden checks (copied in only after the run, and confirmed to fail before it) and an allowed-files list. Both modes start from the same message: Claude, Sonnet 5, medium effort, Do mode, Full auto.

- **Direct** bypasses the orchestrator inside the benchmark runner only. It claims the queued run and calls `executeChildRun`, the single-agent turn every crew member uses, so there is no intake, no Jev and no role prompt. No server setting was added: the bypass lives in `scripts/bench/live.ts`, so a production run can't reach it.
- **Harness** claims the same kind of run and calls `orchestrate` with Auto routing and the Jev intake recorder.

Costs are the per-run USD figures that the Claude agent reports, plus Jev's own reported cost. No run needed an estimate. Codex never ran because no depth chose a Critic.

### Results in one paragraph

All 30 runs passed verification (15/15 per mode), so on these tasks quality is a tie. Over the same 15 tasks the harness cost **1.90×** as much ($2.42 against $1.27) and took **1.71×** the wall time (686 s against 402 s). The result splits cleanly by task size. On single-file work (T1 to T3) the harness broke even or won. On multi-file work (T4, T5) it lost clearly, at 2.6 to 2.7× the cost and 1.6 to 2.7× the time.

### Where the harness won

- **T1, trivial: 54% cheaper and about 15% faster.** Jev routed the only Builder to Haiku 4.5 at low effort with confidence 0.91 to 0.92, just above the 0.9 act threshold, and the Builder made the same 4-line diff. This is the one place where per-agent model routing paid off, and it paid off every time: $0.023 against $0.050 in all 3 repeats.
- **T5, parallel Builders: about 24 s saved on average.** In every T5 run the Architect put the `report.ts` and `invoice.ts` changes in one parallel group. The two Builders ran side by side in worktree copies and merged cleanly, saving 19, 28 and 26 s of Builder time compared with running them one after the other.

### Where the harness lost, and why

- **Planning overhead dominates T4 and T5.** Jev's intake confidence on these prompts was 0.73 to 0.80, below `ACT_AT` = 0.9, so depth fell back to the rules: multi-file risk → `plan_execute` → an Architect on Opus 5.5 at high effort. That Architect alone cost $0.12 to $0.15 and took 25 to 29 s per run, which is 38 to 48% of the harness cost and more than the whole direct run on T4.
- **Splitting a small change across Builders costs more.** The plans had 3 or 4 steps. Each Builder starts cold and re-reads the repo, so the Builders' cache writes were about 2× the direct agent's (25 to 42k tokens against 12 to 15k). Builder spend alone was 1.5 to 1.6× the direct agent's spend on the same task. T4 had no parallelism at all: every step ran in sequence.
- **The small tasks gained nothing from routing when Jev was unsure.** On T2 and T3, Jev's Builder route confidence was 0.36 to 0.54, so the Builder stayed on the pinned Sonnet 5 at medium effort. The cost matched direct to within 4%. The T2 time ratio of 1.43× comes from two slow Builder turns (24 to 25 s, against 14 to 16 s everywhere else) with the same model and the same tool-call count, so it's most likely API latency noise, not harness overhead. The harness's own overhead outside agent turns was about 1 s on single-Builder runs and 3 to 7 s on multi-Builder runs.
- **Quality signals.** Both modes produced equivalent diffs. In 2 of 3 T4 runs the harness also edited the README module list. That's allowed by the check, but nobody asked for it. Jev's per-step quality scores on the first T4 Builder were low (1.8 to 2.7 of 4) even though the final result verified, because intermediate steps leave the refactor half-done by design.

### Noise and sample size

This is 3 repeats per cell on one small fixture with one provider. Per-cell cost was very stable: within ±5% for T1 to T3, ±12% for T4 and T5. Wall time was noisier: the direct T5 run ranged from 44 to 72 s, and harness T5 from 71 to 109 s. Treat time ratios within about 1.5× as noise. Every task passed in both modes, so this benchmark can't show a quality benefit from planning or review. That would need harder tasks where a single agent sometimes fails, and a depth that includes the Critic. The tasks were written for this benchmark and their prompts name the files involved, which favours a single agent. Vaguer real requests may benefit more from an Architect.

### Tuning suggestions

1. **Skip the Architect when the request is already a plan.** When the intake risk is `multi-file` but the request names its files, touches 6 or fewer of them, and Jev's intake confidence is at least 0.7, run `execute` with one Builder instead of `plan_execute`. Based on these runs, that would have saved about $0.13 and about 27 s per T4 or T5 run, taking T4 from 2.7× to roughly 1.5× the direct cost. Also consider Sonnet 5 at high effort for the Architect when the plan will have 4 or fewer steps.
2. **Don't split a plan that has no parallel group.** If `planGroups` finds no independent group (T4), give all the steps to one Builder in one turn instead of 3 or 4 cold starts. That removes about 2× in cache writes and the transition calls between steps. Keep separate Builders only for steps that can actually run in parallel. Even then it only pays off when each parallel step takes more than about 20 s, because T5's roughly 24 s saving was eaten by the extra setup and the final test step.
3. **Use a lower act threshold for downgrades than for upgrades.** Every downgrade to Haiku that cleared 0.9 succeeded (4 of 4) and halved the cost.
