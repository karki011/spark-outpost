### H3 · Ledger file migration (migration, code and tests)

> Ledger files are moving to a new format. Add src/storage.ts with loadLedger(text: string): Entry[], which reads either format; saveLedger(entries: Entry[]): string, which always writes the new format; and migrateLedger(text: string): string, which converts an old file to the new format and returns a new-format file unchanged. The old format (version 1) is a JSON array of { "category": string, "amount": string }, where amount is a dollar string such as "$1,234.50". The new format (version 2) is a JSON object { "version": 2, "entries": [{ "category": string, "cents": number }] }. Loading either format trims and lower-cases categories, and a version 1 entry with an empty or missing category gets the category "uncategorized". Anything else, such as another version number, invalid JSON or an amount that is not a number, throws an Error. Add tests in test/storage.test.ts and list the new module in the README.

## Analysis

### Method

Same runner, fixture, settings and verification as the [first run](harness-vs-direct-2026-09-26.md): fresh git repos under the session scratchpad, the server's real code path against an isolated PostgreSQL schema, Claude Sonnet 5 at medium effort in Do mode at Full auto, and the visible suite plus hidden checks that fail before the run. The harness now runs with the tuning rules in [HARNESS_PLAN.md](../architecture/HARNESS_PLAN.md#harness-tuning-september-26-2026). This run adds the hard set H1 to H3 and uses 2 repeats per cell (the first run used 3), with the order H1–H3, T4, T5, T1–T3 so the hard set got its repeats first. Everything fit in the budget: $3.86 of the $4.80 cap, 32 runs.

### Results in one paragraph

On the standard set (T1 to T5) the tuned harness now costs about the same as the direct agent: $0.410 against $0.416 summed over the task means (0.99×), down from 1.90× before tuning. Wall time went from 1.71× to 1.05×. The whole gain is on T4 and T5, where the harness went from 2.7× and 2.6× the cost to 1.05× and 1.12×. On the hard set the harness passed 5 of 6 runs and direct 4 of 6, at 1.2 to 2.3× the cost. That quality difference is one run and comes down to one ambiguous check (see below), so it is not evidence that the harness is better.

### What each change did

- **Skipping the Architect** fired on every T4 and T5 run: the intake confidence was 0.72 to 0.76 and the requests name 6 and 3 files, so one in-place Sonnet Builder did the work. T4 fell from $0.286 to $0.097 and from 91 s to 38 s; T5 from $0.371 to $0.164 and from 86 s to 48 s. The reason is recorded on the intake decision.
- **The Architect's tier** mattered on the hard set. H2 names its 6 files and Jev scored it moderate, so its Architect ran on Sonnet 5 at high effort for $0.10 to $0.13. H1 names no files, counts as vague, and kept Opus 5.5 at $0.22 to $0.23. That single Architect is most of why H1 cost 2.25× direct.
- **One Builder for sequential steps**: every planned run (H1 and H2, 4 runs) used one Builder after the Architect instead of 3 or 4. No run had a parallel group, so the parallel rules (worth-splitting and the Large line) were not exercised live. They are covered by unit and DB tests only.
- **Architect notes to Builders**: the Builders after an Architect on H1 and H2 cost $0.11 to $0.13, compared with $0.12 to $0.17 for the direct agent doing the whole task. That is in the direction of fewer re-reads, but with 4 runs this is within noise.
- **The lower downgrade threshold never engaged.** On T2 and T3, Jev would have used Haiku 4.5 at 0.34 to 0.58 confidence, well below 0.8. On T4 and T5 the risk was multi-file, which keeps 0.9. Jev's picks are now recorded on every route ("Auto would have used"), which is how this can be read.
- **The Critic never ran**, so Codex did not run either. Jev never answered `plan_execute_review` for these prompts, and none was destructive. The rule that keeps the review when Jev suggests it is in place and tested, but this benchmark did not trigger it.

### Hard set

- **H1 (half-cent rounding) and H2 (split with a stable API)** passed in all 8 runs in both modes. Sonnet found every rounding site and kept every export without help, so these tasks are not hard enough to separate the modes.
- **H3 (ledger migration)** failed 3 of 4 runs, all on the same hidden check: `migrateLedger` must return a new-format file unchanged. Direct and harness agents alike returned the normalised file (lower-cased categories, sometimes pretty-printed), because the prompt also says loading normalises categories. The one harness pass followed the "unchanged" wording literally. This is a prompt ambiguity, not a quality difference between the modes.

### Noise and sample size

2 repeats per cell, one fixture, one provider. Per-cell cost varied by up to ±10%; wall time by up to 2× within a cell (H2 direct 32 and 64 s, T3 direct 14 and 28 s). The old and new harness numbers come from runs about an hour apart, and the old ratios use their own direct runs as the base; the mean direct cost per task moved by at most 12% between the two runs (T4: $0.105 then $0.093). Treat time ratios within about 1.5× and pass-rate differences of one run as noise.

### Next recommendations
