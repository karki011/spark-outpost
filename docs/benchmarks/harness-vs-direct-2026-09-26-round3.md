### H3 · Ledger file migration (migration, code and tests)

> Ledger files are moving to a new format. Add src/storage.ts with loadLedger(text: string): Entry[], which reads either format; saveLedger(entries: Entry[]): string, which always writes the new format; and migrateLedger(text: string): string, which converts an old file to the new format. A file that is already version 2 is returned exactly as given, character for character: migrateLedger does not normalise its categories or reformat it, though it still throws if the file is not a valid version 2 file. The old format (version 1) is a JSON array of { "category": string, "amount": string }, where amount is a dollar string such as "$1,234.50". The new format (version 2) is a JSON object { "version": 2, "entries": [{ "category": string, "cents": number }] }. Loading either format trims and lower-cases categories, and a version 1 entry with an empty or missing category gets the category "uncategorized". Anything else, such as another version number, invalid JSON or an amount that is not a number, throws an Error. Add tests in test/storage.test.ts and list the new module in the README.

### Results in one paragraph

All 20 runs passed. The new hard tasks still do not separate the modes: a lone Sonnet agent solved the cross-module contract (H4), the month-end and time-zone invariants (H5), both deletion tasks and the review. Summed over the runs the harness cost $1.92 against $1.38 direct (1.39×) and took 0.93× the wall time. Where the harness ran one Builder (D1, H3, H4, H5, R1, T1) it cost 0.46× to 1.24× direct. The extra cost is the three planned tasks: D2 at 3.1× (Opus Architect plus Critic), H1 at 2.0× (Opus Architect) and P1 at 1.6× (Sonnet Architect).

### Jev's decisions

- **Scope.** Jev answered the scope on all 10 harness runs, confidently (0.5 or more) on 6. It never chose one spot, so the one-spot skip never fired. The small tasks got low scope confidence (H4 0.38, H5 0.36, T1 0.46), and H1 got "across the codebase" at 0.23.
- **The Architect rule.** An Architect ran 4 times: D2 by the destructive rule (Opus), H1 by the unsure rule (Opus, scope confidence 0.23), and P1 twice by the short-plan rule (Sonnet). The simple rule never fired live, because every planned request was a few modules or wider.
- **Jev's Architect pick vs the rule.** Every Architect route recorded both (table above). Jev's model confidence was 0.32 to 0.35 each time, so the gate never acted and the rule's pick always ran. Jev agreed with the rule once (P1 #2, Sonnet high). It picked Sonnet high for H1, the tuned report's own recommendation, where the rule kept Opus, which would likely have saved $0.05 to $0.10 there (a Sonnet Architect cost $0.11 to $0.15 on P1). It picked Haiku for the P1 #1 and D2 Architects, which would have been a risky downgrade on multi-file and destructive plans; the gate and the destructive rule blocked both.
- **Keep-or-raise conclusion: keep.** No Jev-picked Architect ran, so there is no pass-rate evidence either way, and the policy leaves the 0.9 and 0.8 gates where they are. Jev's Haiku picks argue against lowering them. If later runs show Jev's Architect picks acting and the pass rate on those runs falls below the rule's, raise the Architect gate.
- **Parallelism.** Jev's parallel call ran after all 4 plans and answered each time. No run used parallel Builders. The heuristics (the Architect's `Parallel:` and `Large:` lines plus the changed-file split) proposed no group in any run. Jev's confident answers agreed with them on 8 of 11. In P1 #2 Jev was sure that steps 3 and 4, and 4 and 5, were independent, where the heuristics had nothing, but it also called steps 3 and 5 small, so the group was dropped. The real blocker is structural: the Architect split each feature into three short steps (code, code, tests) and ordered them feature by feature, so the two independent chains (steps 1 to 3 and 4 to 6) cannot be expressed as groups of adjacent single steps. Neither Jev nor the heuristics can run two multi-step chains side by side today.
- **Changed-file heuristic.** The Architect's plan entries did not carry the requested `Files:` lines (the plan tool entries are short titles such as "CSV export: src/csv.ts"), so the verb fallback decided. Two parsing bugs showed up in the D2 and H1 plans and were fixed before P1 #2: "half-away-from-zero" matched the read cue "from", and "overwrite" was not a change verb. Both cases are now unit tests.
- **The Critic.** It ran only on D2, the one run Jev scored destructive. Codex (6 Sol, high) cost $0.004 as reported, Jev judged its review done, and the run passed. It did not change the outcome, since direct also passed D2.

### Regression

T1 is unchanged: a Haiku Builder at low effort for $0.023. H1 is within noise of the tuned run ($0.33 against $0.35, the same Opus Architect). H3 now passes in both modes with the clarified wording.

### Noise and sample size

One repeat for most cells, one fixture, one provider. Wall time varied by up to 5× within a cell (P1 direct: 53 s and 247 s). The heuristic fix landed between P1 #1 and #2. Treat pass-rate differences of one run, and cost ratios within about 1.3×, as noise. A 10/10 pass rate on both sides says the tasks are too easy, not that the harness adds nothing.

### Recommendations

1. **Plan in chains, not adjacent pairs.** Ask Jev, or the Architect, per step "which earlier step does this need?", build the dependency graph, and give each independent chain one Builder in its own worktree. That is what P1 needed.
2. **Get `Files:` into the plan entries.** Take each step's files from the Architect's reply by step number, or require them in the plan-tool entry, so the heuristic stops guessing from verbs.
3. **Send review requests to the Critic.** When Jev's intent is review at 0.5 or more, keep a review step even at `execute` depth. R1 shows that an explicit "review this change" gets no reviewer today.
4. **Keep the Architect gate.** Consider rewording the Architect route question (it only plans and reads), since Jev's confidence stayed near 0.33; until it rises, the call is a record rather than a decision.
5. **Harder tasks, more repeats.** Sonnet passes every hidden check here. The next set needs larger multi-module changes or long-horizon work, with 3 or more repeats, before pass rates can justify the harness's planning cost.
