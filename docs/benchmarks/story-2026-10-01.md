# Story benchmark · 2026-10-01

The C8 story benchmark from [COORDINATOR_PLAN.md §9](../architecture/COORDINATOR_PLAN.md#9-c8-and-the-story-benchmark): one story, "Project budgets", in the `workbench` fixture, run through the real app stack under six arms. Branch `feat/c8-story-bench` (from `checkpoint/harness-m6-round3`). The raw records (every run, its pieces, agents, costs, proxy log and reply) are in [story-2026-10-01.json](story-2026-10-01.json).

**Spend: $27.58 of the $40 cap** ($26.44 in the 24 scored runs, plus $1.14 in one Full auto → PR run that a session restart killed mid-run; it is counted but not scored). The fake dry runs cost nothing.

## Headline

- **Every arm passed the story at Automatic** (hidden tests 10/10, project suite green, nothing outside the story's folders): a 3/3, a2 3/3, b 3/3, c 4/4, d 3/3, direct Claude 3/3. The story is too easy to separate the arms on pass rate; they separate on cost, time and what actually ran.
- **The coordinator rarely got to coordinate.** It engaged (the agreed plan had 5–47 open items) in 16 of 17 coordinated runs, but its piece list failed validation twice in **10 of 16**, and the run fell back to one Builder. Pieces actually ran in 6 runs: a2 ×1, b ×1, c ×2, d ×2. The fallback still paid for two coordinator turns ($0.21–0.33, about 23% of the run).
- **Direct Claude is 10× cheaper per pass than any harness arm** ($0.40 vs $2.95–4.52 incl. developer time) and 3–5× faster (141 s mean). This repeats the dev-day finding.
- **Provider fallback does not fire on a real Codex 429.** In arm d the proxy rate-limited every Codex session from its second model call on. Spark recorded the Codex Builder turns as *succeeded*, landed their pieces with 0 files changed and a passing scoped check, and moved nothing to another provider. At Automatic the verified cascade and the integrator rebuilt the missing parts, so the story still passed. At Full auto → PR the run stopped without a PR (hidden 6/10). See B1.
- **Wall time is not trustworthy in this run.** The machine's load average sat between 16 and 300 while other sessions ran browser suites. Arm a ran its first two runs during the worst of it (835 s and 714 s). Coordinated runs that fell back to one Builder, which do the same work as arm a plus a coordinator turn, averaged 372 s. So the "a is slow" signal is mostly load.

## Setup

- **Stack.** `scripts/e2e-live/stack.ts` on its own schema in `spark_outpost_test_c8` (API 4521), a fake GitHub on 4429, no dev database or dev ports. Jev and Claude were connected, plus Codex in a, a2, b and d. Z.ai was not connected. Claude runs through the local CLI login. Codex runs through its ChatGPT login.
- **Story** (`scripts/e2e-live/story/story.ts`). This is a 7-bullet request with exact interfaces: the `003_project_budgets.sql` migration; `src/budgets.ts`; `GET`/`PUT /projects/:id/budget` with 400 and 404 cases; a budget bar in `renderProjectPage`; an over-budget badge in `analyticsRows`/`renderAnalytics`; a `budget` CSV column; and tests. The fixture is `workbench` with an overlay (`story/fixture/`): the `budget` column is removed from `projects`, and a project page, an analytics list and a CSV export are added. There are 10 hidden tests (`story/hidden/`), one per layer: migration, upgrade, repository, API happy path, 400s, 404s, bar, over bar, badge, CSV. `pnpm e2e:story --selftest` checks that the fixture suite is green, that the hidden tests fail before the story (1/10), and that the reference solution (`story/reference/`) passes 10/10 inside the story's folders.
- **Pass** follows plan §9: hidden 10/10, the project suite green, and no changed file outside `migrations/ src/ test/ README.md`. The work is read from the chat's own worktree (`chat_worktrees`), since chats work in a worktree by default.
- **Cost per pass** = (spend + developer time at $100/h) / passes. Developer time is 1 minute per intervention and 30 minutes per failed story. Interventions are the non-tool cards the driver answered. At Automatic that was "Build this plan?" (answered at once instead of waiting out the countdown) and the occasional keep card, the same for every harness arm.
- **Level.** Automatic (`hands-off`, Accept edits) for the scored runs. One Full auto → PR run per harness arm checked the draft PR.

| Arm | Setup |
| --- | --- |
| a · one Builder | `COORDINATOR_MODE=off`, Claude + Codex connected |
| a2 · pieces in order | `in_order`, Claude + Codex |
| b · shared tree | `parallel` + `COORDINATOR_PLACEMENT=shared`, Claude + Codex |
| c · worktrees | `parallel` + `COORDINATOR_PLACEMENT=worktree`, Claude only |
| d · provider fallback | arm b, with every Codex session going through a local proxy that answers 429 from its 2nd tool call on (see below) |
| direct Claude | `scripts/bench` in-process arm: one Claude Sonnet agent, no orchestrator |

**How arm d fails Codex.** `COORDINATOR_PLACEMENT` and the proxy are bench seams. The stack sets `CODEX_PATH` to a wrapper that runs codex-acp's own bundled `codex` with a custom model provider (`base_url` = the local proxy, `requires_openai_auth = true`). The proxy (`story/proxy.ts`) forwards to the ChatGPT Codex backend untouched. It answers 429 to any Responses request carrying one or more tool results, which means the second model step, where the second tool call would come from. It never reads or logs headers. A probe first confirmed that `OPENAI_BASE_URL` is ignored under ChatGPT login and that the wrapper route works. Codex retried and gave up after about 10 s with "exceeded retry limit, last status: 429". In every arm-d run the proxy log shows each Codex session with 1 request answered 200 and the next answered 429.

### Why piece lists failed

Of 10 fallbacks, 9 were `no piece covers the plan item "…"`, and one was a piece goal over 800 characters. One of the 9 also had `P4 reads src/ui.ts, which P3 owns; add P3 to its dependsOn`.

The agreed plans that Automatic auto-approved were implementation plans with 13–47 bullets, many of them sub-steps, notes or code fragments. For example:
- "No regex change needed."
- "Manually sanity-check via a quick script…"
- "`PUT` on `rest === '/budget'` → read `amount`…"

`covers()` in `pieces-validate.ts` wants each bullet's words in a piece's title, goal, acceptance or files. The coordinator's contracts summarise instead, so the check fails. It then fails again after the one repair re-prompt.

## Recommended default changes

These are not applied. `COORDINATOR_MODE`, the placement thresholds and `parallel_pieces` are unchanged.

1. **Make `COORDINATOR_MODE` default `in_order` or `off`, with the coordinator engaging only on explicit request.** Nothing in this story beat one Builder, and direct Claude beat everything by 10× on cost per pass. The coordinator turn alone cost about 23% of every coordinated run, including the 10 runs where its list was then thrown away.
2. **Do not ship parallel placement as the default.** Neither b nor c meets the 30% bar. The piece runs were not faster than one Builder on a story of this size.
3. **Before re-running this benchmark, fix the plan-coverage check** (`covers()` against implementation-level plan bullets). Until pieces actually run most of the time, the benchmark measures the fallback, not the coordinator.
4. **Treat B1 and B2 as blockers for any multi-provider or shared-tree default.**

## Limits and caveats

- **n = 3 (c: 4), and the story is easy.** Every arm passed every Automatic run, so the pass-rate criteria cannot separate arms, and one failure would move a rate by 33 points.
- **Most coordinated runs did not coordinate.** Placement and multi-provider results rest on 1–2 piece runs per arm.
- **Wall times are confounded** by machine load from other sessions (load average up to about 300; recorded per run from the second batch on as `load`). The arm a mean is the most affected.
- **Arm d is an approximation of "Codex returns 429".** The proxy fails the model request itself, which is the real failure mode for rate limits. But it fails *every* Codex session from the second step on, including the Codex Critic, whose verdict was "unclear".
- **No shared-tree-on-one-provider arm**, so the multi-provider criterion is unanswered.
- **The PR-body piece table was never exercised** (see above).
- Z.ai was skipped (not needed for these arms).
- The interrupted Full auto → PR run for arm a ($1.14) is excluded from the scores and counted in the spend. Its schema was dropped.
