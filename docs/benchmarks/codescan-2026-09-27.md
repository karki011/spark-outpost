# Code scan prototype: benchmark (2026-09-27)

Rollout step 0 of `docs/architecture/ROUTING_PLAN.md`: the indexer, the Postgres cache and the per-task scan, measured on five repositories. The scan also runs in shadow mode beside Jev intake for Do tasks. It records a `run_advice` row with purpose `scan` and changes nothing else.

- **Script:** `scripts/codescan/bench.ts`, run with `node --import tsx`. Each repository gets its own Postgres schema in the `spark_outpost_test_codescan` database.
- **Machine:** the development Intel Mac, with a local Postgres 17 and Node 24.21. Other work was running on the machine, so treat single numbers as ±15%.
- **Where the numbers come from:** the "After" numbers are from one full run of the benchmark at commit `80b06c3`, after the coordinator's fixes. The "Before" sections keep the first round's numbers unchanged for comparison.
- **What "cold" means:** the Postgres cache was empty. The OS file cache was not flushed, because that needs sudo.

## After the fixes (commit `80b06c3`)

What changed since "Before":

- **Large repositories:**
  - Over the 50,000-file cap, test-data trees (`testdata`, `fixtures`, `baselines` and similar) are left out of the index first.
  - ripgrep skips every directory that the index left out, using anchored `--glob !dir/**` rules.
  - ripgrep keeps at most 3 matching lines per file (`--max-count=3`).
- **git status:** reused for 5 s per root, and refreshed early when `.git/index` changes.
- **Neighbour query:** neighbour rows carry only the references that link them to the core files, and each side is limited to 200 rows.
- **Concurrency:** 3 scans at once. The deadline is 2.5 s, counted from when the task starts, not from when the scan leaves the queue.
- **Ranking:**
  - Files linked only by references are damped by how widely their definitions are used across the repository.
  - `vi.mock`/`jest.mock` factories, `vi.fn()` mocks and top-level variables in test files are no longer definitions.
  - A code-shaped name with no exact definition falls back to definitions that contain it at a CamelCase boundary, for example `SearchInput` → `AcmeSearchInput`.
  - Names are looked up as written; only kebab and snake names are respelled.
  - The parser version was bumped, so caches rebuild.
- **Cache cap:** the per-project size used for the 500 MB cap now includes indexes and TOAST. It is the project's share of the total size of the three cache tables.

"Before" ran 2 scans at a time with a 1.5 s deadline counted from when the scan started. "After" runs 3 at a time with a 2.5 s deadline counted from when the task starts. In the benchmark that is the moment `scan` is called, so time in the queue counts.

### Targets after the fixes

- **TypeScript p95 under 1.5 s:** holds. It was 588 ms, or 811 ms when every scan ran `git status` again.
- **Per-task under 2 s:** holds on all five repositories.
- **5 at once with the real deadline:** all 50 scans were complete.
- **API responsive:** holds, with p95 at or under 6.2 ms.
- **Cost of the cap change on the 66,684-file repository:** only 5,496 files are indexed now, because its 61,089 test-data files are left out. The trade-off is that a request about a baseline or fixture file finds nothing there, either in the index or in ripgrep.

### Ranking samples, after (private monorepo)

The per-request top-10 lists for the private monorepo are left out of this report because they name its files. In short:

- **A component named in the request without its prefix** now ranks its real definition #2 instead of outside the top 10.
- **Hubs:** two files that appeared in many lists only through references have left them.
- **Mocks in tests:** test files that mock a named hook or client no longer count as defining it.
- **Still noisy:** path words can fill a list when a request's words match a whole folder.

### Do the plan's targets hold?

- **Per-task scan under 2 s:** holds for spark-outpost, private monorepo, react and ripgrep, with p95 at 421 ms or less. **Missed on the 66,684-file repository:** p95 was 2,034 ms, and 10 of 30 runs took longer than 1.5 s. Most of the time is ripgrep over the full tree (about 1.0 s); the index cap does not limit what ripgrep searches.
- **5 at once:** the p95 was 2,559 ms. With the 1.5 s deadline, 16 of 50 scans were partial or empty. The limit of 2 concurrent scans is what makes the queue wait.
- **API responsive:** holds. API p95 stayed at or under 5.9 ms, and the worst single request took 103 ms, while scans ran in the same process. During cold indexing the API p95 was 1.0 ms, because parsing runs in a worker thread.
- **Cache size:** 1.3 to 4.4 KB per file including indexes. The plan estimated 2 to 5 KB per file.
  - The GIN indexes on `def_ids` and `ref_ids` are most of the total. Row data alone was 1.2, 4.9, 19.8, 5.5 and 0.4 MB.
  - The cache for all five repositories together is about 111 MB, below the 500 MB global cap.
- **First index:** 3 s for a small repository, 12.5 s for private monorepo and 46 s for 50,000 files. It runs in the background when a project is first used.

### Ranking samples (private monorepo, final run)

The lists are left out because they name the private repository's files. In 9 of 10 requests the real defining file of a symbol named in the request was in the top 2; the exception named a component without its prefix. "Linked by references" hubs still appeared in several unrelated lists, and test files that mock a named hook ranked as defining it.

On TypeScript, the cloned `main` is now the Go port. Most TypeScript-named files sit under `tsc/testdata/fixtures`, so its samples say little about ranking; they are in the JSON output only.

## Grammar findings

- **`@vscode/tree-sitter-wasm` 0.3.1 with `web-tree-sitter` 0.27.0:** all 16 grammars load and parse. They are bash, c-sharp, cpp, css, go, ini, java, javascript, php, powershell, python, regex, ruby, rust, tsx and typescript (ABI 14 and 15).
  - The package ships no tag queries. The definition queries in `codescan/tag-queries.ts` are our own, written for 12 languages; each language has a unit test.
  - References are every identifier-type node, collected with a query.
- **`tree-sitter-wasms` 0.1.13 in `web-tree-sitter` 0.27:** none of its 36 grammars load. `getDylinkMetadata` rejects them, because they were built with tree-sitter-cli 0.20.
- **`tree-sitter-wasms` in the runtime that `@vscode/tree-sitter-wasm` ships (tree-sitter 0.25.1):** 33 of 36 load and parse, including Kotlin, Swift, Dart, Scala, Vue, Elixir, Lua, Zig, TOML, JSON and HTML. elm and ql fail with "memory access out of bounds", and yaml fails with "resolved is not a function".
  - So adding those languages would mean switching to the runtime the vscode package ships, not the separate `web-tree-sitter`. It was not added.
- **`ignore`:** not needed. `git ls-files --cached --others --exclude-standard` already respects `.gitignore`, and the fallback for a folder that isn't a git repository is `rg --files`, which does too.

## Deviations from the plan, and limits

- **Words in the request:** a request with no code-shaped names still gets candidates. Plain words of four letters or more, minus a stop list, are matched against file paths. Without this, a request like "the sidebar order breaks…" found nothing.
- **Name statistics:** `code_index_names` also stores how many files define and reference each name. The ranking uses these counts to down-weight common names, and the neighbour search uses them to skip common names.
- **References:** only the distinct referenced names are stored per file, not how often each is used.
- **Reference counts per file:** "referenced by" in the per-file numbers counts only the scanned neighbourhood, not the whole repository. For names in the request, the reference counts cover the whole repository.
- **Not built:** tsconfig `paths` and the package dependency graph. Each file gets its package from the nearest manifest (`package.json`, `project.json`, `Cargo.toml`, `go.mod`, `pyproject.toml`). The branch name is also not read.
- **Superseded by the fixes above:** the 2-slot and 1.5 s settings, the "row size only" cache cap and the unfiltered ripgrep search.
- **Before the first index exists:** a scan uses only ripgrep and `git status`. Named paths are not resolved until the index exists.
- **Cache sizes:**
  - The per-project `bytes` value used for the 500 MB cap now includes indexes and TOAST, as a share of the three tables' total size. The first round counted row sizes only.
  - Old names are pruned on refresh with one anti-join query, so the name table does not keep growing.
- **Process priority:** git and ripgrep run at below-normal priority. The parse worker thread cannot be re-prioritised on macOS.
- **Shadow rows:** `scan` rows are left out of the orchestration decision list, so the UI is unchanged. They carry `jev_status = 'not_asked'`, so Jev usage and cost totals are unaffected.
