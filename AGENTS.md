# AGENTS.md — Spark Outpost

Instructions for humans and coding agents working in Spark Outpost.

## Product and stack

- Build a local-first, provider-agnostic workflow application. Cloud hosting is a future direction, not a reason to add unused infrastructure today.
- Use a pnpm workspace monorepo, TypeScript, React with Vite, and Node.js with Express.
- Use local PostgreSQL with versioned schema migrations. Keep database access in the backend.
- The local web interface comes first. Electron (`apps/desktop`) is the desktop shell; it stays a thin wrapper around the unchanged web app and Node service. A Rust backend is not required.
- Use React state for UI interactions, TanStack Query for cached API data, and AG-UI events for live run updates. Give each piece of state one clear owner.
- Coding agents connect through ACP. CopilotKit is not used; if evaluated later, verify the exact integration license and do not introduce a paid runtime requirement implicitly.
- Spark owns run state, the approval gate, cancellation and recovery. The agent owns the work: it plans, delegates and checks as it sees fit. One chat is one agent session and the user's message goes to the agent as typed; Spark never splits a turn into roles, runs no checks of its own and adds nothing to the reply but the publish result line. There are no run budgets: time, tool calls, tokens and cost are measured and shown, never capped, and no card or setting limits them. Jev is an optional decision service used outside turns (the Map, pull request feedback sorting, the companion) and is never called inside a turn; providers execute through explicit adapters.
- The Mac app's Browser pane runs pages in their own session partitions, never the app session, with Spark's ports blocked; agents read pages through `spark_browser_*` tools and page content is untrusted data. Saved sign-ins keep their username and password only in the keychain; Spark types them into the exact saved origin after a card, and no tool result, event, log or table holds them. Read `docs/architecture/BROWSER.md` before changing it.
- A paired device (a phone or computer browser, or another Spark Outpost) reaches the Mac only through Tailscale Serve (never Funnel) and the remote gateway in `apps/server/src/remote/`: the server still listens on `127.0.0.1` alone, a device signs in with a pairing confirmed on the Mac, and every route is refused unless `route-rules.ts` allows it, some behind the switches on the Remote control page (left bar, above Settings). A paired device may save a passkey and use it to sign in again in another browser at the exact Serve hostname, as the same device; a passkey never pairs a new device, stops working when the device is revoked or unused for 30 days, and its switch and removal stay on the Mac. Terminal, Browser pane, preview, and everything that manages remote control (Tailscale, pairing, devices, switches, audit) stay on the Mac; a new route needs a rule or the policy test fails. Read `docs/architecture/PHONE_REMOTE.md` and `docs/architecture/REMOTE_CONTROL.md` before changing it.
- Agent terminals are designed in `docs/architecture/AGENT_TERMINAL.md`. Read it before changing how Spark runs a command for an agent.
- An outpost is a shared thread for several chats: the user's message may address several member chats with `@handle` anywhere in it, one request per chat, each starting a turn in its chat; a message that addresses no chat is a note, which starts nothing. Agents in an outpost may ask each other and leave notes, and a chat may propose an outpost or sub-chats as a draft (a story): the lead proposes and the user starts, and nothing is created until the user starts it. The outpost tools belong to the chat's own turn; a child run, such as a Spark handed a job, gets none. A request or a wrap-up from another chat or from Spark, and a draft's first messages, are never the user's message and cannot authorise a push or a pull request; the receiving chat's own mode and autonomy decide what happens to the result. The lead decides whether a sub-chat is parallel or stacked; a sub-chat's first turn may ask, a held request is released when the request it waits on is Answered, and a story gets one wrap-up request to its lead. The wrap-up is one read-only reply in the lead chat: it starts no build and no publish step, and gives no basis to push or open a pull request at any autonomy level or in any mode. The mode cap limits what the lead proposes, and the user may raise a sub-chat's mode by hand. A chat may base its branch and pull request on another member chat's branch: it pushes only its own spark/* branch, never force pushes, updates by merge, and is refused a push, by `spark_push` and by a `git push` the gate sees, with the same reason, while its parent branch is not on the remote; in a mode the gate can't see, that push is flagged as an observed rail crossing (card, island notice, audit entry) and never stopped. At Automatic, when a stacked sub-chat's held request waits on its parent chat, Spark commits the parent's kept changes on the parent's own spark/* branch before the sub-chat starts: a local commit like Ship → Commit, never pushed, and if the commit cannot be made the sub-chat stays held. A chat is in at most one story, and nothing here has a cap, budget or timer. Each member chat is served as an A2A agent and each request is an A2A task, on `127.0.0.1` only, behind the launch token, never to a paired device or through Tailscale. A paired device may read an outpost, post, cancel, pause, rename and start a held request anyway; creating, deleting, changing members and starting a story from a draft stay on the Mac. Read `docs/architecture/A2A_CHATS.md` before changing it.
- Use A2A where independent agent communication is needed; today that is outpost requests between chats. Do not wrap every internal function or worker in a protocol without a current need.
- Agents operate within authorized boundaries. Approval checkpoints are enforced by the backend; model recommendations cannot grant authority.
- A Codex chat session Spark starts does not use the Codex account's own apps (connectors): Spark turns them off for that session only and edits no user file. An MCP server the user adds in Spark is used through the gate, and Terminal sessions are untouched.
- Agent permissions come from the provider: users pick one of the modes the agent's session advertises (for example Claude Manual, Accept edits, Plan, Auto, Bypass permissions; Codex Read-only, Ask every time, Approve for me, Full access), shown with the agent's own names; stored as `agentMode`, with `permission` derived (read-only modes are Ask runs). Separately, Spark autonomy (set in the chat's Work panel, shown as a chip in the context bar) decides only what happens to the result: Automatic (keeps changes without stopping) and Full auto → PR (the default for new chats; the same, then opens a PR; with no remote it commits on the chat's branch, without a GitHub connection it pushes and gives a Create PR link, in a folder that is not a git repository it keeps the change and says "No pull request" in one line, a chat that works in the user's checkout has no branch of its own, so the change is kept and one line says nothing was pushed, and a chat with no project gets no such line); Spark raises no plan card at either level and saves no plan of its own: a plan the agent proposed and the user approved is the chat's agreed plan and is shown as one line ("Plan saved"); the agent's own plan approval (its Plan mode, or `/plan`) is the only stop before building, and every message in a Plan-mode chat runs in the agent's Plan mode, which changes no files until the user approves the agent's plan; and the level never decides whether a Spark action tool (tickets, Slack, MCP servers, Sparks) asks first: that follows the agent's mode (at once in Auto, Bypass permissions, Approve for me and Full access, a confirm card otherwise), stored as `level`: `hands-off`, `full-auto`. An agent may ask Spark to run one command in a Spark-owned terminal tab that keeps running after the turn (`spark_terminal_run`), in a chat with a project folder and never in an Ask or read-only turn: Spark judges it through the same approval gate as the agent's own commands, in every mode, so it runs at once in Auto, Bypass permissions, Approve for me and Full access and shows an ordinary approval card otherwise (Allow once or Reject only; the allowlist and run rules do not apply), the safety floor and the publish rules hold as they do for the chat agent's own commands and, unlike the agent's own commands in Bypass permissions, Approve for me and Full access, a hard-rail crossing asks or is refused before the command starts, a start that no card approved is marked ran without review, and each start and stop is an audit entry. Such a tab takes no input, is labelled as the agent's, has no time, idle or count limit, stops when the user or the agent stops it, when the user stops the turn that started it, when the chat is removed or when Spark quits, is never started again by Spark, and is not a Terminal session; like Terminal, it stays on the Mac, and a paired device sees its state as text only. Reviewing each step is the agent mode's job (for example Manual or Plan). Use these names in user-facing text; never say "harness" to users. The safety floor (changing, moving or deleting a secret file is refused by Claude's own harness in every mode and asks in Codex, a command that does it asks wherever Spark gets the request, and changing an agent instruction file always asks; reading a secret file, inside or outside the linked repos, follows the agent's mode like any other read and is recorded in the audit by path, never content, while a file listed in `.sparkignore` still asks to read; git hooks and git config ask with hold-to-confirm, including, in a chat that works in a worktree, the hooks and config in the checkout's real git folder and the worktree's own `config.worktree`, no force pushes, no pushes of any branch but the chat's own spark/* branch, no remote changes, no writes or deletes outside linked repos except inside the system temp folders (`/tmp`, `/var/tmp`, `$TMPDIR`), which are scratch space and follow the agent's mode, audit) holds in every mode of a chat and does not apply to Terminal sessions; where the agent's mode runs a shell command without sending Spark a request (Claude Accept edits, Auto and Bypass permissions; Codex Approve for me and Full access), Spark cannot ask first and flags the crossing instead; the chat's agent may push the chat's own spark/* branch (with `spark_push`, which runs the push with the user's login-shell environment, or `git push`) and open its pull request (`gh pr create`/`edit`, or `spark_pull_request` when `gh` is not signed in) only when the user's message asks for it, the chat is at Full auto → PR, its mode is Auto/Bypass permissions (Full access), or the turn is a PR follow-up round on the chat's own open pull request, and otherwise it doesn't publish. The user's message is read per action: asking for a pull request includes the push, and a message that asks for the push and not the pull request allows the push and not the pull request: its publish prompt asks for the push alone except at Full auto → PR, and the pull request (`gh pr create`, `spark_pull_request`) stays refused unless the level, the mode or a follow-up round allows it. A push or a pull request with none of these is refused in every mode the gate can see, never asked about. A turn started by an outpost request follows the receiving chat's own agent mode and autonomy, so at Full auto → PR, or in Auto/Bypass permissions (Full access), it may push that chat's own spark/* branch and open that chat's pull request. A request the user typed in the outpost counts as the user's message in the receiving chat. A request another chat wrote, and any other text the user did not write, is never "the user's message asks for it": not for a push, not for a pull request and not for a Spark action tool. Reading through `gh` is not publishing: `gh pr view`/`checks`/`diff`/`list`/`status` for any pull request, `gh run view`/`list`/`watch`, `gh issue`/`repo`/`release` views and lists, `gh search`, `gh auth status`, `gh api` GETs and GraphQL queries are never refused by the publish rule and follow the agent's mode like any other command, while creating and editing stay limited to the chat's own pull request, comments, review-thread replies and resolves by the agent stay limited to the chat's own open pull request while follow-up is on and follow the agent's mode, and every other `gh` subcommand (merging, reviewing, dismissing, closing, reopening, anything on another pull request) is refused by name. Publishing at Full auto → PR, on request and in a follow-up round happens in one publish prompt that Spark sends to the chat's agent after its reply, on the same session and run, when the chat's branch has unpublished work and this turn changed files, the user's message asked to publish, or the turn is a follow-up round; older unpublished work alone never starts it. A publish prompt that fails or is stopped leaves the turn succeeded with the reply and the kept record, and one line says it was not published and why. A pull request the chat opened carries standing permission for follow-up fixes pushed to that same branch, and for replies on its threads, at every autonomy level until it is merged or closed or the user turns Follow up on pull requests off (or to ask first); the agent judges each item and may push back instead of changing code. Agents open pull requests themselves; Spark has no pull request card, records the PR it sees in the command output (Links, PR row, audit), never skips repository hooks (`--no-verify` is refused), after a turn read a secret file, a web page or other work data Spark returned (tickets, Slack, lists across chats, another project's pull requests), a send off this computer never adds a card of its own: when the agent's mode would run it, it runs, with an audit entry and a non-blocking flag ("sent data … after reading …", once per destination per turn), and when the mode asks, its ordinary card carries the note; the note ends with the turn; Spark's own data about the chat (task, history, run, audit, its own project's pull requests and follow-up) is not such a read, work on the chat's own repository and pull request (`git status`/`log`/`diff`/`fetch`/`pull`, a push of its own spark/* branch, `gh pr view`/`checks`/`status`/`diff`/`list`, `gh run view`/`list`/`watch`, `gh api` GETs, and comments, review-thread replies and resolves on its own open pull request while follow-up is on) is not a send, and a local script that opens no connection is not sending data out. One send is part of the safety floor in every mode: a `git push` or `gh` upload whose content the gate can read and that holds a value from the project's secret files asks with hold-to-confirm, naming the file and never the value (`spark_push` refuses it); content the gate can't read is never asked about on suspicion. Spark is a moderator, not a gatekeeper: modes the approval gate can't see (Claude Bypass permissions, Codex Approve for me and Full access) run wherever the user chose to work (the chat's worktree by default, the checkout if picked); Spark marks each tool call that ran without a permission request as ran without review in the audit, and flags an observed action that crosses a hard rail with a non-blocking card, an island notice and an audit entry, never stopping the run. Spark honours the agent's mode: it injects no ask rules of its own beyond the safety floor: path rules that send an edit of an agent instruction file, a git hook or git config, and a `git config` command, to the gate in every mode (only the chat agent's `git push`/`gh` go to the gate for the publish rules), so a card appears when the agent's mode asks, with the agent's reason. Full auto → PR is the user's authorization to push the task's own branch and open a PR (a draft only when the user asks for one or Settings says to open pull requests as drafts) without being asked in the message; nothing ever merges, and Spark never resolves threads, approves or dismisses reviews. A Terminal session runs the provider's CLI directly under the agent's own permission mode: Spark's approval cards, the protected-path rules (secret files, instruction files, git hooks and config, push rules, writes outside the project) and the ran-without-review audit do not apply inside it, and Spark records that the session started, its mode and its observed state, the tool names and times of its steps, and the token counts, model and estimated cost of each turn read from the CLI's own session file, with the CLI's own session total when it writes one; never commands, paths, prompts, replies or tool output. A Terminal run carries no autonomy level that publishes: Spark's own push and pull request tools act there only when the user's message asks for it or the agent's mode would run them.

Read `docs/product/PLAN.md` for product direction and `docs/architecture/PROTOCOL_ALIGNMENT.md` before persistence or agent integration changes. Keep protocol support claims tied to pinned SDK versions and passing contract tests.

## Design principles

- Follow YAGNI, KISS, and DRY: implement what is needed, keep it understandable, and avoid duplicated knowledge.
- Design for today's actual caller. Do not introduce speculative APIs, registries, configuration, or extension systems.
- Abstract around knowledge, side effects, volatility, or a useful test seam that exists today. One caller is enough when the boundary has a concrete purpose.
- Prefer a small meaningful interface over chains of pass-through wrappers.
- Keep decisions pure where practical. Put filesystem, network, process, and clock effects at the edges.
- Make dependencies explicit. Validate external inputs at trust boundaries, including API requests, provider events, tool results, and persisted records.
- Treat agent output and retrieved content as data, not execution authority.
- Prefer clear names, small functions, and explicit control flow over clever or compressed expressions.
- Reduce needless nesting, redundant logic, and pass-through abstractions. Preserve useful boundaries and test seams.

## Organization and duplication

- Organize code by feature and responsibility. Keep related implementation and tests easy to find.
- Keep applications under `apps/`, shared packages under `packages/`, infrastructure under `infra/`, and architecture and decisions under `docs/`.
- Create directories and packages only when they have an actual implementation purpose. Do not scaffold empty abstractions.
- Keep handwritten source and test files at or below 500 lines. Split by coherent responsibility before exceeding the limit; do not compress code to fit.
- Do not manually split generated files, lockfiles, or vendor code to satisfy the source-file limit. Keep them separate from handwritten code.
- When the same UI pattern appears more than twice, extract a shared component. For repeated non-UI behavior, extract a shared function or module.
- Share the repeated behavior or knowledge, not merely similar syntax. Do not combine unrelated behavior into a configurable catch-all component.
- Keep shared code at the narrowest scope that serves its actual callers.
- Frontend code may import shared contracts, but must not import database access, credentials, or provider execution internals.

## Interface conventions

- Follow the design kit in `docs/design/`. Use the shared semantic colors in `apps/web/public/theme.css`; do not hard-code palette colors in feature styles. Load the saved theme before React mounts.
- Keep onboarding and Integrations on the same connection components and query cache. Show only supported connection methods and backend-reported status.
- Use shared outline icons, restrained accent colors and visible keyboard focus; preserve mounted conversations when changing appearance.

## Changes and refactoring

- Make small, coherent changes. Preserve security, data integrity, accessibility, and all requested behavior.
- Refactor only when today's change benefits. Do not broaden a task into unrelated cleanup.
- Preserve observable behavior during refactoring, including errors, side effects, evaluation order, and public contracts, except for the approved behavior change.
- Do not trade readability for fewer lines.
- Preserve mounted UI state, focus, and scroll position during streaming and background refreshes.
- Keep workflow execution independent of the HTTP request or UI connection that observes it. A disconnected progress stream is not a cancellation request.

## No explanatory code comments

- In every mode, add no explanatory code comments, including in tests.
- Do not add docblocks that merely explain implementation.
- Use clear names, small functions, and explicit control flow instead.
- Preserve required license notices and machine-consumed directives. Record any newly required exception and its reason in the completion record.
- Put design rationale in the PR description, completion summary, or appropriate documentation.

## Testing and review

- Test observable behavior and meaningful edge cases. Avoid tests that only mirror the implementation.
- Run checks appropriate to the changed behavior. Report what ran and what remains unverified.
- For execution and persistence changes, cover relevant cancellation, restart recovery, duplicate requests, stale events, and failure cases.
- For UI changes, verify relevant keyboard, focus, accessibility, streaming, and loading behavior.
- Self-review gathers evidence; it is never the final independent verdict.
- Keep provider claims, reviewer opinions, executable checks, and human acceptance distinct. Do not claim independent verification when none occurred.
- Completion records identify the behavior changed, validation evidence, material limitations, and any required comment exception.

## Repository maintenance

- Keep this file concise and current. Update it when approved conventions change.
- Document runnable development and verification commands as the repository is implemented; do not claim nonexistent commands or checks.
- Keep secrets out of source control, logs, browser bundles, and agent-visible artifacts.

## Commands

- Run `pnpm test:db` for storage changes against an isolated PostgreSQL schema in `TEST_DATABASE_URL` (falls back to `DATABASE_URL`); `pnpm db:setup` writes both to `.local/credentials.env`.
- Run `pnpm check` (format, lint, typecheck, source rules, guide rules, unused files and exports via knip, contrast audit, ACP coverage, unit tests) and `pnpm test:browser` for browser behavior. Set `SPARK_WEB_BUILD=1` to run browser specs against a production build of the web app (the map perf spec holds the tree to 50 ms tasks there). Run `pnpm test:browser:packaged` for the `@packaged` specs the way the desktop app runs: the API serves a production build on its own origin and the launch token is added below the page, with no Vite proxy (`SPARK_PACKAGED=1` runs any spec that way). Tag a test `@packaged` when it covers a request path the proxy could hide (bodyless requests, uploads, streams, sockets, downloads). Set `SPARK_FAKE_BROWSER=1` to give the test worker a fake browser host, which the agent flow in `tests/browser/sign-ins.spec.ts` needs.
- For the inner loop on a branch, run `pnpm test:changed`, `pnpm test:db:changed` and `pnpm test:browser:changed`: they run the tests a change since `main` affects (`--dry-run` on the last two prints the choice and the rule behind it), `pnpm test:browser:perf` runs only the perf specs, and `pnpm test:browser:shards <N>` runs the browser specs in N processes, each with its own ports and test database. A new browser spec goes in `tests/browser/spec-map.ts` or the unit tests fail. Before merging to `main` and before a release, run `pnpm check` and the changed-test commands above; run the full `pnpm test:db` and `pnpm test:browser` only when the owner asks.
- Run `pnpm db:setup` once for the isolated native macOS PostgreSQL cluster, then `pnpm db:up`, `pnpm db:migrate` and `pnpm dev`. Stop only this cluster with `pnpm db:stop`; preserve `.local` data and ignored credentials. See `infra/local/README.md`.
- The user guide lives in `docs/guide/` (Markdown with frontmatter; see its README for audiences, page types and word caps). The app bundles it into Docs and agents read it with `spark_docs`. A change to a UI label, setting, card, Spark tool, agent mode, protected path or what leaves the computer updates the page that documents it in the same commit, and every user-visible change adds a row to `docs/guide/whats-new.md`. There is no redirect for a renamed page or heading: update every link to it in the same commit. Run `pnpm check:docs` (part of `pnpm check`), which fails on a link to a page or heading that does not exist, for frontmatter, word caps, links, images, reference coverage of Spark tools and Settings sections, and `spark_docs` limits. Run `pnpm docs:screenshots` to regenerate the light and dark screenshots from a seeded demo test database (`tests/browser/docs-shots*.spec.ts`).
- Run `pnpm exec tsx scripts/spark-tool-budget.ts` to print the size of the Spark tool list a session is sent (plain chat, linked project with GitHub, everything connected); `apps/server/test/spark-tool-budget.test.ts` caps the plain-chat case.
- Run `pnpm desktop:dev` for the Electron shell (dev channel, own data folder and bundled Postgres); see `docs/architecture/ELECTRON_PLAN.md`.
- Run `pnpm desktop:package` for an unsigned local build in `apps/desktop/release/` and `pnpm desktop:e2e-update` for the local update check; releases, signing and the update feed are in `docs/architecture/RELEASES.md`. Never publish a build without user authorization.
- Do not create or publish a remote repository, push, or deploy without user authorization.
