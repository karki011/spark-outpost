# AGENTS.md — Spark Outpost

Instructions for humans and coding agents working in Spark Outpost.

## Product and stack

- Build a local-first, provider-agnostic workflow application. Cloud hosting is a future direction, not a reason to add unused infrastructure today.
- Use a pnpm workspace monorepo, TypeScript, React with Vite, and Node.js with Express.
- Use local PostgreSQL with versioned schema migrations. Keep database access in the backend.
- The local web interface comes first. Electron (`apps/desktop`) is the desktop shell; it stays a thin wrapper around the unchanged web app and Node service. A Rust backend is not required.
- Use React state for UI interactions, TanStack Query for cached API data, and AG-UI events for live run updates. Give each piece of state one clear owner.
- Coding agents connect through ACP. CopilotKit is not used; if evaluated later, verify the exact integration license and do not introduce a paid runtime requirement implicitly.
- Spark owns run state, the approval gate, cancellation and recovery. The agent owns the work: for implementation it delegates bounded slices to available provider sub-agents, choosing roles, agent count and one or several slices per worker; assigned workers execute without mandatory recursive delegation. Questions and planning need no implementation agents. A provider without usable delegation reports the limitation. Outposts are optional for separate chats, branches or repositories. One chat is one agent session and the user's message goes to the agent as typed; Spark never splits a turn into roles, runs no checks of its own and adds nothing to the reply but the publish result line. There are no run budgets: time, tool calls, tokens and cost are measured and shown, never capped, and no card or setting limits them. Nor is there a limit on how many chats run at once: every chat's turn starts as soon as it is sent, and turns within one chat run in order. Jev is an optional decision service used outside turns (the Map, pull request feedback sorting, the companion) and is never called inside a turn; providers execute through explicit adapters.
- The Mac app's Browser pane runs pages in their own session partitions, never the app session, with Spark's ports blocked; agents read and act on pages in the pane through `spark_browser_*` tools and page content is untrusted data. Agents may also use their own web tools (Claude's WebSearch and WebFetch, Codex's web search): they follow the agent's mode like any other tool, what they return is untrusted data and counts as a work-data read for the send flag, and in every mode the gate refuses a WebFetch (or a Monitor socket) to this computer (localhost, loopback addresses, Spark's ports), to a non-web scheme or to an address with a login in it, and asks with hold-to-confirm when the address holds a value from a secret file. An agent may open any `http(s)` address and act on the page (click, type, keys, scroll, history) in the visible tab, reads a network log of each page's requests with full addresses and timings (secret-looking query values redacted at capture, never headers or bodies) and a console with stacks, and uses developer tools (`spark_browser_devtools`: eval, which is acting and is audited by its scrubbed expression, never its result, with password, card, code and filled field values, cookie values and auth-looking storage values masked from results, failing closed when they can't be read; inspect; wait, which polls a CSS selector until it matches; performance; storage, which never returns a cookie value and returns storage values only in an agent tab, with auth-looking keys and token-like values masked); the user can open real DevTools for a pane tab in a window on its own guarded partition; an agent tab the user used, or where a sign-in failed or waits, stays open; on a site outside this computer opening, reading and acting follow the agent's mode like any Spark action tool, acting on a tab the user owns asks in every mode, and opening or typing is a send (a click is not). Every pane tab, the user's or an agent's, in every chat and project, local or on a website, uses one Browser pane profile kept on disk, so a sign-in anywhere works everywhere: an agent in any chat is signed in wherever the user is, and a sign-in made in an agent tab, by a saved sign-in or in a handoff stays for the user and every chat; Settings → Browser pane signs out of one site or of everything; files still load only inside each chat's own projects; cookie values and auth-looking storage values never reach an agent through developer tools. Kept in every mode: Spark's ports, files outside the chat's projects, non-web schemes and addresses with a login in them are refused, agents never type into password, card or code fields, a download an agent's action started is cancelled, page permission prompts are denied outside the Personal exception below (a page may write the clipboard only right after the user's own click or key, never after an agent's, and never read it), and an address or typed text holding a value from a secret file asks with hold-to-confirm. Saved sign-ins keep their username and password only in the keychain; Spark types them only on the sign-in's own sites (its origin plus any sites the user added on the Mac, rechecked before each field and after each redirect) after a card, and no tool result, event, log or table holds them. For SSO, MFA or a passkey an agent may hand its tab to the user, who signs in there themselves while the turn waits with Done and Cancel (Mac only); the agent never sees what they typed. The Browser view has two profiles: **Work**, the one Browser pane profile that every chat, agent, Ask Spark and Terminal session uses, and **Personal**, a second profile kept on disk on its own partition that no agent, Ask Spark, Terminal session, `spark_browser_*` tool or paired device can open, read, act in or list. A Personal tab reaches a chat or Ask Spark only as text the user attaches to a message, or as an address the user hands to a chat, which opens in a Work tab. Every kept block applies to both profiles. Browser view tabs belong to no chat: they load no `file:` address, and no agent can see or act on them until the user hands one to a chat (a Work tab moves to the chat as the user's tab, so acting on it asks in every mode; a Personal tab's address opens in a new Work tab). The Browser view is Mac only and hidden on paired devices. A download is saved only when the user's own click or key in a tab on screen started it, after the end of the last agent call on that tab and while none runs, after a Save prompt, to ~/Downloads or a folder the user picks. A download an agent's action started is cancelled and listed as the agent's. Agents get no tool to read or open downloads. In the Personal profile only, a page may ask for the camera, microphone, location or notifications; Spark asks the user in the window (this time, always on this site, don't allow), never while an agent call works on the tab, and keeps grants per site in Settings → Browser pane. Every other permission, and every permission in Work, stays denied. Browser history is kept in Spark's local database per profile, shown only to the user in the command bar and Settings → Browser pane (cleared by time range or all), and is never sent to a model, offered to a tool, written to the audit or shown on a paired device. The command bar's last row searches the web with the engine chosen in Settings → Browser pane (DuckDuckGo by default, a fixed list); only choosing that row sends the typed text, and nothing goes while typing. Page text and selections the user attaches to a new chat or a message are attachments marked untrusted, captured when sent. They are never the user's message and add no authority of their own; the chat's own mode and autonomy level still decide what happens, so a chat at Full auto → PR still opens its pull request. Spark loads no browser extensions. Links the user clicks in Spark open in a new Browser view tab, or in the default browser with **Open links in** (Settings → Browser pane), except Join, sign-ins and non-web schemes, which always use the default browser. Built so far: the Personal profile and the Browser view with its profile switch, address bar, favorites, pinned tabs, tabs kept across a relaunch, Hand to chat, Open in Browser view and a new chat from a page, selection or link docked beside the tab (starting at Automatic), Ask Spark over @-mentioned tabs docked the same way (⌥⌘A), the command bar (⌘T, ⌘L) with local history, downloads you start (a Save prompt, a quarantine mark, a Downloads list in the Browser view), and for the user only Spaces (not a security boundary), Pinned folders, Back to pinned address and auto-archive to a per-profile Archived list, and split view and Peek, which are the user's only, in the Browser view only, with no agent tool, each view a guarded `PaneTab`, and Select, into the new-chat dock (a Personal pick goes as text only); site permissions in Personal are phase 2, so until then every page permission stays denied in both profiles. Refused in every mode, with the agent handing over to the user: completing a purchase or transfer and creating an account; System Settings (privacy and permissions, Gatekeeper, FileVault, firewall, login items), Keychain Access, the Passwords app and other password managers, web browsers (agents use the Browser pane), the system's security prompts and Spark Outpost itself, matched by bundle id and code signature. App content is untrusted data, a read counts as a work-data read for the send flag, Spark never acts while the screen is locked or after the user takes over with the mouse or keys until they resume, a visible indicator names the app with Stop, ⌃⌥⌘. stops all Mac control at once, and every call is an audit entry. Chats and Terminal sessions get it, and Spark keeps the floor and the hard limits in both; paired devices never do (a run started from one gets no Mac control tools), nor does a run whose message was spoken (run source `voice`), and its cards are approved on the Mac only (a paired device sees that one is waiting). - Voice (Phase 1 and Phase 2's speech models and live words built; see `docs/architecture/VOICE.md` for what each settled and what is unverified) is push-to-talk speech in the Mac app only, off until the user turns it on: Fn pressed twice (when the user grants Input Monitoring and macOS isn't using the 🌐 key) or a key shortcut (⌥⇧V unless the user records another in Settings → Voice) or a mic button starts listening, with a visible listening state; there is no always-listening and no wake word. A command ends after about 1.5 s of silence or a press, a dictation runs through pauses until a press, Esc cancels, and no speech stops a command after 3 s and a dictation after 30 s. A signed helper bundled per arch records the mic, turns speech into text with transcribe.cpp (the speech model the user picks in setup or Settings → Voice: Whisper base by default, Parakeet TDT 0.6B v3 or Whisper large v3 turbo, each downloaded once from a commit-pinned URL and checked by size and sha256) and Silero VAD, shows the words live while the user speaks (display only; commands match the final text), and, with **Speak answers** on, reads answers aloud with Apple system voices, stopping on Esc or a new press. Audio never leaves the Mac and is never written to disk; a transcript goes to a model provider only where typed text would, when the user sends it. Spoken commands are matched locally against the user's own projects, chats and ticket keys and only open a prefilled screen (a new chat with project, ticket and task, a result card for open, a reply draft); an ambiguous match asks which one. Every question, including questions about Spark (who needs me, what's running, spend, pending tickets, a ticket's status), goes to Ask Spark (the model) as text on the same confirm as a typed one, marked as spoken; there are no instant answers, and Ask Spark never answers an approval card from a spoken question. Voice never starts work on its own: the user confirms with Enter, a click, or by pressing again and saying "send", a dictated message is never sent automatically, what Ask Spark does with a sent spoken question follows **When Ask Spark acts** as for a typed one (Mac control stays off for it), and approvals, denials, pushes, pull requests and Mac control are never voiced. Only the helper gets the microphone; the app's windows and the Work profile deny it; a Personal site the user allowed may use it in its own tab (site permissions in Personal are phase 2, so until then the Personal profile denies it too), and paired devices get no voice. A Phase 1 change is not done until the real tests in `docs/architecture/VOICE.md` have run on this Mac and their results are reported. Read `docs/architecture/VOICE.md` before changing it.

Google syncs every 3 minutes with sync tokens (a 410 starts a full windowed sync; no push channels), backs off on rate limits and errors, and **Disconnect** revokes the token and deletes it from the keychain. No iCal addresses. Per calendar: an **Include** checkbox and a **Nudge** switch, nudges on by default; every included calendar counts as busy; copies of one event (same `uid` and start, the Google `iCalUID`) show once across both sources, and a calendar whose identifier a full sync changed is matched again by account and title, or reset with a note. Events stay in memory (EventKit's in the Mac app, Google's in the API process); only calendar choices, settings, Google account ids and emails, Spark's marks (Remind me, Hold alerts, a dismissed meeting alert) and Ask Spark's one-shot snooze and join requests (an event key and an expiry) are stored, the marks purged an hour after the event and on Disconnect. Today is a left-bar item and Upcoming a Home card, both hidden on paired devices; the brief's calendar block is drawn on the Mac, never in its prompt, and no event detail goes to a model. Nudges are island lines (before a meeting, Remind me, wrap-up, anything to capture; by default a meeting's alert is a card Scout lowers to the centre of the screen in a click-through overlay that never takes focus (Join, Snooze 1 min, Dismiss), or with **Bubble from Scout** or during a hold a card hanging from Scout (Join, Snooze 2 min, Dismiss, Open); before the start the bubble and the centre card also offer **Join at start**, a saved per-occurrence mark, confirmed by a 4-second island note "Opens at <time>" with ✕, that quiets nothing (its reminders show "Opens at <time>" with **Don't open**, which removes it) and opens its link at the start through the auto-join countdown even with **Join meetings automatically** off, in a hold or a clash, skipping only when away, locked or asleep, without an allowed link, declined, dismissed or over 2 minutes late; every island meeting line has Dismiss (every meeting of a grouped line); Dismiss and ✕ are a mark on that occurrence, so it never alerts again on any view or after a reload, a meeting's reminders (centre card, notification, bubble, nudge lines, Home's big card) stop 5 minutes after its start or at a shorter meeting's end, and every other calendar item clears itself at the meeting's end; times follow the Mac's 24-hour setting) that never start, stop or pause work, and holds (focus blocks found by title by default, or all meetings, or Hold alerts) silence the island's chimes and delay phone pushes while cards still appear, with one catch-up line after; a meeting nudge hops the island's mascot once with a short tune (a glow alone with reduced motion; no tune when chimes are off or held), and the island's Home gives a meeting the big card from a minute before its start (Join ⌘J, Snooze 1 min, Dismiss, Open Today; Choose for a clash), shows one within 10 minutes as a strip under a request and on the resting strip, and lists the meetings left today when nothing needs you; **Refresh now** (Today and the Calendar card, Mac only) syncs Google at once unless an account is backing off and re-reads EventKit; meetings that overlap share one nudge with **Choose** and carry a clash tag, and ⌘J opens Choose when two or more can be joined. Join opens only `https` links on a fixed host allowlist (Zoom, Meet, Teams, Webex; an Outlook SafeLinks wrapper only around a Teams link, showing the unwrapped host) in the default browser through the external-link path, never the Browser pane, from the **Join opens** time (10 minutes before by default; 5 or 2 minutes before or at the start in Mac → Notifications) (the start time until then) and never on its own unless the user turns on **Join meetings automatically** (off; a cancellable 10-second countdown at the start, skipped in a clash, a hold, when away or locked, and logged); ⌘J is in-app. `spark_calendar` reads (with **Let agents read my calendar** on, on by default, existing connections included since migration 0202; a later choice is kept) and `spark_calendar_edit` writes (on calendars with **Agents can edit** on, off by default) follow the agent's mode as Spark actions do (at once in Auto, Bypass permissions, Auto review and Full access, and in Accept edits when the user's message asked; otherwise a card with the change before and after), while a change to an event with other attendees and any write on a shared or unclassified calendar ask in every mode; a delete follows the mode, and its result line names the event (and says Google keeps it in its trash); inviting and RSVP are not offered, Google writes tell no one, and the card's change is checked against the event again before it is written. - A paired device (a phone or computer browser, or another Spark Outpost) reaches the Mac only through Tailscale Serve (never Funnel) and the remote gateway in `apps/server/src/remote/`: the server still listens on `127.0.0.1` alone, a device signs in with a pairing confirmed on the Mac, and every route is refused unless `route-rules.ts` allows it, some behind the switches on the Remote control page (left bar, above Settings). A paired device may browse the Mac's folders, make a new folder inside the home folder (`POST /api/folders`, audited) and link it as a project, behind the **Link a new folder or clone a repo** switch. A paired device may save a passkey and use it to sign in again in another browser at the exact Serve hostname, as the same device; a passkey never pairs a new device, stops working when the device is revoked or unused for 30 days, and its switch and removal stay on the Mac. Starting a Terminal session, shell tabs, Browser pane, preview, and everything that manages remote control (Tailscale, pairing, devices, switches, audit) stay on the Mac; a new route needs a rule or the policy test fails. A paired device may follow a running Terminal session (its messages and tool steps, read from the CLI's session file to show and never stored), type a message into it and stop it behind one switch, and approve its permission requests behind a second; both are off by default. A message is refused while the agent waits for an answer or, when it would be typed into the pane, any CLI menu shows, and when it starts with `/` or `!`, which would run a CLI command; a queued message to a Claude session whose Spark mod (written per session and loaded with `--plugin-dir`, never a user settings file) has checked in goes through the mod, which submits it once Claude is idle, and otherwise it is typed as before; Stop sends Esc only while the agent is working, since Esc twice at an idle prompt opens Claude's rewind. Claude's permission hook waits for a device's answer while Claude shows its own menu on the Mac, and whichever answers first wins; Codex hides its menu while a hook runs, so its hook never waits and a device's answer is typed as Codex's own key, only after the pane shows that request. A session started before this has no permission address and is answered on the Mac. A paired device may get a Web Push notification when a chat needs you, behind a switch that is off by default: the Mac sends it itself with a VAPID key kept in the keychain, only to a known push service, with the chat title and a fixed line per card kind, never a command or path, signed with a sender contact set on the Mac (the project page by default) that is never the tailnet name. - A Terminal session runs under a tmux bundled with the app, on Spark's own socket, and keeps running across a Spark restart, an update relaunch or a crash; Quit stops it. Read `docs/architecture/NATIVE_TERMINALS.md` before changing it.
- An outpost is a shared thread for several chats: the user's message may address several member chats with `@handle` anywhere in it, one request per chat, each starting a turn in its chat; the composer sends an unaddressed user message to its visible selected lead by conversation ID. Post note is an explicit composer choice and starts nothing; unaddressed agent posts and API posts without a direct target retain note semantics. Agents in an outpost may ask each other and leave notes, and a chat (the lead) may split work into a story of sub-chats: `spark_outpost_start` creates and starts them as a Spark action that follows the agent's mode (at once in Auto, Bypass permissions, Auto review and Full access, a Start/Edit/Discard card otherwise), and `spark_outpost_draft` saves a draft that nothing creates until the user starts it; a sub-chat may instead be an existing chat the lead names with `chat` (a chat already in that repo, not in another story or outpost, never the lead or a Terminal session), which gets the lead's task as a request, never the user's message, and keeps its own title, mode, autonomy and branch: the mode cap does not apply to it and its starts-after is order only, never stacked; every start is an audit entry and a "Started outpost … with N chats" line in the lead chat, and a story's sub-chat, a turn another chat's request started and a child run cannot start one. The outpost tools belong to the chat's own turn; a child run, such as a Spark handed a job, gets none. A request or a wrap-up from another chat or from Spark, and a draft's first messages, are never the user's message and cannot authorise a push or a pull request; the receiving chat's own mode and autonomy decide what happens to the result. The lead decides whether a sub-chat is parallel or stacked; a sub-chat's first turn may ask, a held request is released when the request it waits on is Answered, and a story gets one wrap-up request to its lead. The wrap-up is one read-only reply in the lead chat: it starts no build and no publish step, and gives no basis to push or open a pull request at any autonomy level or in any mode. The mode cap holds the new chats the lead proposes or starts to the lead's own mode, and the user may raise a sub-chat's mode by hand. A chat may base its branch and pull request on another member chat's branch: it pushes only its own `spark/*` branch, never force pushes (both while the recommended `Push(other)` and `Push(force)` rules are set), updates by merge, and is refused a push, by `spark_push` and by a `git push` the gate sees, with the same reason, while its parent branch is not on the remote; in a mode the gate can't see, that push is flagged as an observed rail crossing (card, island notice, audit entry) and never stopped. At Automatic, when a stacked sub-chat's held request waits on its parent chat, Spark commits the parent's kept changes on the parent's own `spark/*` branch before the sub-chat starts: a local commit like Ship → Commit, never pushed, and if the commit cannot be made the sub-chat stays held. A chat is in at most one story, and nothing here has a cap, budget or timer. Each member chat is served as an A2A agent and each request is an A2A task, on `127.0.0.1` only, behind the launch token, never to a paired device or through Tailscale. The outpost page is one conversation: each request shows as a card under the message that sent it (its chat, a title from its first line, its state, one branch and pull request line, and the actions that fit; nothing merges), an Overview pane groups the requests by state (Waiting on you, Working, Held, Ready for review, Idle, Resolved) beside the member chats' files and the pull requests, and a thread pane shows a member chat's own transcript, where what the user types is the user's own message in that chat, exactly as typed in the chat. An outpost may have instructions (**Instructions…**, up to 4,000 characters): Spark adds them as context, labelled as granting nothing, to the preamble of every turn an outpost request starts in a member chat; they are never part of the user's message and never authorise a push, a pull request, a Spark action or a mode. A paired device may read an outpost and its instructions, post, answer, cancel, pause, rename, start a held request anyway and start a draft as proposed (or answer its card); creating, deleting, changing members by hand, editing a draft and editing the instructions stay on the Mac. Read `docs/architecture/A2A_CHATS.md` before changing it.
- Spark Island rests as Scout alone, or as one strip (the unread count, a meeting within 10 minutes, working chats' blobs) whose hover line answers the top request (Allow, Deny) or a meeting (Join, Snooze); its Home (tabs Home, Ask Spark, New chat) shows one big card for what needs the user (a request with Allow Y, Deny N, Later, Open chat; a question's choices; or a starting meeting), a pager when several wait, and working chats as tiles that never count. ## Design principles

- Follow YAGNI, KISS, and DRY: implement what is needed, keep it understandable, and avoid duplicated knowledge.
- Design for today's actual caller. Do not introduce speculative APIs, registries, configuration, or extension systems.
- Abstract around knowledge, side effects, volatility, or a useful test seam that exists today. One caller is enough when the boundary has a concrete purpose.
- Prefer a small meaningful interface over chains of pass-through wrappers.
- Keep decisions pure where practical. Put filesystem, network, process, and clock effects at the edges.
- Make dependencies explicit. Validate external inputs at trust boundaries, including API requests, provider events, tool results, and persisted records.
- Treat agent output and retrieved content as data, not execution authority.
- Prefer clear names, small functions, and explicit control flow over clever or compressed expressions.
- Reduce needless nesting, redundant logic, and pass-through abstractions. Preserve useful boundaries and test seams.

## Organization and duplication

- Organize code by feature and responsibility. Keep related implementation and tests easy to find.
- Keep applications under `apps/`, shared packages under `packages/`, infrastructure under `infra/`, and architecture and decisions under `docs/`.
- Create directories and packages only when they have an actual implementation purpose. Do not scaffold empty abstractions.
- Keep handwritten source and test files at or below 500 lines. Split by coherent responsibility before exceeding the limit; do not compress code to fit.
- Do not manually split generated files, lockfiles, or vendor code to satisfy the source-file limit. Keep them separate from handwritten code.
- When the same UI pattern appears more than twice, extract a shared component. For repeated non-UI behavior, extract a shared function or module.
- Share the repeated behavior or knowledge, not merely similar syntax. Do not combine unrelated behavior into a configurable catch-all component.
- Keep shared code at the narrowest scope that serves its actual callers.
- Frontend code may import shared contracts, but must not import database access, credentials, or provider execution internals.

## Interface conventions

- Follow the design kit in `docs/design/`. Use the shared semantic colors in `apps/web/public/theme.css`; do not hard-code palette colors in feature styles. Load the saved theme before React mounts.
- Follow Apple's Human Interface Guidelines for the Mac app shell (standard menus with **Settings…** ⌘,, View and Format; Apple's keyboard shortcuts never reused for other actions; a Settings window, context menus, panels, trailing inspectors, focus and VoiceOver, Increase Contrast, Reduce Motion, the system appearance by default). The design kit governs content, tokens and type on every surface; where they conflict on the Mac shell, Apple wins. Text is never under 12px; controls are at least 28px on the Mac and 44px on touch; status is an icon plus a word, never colour alone, one meaning per colour. See `docs/design/README.md`.
- Keep onboarding and Integrations on the same connection components and query cache. Show only supported connection methods and backend-reported status.
- Every picker of a project or folder ends with **Add folder…** and **Clone a repository…** from `useAddFolder` (`apps/web/src/projects/`), which opens Spark's own folder browser everywhere, the Mac included (no macOS dialog): it starts next to the newest project or in Documents, has places, a typed path, keys, **New folder**, project and git marks, and a line saying how to allow access when macOS refuses a folder; the new project is selected in place.
- Use shared outline icons, restrained accent colors and visible keyboard focus; preserve mounted conversations when changing appearance.
- Two chats can show side by side (split chat, `apps/web/src/chat/split/`): a window- or document-level listener inside a chat acts only while `usePaneFocused()` is true, and a DOM id that ARIA or `getElementById` references inside a chat comes from `usePaneId()`.

## Changes and refactoring

- Make small, coherent changes. Preserve security, data integrity, accessibility, and all requested behavior.
- Refactor only when today's change benefits. Do not broaden a task into unrelated cleanup.
- Preserve observable behavior during refactoring, including errors, side effects, evaluation order, and public contracts, except for the approved behavior change.
- Do not trade readability for fewer lines.
- Preserve mounted UI state, focus, and scroll position during streaming and background refreshes.
- Keep workflow execution independent of the HTTP request or UI connection that observes it. A disconnected progress stream is not a cancellation request.

## No explanatory code comments

- In every mode, add no explanatory code comments, including in tests.
- Do not add docblocks that merely explain implementation.
- Use clear names, small functions, and explicit control flow instead.
- Preserve required license notices and machine-consumed directives. Record any newly required exception and its reason in the completion record.
- Put design rationale in the PR description, completion summary, or appropriate documentation.

## Testing and review

- Test observable behavior and meaningful edge cases. Avoid tests that only mirror the implementation.
- Run checks appropriate to the changed behavior. Report what ran and what remains unverified.
- For execution and persistence changes, cover relevant cancellation, restart recovery, duplicate requests, stale events, and failure cases.
- For UI changes, verify relevant keyboard, focus, accessibility, streaming, and loading behavior.
- Self-review gathers evidence; it is never the final independent verdict.
- Keep provider claims, reviewer opinions, executable checks, and human acceptance distinct. Do not claim independent verification when none occurred.
- Completion records identify the behavior changed, validation evidence, material limitations, and any required comment exception.

## Repository maintenance

- Keep this file concise and current. Update it when approved conventions change.
- Document runnable development and verification commands as the repository is implemented; do not claim nonexistent commands or checks.
- Keep secrets out of source control, logs, browser bundles, and agent-visible artifacts.

## Commands

- Run `pnpm test:db` for storage changes against an isolated PostgreSQL schema in `TEST_DATABASE_URL` (falls back to `DATABASE_URL`); `pnpm db:setup` writes both to `.local/credentials.env`.
- Run `pnpm check` (format, lint, typecheck, source rules, guide rules, release download links, model cards, unused files and exports via knip, contrast audit, ACP coverage, unit tests) and `pnpm test:browser` for browser behavior. Set `SPARK_WEB_BUILD=1` to run browser specs against a production build of the web app (the map perf spec holds the tree to 50 ms tasks there). Run `pnpm test:browser:packaged` for the `@packaged` specs the way the desktop app runs: the API serves a production build on its own origin and the launch token is added below the page, with no Vite proxy (`SPARK_PACKAGED=1` runs any spec that way). Tag a test `@packaged` when it covers a request path the proxy could hide (bodyless requests, uploads, streams, sockets, downloads). Set `SPARK_FAKE_BROWSER=1` to give the test worker a fake browser host, which the agent flow in `tests/browser/sign-ins.spec.ts` needs.
- Run `pnpm test:live` only when the owner asks: it uses the installed Claude and Codex logins and spends real usage.
- For the inner loop on a branch, run `pnpm test:changed`, `pnpm test:db:changed` and `pnpm test:browser:changed`: they run the tests a change since `main` affects (`--dry-run` on the last two prints the choice and the rule behind it), `pnpm test:browser:perf` runs only the perf specs, and `pnpm test:browser:shards [N]` runs the browser specs in N processes (6 by default), each with its own ports and test database. Every browser run gets an empty temp folder per slot (`/var/tmp/spark-outpost-test-slot<N>`, its `TMPDIR`), removed when the run ends. Before starting, the shard runner stops test servers an earlier run of this checkout left on a slot's ports, and refuses, listing them, when anything else holds them; Ctrl-C stops every shard and its servers. A new browser spec goes in `tests/browser/spec-map.ts` or the unit tests fail. Before merging to `main` and before a release, run `pnpm check` and the changed-test commands above; run the full `pnpm test:db` and `pnpm test:browser` only when the owner asks.
- Run `pnpm db:setup` once for the isolated native macOS PostgreSQL cluster, then `pnpm db:up`, `pnpm db:migrate` and `pnpm dev`. Stop only this cluster with `pnpm db:stop`; preserve `.local` data and ignored credentials. See `infra/local/README.md`.
- The user guide lives in `docs/guide/` (Markdown with frontmatter; see its README for audiences, page types and word caps). The app bundles it into Docs and agents read it with `spark_docs`. A change to a UI label, setting, card, Spark tool, agent mode, protected path or what leaves the computer updates the page that documents it in the same commit, and every user-visible change adds a row to `docs/guide/whats-new.md`. There is no redirect for a renamed page or heading: update every link to it in the same commit. Run `pnpm check:docs` (part of `pnpm check`), which fails on a link to a page or heading that does not exist, for frontmatter, word caps, links, images, reference coverage of Spark tools and Settings sections, and `spark_docs` limits. Run `pnpm docs:screenshots` to regenerate the light and dark screenshots from a seeded demo test database (`tests/browser/docs-shots*.spec.ts`).
- Run `pnpm exec tsx scripts/spark-tool-budget.ts` to print the size of the Spark tool list a session is sent (plain chat, linked project with GitHub, everything connected, and each as Ask Spark); `apps/server/test/spark-tool-budget.test.ts` caps the plain-chat case.
- Run `pnpm desktop:dev` for the Electron shell (dev channel, own data folder and bundled Postgres); see `docs/architecture/ELECTRON_PLAN.md`.
- Run `pnpm desktop:dev-app [--data <dir>] [--port <n> | --debug] [--app-dir <checkout>]` to run the dev app in one Developer ID signed shell, **Spark Outpost Dev** (`.local/dev-app/` in the main checkout, shared by worktrees), so macOS permissions are granted once; the debug port is off unless `--port` or `--debug` is given, since it lets any local process use those permissions; see `docs/architecture/ELECTRON_PLAN.md`.
- Run `pnpm desktop:mac-control` to build the Swift Mac control helper into `.local/mac-control/<arch>/` (`--arch all` for both, `--test` runs its Swift tests with a fake Accessibility tree first); it needs the Xcode toolchain, and from source Mac control reports the helper missing until it is built.
- Run `pnpm desktop:voice` to build the Swift voice helper with transcribe.cpp (static, from a sha256-pinned source tarball) and the pinned Silero VAD model into `.local/voice/<arch>/` (`--arch all` for both, `--test` runs its Swift tests first); it needs the Xcode toolchain and cmake (`CMAKE` names it when it is not on `PATH`). `SPARK_FAKE_VOICE=1` gives a dev app a fake helper, and `SPARK_VOICE_FILE_INPUT=1` lets a dev app send a WAV path instead of the microphone.
- Run `pnpm desktop:calendar` to build the Swift calendar helper and its dev-only seed tool into `.local/calendar/<arch>/` (`--arch all` for both, `--test` runs its Swift tests over a fake store first); it needs the Xcode toolchain, and from source Calendar reports the helper missing until it is built. A dev app started with `SPARK_CALENDAR_SEED=seed` (or `remove`) and `SPARK_CALENDAR_SEED_STATE=<file>` creates (or deletes, by identifier) the throwaway **Spark Test** and **Spark Test Family** calendars on the On My Mac source (`SPARK_CALENDAR_SEED_ONE=<minutes>` seeds a single Zoom meeting that many minutes out instead); packaging never stages the seed tool. `SPARK_FAKE_CALENDAR=1` gives the browser specs a fake calendar host, in the API and in the chat worker for agent calendar tools (beside the fake browser host when both are set).
